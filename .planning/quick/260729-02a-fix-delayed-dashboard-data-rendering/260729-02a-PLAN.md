<design_decisions>
Read this before touching code. Each decision below is settled; do not re-litigate it
mid-task, and do not extend it beyond what is written.

**DD-1 — QueryClient defaults live in one module, freshness-sensitive reads override.**
`new QueryClient()` (App.tsx:51) gives every query `staleTime: 0` / `gcTime: 5min` /
`refetchOnWindowFocus: true` / `retry: 3`. Defaults chosen: `staleTime: 60_000`,
`gcTime: 30 * 60_000`, `refetchOnWindowFocus: false`, `retry: 1`.
- `gcTime` is what actually satisfies "cache preserved across route changes" for a user who
  spends >5 min elsewhere; `staleTime` only decides whether a *background* refetch fires —
  React Query renders cached data first either way.
- `refetchOnWindowFocus: false` as a default because ~10 dashboard queries re-firing on tab
  return is a visible churn storm. Tradeoff: balance-sensitive reads must opt back in.
  `useMerits` ALREADY sets `refetchOnWindowFocus: true` + `staleTime: 5_000` — keep both
  verbatim. Add the same opt-in to `useSubscriptionState` (`staleTime: 30_000`,
  `refetchOnWindowFocus: true`) since it drives billing/downgrade UI.
- `retry: 1` because `retry: 3` with backoff makes a genuinely failing query hold the cold
  gate for ~7s.

**DD-2 — Replace `['currentUser']` with a session-derived id. This is the biggest single win.**
`supabase.auth.getUser()` is a network round-trip to `/auth/v1/user`; `getSession()` reads
local storage and resolves effectively immediately. Every dashboard data query is gated
`enabled: !!userId`, so that round-trip is a hard serial barrier in front of all of them.
New `useAuthUserId()` uses `getSession()` with `staleTime: Infinity` / `gcTime: Infinity`;
freshness comes from the DD-3 listener writing new ids into the cache, not from refetching.
Security justification: the id is used ONLY to scope cache keys and filter user-owned reads.
It is never an authorization decision — the database still enforces identity via RLS against
the access token on every request. Do NOT use it to grant access to anything.

**DD-3 — Sign-out teardown is app-root and event-driven, and lands BEFORE the cache lives longer.**
There is no `queryClient.clear()` anywhere today. Wiring it into the two `signOut()` call
sites (Navbar.tsx:136, TopBar.tsx:68) would miss token-expiry-driven `SIGNED_OUT` and could
double-fire. Instead: ONE `<AuthCacheSync />` mounted once inside `QueryClientProvider`,
holding one `onAuthStateChange` subscription. It clears on `SIGNED_OUT` and on any
transition where the new session's user id differs from the last seen id (covers account
switching). Because it is one subscription in one always-mounted component, it fires exactly
once per event regardless of which button triggered the sign-out.
ORDERING IS MANDATORY: `['currentUser']` is NOT user-scoped and carries `staleTime: 5min`,
so today a logout->login-as-B can serve A's id and hydrate every user-scoped key with it.
Raising `gcTime` widens that window. Implement AuthCacheSync in the same task and verify it
before/alongside raising the cache lifetimes — never after.

**DD-4 (REVISED) — Cache the onboarding gate ONLY on a passing verdict. Never cache a redirect.**
`ProtectedRoute` remounts per protected navigation (each route renders a distinct element,
and its effect depends on `location.pathname`), resets `isLoading=true`, and awaits two DB
queries before children mount at all. That is the dominant serial cost, so the gate must be
cacheable — but the two possible verdicts are NOT symmetric:

- A stale **pass** (`hasResume && hasGoal`) is benign. The user is already onboarded, and
  every actual data read is still gated by RLS on the server. Worst case is a few minutes of
  optimism about a state the user already reached.
- A stale **fail** is the harmful one. It bounces a just-onboarded user back to `/onboarding`
  — the precise regression a naive `staleTime` on this key would introduce.

So: `staleTime: 5 * 60_000` when the verdict passes, and `staleTime: 0` (always refetch) when
the verdict would redirect. A failing verdict is therefore never served from cache, which
means **no write-site invalidation is load-bearing for correctness**. This supersedes the
earlier "locate the onboarding completion write site / invalidate on unmount" language
entirely — that fallback is withdrawn.

Consequence, and the reason this shape was chosen: `src/pages/Onboarding.tsx` writes
`career_targets` via a raw `.upsert()` at ~:417 on the primary new-user path, bypassing
`useProfessionalGoal().saveGoal()` (which only serves the goal-only/legacy branch at :286).
Chasing every such write site is fragile and would drag `Onboarding.tsx` and its
provider-less test into scope. The asymmetry removes that entire class of bug instead.
`src/pages/Onboarding.tsx` and `src/pages/__tests__/Onboarding.freshness.test.tsx` are
therefore explicitly OUT OF SCOPE for this plan — do not modify either.

Two cheap invalidations are still specified, as belt-and-braces rather than as the
correctness mechanism:
- `handleDeleteResume` in `Dashboard.tsx` (:603-614) — deleting the last resume is the one
  in-scope action that can falsify a cached PASS.
- `useProfessionalGoal`'s `saveMutation.onSuccess` — already specified, correct, cheap.

Record the asymmetry as a short comment in `ProtectedRoute.tsx` stating WHY (repo convention
is to comment intent, not mechanics).

**DD-5 — Prefetch on hover/focus of the sidebar "Home" link.**
Chosen over app-shell-mount prefetch (fires ~7 queries on every protected page, including
for users who never open the dashboard) and over after-auth prefetch (same waste, and it
competes with the current page's own queries). Hover/focus fires only on demonstrated
intent, needs no new lifecycle, and targets exactly the reported "repeat navigation"
complaint. It is a pure warm-up: it must never change what renders.

**DD-6 — The cold-load gate keys off `isLoading`, never `isFetching`.**
React Query sets `isLoading = isPending && isFetching`, i.e. true ONLY when there is no
cached data. So a single gate built from the core queries' `isLoading` flags fires on a true
cold load and is structurally incapable of firing on warm navigation with a populated cache
— req 1 and req 7 are satisfied by the same expression. Use `isLoading`. Do not substitute
`isFetching` or `isPending`, which would gate warm loads and defeat the entire fix.
No fabricated values: the gate shows a loading treatment, never zeros or placeholders.
</design_decisions>
