<objective>
Make Resume Analysis upgrade-aware: record the tier that produced each analysis, stop
serving a cached Free analysis to an Elite user as though it were Elite, and offer a
paid, idempotent, once-charged "Rerun with Elite — N merits" full re-analysis that lands
in a NEW row while the original Free analysis stays in history.

Purpose: an upgraded user currently pays for Elite and silently receives their old Free
result rendered under the paid layout. That is both a product defect and a trust defect.

Output: one additive column + a tamper boundary, a refund-aware `check_and_deduct_merits`
(the money-path fix LOCKED by CONTEXT — it closes the refunded-key replay hole for EVERY
feature routed through `withMerits`, not just resume), a restored Elite payload, a threaded
idempotency nonce, a tier-aware client cache, a tier-honest Results page, a CTA, and three
new remote (live-Postgres) test suites folded into the gate.

**Scope guard (LOCKED):** Resume Analysis ONLY. No Career Compass retrofit. No
partial-section generation — the rerun is a FULL Elite re-analysis through the existing
`analyze-resume` streaming pipeline.

**CTA surface decision (discretion granted by CONTEXT).** Requirement 2 covers an Elite
user who "opens OR uploads" a resume with only a cached Free analysis. This plan handles
those two branches ASYMMETRICALLY, deliberately:

- **Opens** (`/results/:id` on an `analyzed_tier='free'` row while `userTier==='elite'`)
  → the CTA renders. This is the branch where the user would otherwise be shown a Free
  result under a paid layout with no way out. Task 9.
- **Uploads** (drops the same file on `/upload` while Elite) → Task 6's tier predicate
  makes the Free row MISS the short-circuit, so the upload falls through into the normal
  analyze path, which already prices, consents and charges through `withMerits`. Adding a
  CTA on that branch would be a second, redundant consent surface for a flow the user has
  already initiated.

This is a choice, not an omission: one CTA, on the surface that has no other exit.
</objective>

<design_decisions>

These five decisions were derived during planning and are binding on the tasks below.
Do not re-litigate them mid-execution.

## D-1. Cache tier-awareness: ADD A TIER PREDICATE, do not remove the short-circuit

`src/pages/Upload.tsx:115-130` short-circuits on `(user_id, file_hash)` with zero tier
awareness and navigates away BEFORE any edge function runs, so the already-correct
tier-aware server cache never gets a chance.

**Decision: add a tier predicate to the client query. Do NOT delete the short-circuit.**

Tradeoff, stated explicitly:

| Option | Cost |
|--------|------|
| Delete the short-circuit, let `withMerits` + `precheck_cache` decide | Architecturally purer — ONE cache authority. But `readResumeAnalysisCache` keys on `computeCacheKey({..., previousScore, previousSuggestions})`, and `previousSuggestions`/`previousScore` are recomputed from the user's LATEST analysis on every upload. Re-uploading the same file after any other analysis changes those inputs, changes the cache key, and MISSES — so the user pays merits for a re-upload that is free today. It also forces a full storage upload + text extraction round-trip on every duplicate upload. |
| **Add a tier predicate (CHOSEN)** | Keeps the zero-cost, zero-charge duplicate-upload path intact. Cost: two cache authorities remain (client short-circuit + server `precheck_cache`), which is pre-existing debt this task does not pay down. |

The predicate must be `analyzed_tier.eq.<normalizedTier>` **OR** `analyzed_tier.is.null`
(see D-4 for NULL, D-6 for the normalization).

An Elite user who re-uploads a Free-analyzed file therefore MISSES and falls through to
the normal, already-consented, already-priced upload flow. No CTA is rendered on that
branch — see the objective's CTA surface decision.

## D-2. The "separate Elite analysis" row: CLONE the `resumes` row

The Elite rerun inserts a **new `public.resumes` row** cloned from the source row
(`file_name`, `file_url`, `file_path`, `file_hash`, `file_size`, `extracted_text`,
`text_hash`), with `grading_data` NULL. `analyze-resume` then writes its authoritative
save into THAT row.

Why this is the correct key and what it preserves:

- **Original Free row untouched.** `completeAndRecordSuccess`
  (`analyze-resume/index.ts:103-107`) scopes its update to `.eq('id', resumeId)`, and
  `resumeId` is the new row. The Free `grading_data`, `overall_score` and `analyzed_at`
  are never overwritten.
- **`AnalysisHistory.tsx:189-214` keeps working unchanged.** It queries `resumes` by
  `user_id` (both rows return) and `analysis_results` filtered on
  `analysis_type='resume_analysis'` (both mirrors return). No shape or query change.
- **`source_reference` routing keeps working unchanged.** `persistResumeAnalysis`
  (`index.ts:50`) writes `source_reference: resumeId`, so the Elite mirror points at the
  Elite row and `AnalysisHistory.tsx:304` routes to `/results/<eliteRowId>`. The Free
  mirror still points at the Free row. Two distinct, correct routes.
- **Landing page after the rerun:** `/results/<newEliteRowId>?stream=true`. The user
  watches the Elite analysis stream in, exactly like a fresh upload. The Free result
  remains reachable at its own `/results/<originalId>`.
- **`file_hash` is duplicated across the two rows by design.** This is precisely why D-1's
  tier predicate is required: without it the Upload short-circuit (`.limit(1)`,
  `.order('analyzed_at', desc)`) would non-deterministically serve whichever row analyzed
  last.

Rejected alternative: mutating the Free row in place, or adding a `parent_resume_id`
self-reference. In-place mutation violates requirement 5. A self-reference column adds a
second migration and a second tamper surface for no behavior the clone does not deliver.

## D-3. Idempotency: thread the EXISTING `attemptNonce`, held as a BOUNDED IN-FLIGHT LEASE

`tier` is already a component of `deriveIdempotencyKey` (`_shared/idempotency-key.ts:87-93`),
so a Free run and an Elite rerun of the same resume derive different keys automatically.
Nothing new is needed there.

**But there is a live defect this plan must fix first:** `Upload.tsx:217` mints an
`attemptNonce` and writes it to `sessionStorage`, `useResumeStream.ts:166-174` **does not
forward it**, and `analyze-resume/index.ts:1518-1520` therefore falls back to
`crypto.randomUUID()` **server-side on every single request**. Every retry today derives a
fresh key and charges again. Requirement 7 is unmet at HEAD for the streaming path.
Task 5 closes this.

### D-3a. The refund/replay hazard that dictates the lease design (READ THIS FIRST)

A naive reuse predicate — "the recorded row still has `grading_data IS NULL`, so reuse the
nonce" — is **true in two different states**, and only one of them is safe:

1. the rerun is genuinely IN FLIGHT (safe: replaying the key is exactly what prevents a
   double charge), and
2. the rerun FAILED AND WAS REFUNDED (catastrophic).

State 2 is catastrophic because of a verified interaction between three files:

- `_shared/merit-gateway.ts:299-309` refunds on a refundable throw when `!alreadyDeducted`.
- `refund_merits` (`20260415000000_merit_rpcs.sql:165-209`) writes a **separate**
  `balance_type='refund'` row and leaves the original `source='feature-deduct'` row —
  **with its `idempotency_key` intact**.
- The entry-time pre-check in `20260512000003:118-133` looks up ONLY
  `idempotency_key + source='feature-deduct'` and **never consults refund state**.

Net: rerun fails → merits refunded → row still `grading_data IS NULL` → user clicks the
CTA again → same row, same nonce, same derived key → `already_deducted:true` → **charges
zero, indefinitely repeatable.** The Upload path does not have this hole only because it
mints a fresh nonce on every submit; persisting a nonce across failures introduces it.

**This hazard is now CLOSED AT THE SOURCE by D-7** (operator decision, LOCKED in CONTEXT
under "Refund/replay hole — CLOSE IT AT THE RPC"). Task 7b makes
`check_and_deduct_merits` refund-aware, so replaying the key of a refunded deduction
charges again rather than returning `already_deducted:true`. That supersedes the earlier
planning position — recorded here and struck rather than deleted — that the RPC was too
central to touch. The operator weighed that and chose the deeper fix, because the hole is
reachable BY ACCIDENT (any transient Anthropic failure plus a refresh) and it affects every
feature routed through `withMerits`, not just resume.

**The client-side lease in D-3b STAYS**, unchanged, as defense-in-depth. It is no longer
the security boundary — the RPC is — but it remains the thing that keeps a legitimate
in-flight retry collapsing onto ONE derived key, and it is a second layer if a future
migration regresses the RPC. Read the rest of D-3a as a description of the hazard the
lease was originally sized against, not as a live, unmitigated defect.

### D-3b. The lease: `grading_data IS NULL` **AND** in-flight **AND** bounded

The persisted record is a **lease on an in-flight attempt**, not a permanent nonce store.
Reuse requires ALL of:

```
record exists
  AND resumes[newResumeId].grading_data IS NULL     // not completed
  AND Date.now() - record.createdAt < LEASE_TTL_MS  // still plausibly in flight
  AND record.reuses < MAX_LEASE_REUSES              // bounded
```

with `LEASE_TTL_MS = 15 * 60 * 1000` and `MAX_LEASE_REUSES = 3`. Any failed condition →
delete the record and mint a fresh nonce (which charges again — the correct outcome after
a refund).

Three layers, because no single one is sufficient:

| Layer | Closes | Why it alone is not enough |
|-------|--------|----------------------------|
| **(b) Clear the lease on a SETTLED failure.** `useResumeStream`'s error path calls `clearEliteRerunRecord(sourceResumeId)` whenever the stream settles in a terminal error (edge returned a terminal error response, or the SSE emitted an `error` event) — precisely the condition under which merit-gateway has already refunded. | The common case, exactly and immediately. | Does not survive a hard refresh or tab close DURING the failure: the handler never runs, the lease survives, and the next click replays a refunded key. |
| **(a) `LEASE_TTL_MS` = 15 min.** | The hard-refresh-mid-failure gap, eventually. Analysis wall-clock is ~42s and every server timeout is far under 15 min, so a lease older than that cannot be in flight. | 15 minutes is still a window. |
| **(bounded) `MAX_LEASE_REUSES` = 3.** | The window in (a). A legitimate retry-after-refresh needs one or two reuses; three is generous. After that the lease is dead regardless of clock. | — |

Worst case after all three, **and with D-7's RPC fix in place: zero free replays.** A
refunded deduction is retired from the idempotency namespace, so even a lease that survives
a hard refresh and is replayed inside its TTL re-derives a key the RPC will now charge for.
The residual the lease was originally sized against — "at most 3 replays inside a 15-minute
window" — is what remains if D-7 is ever reverted; it is the second layer's budget, not the
shipped behavior. Bounding retries before refund is the same shape as the existing fix in
commit `75c25412 fix(resume): bound onboarding retries before refund`.

Stated plainly so no executor mis-reads the layering: **the RPC (D-7) is the guarantee; the
lease (D-3b) is defense-in-depth.** Neither may be dropped on the grounds that the other
exists.

`clearEliteRerunRecord` must NOT fire on a transport interruption (abort, offline,
navigation-away) — those are the states where the run may still be in flight server-side
and the lease is what protects the user from a second charge.

### D-3c. Lifecycle, precisely

1. On CTA click, read `localStorage['elite_rerun_<sourceResumeId>']`.
2. **If the lease is valid per D-3b**, REUSE `{newResumeId, attemptNonce}` verbatim:
   increment `reuses`, re-seed `sessionStorage['stream_params_<newResumeId>']` with the
   SAME nonce, navigate to `/results/<newResumeId>?stream=true`.
   `inputIdentity = sha256({text_hash, resumeId, targetRole, targetIndustry})` includes
   `resumeId`, so reusing the same row AND the same nonce is what makes the derived key
   identical — `check_and_deduct_merits` returns `already_deducted:true` and charges zero.
3. **Otherwise** (no record / completed / expired / exhausted), delete any stale record,
   mint ONE fresh `crypto.randomUUID()`, insert a fresh cloned row, write a fresh lease.
4. Delete the lease once the recorded row has `grading_data` (Task 9d) or on a settled
   failure (D-3b layer b).

`localStorage`, not `sessionStorage`, so a tab close / reopen retry still reuses the
nonce inside the lease window. `stream_params_*` stays in `sessionStorage` (existing
pattern) — if it is lost the stream simply cannot restart, which cannot double-charge
because no request is issued.

**Do NOT build on `src/hooks/useIdempotencyKey.ts`** — vestigial, client-only, referenced
by nothing but its own test.

**Production charging note (must be stated, not discovered):** `analyze-resume`'s
`withMerits` is unconditional — Phase 30 removed the flag and `merit-branch.test.ts:18-19`
plus `failure-branches.test.ts:297-304` assert the literal string `MERIT_SYSTEM_ENABLED`
does not appear in that file. The CTA rerun **will charge in production even with
`MERIT_SYSTEM_ENABLED=false`**. That is the intended behavior. Do not reintroduce that
string into `analyze-resume/index.ts`.

## D-4. Unknown tier (`analyzed_tier IS NULL`) semantics — deliberately asymmetric

`analysis_results` is a best-effort mirror that can be null (`index.ts:142`), so backfill
coverage will not be 100%. NULL means "unknown", never "free".

| Surface | NULL behavior | Rationale |
|---------|---------------|-----------|
| Upload cache short-circuit (D-1) | NULL **matches any tier** → row is reused, no charge | Preserves today's behavior byte-for-byte for legacy rows. Treating NULL as a miss would silently start charging merits for duplicate uploads that are free today. |
| Results `showFullResults` | Falls back to the current `userTier !== 'free'` behavior | No change from HEAD for legacy rows; avoids blanking sections on data whose provenance we cannot prove. |
| Elite rerun CTA | **Not shown** | Fail-closed against a spurious charge prompt. We cannot prove the row is Free. |
| Results affordance for NULL rows viewed by an Elite user | Neutral, non-charging line: "Tier of this analysis isn't recorded (pre-upgrade record)" + a plain link to `/upload` | Satisfies requirement 3 (never *claim* a cached result is Elite) without inventing a charge prompt. The `/upload` path charges through the normal, already-consented flow. |

Net: NULL suppresses the *prompt*, never the *cache reuse*. Every row written after Task 4
carries a real tier, so the NULL set is closed and shrinks to zero over time.

## D-6. `analyzed_tier` carries ONLY `free` | `elite` — the column, the CHECK and the client predicate agree

The column must not carry a value the client predicate will never ask for, or D-1 turns
into a permanent cache MISS that starts charging merits for duplicate uploads that are
free today — the exact outcome D-1 exists to prevent.

2. **The write** (Task 4): stamp `normalizeActiveTier(params.tier)`, not `params.tier`.
3. **The read predicate** (Task 6) and the CTA condition (Task 9): normalize the

## D-7. The refund/replay hole is CLOSED AT THE RPC (LOCKED — supersedes D-3a's earlier position)

CONTEXT.md § "Refund/replay hole — CLOSE IT AT THE RPC" is a LOCKED operator decision made
after plan-check. It overrides the earlier planning judgement that the RPC was too central
to touch. Task 7b implements it. Everything below is binding.

### The mechanism: a REFUNDED deduction is RETIRED from the idempotency namespace

One migration, three coordinated changes that must land together:

1. **`refund_merits` stamps the deduction it reverses.** After writing its mirroring
   `balance_type='refund'` rows, it stamps the original leg rows:
   `metadata = metadata || jsonb_build_object('refunded_at', to_jsonb(now()))`, scoped to
   `user_id = p_user_id AND metadata->>'deduction_id' = p_transaction_id::text AND
   balance_type IN ('subscription','shop')`. Nothing is deleted; the audit row survives
   verbatim plus one key.
2. **The partial unique index is replaced with one that excludes stamped rows.**
3. **`check_and_deduct_merits`'s entry-time pre-check AND its `unique_violation` race arm
   both add the same `metadata->>'refunded_at' IS NULL` filter** — byte-identical to the
   index predicate, so index and pre-check cannot drift into disagreeing about what
   "a live deduction" means.

### D-7a. The index collision, resolved explicitly

This is the collision CONTEXT.md demands be named rather than discovered at runtime: with
the pre-check fixed but the index untouched, a post-refund replay would insert a SECOND
`feature-deduct` row with the same key and be rejected by
`merit_transactions_idempotency_key_unique`.

| | predicate |
|---|---|
| **Old** (`20260512000003:62-64`) | `UNIQUE (idempotency_key) WHERE source = 'feature-deduct' AND idempotency_key IS NOT NULL` |
| **New** | `UNIQUE (idempotency_key, balance_type) WHERE source = 'feature-deduct' AND idempotency_key IS NOT NULL AND metadata->>'refunded_at' IS NULL` |

**Why marking, and not the alternatives:**

| Option | Rejected because |
|--------|------------------|
| Delete the refunded `feature-deduct` row | Destroys the audit trail, and `refund_merits`'s own `already_refunded` guard (`20260415000000:...`) plus every balance-reconstruction query read those rows. |
| Key on an extra client-supplied attempt counter | Leaks the fix into every `withMerits` caller and every client. The RPC must fix this for all features without any caller change. |
| Narrow the index only, leaving the pre-check broad | Then the pre-check still short-circuits on the retired row and no second charge ever happens. Both must move. |
| **Mark + narrow (CHOSEN)** | One definition of "live deduction", shared by the index and the pre-check. No caller changes. Fully reversible. |

Both `->>` and `||` on `jsonb` are IMMUTABLE, so `metadata->>'refunded_at' IS NULL` is
legal in an index predicate. Verify this at apply time rather than assuming it — if
Postgres rejects the predicate, STOP and report; do not fall back to a trigger.

**The race absorber still works, unchanged in shape.** Two concurrent callers with the same
key both see an unmarked namespace, both attempt the insert, one wins, the loser takes
`SQLSTATE 23505` and returns the winner's `deduction_id`. Adding `balance_type` to the key
does not weaken this: a genuine duplicate replay writes the same legs with the same key, so
it still collides. Both lookup sites (`:118-133` and `:196-212`) must gain the refunded
filter AND an `ORDER BY created_at DESC LIMIT 1`, because a key may now legitimately have
MORE THAN ONE `feature-deduct` row over its lifetime (one retired, one live) — an unordered
`LIMIT 1` could return the retired one.

**The legitimate replay case is preserved exactly.** Same key, no refund → the row is
unmarked → the pre-check hits → `already_deducted: true`, zero charge, no `user_merits`
touch. Byte-identical to today. The ONLY behavior that changes is for keys whose deduction
has since been refunded.

**`merit-gateway.ts:319-330` is NOT touched and NOT reversed.** An idempotent replay still
deliberately does not refund. No TypeScript changes in this task at all.

### D-7b. The split-deduction collision (found during this revision — resolve it here)

Independent of refunds: `20260512000003:179-195` writes TWO `feature-deduct` rows (one
`subscription`, one `shop`) sharing ONE `idempotency_key` whenever the cost is split across
buckets. The OLD index is unique on `idempotency_key` alone, so the second leg raises
`unique_violation`. What happens NEXT is counterintuitive, and a future reader will
re-derive it wrongly (this plan did, once) — so it is spelled out step by step, each step
verified against `20260512000003:178-213` and `merit-gateway.ts:249-263`:

1. **Both leg INSERTs sit inside `BEGIN ... EXCEPTION WHEN unique_violation ... END`
   (`:178-213`), and a PL/pgSQL block with an EXCEPTION clause IS A SUBTRANSACTION.** When
   the second leg raises 23505 the subtransaction rolls back — and it takes the FIRST leg's
   already-executed INSERT with it. **No row survives.** This is the step everyone misses:
   the end state is not "one leg written", it is "zero legs written".
2. The recovery `SELECT` in the exception arm (`:201-206`) therefore finds nothing (absent a
   genuinely concurrent winner), so `v_prior_id` stays **NULL**.
3. The function returns `{ success: true, transaction_id: null, already_deducted: true }`.
   The `user_merits` UPDATE at `:218-222` is never reached, so the balance is untouched.
4. `merit-gateway.ts:256-263` — the WR-03 / SEC-13 null guard — sees the falsy
   `transactionId` and returns `genericError(500, 'merit_system_error')`. **The wrapped
   callback never runs.**

Net: a split deduction with a non-NULL key is **BLOCKED, not free**. HTTP 500, no analysis,
no charge, zero ledger rows — permanently repeatable for any user whose
`subscription_balance` sits between 1 and `cost - 1` while `shop_balance` covers the
remainder. That is a paying customer who topped up being unable to run a resume analysis
AT ALL.

**This is a LIVE PRODUCTION DEFECT, not a test-only finding.** `analyze-resume`'s
`withMerits` is unconditional in production (Phase 30 removed the flag — see D-3c's
production charging note), so this path is reachable by real users today.

That is why the new index is keyed on `(idempotency_key, balance_type)` rather than merely
narrowed by the refund predicate: with the composite key the two legs no longer collide, the
subtransaction never aborts, both rows commit, and `user_merits` is updated once for the
full cost. **The remedy is unchanged — only the diagnosis moved** (hard 500, not free run).
Task 7 case 5 characterizes the pre-fix behavior against real Postgres FIRST; if that
observation contradicts this analysis, drop the composite and say so in the summary rather
than shipping an unjustified index change.

### D-7c. Historical rows

Deductions refunded BEFORE this migration carry no `refunded_at` stamp, so their keys stay
retired-less and remain replayable-for-free. The migration backfills the stamp onto every
`feature-deduct` row that already has a matching `balance_type='refund'` row. Backfill runs
BEFORE the new index is created — a PREFERENCE, not a load-bearing constraint. Either order
is safe: the OLD single-column index already guarantees at most one `feature-deduct` row per
non-NULL key, so no duplicate `(idempotency_key, balance_type)` pair can exist at migration
time and the index build cannot fail in either order. Keep the ordering because it reads
well; do not treat it as a correctness requirement.

### D-7d. What this does and does not guarantee

It guarantees the CHARGE side. It does not make refunds idempotent in some new way, does
not change costs, and does not alter any of the four existing Task 7 cases. And it does not
retire the D-3b lease — see D-3b's closing note.
