## Two live production defects fixed (found during planning, not asked for)

1. **Streaming retry double-charge (Task 5).** `attemptNonce` was minted in `Upload.tsx`
   but never threaded through `useResumeStream`, so the server minted a fresh UUID per
   request and every retry re-derived a new idempotency key → re-charged. Resume was the
   only feature that dropped its nonce.

2. **Refund/replay + split-deduction defects (Task 7b).** `check_and_deduct_merits` was
   not refund-aware. Two observed pre-fix behaviors, characterized live on preview by
   Task 7 before the fix:
   - **Refund/replay:** a refunded deduction kept its `feature-deduct` row + key, so
     replaying the key returned `already_deducted:true` and charged 0 — repeatable free reruns.
   - **Split deduction (D-7b):** a deduction spanning `subscription`+`shop` inserted two
     rows sharing one key; the old single-column unique index rejected the second leg; the
     PL/pgSQL `EXCEPTION` subtransaction rolled back BOTH legs; recovery `SELECT` found
     nothing; the RPC returned `transaction_id:null`; the gateway's WR-03 guard turned that
     into **HTTP 500 `merit_system_error`** — ZERO ledger rows, unchanged balance, feature
     BLOCKED (NOT a free run). **Live production defect** because `analyze-resume`'s
     `withMerits` is unconditional in production — any user whose `subscription_balance` is
     in `[1, cost-1]` with shop merits covering the rest was denied resume analysis.
   Fix: refund-aware idempotency. `refund_merits` stamps reversed rows with
   `metadata.refunded_at`; the partial unique index became
   `UNIQUE (idempotency_key, balance_type) WHERE source='feature-deduct' AND
   idempotency_key IS NOT NULL AND metadata->>'refunded_at' IS NULL`; the pre-check and
   race arm gained the same predicate + `ORDER BY created_at DESC`. The composite
   `balance_type` key was **justified by Task 7's live observation** — it is exactly what
   lets the two split legs coexist. Gated R0–R4 rollback in the migration header.
