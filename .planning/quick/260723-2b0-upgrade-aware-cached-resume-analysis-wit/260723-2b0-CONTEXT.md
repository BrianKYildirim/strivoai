# Quick Task 260723-2b0: Upgrade-aware cached Resume Analysis with Elite rerun - Context

**Gathered:** 2026-07-22
**Status:** Ready for planning

<domain>
## Task Boundary

Build an upgrade-aware cached Resume Analysis flow so an Elite user who has only a
cached **Free** resume analysis is offered a paid rerun instead of being silently
served the Free result as though it were Elite.

Required behaviors:
1. Record / reliably identify which membership tier produced each resume analysis.
2. When an Elite user opens or uploads a resume that only has a cached Free analysis,
   keep displaying the Free result but surface a CTA: **"Rerun with Elite — 3 merits."**
3. Never silently treat a cached Free result as an Elite result.
4. On CTA click: charge 3 merits **once**, run a complete new analysis through the
   existing Elite resume pipeline (full rerun, NOT partial-section generation).
5. Save the result as a separate Elite analysis; preserve the original Free analysis
   in history.
6. Make resume caching tier-aware so Free and Elite analyses cannot share a cache entry.
7. Idempotency + refund protection: retries, refreshes, or failed requests must not
   cause duplicate charges.

**Explicitly OUT of scope:**
- Do NOT retrofit Career Compass.
- Do NOT build partial-section generation (the rerun is a full Elite re-analysis).
- Leave all other features and behavior as-is. Resume Analysis only.

</domain>

<decisions>
## Implementation Decisions

### Elite payload — restore elite-extras budget
**LOCKED: Restore the elite-extras token budget as part of this task.**

`supabase/functions/analyze-resume/index.ts:350` currently declares
`{ callType: 'elite-extras', maxTokensFree: 0, maxTokensPro: 0, maxTokensElite: 0 }`,
and zero-budget calls are filtered out at `index.ts:434`. The code comment at `:327`
states "elite-extras is DISABLED (budget 0)".

That call is the SOLE producer of `eliteInsights` — `interviewLikelihood`,
`interviewLikelihoodExplanation`, `competitiveRanking`,
`recruiterFirstImpressions{atThreeSeconds, atSevenSeconds, whatTheyMiss}`,
`hiddenWeaknesses`, `powerPhrases`, `detailedATSGapAnalysis`
(see `_shared/resume-prompts.ts:290-292, 301`).

Without restoring it, a user paying 3 merits for "Rerun with Elite" receives an empty
`eliteInsights` object. `applyTierShape` (`_shared/result-merger.ts:84-86`) whitelists
`eliteInsights` as the ONLY Elite-additive field, so the marquee Elite differentiator
would be blank.

Implications the planner MUST handle:
- Restoring the budget adds a 4th parallel Anthropic call to the Elite fan-out.
  Latency and per-run cost both rise. The README records a <$0.10/run ceiling and a
  ~42s average — the plan must state the expected impact and keep within budget.
- `maxTokensElite` needs a concrete value; `_shared/tier-config.ts:89-93` sets
  `TIER_MAX_TOKENS` elite = 20000 as the overall envelope.
- Free and Pro must stay at 0 (Free tier prompt `FREE_TIER_SUFFIX` at
  `resume-prompts.ts:61-66` explicitly forbids every eliteInsights field).

### Tier storage — column on `resumes` + backfill from JSONB
**LOCKED: Both. Add a queryable column AND backfill history.**

- Add an `analyzed_tier` (or equivalent) column to `public.resumes` — this is the table
  the UI actually reads (`src/pages/Results.tsx:287`, `:410`, `:460`, `:503`).
- Backfill historical rows from `analysis_results.raw_response.metadata.tier`, which is
  already written at `analyze-resume/index.ts:52-58` but read by nothing in `src/`.
- Rows with no recoverable tier must be handled explicitly (documented default or NULL
  meaning "unknown") — the `analysis_results` mirror can be null
  (`analyze-resume/index.ts:142`), so backfill coverage will NOT be 100%.

**CRITICAL SECURITY CONSTRAINT — column-level GRANT.**
`resumes` has a user-facing UPDATE RLS policy
(`20251129_create_all_tables.sql:119-122`). RLS gates ROWS, not COLUMNS. Without an
explicit column-level `GRANT UPDATE (...)` that EXCLUDES the new tier column, an
authenticated user can forge their own `analyzed_tier` via PostgREST and suppress the
paid rerun CTA.

This is the exact defect already suffered and fixed in this repo — see
`supabase/migrations/20260712000001_...:222-235` and the repair migration
`20260712000003_fix_career_targets_update_grant.sql:5-51`. Note the documented trap in
that repair: a `session_user <> 'authenticated'` guard trigger ALWAYS passes under
PostgREST and is NOT a valid defense.

Also note the inverse trap recorded in project memory: a PostgREST upsert requires
column-level UPDATE on the conflict column, or every write 403s — inserts included.
Service-role tests will NOT catch either failure mode; the grant must be verified as an
authenticated user.

Every migration requires accompanying rollback SQL (project rule).

### Merit verification — remote deno tests AND live test-project run
**LOCKED: Both.**

1. Extend `test:edge:remote` to cover the `check_and_deduct_merits` idempotency
   contract against real Postgres. The partial unique index
   (`20260512000003_merit_transactions_idempotency.sql:62-64`,
   `CREATE UNIQUE INDEX ... WHERE source = 'feature-deduct' AND idempotency_key IS NOT NULL`)
   plus the entry-time `already_deducted` pre-check (`:118-133`) and the
   `EXCEPTION WHEN unique_violation` race absorber (`:196-212`) currently have NO
   automated test against a live database — the migration's own `DO $$` block (`:261-277`)
   is the only proof.
2. Run the full CTA flow live on the TEST Supabase project with
   `MERIT_SYSTEM_ENABLED=true`. `e2e/helpers/test-user.ts` already writes `user_il`
   balances directly against that project, so balances are assertable.

**Environment facts the plan must respect:**
- `MERIT_SYSTEM_ENABLED` is read at module scope / cold start only
  (`_shared/merit-gateway.ts:37-38`) — flipping it requires a redeploy or cold start.
- It is `false` on ALL environments including production, and per Phase-9 D-03
  (`docs/ENVIRONMENT.md:82`) it STAYS false on production.
- BUT `analyze-resume` had the flag REMOVED in Phase 30 — `withMerits` there is
  unconditional (`analyze-resume/index.ts:1348-1355`). Tests `merit-branch.test.ts:18-19`
  and `failure-branches.test.ts:297-304` assert the literal string `MERIT_SYSTEM_ENABLED`
  does NOT appear in that file. Any new code in `analyze-resume` must not reintroduce it
  or those tests break.
- Therefore the sync/stream rerun WILL charge in production even with the flag off.
  This is intended, but must be stated explicitly in the plan.
- Preview runs `AI_TEST_MODE` fixtures and never calls Anthropic — Elite payload content
  cannot be QA'd there.

### Refund/replay hole — CLOSE IT AT THE RPC (added 2026-07-22, post plan-check)
**LOCKED: Fix `check_and_deduct_merits` so a REFUNDED transaction is not treated as
`already_deducted`. Do not settle for the client-side lease alone.**

Discovered during plan verification. The hazard chain, verified in source:
- `_shared/merit-gateway.ts:299-309` refunds on a refundable throw when `!alreadyDeducted`.
- `refund_merits` (`20260415000000_merit_rpcs.sql:165-209`) writes a SEPARATE
  `balance_type='refund'` row and leaves the original `source='feature-deduct'` row —
  including its `idempotency_key` — intact.
- The entry-time pre-check in `20260512000003_merit_transactions_idempotency.sql:118-133`
  looks up ONLY `idempotency_key + source='feature-deduct'` and never consults refund
  state.

Net: a refunded attempt whose idempotency key is replayed returns
`already_deducted: true` and charges 0.

The client-side lease (D-3b: `grading_data IS NULL` + TTL + max-reuses) BOUNDS this to
≤3 free reruns per refunded attempt inside a 15-minute window, but cannot close it — a
hard refresh or tab close mid-failure prevents `clearEliteRerunRecord` from ever running,
leaving all reuse conditions true. It is reachable BY ACCIDENT: any transient Anthropic
failure where the user refreshes before the error settles yields a free Elite rerun.

**Operator decision: close it properly at the RPC.** The pre-check must treat a
transaction that has since been refunded as NOT already-deducted, so a replay charges
again. This benefits every feature routed through `withMerits`, not just resume.

Constraints on this fix:
- It touches a core money path. Own migration, own rollback SQL, own remote test.
- Must NOT break the legitimate idempotent-replay case (same key, no refund → still one
  charge). That is the behavior the partial unique index and the
  `EXCEPTION WHEN unique_violation` race absorber (`20260512000003:196-212`) exist to
  protect; preserve both.
- Must not reverse `merit-gateway.ts:319-330`, which deliberately does NOT refund on an
  idempotent replay.
- The partial unique index is `WHERE source = 'feature-deduct' AND idempotency_key IS NOT
  NULL` — if a replay after refund now inserts a SECOND `feature-deduct` row with the
  same key, that index will reject it. The fix must resolve this collision explicitly
  (whichever way, state it), not discover it at runtime.
- Retain the migration's own `DO $$` verification-block convention.

Once closed at the RPC, the client-side lease stays as defense-in-depth, but
`must_haves` truth #3 may then legitimately claim the next CTA click charges again —
and a test must prove it against real Postgres, not just assert it.

<specifics>
## Specific Ideas

### The core defect is client-side, not server-side

The server cache is ALREADY tier-aware and needs no redesign:
- `analysis_cache` has a first-class `tier` column with a CHECK constraint
  (`20260512000000_analysis_cache_table.sql:44-59`).
- Tier is hashed into `cache_key` itself (`_shared/cache-fingerprint.ts:117`,
  `analyze-resume/index.ts:1362-1375`).
- So an upgraded user's request already produces a different key and MISSES the Free row.

The actual bug is the client-side short-circuit in `src/pages/Upload.tsx:112-130`:

```ts
const { data: existingResume } = await supabase
  .from('resumes')
  .select('id, analyzed_at')
  .eq('user_id', user.id)
  .eq('file_hash', fileHash)
  .not('grading_data', 'is', null)
  .order('analyzed_at', { ascending: false })
  .limit(1)
  .maybeSingle();

if (!existingResumeError && existingResume?.id) {
  toast.message('Using your previous analysis for this resume.');
  navigate(`/results/${existingResume.id}`);
  return;
}
```

Keyed on `(user_id, file_hash)` with ZERO tier awareness, and it navigates away BEFORE
any edge function runs — so the correct tier-aware server cache never gets a chance.
Fixing this query (or removing the short-circuit and letting `withMerits` +
`precheck_cache` decide) is the heart of requirement 6.

### The rendering mismatch that must be reconciled

`src/pages/Results.tsx:346-358` reads the user's CURRENT tier from
`profiles.subscription_tier`, and `Results.tsx:540` sets
`const showFullResults = userTier !== 'free'` (consumed at `:1062, :1075, :1087, :1183`).

So an upgraded user ALREADY sees the paid layout rendered over Free-shaped
`grading_data` from which `applyTierShape` deleted the Elite/Pro fields. Rendering tier
and data tier are decoupled with nothing reconciling them. `showFullResults` is the
natural reconciliation point and is where the "this is a Free analysis" state and the
CTA should hang.

### Existing merit + idempotency machinery to REUSE (do not rebuild)

- `withMerits(ctx, 'resume_analysis', ...)` — `_shared/merit-gateway.ts:219-230`, calls
  RPC `check_and_deduct_merits({p_user_id, p_feature, p_tier, p_idempotency_key})`.
  NOTE: there is no `check_and_deduct_il` / `refund_il` in this repo despite older naming.
- Server-derived idempotency: `_shared/idempotency-key.ts:87-93`
  `deriveIdempotencyKey({userId, feature, tier, inputIdentity, attemptNonce})`.
  Resume wires it at `analyze-resume/index.ts:1513-1526` with
  `inputIdentity = sha256({text_hash, resumeId, targetRole, targetIndustry})`.
  The client supplies ONLY `attemptNonce` (`Upload.tsx:217, 233`).
  **Because tier is already a component of the derived key, a Free run and an Elite
  rerun of the same resume naturally produce different keys — but the same Elite rerun
  retried with the same nonce collapses to one charge. This is the mechanism that
  satisfies requirement 7; reuse it rather than inventing a new one.**
- `src/hooks/useIdempotencyKey.ts` is VESTIGIAL — client-only, returns a bare
  `randomUUID()`, and is referenced by nothing but its own test. Do NOT build on it.
- Refunds: automatic in-gateway on refundable throw (`merit-gateway.ts:301-304`);
  deliberately NOT refunded on idempotent replay (`:319-330`).
  Worker path uses `refundMeritsForJob` (`:352-360`).
- Cost source of truth is the `merit_feature_costs` table; `resume_analysis` = 3 on
  free/pro/elite after `20260607000000_update_feature_merit_costs.sql:5-9`. Frontend
  reads it via `src/hooks/useFeatureCosts.ts:15`. The CTA must read the real cost, not
  hardcode "3".

### Known drift worth fixing while in here (low risk, optional)

`analyze-resume/index.ts:365` hardcodes
`const MERIT_COST: Record<string, number> = { free: 3, pro: 2, elite: 3 }`.
Pro is stale (DB says 3). It is NOT used for charging — only passed as `credits` into
`recordUsageWithAnalysis` — so `usage_tracking.credits` under-reports Pro resume runs.

### Test-coverage gap to close

`supabase/functions/analyze-resume/cache.test.ts` is NOT in the `test:ci` task list in
`supabase/functions/deno.json`, even though `analyze-career/cache.test.ts` IS. The
resume cache contract test never runs in CI. Same for `index.test.ts` and
`__tests__/onboarding-timeout-budget.test.ts`. Since this task changes resume cache
behavior, that test must be wired into CI or the change ships unverified.

Also relevant (project memory): `verify:baseline` can be GREEN while an edge function
has a SyntaxError, because edge tests never parse the module. Run the boot test.
