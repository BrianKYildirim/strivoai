<root_cause_verified>
Diagnosis confirmed by inspection at HEAD — do NOT re-derive:

1. `src/pages/Results.tsx:421-430` (`fetchOnce`) reads the `resumes` row on mount. For a fresh
   streaming run this happens BEFORE the server writes `analyzed_tier`, so the local copy holds
   `analyzed_tier: null`.
2. `src/pages/Results.tsx:256-263` — the stream-completion branch merges **only**
   `overall_score` and `grading_data` into `prev`. The stale `analyzed_tier: null` survives the
   spread.
3. `src/components/EliteRerunCta.tsx:38-50` takes its `analyzedTier == null` branch and renders
   the D-4 neutral "pre-upgrade record" copy.
4. The realtime `postgres_changes` UPDATE subscription (`Results.tsx:432-447`) *would* have
   carried the tier, but it races the stream and demonstrably loses in production. It is a
   best-effort backstop, not an authority.
</root_cause_verified>

<decision_carry_the_tier>
**The stream-completion payload does NOT carry the analyzed tier.** Verified at
`supabase/functions/analyze-resume/index.ts:1242` (`sendEvent({ type: 'complete', result,
run_id })`), `:1681`, `:1772`, `:1800` and `responseForResumeResult` at `:165-175` — the
`complete` SSE event carries `result` (+ `run_id` on the lifecycle path) and nothing else.
`useResumeStream` therefore has no tier to expose.

Two options were available:

| Option | Verdict |
|--------|---------|
| (b) Thread the server-written tier into the `complete` SSE payload | **REJECTED.** Requires editing `analyze-resume/index.ts` at four `sendEvent` sites plus the shared `responseForResumeResult` helper — outside this task's frontend-only constraint, and it would need an edge redeploy to fix a cosmetic client-state bug. It also widens a money-path file for a non-money defect. |
| (a) Re-read `resumes.analyzed_tier` after the complete event | **CHOSEN.** Frontend-only, zero deploy coupling, and it reads the *same authoritative column* the server already wrote. Ordering is safe: the server writes `analyzed_tier` inside `persistAndCacheResumeResult` / the `saving->completed` CAS, which happens **before** the `complete` event is emitted — so by the time the client observes completion, the row is committed. One read, no retry loop needed. The existing 90s stream-stuck safeguard (`Results.tsx:288-300`) already uses exactly this `supabase.from('resumes').select(...).eq('id', id)` pattern, so this is the established convention, not a new one. |
</decision_carry_the_tier>

```ts
// 260724-2iv — carry the SERVER-WRITTEN analyzed_tier through stream completion.
//
// The row is read on mount BEFORE the analysis finishes writing analyzed_tier, so the local
// copy holds a STALE null that survives the completion merge and makes EliteRerunCta render
// the D-4 "pre-upgrade record" line over a brand-new Elite result.
//
// D-4 is PRESERVED: an honest NULL from the DB stays NULL (the neutral, non-charging line is
// still correct for real pre-upgrade rows). The tier is only ever taken from what the server
// wrote — never from the viewing account's subscription tier.
export function applyAuthoritativeTier(
  prev: any,
  read: { data: { analyzed_tier?: 'free' | 'elite' | null } | null; error: unknown },
) {
  if (!prev) return prev;
  // Read failed or the row is not visible -> never guess. Leave the local value untouched.
  if (read.error || !read.data) return prev;
  return { ...prev, analyzed_tier: read.data.analyzed_tier ?? null };
}
```
