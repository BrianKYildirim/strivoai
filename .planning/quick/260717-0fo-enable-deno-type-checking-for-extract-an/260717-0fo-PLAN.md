# Quick Task: Enable Deno type checking for extract-analysis-structure

Follow-up to 260716-qtt. `test:ci` runs with `--no-check`, so edge function sources are
unprotected by Deno type checking. Close that gap for the `extract-analysis-structure`
module and make the gate enforce it.

## Investigated findings (verified locally — do NOT re-derive)

### 1. The config was masking everything (fix this FIRST)

`supabase/functions/tsconfig.json` (added by "Preview (#227)", referenced by NOTHING —
grep across `.vscode/`, `scripts/`, `.github/`, `supabase/` finds no consumer) contains:

```json
{ "compilerOptions": { "lib": ["dom","esnext"], "moduleResolution": "bundler",
  "allowImportingTsExtensions": true, "noEmit": true } }
```

Deno 2.7.1 reads it. Consequences:
- `lib` omits `deno.ns` → `TS2304: Cannot find name 'Deno'` (7x in index.ts alone)
- `moduleResolution: bundler` conflicts with Deno's `module: NodeNext` → `TS5095` + `TS5109`
  on EVERY file, including files with zero real errors.

`supabase/functions/deno.json` has NO `compilerOptions`.

**Proven fix:** adding `compilerOptions` to `deno.json` makes `deno check` behave — verified
by adding `{"compilerOptions":{"lib":["deno.ns","deno.window","dom","esnext"]}}` to
`deno.json` and re-running: `deno check extract-analysis-structure/extract-recruiting-lens.ts`
went from 2 config errors to CLEAN, with `tsconfig.json` still present. `deno.json` wins, so
deleting `tsconfig.json` is NOT required.

**Do NOT delete `supabase/functions/tsconfig.json`.** Nothing references it, but the Supabase
CLI bundling path is unverified and this task does not deploy. Leave it; it is recorded as a
follow-up landmine.

### 2. Real errors, once the config is fixed

Repo-wide: 36 errors across 14 files. **This task fixes ONLY the 12 in
`extract-analysis-structure`:**

| File | Errors |
|---|---|
| `extract-analysis-structure/index.ts` | 7 |
| `extract-analysis-structure/extract-linkedin.ts` | 3 |
| `extract-analysis-structure/extract-resume.ts` | 2 |
| `extract-analysis-structure/extract-recruiting-lens.ts` | 0 (already clean) |

Their shapes:
- `TS2339: Property 'error' does not exist on type 'QueryBuilderLike'` (4x) — the hand-rolled
  `QueryBuilderLike` does not model the awaited `{ data, error }` terminal result, so
  `const r = await supabase.from(x).insert(y); r.error` fails to type.
- `TS2345: Argument of type 'SupabaseClientLike' is not assignable to parameter of type
  'SupabaseClientLike'` (3x) — `index.ts` and each `extract-*.ts` declare their OWN
  structurally-different copies of identically-named types.
- `TS2322: Type '{} | null' is not assignable to type 'string | null'` (2x) — `raw_response`
  field typing.

**The out-of-scope 24 errors in 11 other files are NOT to be touched.** Critically, 11 of them
are `'userContext' is possibly 'null'` in `analyze-career`, `submit-resume-analysis-job`,
`submit-career-analysis-job`, `process-career-analysis-job`. That is the EXACT bug class
behind quick task 260713-hrd (Career Compass: `requireInternalAuth()` returns `null` by type
→ every queued run resolved `tier='free'` → Elite users paid Elite and were analyzed as Free,
with real refunds). Silencing those with `!` would re-hide a failure that already cost money.
They need individual diagnosis in their own task. Same for `ocr-pdf/index.ts:247`, which
guards `if (reuse.ok && reuse.found)` then reads `reuse.result.text` — the guard narrows the
lookup, not the inner `ExtractionResult` union; possibly a live bug.

## Task 1: Fix the Deno config

**File:** `supabase/functions/deno.json`

Add a `compilerOptions` key with `lib` including `deno.ns` (plus `dom`, `esnext`) so Deno
stops falling back to the stray `tsconfig.json`. Do not set `moduleResolution`. Keep the
existing `lock`, `tasks`, `imports` keys byte-identical apart from formatting the file
requires.

Verify: `deno check extract-analysis-structure/extract-recruiting-lens.ts` reports zero
errors (no TS5095/TS5109/TS2304).

## Task 2: Fix the 12 module type errors

**Files:** `extract-analysis-structure/{index,extract-resume,extract-linkedin}.ts`
(+ a new shared types module if warranted)

The duplicate-type errors (TS2345) mean the same-named types are redeclared per file. Prefer
extracting the shared `SupabaseClientLike` / `QueryBuilderLike` / `AnalysisResultRow` types
into a single `extract-analysis-structure/types.ts` imported by all four files — that removes
the class of error rather than patching each site. Model the awaited terminal result
(`{ data, error }`) accurately so `TS2339` resolves honestly.

**Hard constraints:**
- These are TYPE-ONLY fixes. Runtime behavior must not change. The module was deployed to
  prod today (fn v102) and is verified working — do not alter control flow.
- Do NOT use `any`, `@ts-ignore`, `@ts-expect-error`, or non-null assertions (`!`) to force
  a green check. Make the types describe what the code actually does. If a type error can
  only be silenced rather than fixed, STOP and report it instead.
- Do not touch `extract-recruiting-lens.ts` logic (already clean) beyond importing shared
  types.

## Task 3: Wire the gate so a regression FAILS
