# Quick Task 260727-0s6: Fix Slow Stripe Checkout Open Window Summary

Both Stripe checkout entry points now render visible UI on the same tick as the click — an explicit "Preparing secure checkout…" body replaces several seconds of dead time — with an in-flight guard that guarantees exactly one Stripe session/PaymentIntent per click and a controlled close on every non-embedded outcome.

## What Was Built

**Task 1 — pending state + removed auth round trip (`e583434a`)**

`StripeCheckoutWrapper` used to hard-return `null` whenever `clientSecret` was null, so nothing could be shown while a session was being created. It now returns null only when *closed and* secretless; an open, secretless wrapper renders a `checkout-preparing` body with a spinner and the shared copy. Ordering inside `DialogContent` is pending → unavailable → embedded, and the pending branch deliberately does not mount `EmbeddedCheckoutProvider` (Stripe forbids swapping `client_secret` on a mounted provider).

The mode-mismatch refusal is intact: `clientSecretMode()` is never called with null (`backendMode` short-circuits to `'unknown'`), the `console.error(describeStripeMode(...))` still fires during render, and `key={clientSecret}` plus its comment are untouched.

`useStripeCheckout.fetchClientSecret` swapped `supabase.auth.getUser()` (a `/auth/v1/user` network call on the critical path) for `supabase.auth.getSession()` (local read). Everything else — the `ui_mode: 'embedded'` body merge, error toast + `console.error`, the H-01 `setPendingUpgrade` block, `setIsLoading` transitions — is byte-identical.

**Task 2 — synchronous open + single-session guard (`c7a73e60`, `827f5f05`)**

`Pricing.handleTierCta`'s paid-tier branch now clears the secret, sets the title and opens the dialog *before* any `await`. `checkoutInFlightRef` drops repeat clicks and is released in a `finally`, so a retry after a failure still works. All five post-await outcomes were reworked so none can strand the dialog in "preparing": invoke error, `swap` (closes before `navigate`), `portal_required` (closes before the portal invoke), unexpected shape, and the `catch`. The `free` branch, `handleConfirmDowngrade`, the downgrade/renewal effects and the `<StripeCheckoutWrapper>` JSX are untouched.

`PricingTable.handleSubscribe` got the same treatment, relying on the existing `isCtaDisabled` (`loadingTier` / `isCheckoutLoading`) for re-click blocking, plus `setCheckoutOpen(false)` when the hook returns no secret.

`827f5f05` is a comment-only move: my added close-on-failure note sat between `setCheckoutOpen(true)` and the invoke, pushing them 647 chars apart and breaking the plan's declared 600-char adjacency guard. Hoisting the note above the open call restored it to ~517. No pre-existing comment was removed.

**Task 3 — top-up copy + same-pack de-dup (`beebb381`)**

`StripePaymentElementModal`'s loading branch shows the same "Preparing secure checkout…" line under its spinner, keeping the `payment-loading` testid and both surrounding branch conditions.

`TopUpProvider` gained `inFlightPackRef`: a repeat `topup:open` for the pack already awaiting a PaymentIntent is dropped, while a *different* pack still falls through and supersedes via `requestIdRef` (WR-01). The guard is cleared only after the WR-01 staleness check — so a superseded response cannot clear a newer request's marker — and on dialog close. The IN-03 malformed-event contract is verbatim: invalid detail still returns without touching `requestIdRef`, `inFlightPackRef`, or state.

## Key Implementation Details

- The perf win has two independent parts: the dialog appears instantly (perceived), and one network round trip was removed from the critical path (actual).
- `backendMode` is typed `StripeMode` and defaults to `'unknown'` rather than `null`, which keeps `describeStripeMode`'s signature satisfied without a cast — TypeScript cannot narrow it from the boolean `mismatch`.
- The `swap` / `portal_required` paths close the dialog *before* navigating or redirecting, so the user never sees a flash of a dialog closing after the page has moved on.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `describeStripeMode` type mismatch on the null-guarded `backendMode`**
- **Found during:** Task 1
- **Issue:** The plan's suggested `const backendMode = clientSecret ? clientSecretMode(clientSecret) : null` makes `backendMode: StripeMode | null`, which `describeStripeMode(context, StripeMode, StripeMode)` rejects — TS cannot narrow it from the separate boolean `mismatch`. `npm run type-check` would have failed.
- **Fix:** Defaulted to `'unknown'` instead of `null` and annotated `const backendMode: StripeMode`. Behaviourally identical (`isStripeModeMismatch` treats `'unknown'` as never-a-mismatch, and the branch is gated on `clientSecret` anyway) and still never calls `clientSecretMode(null)`, which was the plan's actual requirement.
- **Files modified:** `src/components/StripeCheckoutWrapper.tsx`
- **Commit:** `e583434a`

- **Comment relocation commit** (`827f5f05`) — see Task 2 above.
