# Phase 15.2 Quick Task 260419-20o: Analysis Loading Overlay Consistency Summary

One-liner: Universal analyzing overlay (z-fix + scroll/nav lock + monotonic rAF progress) wired into all 6 analysis features, plus a documented resilience contract on the resume/career queue workers flagging the missing merit-refund pathway.

## What Shipped

**Task 1 — Overlay correctness** (commit `332bc78`)
- Bumped `UniversalAnalyzing` z-index from `z-40` to `z-[60]` so it sits above the `z-50` navbar.
- Added body scroll lock (`document.body.style.overflow = 'hidden'`) while the overlay is mounted.
- Added `role="dialog"` + `aria-modal="true"` for screen-reader handling.
- Replaced the buggy `setInterval`-driven step animator (which reset `currentStep` to 0 every render of inline arrays) with a `requestAnimationFrame` asymptotic curve: `target = 95 * (1 - exp(-elapsed / (expectedDurationMs / 3)))`. Progress is monotonic — `setProgressPercent(prev => Math.max(prev, Math.min(target, 95)))` — so it can never go backwards on parent re-renders.
- Memoized `stepConfig` by stable id signature so inline step arrays no longer churn the animator.
- Created `AnalysisLockContext` with refcount semantics (`lock()`/`unlock()` increment/decrement; `isLocked = lockCount > 0`), wired `<AnalysisLockProvider>` into `App.tsx` above the navbar, and made `UniversalAnalyzing` auto-call `lock()`/`unlock()` on mount/unmount when `isAnalyzing=true`.
- Updated `Navbar.tsx` to consume `useAnalysisLock()` and disable the logo, hamburger, popover, popover links, desktop NavigationMenu links, and both the desktop + mobile avatar dropdown triggers/items while `isLocked` is true (via `disabled`, `pointer-events-none opacity-60`, and `onClick` preventDefault).

**Task 2 — Feature audit + unification** (commit `a0fef97`)
- Replaced the custom inline streaming/loading UI in `Results.tsx` (~100 lines of bespoke stage chips, Loader2 spinner, and partial-summary card) with `<UniversalAnalyzing>` so resume Results now matches the look-and-feel of every other analysis page. Stream-mode error state is preserved as a dedicated retry CTA branch.
- Added `expectedDurationMs` to all 6 features so the progress curve is calibrated per workload:
  - Resume Analysis (Upload + Results): `45000`
  - Career Compass: `60000`
  - Recruiting Lens: `40000`
  - LinkedIn Grader: `25000`
  - Interview Prep Coach: `20000`
  - Skills Gap Analysis: `30000`
- Hoisted previously-inline step arrays in `Results.tsx`, `RecruitingLens.tsx`, and `InterviewPrepCoach.tsx` to module scope, eliminating identity churn on parent re-renders.
- Audited every analysis page for raw debug output (`JSON.stringify(state)`, dumped state objects in JSX, naked `console.log` to JSX children). Only matches were intentional JSON-LD schema in `Index.tsx`.

**Task 3 — Server-side resilience verification** (commit `b3e2569`)
- Audited every `analyze-resume` write site (13 paths across streaming/non-streaming × free/parallel/fallback × merit/legacy branches) and confirmed `grading_data` is persisted on every success path.
- Confirmed `analyze-career` writes `career_compass_analyses` on success and surfaces non-2xx on failure (no silent completes).
- Confirmed both queue workers correctly route non-2xx into either retry (via `computeRetryBackoffMs` + `isRetryableHttpStatus`) or terminal `failed` status — no silent completes.
- Added a RESILIENCE CONTRACT comment block to both processors capturing the verified invariants and the one outstanding gap (see Deferred Items below).

## Deferred Items

**Merit refund on terminal failure (schema migration required)**

`submit-resume-analysis-job` and `submit-career-analysis-job` both call `withMerits()` at insertion time and receive a `_txId` from the `check_and_deduct_merits` RPC, but they do NOT persist that transaction id onto the `analysis_jobs` row. As a result, the queue workers cannot call `refundMeritsForJob({ supabase, jobId, transactionId, reason })` when a job exhausts `max_attempts` and is marked `failed` — they have no transaction id to pass.

Required follow-up (single migration, two function patches):
1. `ALTER TABLE analysis_jobs ADD COLUMN merit_transaction_id text;`
2. `submit-resume-analysis-job` + `submit-career-analysis-job` persist `_txId` on row insert.
3. `process-resume-analysis-job` + `process-career-analysis-job` call `refundMeritsForJob` in the terminal-failure branch BEFORE setting `status='failed'`.

Until shipped, terminal failures consume merits without refund. User-visible impact is bounded — the retry budget is generous (multi-day window), so free/Pro users see at most 0–1 lost merits per terminal failure, but the right thing to do is wire the refund.
