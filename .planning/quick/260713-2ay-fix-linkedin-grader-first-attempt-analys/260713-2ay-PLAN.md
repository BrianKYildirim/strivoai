<objective>
Fix the LinkedIn Grader first-attempt failure: the first click errors + refunds, the second click succeeds.

Root cause (CONFIRMED against production — see `260713-2ay-ROOT-CAUSE.md`, do NOT re-investigate): the free-tier
Anthropic call gets a **50s** timeout but a LinkedIn grade legitimately takes **45-70s**. The AbortController
fires, `_shared/anthropic.ts:731` reports **408**, and `grade-linkedin/index.ts:51` classifies 408 as a
**non-retryable 4xx client error** — so the 3-attempt retry loop is skipped on the single most transient
failure mode there is. Eight production free-tier refunds landed within half a second of the exact 50 000 ms
timeout value. The user is manually performing the retry the server should have performed itself.

Purpose: one click = one grade = one charge, with honest errors when something genuinely fails.
Output: server retries the timeout inside a bounded deadline; the live paid path is idempotent; the client
recovers a grade that landed anyway and never lies about refunds.

**NOT in scope (locked):** do NOT reduce `maxTokensOutput.linkedinGrader`, do NOT tighten the prompt (D1),
do NOT enable the analysis-lifecycle / `run_id` path (D5 — it is dormant AND broken: it passes
`jobType: 'linkedin_grading'`, which violates the live `analysis_jobs_job_type_check` CHECK constraint and
would 500 100% of LinkedIn requests). Only Free and Elite are live tiers (D6) — `pro` exists in
`Record<Tier, …>` literals for structural consistency only and is collapsed onto Elite by
`normalizeActiveTier()`. **No DB migration is required by this plan.**

<budget_invariant>
The ONE number relationship this fix rests on. Every task must preserve it:

```
client_budget (180_000ms)  >  server_total_deadline (165_000ms)  >  per_call_timeout (90_000ms)
   LinkedInGrader.tsx              grade-linkedin/index.ts             tier-config.ts 'linkedin'
   invokeWithTimeout                LINKEDIN_TOTAL_DEADLINE_MS          TIER_TIMEOUTS.*.linkedin
```

Why these numbers:
- **90s per call** — real workload is 45-70s against today's 50s wall. 90s clears the observed p100 with headroom.
- **165s total** — worst case is attempt 1 (90s) -> 408 -> short backoff -> attempt 2 clamped to the ~72s
  remaining. A second attempt at ~72s still comfortably covers the 45-70s p50-p100 band. Naive unbounded
  retries would be 3 x 90s x 2 loops = 540s; the deadline is what makes 408-retryability safe.
- **180s client** — the client must NEVER give up before the server does, or it abandons a run the server
  completes (that is defect S2). 180 > 165 with 15s of slack for network + cold start.
- Elite `core` is already 155_000 in production, so a 165s server budget is inside the established envelope.
</budget_invariant>

```ts

  /** Absolute epoch-ms deadline for ALL attempts across the whole handler. */
  deadlineAt: number;
  /** Injectable for tests. Defaults to invokeAnthropicText. */
  invoke?: (p: AnthropicInvokeParams) => Promise<AnthropicInvokeResult>;

  maxAttempts?: number; // default 3
}

  params: AnthropicInvokeParams,
```

Behavior — the three changes that matter:

- **408 IS RETRYABLE (THE headline bug).** Replace the `status >= 400 && status < 500 && status !== 429`
  early-return with an explicit retryable predicate:
  `isRetryableAiStatus(s) => s >= 500 || s === 429 || s === 408`.
  Everything else (400 / 401 / 403 / 422) stays a non-retryable immediate return. Also treat an
  abort/timeout-shaped `error` string as retryable, mirroring `merit-gateway.isRefundableAnthropicError`.
  Leave a comment naming the bug so it cannot be silently re-introduced.

- **Hard total deadline.** Before EVERY attempt compute `remaining = opts.deadlineAt - now()`.
  - If `remaining < MIN_ATTEMPT_MS` (15_000), STOP and return `lastResult` — or, if no attempt ever ran,
    a synthetic `{ ok: false, status: 408, error: 'AI deadline exhausted' }` (408 keeps it inside
    `isRefundableAnthropicError`, so the Merit is still refunded on a genuine give-up).
  - Clamp the per-attempt timeout: `timeoutMs: Math.min(params.timeoutMs ?? remaining, remaining - 1_000)`.
    This is what stops a 90s attempt 2 from overrunning a 165s deadline.

- **D4 — slower, jittered backoff for 529/overload.** Today's flat `[1000, 2000, 3000]` burns ~4s and gives
  up, which is exactly why the ~3-5s Elite refunds happen. Use status-aware backoff:
  - `529 / 5xx / 429`: `base = 2_000 * 2 ** attempt` (2s, 4s) **plus 0-1000ms jitter** — rides out a short
    overload window instead of failing fast.
  - `408`: short (`500ms + 0-500ms jitter`) — a 90s wall already consumed most of the budget; do not spend
    the remainder sleeping.
  - ALWAYS clamp: `sleepMs = Math.min(backoff, remaining - MIN_ATTEMPT_MS)`; if `<= 0`, stop instead of
    sleeping.
  Keep the existing `log.warn('ai-retry', { attempt, status })` line and add `remainingMs`.
