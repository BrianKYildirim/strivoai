# Quick Task: Fix the 24 remaining Deno type errors + widen the check gate

Follow-up to 260717-0fo, which fixed the `deno.json` config and gated
`extract-analysis-structure` only. This closes the remaining 24 errors across 11 edge
functions and widens the `check` task to every function entrypoint.

Reproduce the current state: `cd supabase/functions && deno check $(ls */index.ts)`
→ **36 errors** (12 already fixed in the extract module = 24 remaining here).

## Investigated findings — do NOT re-derive

### A. `ocr-pdf` is a TYPE-MODELING GAP, not a live bug (disproven suspicion)

STATE.md flagged `ocr-pdf/index.ts:247` as a suspected live bug: it guards
`if (reuse.ok && reuse.found)` then reads `reuse.result.text` / `.metadata`, and the guard
narrows the *lookup*, not the inner `ExtractionResult` union.

**I traced it. It is NOT a runtime bug.** `buildLookupResult`
(`_shared/document-persistence.ts:196-210`) is the ONLY code path that returns
`found: true`, and it always constructs `result: { ok: true, text, metadata }`. The
failure variant can never reach that branch. `lookupAcceptedExtraction` has exactly one
non-test caller (`ocr-pdf/index.ts:243`).

The defect is that the declared type is too loose:
```ts
// _shared/document-persistence.ts:68-71
export type LookupAcceptedExtractionResult =
  | { ok: true; found: true; result: ExtractionResult }   // <-- too wide
  | { ok: true; found: false }
  | { ok: false; found: false; error: string };
```
`ExtractionResult` (`_shared/document-extraction-types.ts:38-50`) is a union whose success
arm is anonymous, so it cannot be referenced.

**Fix:** name the success arm and narrow the lookup result.
```ts
// document-extraction-types.ts
export type ExtractionSuccess = { ok: true; text: string; metadata: ExtractionMetadata };
export type ExtractionResult = ExtractionSuccess | { ok: false; /* unchanged */ };

// document-persistence.ts
| { ok: true; found: true; result: ExtractionSuccess }
```
Type-only. Narrowing a return type cannot break consumers. Do NOT restructure `ocr-pdf`.

### B. `requireAuth`'s signature is the Career Compass bug, still latent in the types

The 11 `TS18047 'userContext'/'authenticatedUserCtx' is possibly 'null'` errors are NOT
individually bugs — they are one signature defect. The three auth types have completely
different real contracts (`_shared/auth.ts`):

| `opts.type` | Implementation | Real contract |
|---|---|---|
| `'user'` | `requireUserAuth(req): Promise<UserContext>` (auth.ts:94) | **never null** — throws a Response on failure |
| `'internal'` | `requireInternalAuth(req): Promise<null>` (auth.ts:142) | **always null** on success — throws on failure |
| `'webhook'` | returns `null` (auth.ts:86) | always null — signature checked by the handler itself |

`requireAuth` (auth.ts:74-90) collapses all three into `Promise<UserContext | null>`,
destroying that information. Consequences, both live today:
1. Every `type: 'user'` call site (14 of them) must dereference a value the compiler
   thinks may be null, even though it provably never is → the 11 TS18047 errors.
2. Every `type: 'internal'` call site (11 of them) gets `UserContext | null` and looks
   like it *might* carry a user — when it is **always null**. That is precisely quick
   260713-hrd: `analyze-career`'s queued path resolved `tier = ctx?.tier ?? 'free'` for
   EVERY run, so Elite users paid Elite and were analyzed as Free, with real refunds.

**Fix — overloads (no behavior change, no `!`):**
```ts
export async function requireAuth(req: Request, opts: { type: 'user' }): Promise<UserContext>;
export async function requireAuth(req: Request, opts: { type: 'internal' | 'webhook' }): Promise<null>;
export async function requireAuth(req: Request, opts: { type: AuthType }): Promise<UserContext | null>;
export async function requireAuth(req: Request, opts: { type: AuthType }): Promise<UserContext | null> {
  /* body unchanged */
}
```
The third overload preserves today's behavior for any caller passing a widened
`AuthType`. **Verified: there are no dynamic call sites** (`requireAuth(req, { type: someVar })`
finds nothing), so ordering is safe — literal `'user'` matches overload 1.

This makes the type system encode the exact distinction that caused the incident: an
`'internal'` caller now sees `null` and cannot silently read `.tier` off it.

**Constraint:** the body of `requireAuth` / `requireUserAuth` / `requireInternalAuth` must
NOT change. This is a signature-only fix. Do not "improve" internal auth to return a user
context — that is a behavioral change and out of scope.

### C. The hand-rolled Supabase mimics (same root cause as 260717-0fo)

~12 errors of the form `TS2322/TS2345: Type 'SupabaseClient<any, "public", ...>' is not
assignable to type 'SupabaseClientLike' / 'SupaLike'`, in `analyze-career`,
`analyze-skills-gap`, `compare-jobs`, `chat-agent`, `check-merit-alerts`,
`interview-prep-analyze`, `lifecycle-archive-writer`, `process-career-analysis-job`,
`submit-*`, `_shared/document-persistence.ts:37`.

This is the identical defect 260717-0fo already solved for the extract module: hand-rolled
structural mimics of the Supabase client cannot be made honest (PostgREST builders are
self-recursive AND heavily generic → assigning a real `SupabaseClient` to any chainable
mimic yields `TS2589`). Apply the same proven remedy: alias the REAL `SupabaseClient` type
(`import type { SupabaseClient } from "npm:@supabase/supabase-js@2"` — the repo convention;
`esm.sh` count is 0). See `extract-analysis-structure/types.ts` for the precedent and the
recorded trade-off.

Prefer ONE shared declaration over per-file copies. Judgement call left to you: if a
`_shared/` home is natural, use it; do not create a sprawl of near-identical type files.
