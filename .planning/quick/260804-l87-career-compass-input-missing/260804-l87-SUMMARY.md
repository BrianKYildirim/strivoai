# Summary — Career Compass `INPUT_MISSING` on a fresh Free account

## Exact production error

`POST /functions/v1/analyze-career` → **500** (twice: 9557ms, 4810ms).
Underlying body from `analyze-career/index.ts:1876`:

```json
{"error":"Unable to extract text from your resume.",
 "details":{"resumeExtracted":false,"linkedinExtracted":false,
            "reason":"<extraction reason>","hadResumeOcrImages":false}}
```

`process-career-analysis-job/index.ts:15` maps 400 → `INPUT_MISSING`; the job row
recorded `failure_code=INPUT_MISSING`, `failure_stage=generating`, `refunded=true`.

## Root cause

A broken telemetry endpoint cascaded into permanent loss of the user's resume text.

`begin-feature-run` answers **503 `feature_run_unavailable`** on 100% of Production calls
— `createFeatureRun` fails and returns `{ok:false}`. Proof: prod `feature_runs` and
`costing_subjects` hold **0 rows, ever**.

> **CORRECTION (2026-08-05).** This section originally named a missing
> `STRIVO_RUNTIME_ENV` secret as the cause of the 503. **That was wrong.** The secret was
> set in Production on 2026-08-04 and the 503 persisted. `getRuntimeEnvironment()` is read
> at `feature-run-telemetry.ts:280`, *after* `createCostingSubject` at :254 — and
> `costing_subjects` has 0 rows for all time, so the failure occurs at or before :258,
> before the env var is ever read. The true cause of the 503 is still unknown and is
> tracked as a SEPARATE launch blocker. It never affected the Career Compass diagnosis or
> fix: what mattered was only that the token could not be minted.

Callers degrade silently (`catch { featureRunToken = undefined }`) — telemetry is
meant to be best-effort. But `ocr-pdf` HARD-REQUIRES that token
(`ocr-pdf/index.ts:343-353`) and returned **400 `invalid_feature_run_token`**.
`persistAcceptedPdfjsResumeText` only `console.warn`ed, so `resumes.extracted_text`
was never written.

Because backend raw-byte PDF parsing is an intentional no-op
(`_shared/pdf-parser.ts` pins `pdfjsText:null`, `images:[]`,
`claude_ocr_blocked_by_policy`), and `CareerCompass.tsx` only produced
`resumeTextContent` when a NEW file was uploaded, a saved-resume run had **zero**
sources of resume text and failed closed.

Regression window confirmed in production:

| day | resumes created | with `extracted_text` |
|---|---|---|
| ≤ 2026-07-30 | 6, 1, 4, 1, 2 | all |
| 2026-08-02 | 1 | 1 |
| 2026-08-03 | 3 | **0** |
| 2026-08-04 | 1 | **0** |

## Why Resume Analysis and LinkedIn Grader passed

Resume Analysis receives the browser-extracted text INLINE in the same session
(`Onboarding.tsx:508` → `analyze-resume`). LinkedIn Grader never reads resume text.
Career Compass is the only feature that must read resume text in a LATER session
from persisted state.

## Migration / schema drift — RULED OUT

- Deployed `parse_professional_goal` body is the new sentence-aware version
  (`v_sentences`, `v_seniority`, `v_company`, `v_direction`, `c_place_stopwords`).

  keys, `goal_readiness_score=43`.
- `rg professional_goal supabase/functions` matches ONLY generated `database.types.ts`
  — no edge function reads it.

There is no code↔Production goal drift, and the goal change is not involved.

## Changes

1. `src/lib/document-extraction.ts` — when the `ocr-pdf` persistence call fails,
   `persistAcceptedResumeTextDirect` writes the accepted text straight to `resumes`,
   touching only the five sanctioned client-write columns. Returns null on failure so
   the caller keeps its previous behavior.
2. `src/pages/CareerCompass.tsx` — reads `id` + `extracted_text` with the saved resume;
   on submit without a new upload uses the durable text, else re-extracts from the
   stored file with the same browser parser (threading `resumeId`, so the row heals
   permanently). Returns `""` when unrecoverable — never fabricates text.
