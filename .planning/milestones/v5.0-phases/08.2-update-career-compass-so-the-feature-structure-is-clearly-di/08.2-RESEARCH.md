## Summary

This phase is a pure in-repo restructure with no new external dependencies. The work spans two layers that must stay in sync: the Supabase Edge Function `supabase/functions/analyze-career/index.ts` (+ its shared helpers `_shared/career-prompts.ts`, `_shared/career-validation.ts`, `_shared/result-merger.ts`) which generates and shapes the AI output, and the React page `src/pages/CareerCompass.tsx` (+ `src/components/career-compass/*`) which renders it.

The most important finding — not stated in CONTEXT.md and easy to miss during planning — is that **there are FOUR separate places in the backend that independently define the Career Compass prompt/JSON-skeleton**, not one. `resumeImprovements` (to be removed) and the new `whyMatch`/`mainBarriers`/`actionsNeeded` fields (to be added) potentially need touching in all four:
1. `_shared/career-prompts.ts` — `_buildProJsonSkeleton()` (shared by Pro AND Elite tiers via `loadPromptVariant('career', tier, ...)`), plus `PRO_BREVITY`/`ELITE_BREVITY` copy blocks and doc comments. **This is the live path** used by `executeCareerParallelCalls()` (the `'base'` call), which is what actually runs in the current architecture (parallel 3-call/2-call merge).
2. `analyze-career/index.ts` inline prompt at ~L1645-1701 — explicitly commented `// === Legacy path (unchanged — MIG-05) ===` at L1352, but still reachable code (runs when there's no cache hit / not the newer prior-analyses-sourced free path / not multi-role). CONTEXT.md's own line-number references (`~L1694`, `~L1699`) point at THIS legacy block specifically, confirming it must be updated too, despite being labeled "legacy."
3. `buildFreePriorAnalysesPrompt()` in `career-prompts.ts` — the free-tier-from-prior-analyses single-call path. Already omits `resumeImprovements` and never includes `skillGaps`/`roleReadinessBreakdown` beyond `{overallScore, targetRole}` — **no change needed** here, it's already free-tier-correct.
4. `handleMultiRoleComparison()` at `index.ts` L690-754 — a wholly separate, hand-written system/user prompt that produces the `multiRoleReadiness` array (used when a user compares 2+ roles). This currently does NOT collect `whyMatch`/`mainBarriers`/`actionsNeeded` and does not touch `resumeImprovements`. Because `ReadinessTab` renders `multiRoleReadiness` entries with the same `RoleReadinessBreakdown`-shaped UI as the single-role case, the Career Comparison feature will look inconsistent (missing the 3 new fields) in multi-role-compare mode unless this prompt is also extended — flagged as an **open question** for the planner to explicitly scope in or out.

On the frontend, the CONTEXT.md description of "Free: top cards" vs "Elite: tabs" is *mostly* already the shape of the code, but with one gap: today the "Readiness" and "Roadmap" tabs are **already visible to Free-tier users** in the always-shown 4-tab grid (`grid-cols-4`), with `BlurredLockCard` teaser/blur content shown internally for Free. Only Salary/Strategy are truly hidden-for-Free (wrapped in `{subscriptionTier === "elite" && (...)}` at both `TabsList` and `TabsContent`). CONTEXT.md's wording ("Elite items... live as tabs, **alongside the existing Salary/Strategy tabs**") strongly implies Career Comparison/12-Month Roadmap/Skills Gap should adopt the Salary/Strategy full-hide pattern (tab itself absent for Free), which is a **UX behavior change** from today's blur-teaser pattern for Readiness/Roadmap — not merely a rename. This should be an explicit decision in the plan, not an assumption.

**Primary recommendation:** Treat this as two synchronized workstreams — (1) backend: strip `resumeImprovements` and add `whyMatch`/`mainBarriers`/`actionsNeeded` across all 4 prompt-construction call sites + the Zod schema doc/passthrough + `result-merger.ts` tier-whitelists + the `anthropic.ts` mock fixture, and (2) frontend: rename/relabel `ReadinessTab`→Career Comparison and `RoadmapTab`→12-Month Roadmap (keeping their internal data contracts), build a new `SkillsGapTab` component reusing `SkillGap[]`, and restructure `CareerCompass.tsx`'s tab-visibility gating so Career Comparison/12-Month Roadmap/Skills Gap fully hide (not blur-tease) for Free tier, matching the Salary/Strategy pattern.

## Architecture Patterns

### Pattern 1: Permissive `.passthrough()` Zod schema (already in place, no structural change needed)
**What:** `careerCompassSchema` in `_shared/career-validation.ts` is `.object({}).passthrough()` with only `careerDNA` and `careerFields` as hard-required core fields; every other field (including `roleReadinessBreakdown`, `skillGaps`, and the new `whyMatch`/`mainBarriers`/`actionsNeeded`) passes through untouched.
**Why it matters for this phase:** Adding new fields to `RoleReadinessBreakdown` or removing `resumeImprovements` does NOT require a Zod schema code change — the schema's job is only to assert core-completeness, not enumerate every field. The doc comments at the top of the file (lines 13-46) DO reference `resumeImprovements`-adjacent concepts implicitly through the "elite extras stay non-fatal" framing, and mention `compensationIntelligence` specifically as the one documented optional field — but no line of actual schema code needs editing for the field additions/removals. Only the doc comment prose (and `careerSemanticCheck`, which already checks `roleReadinessBreakdown` presence as an object, not its sub-fields) may warrant a note update for accuracy.
**Source:** `supabase/functions/_shared/career-validation.ts` (read in full)

### Pattern 2: Per-tier prompt-variant registry (`tier-prompts.ts` / `loadPromptVariant`)
**What:** `_shared/career-prompts.ts` registers `{ free, pro, elite }` builder functions via `registerFeaturePrompts('career', CAREER_PROMPT_VARIANTS)`; `analyze-career/index.ts` calls `loadPromptVariant('career', resolvedTier, promptParams)` to get the live system prompt for the `'base'` parallel call.
**When to use:** This is the pattern to extend for adding the new Career Comparison fields to the Pro/Elite JSON skeleton (`_buildProJsonSkeleton`, reused by `_buildEliteJsonSkeleton`).
**Example:**
```typescript
// Source: supabase/functions/_shared/career-prompts.ts (read in full)
export const CAREER_PROMPT_VARIANTS: PromptVariantBuilder<CareerPromptParams> = {
  free: buildFreeCareerPrompt,
  pro: buildProCareerPrompt,
  elite: buildEliteCareerPrompt,
};
registerFeaturePrompts('career', CAREER_PROMPT_VARIANTS);
```

### Pattern 3: Server-side tier-shape whitelist as defense-in-depth (`applyCareerTierShape`)
**What:** `_shared/result-merger.ts` maintains `CAREER_FREE_ALLOWED_FIELDS` / `CAREER_PRO_ADDITIONS` / `CAREER_ELITE_ADDITIONS` sets and strips any field not in the tier's allowed set, independent of prompt compliance.
**When to use:** `resumeImprovements` currently lives in `CAREER_PRO_ADDITIONS` (result-merger.ts:110) — removing the field from the type system means also removing this list entry (dead entry otherwise, harmless but sloppy). No new entry is needed for `whyMatch`/`mainBarriers`/`actionsNeeded` since they are nested *inside* `roleReadinessBreakdown`, which is already a whitelisted top-level key at all tiers (`CAREER_CORE_FIELDS`/`CAREER_FREE_ALLOWED_FIELDS`) — the shaper does not prune sub-fields of `roleReadinessBreakdown` beyond the Free-tier "scorebox only" reduction (see Pitfall 1 below).
**Source:** `supabase/functions/_shared/result-merger.ts` lines 89-124

### Pattern 4: Elite-only teaser via `BlurredLockCard` vs. full-hide via conditional render
**What:** Two distinct existing patterns for gating Elite content from Free users:
  - **Teaser/blur pattern** (used today by `ReadinessTab`/`RoadmapTab`): the tab is always visible; when `subscriptionTier === 'free'`, real content is replaced with `<BlurredLockCard tier="pro" minHeight="...">` wrapping hardcoded placeholder copy.
  - **Full-hide pattern** (used today by Salary/Strategy): both the `TabsTrigger` in `TabsList` and the corresponding `TabsContent` are wrapped in `{subscriptionTier === "elite" && (...)}` — Free users never see the tab exists.
**When to use:** CONTEXT.md D-02's phrasing ("alongside the existing Salary/Strategy tabs") points toward the full-hide pattern for the new/renamed Elite tabs (Career Comparison, 12-Month Roadmap, Skills Gap Analysis). This is a **decision point for the plan**, not something to silently infer — flagged in Open Questions.
**Source:** `src/pages/CareerCompass.tsx` L1290-1404; `src/components/career-compass/ReadinessTab.tsx`, `RoadmapTab.tsx`

### Anti-Patterns to Avoid
- **Editing only one of the four prompt-construction call sites:** Because `resumeImprovements` and the target new fields appear in `career-prompts.ts`, the legacy inline block in `index.ts`, and (for the new fields) potentially `handleMultiRoleComparison`, a partial edit will leave some code paths (legacy/no-cache-hit requests, multi-role compare) emitting stale/removed fields or missing new ones. Grep for `resumeImprovements` across `supabase/functions/` before considering the removal done.
- **Assuming the Zod schema needs new field declarations:** Because `careerCompassSchema` is `.passthrough()`, do not add explicit `whyMatch`/`mainBarriers`/`actionsNeeded` Zod fields unless a stricter validation contract is intentionally being introduced — that would be a scope expansion beyond what CONTEXT.md asks for.
- **Renaming component files without checking test imports:** `ReadinessTab.test.tsx` and `RoadmapTab.test.tsx` exist under `src/components/career-compass/__tests__/` (per directory listing) and import the component by name — a file rename requires updating the test file's import path and the `index.ts` barrel export in the same change.

## Common Pitfalls

### Pitfall 1: Free-tier `roleReadinessBreakdown` is already reduced to `{overallScore, targetRole}` only
**What goes wrong:** A plan step might assume `whyMatch`/`mainBarriers`/`actionsNeeded` need explicit Free-tier stripping logic in `applyCareerTierShape`.
**Why it happens:** `CC-01: Free tier reduces roleReadinessBreakdown to scorebox only (no verdict)` (`career-shape.test.ts:124-131`) already asserts the Free-tier shaper reduces the ENTIRE `roleReadinessBreakdown` object down to exactly `['overallScore', 'targetRole']` keys, regardless of what other fields exist on it server-side. Any new field added to the object is automatically stripped for Free tier by the existing generic reduction logic — no new gating code is needed for the 3 new fields specifically.
**How to avoid:** Verify `applyCareerTierShape`'s Free-tier `roleReadinessBreakdown` handling in `result-merger.ts` (~L398 area) before writing new gating code; it likely already does the right thing.
**Warning signs:** A plan task titled something like "strip whyMatch for free tier in result-merger.ts" is probably unnecessary — confirm via the existing test first.

### Pitfall 2: The "legacy path" comment doesn't mean the code is unreachable
**What goes wrong:** A plan might skip editing `analyze-career/index.ts` L1645-1701 because it's labeled `// === Legacy path (unchanged — MIG-05) ===` at L1352, assuming it's dead code.
**Why it happens:** The comment signals "don't casually refactor this," not "this never executes." It's the fallback branch reached when the request isn't a cache hit, isn't the free single-call prior-analyses path, and isn't a multi-role comparison — i.e., ordinary first-time or cache-miss paid-tier analysis requests still run through it.
**How to avoid:** CONTEXT.md's own D-06 line references (`~L1694`, `~L1699`) point directly at this block — treat it as an equal-priority edit site alongside `career-prompts.ts`, not a legacy artifact to leave alone.
**Warning signs:** `grep -n resumeImprovements supabase/functions/analyze-career/index.ts` still returns matches after the edit.

### Pitfall 3: Multi-role comparison prompt is a 4th, easy-to-miss call site
**What goes wrong:** `handleMultiRoleComparison()` (L690-754) has its own hand-written prompt producing `multiRoleReadiness` entries with the SAME `RoleReadinessBreakdown` shape rendered by `ReadinessTab`/Career Comparison — but it currently has no `whyMatch`/`mainBarriers`/`actionsNeeded` fields and never will unless this prompt is separately extended.
**Why it happens:** It's structurally separate from `executeCareerParallelCalls`/`loadPromptVariant`, easy to overlook since it's a different code path entirely (triggered by `compareRoles` request param, not the standard analysis flow).
**How to avoid:** Explicitly decide in planning whether multi-role Career Comparison gets the 3 new fields too (for UI consistency) or intentionally stays without them (documented as an accepted gap, matching D-08's "defensive rendering" philosophy where missing fields are just omitted from render, not backfilled).
**Warning signs:** After the plan is implemented, comparing 2+ roles in Career Comparison shows different content shape than comparing a single role.

### Pitfall 4: Hardcoded test assertions on `resumeImprovements` will fail after removal
**What goes wrong:** `career-shape.test.ts` has two tests that directly assert `resumeImprovements` presence/absence (`CC-02: Free tier omits resumeImprovements` L143-147, `CC-03: Pro tier retains resumeImprovements` L178-183), and `tier-validation.test.ts:211` also references it in a list. These will fail (or, worse, silently pass vacuously) once the field is removed from the golden fixture and shaper logic.
**Why it happens:** Same class of risk flagged in the 08.1 LinkedIn Grader precedent — test fixtures hardcode old field/section shape.
**How to avoid:** Update/delete these specific test cases as part of the same plan wave that removes the field; do not leave them referencing a field that no longer exists anywhere in the type system.
**Warning signs:** `npm run test:edge` (deno test suite) fails after the backend change, or passes suspiciously (asserting `undefined === undefined` is trivially true even with no real production behavior change — check the assertion still tests something meaningful, e.g., replace with "field does not exist in golden fixture at all").

### Pitfall 5: `anthropic.ts` mock fixture (`fixtureKey: 'analyze_career'`) still contains `resumeImprovements`
**What goes wrong:** `_shared/anthropic.ts` L133-136 has a hardcoded test/offline-mode mock response including `resumeImprovements` — used when `DENO_TEST_SUPABASE_REMOTE=0` (offline deno test mode per `test:edge` script). If left unchanged, offline tests that consume this fixture will still see the old field, masking the removal in one test mode while it's correctly absent in the live-call path.
**How to avoid:** Update this fixture alongside the prompt changes — remove `resumeImprovements`, and consider adding `whyMatch`/`mainBarriers`/`actionsNeeded` to `roleReadinessBreakdown` in the fixture so offline tests can exercise the new fields' rendering.
**Source:** `supabase/functions/_shared/anthropic.ts` (read L100-160)

### Pitfall 6: `'pro'` tier checks are already legacy/dead in practice but still present in code
**What goes wrong:** `ReadinessTab.tsx`/`RoadmapTab.tsx` and others use `subscriptionTier === "pro" || subscriptionTier === "elite"` checks throughout. Per `pricing-config.ts`'s `normalizeActiveTier()`, `'pro'` is collapsed to `'elite'` before reaching these components in production, meaning the `=== "pro"` branch is very likely unreachable dead code today. This is a **pre-existing** inconsistency, not something this phase strictly needs to fix, but any new gating code added in this phase should use `subscriptionTier === "elite"` only (matching the Salary/Strategy pattern), not perpetuate the `pro||elite` pattern into new code.
**Source:** CONTEXT.md code_context section; confirmed by grep across `ReadinessTab.tsx`/`RoadmapTab.tsx`

## Open Questions

1. **Should Career Comparison / 12-Month Roadmap / Skills Gap Analysis fully hide from Free tier (matching Salary/Strategy), or keep today's blur-teaser pattern (matching current Readiness/Roadmap)?**
   - What we know: CONTEXT.md D-02 says these live "as tabs, alongside the existing Salary/Strategy tabs" — the strongest reading is full-hide, matching Salary/Strategy's `{subscriptionTier === "elite" && (...)}` wrapper at both `TabsList` and `TabsContent`.
   - What's unclear: Whether removing the existing `BlurredLockCard` teaser for Readiness/Roadmap is an intentional UX regression (losing an upsell touchpoint) or the correct interpretation of "structure clearly differentiated."
   - Recommendation: Plan should explicitly choose full-hide (consistent tab count: 2 free / 7 elite: Fields, Roles + Career Comparison, 12-Month Roadmap, Skills Gap, Salary, Strategy) and document this as an intentional behavior change, since it best matches the literal decision text and produces the clearest "structure clearly differentiated" outcome the phase title asks for.

2. **Does `handleMultiRoleComparison()` (multi-role compare) get the new `whyMatch`/`mainBarriers`/`actionsNeeded` fields, or stay as-is?**
   - What we know: It's a structurally separate prompt/call site from the single-role base call; today it produces `multiRoleReadiness` entries rendered by the same `ReadinessTab` UI.
   - What's unclear: Whether leaving it unextended is acceptable (D-08's "defensive rendering" principle would let the UI simply omit the 3 new fields/rows for multi-role entries, same as it does for legacy stored single-role data) or whether feature parity is expected.
   - Recommendation: Given D-08 already establishes the "omit if absent" pattern for legacy data, the same pattern can cleanly cover multi-role-compare without extending its prompt — recommend leaving `handleMultiRoleComparison` unchanged in this phase and documenting the gap, unless the user explicitly wants multi-role parity, which would require an additional prompt edit.
