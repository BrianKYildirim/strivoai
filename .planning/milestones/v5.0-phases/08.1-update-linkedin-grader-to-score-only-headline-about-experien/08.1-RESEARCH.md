## Summary

This phase restricts the LinkedIn Grader's section catalogue from 11 to 4 (Headline, About, Experience, Education). CONTEXT.md's file/line references were verified against current on-disk source and are **accurate** (schema.ts L45-57 catalogue, L156 `.length(11)`, L157-167 superRefine; prompts.ts full 11-section rubric; validation.ts count-agnostic; LinkedInGrader.tsx L90-113 shape gates, L183-193 reorder).

The architecture is well-factored for this change: `schema.ts` `LINKEDIN_SECTIONS` is the single source of truth. `normalizeFromSections`, `linkedInSemanticCheck`, `injectLinkedInRawScore` (validation.ts), the frontend card render, and `AnalysisComparisonModal` are all **section-count-agnostic** — they iterate over whatever sections exist. The real work is (1) `schema.ts` catalogue + `.length()`, (2) a substantial hand-written prompt rewrite in `prompts.ts`, and (3) **updating several Deno test fixtures that hardcode the 11-section shape and will break**.

**Primary recommendation:** Edit `LINKEDIN_SECTIONS` to the 4 retained rows and `.length(11)`→`.length(4)` in `schema.ts` (superRefine auto-follows `LINKEDIN_SECTION_NAMES`); rewrite the 4-section rubric in `prompts.ts`; then fix the three test files that assert on 11-section shape (`validation.test.ts`, `__tests__/distribution.test.ts`, `prompts.test.ts`). `validation.ts` and `LinkedInGrader.tsx` need no functional change — only an optional `isV5Grade` discriminator per D-05 and cosmetic comment updates.

## Shape-Gate Analysis (D-05 — the one genuinely subtle area)

**Current gates (`LinkedInGrader.tsx` L90-113):**
- `isV3Grade` (L90-93): `typeof rawScore === 'number' && Array.isArray(sectionBreakdown)` — loose; matches **any** grade shape.
- `isV4Grade` (L102-108): first section has `typeof applicable === 'boolean' && typeof evidence === 'string'`.
- `isRenderableGrade` (L111-113): `isV3Grade || isV4Grade`.

**Critical finding:** The **new 4-section shape is structurally identical to v4** — it carries the same per-section `applicable`/`evidence` fields, only with 4 rows and different names. Therefore a new grade **already satisfies both `isV3Grade` and `isV4Grade`**, so `isRenderableGrade` already returns `true` for it. The results render is **fully dynamic** (`orderedSections.map`, field-driven per card) and does not branch differently for v4 vs a hypothetical v5. **Rendering of new 4-section grades works with zero gate changes.**

**Implication for the planner:** A new `isV5Grade` discriminator is **not required for correct rendering** — it is belt-and-suspenders that matches the established pattern and D-05's explicit direction. If added, key it on `sectionBreakdown.length === 4` AND the 4 retained names, and be aware it will overlap `isV4Grade` (a 4-section grade matches both). This is an **Open Question** for the planner: implement the explicit `isV5Grade` per D-05's letter, or document that dynamic rendering already satisfies the D-05 invariant ("old shape renders old, new shape renders new") without it. Recommendation: add a minimal `isV5Grade` (length===4 + retained-name check) to honor D-05 explicitly and future-proof History filtering, but do **not** re-architect the render — it needs none.

**The L185-193 "Profile Completeness" reorder is already dead for v4/new grades.** It matches `s.name?.toLowerCase().includes('profile completeness')`, but the v4 catalogue section is named **"Completeness"** (schema.ts L52), and `'completeness'.includes('profile completeness')` is `false`. It only ever matches the legacy **v3** section literally named "Profile Completeness" (see the v3 fixture in `runtime-validation-convergence.test.ts` L127). So removing Completeness from the schema has **no effect** on this reorder — leave it untouched for legacy v3 correctness. (CONTEXT.md L183-193 slightly overstates this as "must stay correct for legacy v4"; in fact it never fired for v4.)

## Architecture Patterns (carried forward, DO NOT reopen)

- **Math-from-sections** (`normalizeFromSections`, schema.ts L79-89): total = `round(100 × Σ score_applicable / Σ max_applicable)`. Count-agnostic; with 4 sections at full max the denominator is 44 and still normalizes to 100. The 4 `baseMax` values (18/11/11/4) do **not** need to sum to 100 — the normalizer divides by whatever the applicable maxes sum to. **No formula change** (D-04).
- **Server owns the total** (`injectLinkedInRawScore` + `linkedInSemanticCheck`, validation.ts): the model never emits `rawScore`; the server injects it and `semanticCheck` enforces `rawScore === normalizeFromSections(...)`. Unchanged.
- **Strict no-masking parse** (`linkedInGradeSchema`, schema.ts): no `.default()`; a missing mandated section or per-section field is a hard `SCHEMA_VALIDATION_FAILED`. The `superRefine` (L157-167) iterates `LINKEDIN_SECTION_NAMES`, so narrowing the catalogue automatically narrows the required-set — one edit point. Keep `.length(11)`→`.length(4)` in lockstep so extra sections are also rejected.
- **Context-aware max (D-01 Phase 4)** still applies within the 4 retained sections (a legitimately non-applicable section drops from the denominator). Education is now the only `contextual`-class retained section (the other 3 are `core`). Preserve the `klass` field.
- **Determinism (D-02 Phase 4)**: evidence-anchored discrete point bands, no follow-up/prior-grade re-injection, stable cache key. `buildUserMessage` arity stays 2. Not reopened.

## Common Pitfalls

### Pitfall 1: Forgetting the test fixtures (biggest risk)
CONTEXT.md names 4 source files but **three Deno test files will fail** the moment the schema catalogue shrinks: `validation.test.ts` (hardcoded `LINKEDIN_SECTIONS.length === 11`, `sum === 100`, `slice(0,10)`, and a `Projects`-targeted D-01 test), `__tests__/distribution.test.ts` (score-map fixtures + `Projects` D-01 test), and `prompts.test.ts` (`SECTION_NAMES` list of 11). These are on the `verify:baseline` deno gate — a miss blocks deploy. **Verification step: run `deno task test:ci` (or `.\scripts\run-edge-tests.ps1`) for grade-linkedin after the change.**

### Pitfall 2: `baseMax` sum ≠ 100 tripping an assertion, not the math
The math is fine with sum 44, but `validation.test.ts` L237 asserts the sum is 100. Update the assertion to the new retained-max sum (44) or drop the "sums to 100" invariant — do **not** rescale the weights to force 100 (that would violate D-04's "keep today's relative weights").

### Pitfall 3: `.length(11)` and the catalogue drifting apart
If only `LINKEDIN_SECTIONS` is trimmed but `.length(11)` is left, every real 4-section response fails parse (exactly the 04-GAP-01 class of bug that made the grader non-functional once before — see `runtime-validation-convergence.test.ts` preamble). Change both together.

### Pitfall 4: `D-02` prompt hygiene — topFixes/keyStrengths must not name removed sections
After the prompt rewrite, ensure no residual instruction/example asks the model to reference Skills, Projects, etc. in `topFixes`/`keyStrengths`/`nextBestAction`. The current `OUTPUT SCHEMA` `topFixes` example (L185-194) is section-agnostic, but the `pointsGain` field ("Which section it lifts") must only reference the 4 retained sections now.

### Pitfall 5: Frontend/edge band-constant drift
`LINKEDIN_SCORE_BANDS` is duplicated in `LinkedInGrader.tsx` (L118-123) as a hand-copied mirror of `schema.ts` (D-03 keeps both unchanged). Do **not** touch either (D-03) — just be aware they must stay in sync if ever edited.
