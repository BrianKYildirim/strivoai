<threat_model>
Surface: `grade-linkedin` edge function schema + total-math (user-auth, usage-gated). No new auth surface.

Threats addressed by this plan:
- **Schema-validation bypass / score fabrication (ASVS V5 output validation):** A malicious or malformed model body could try to inject an inflated `overallScore`/`totalScore`/`rawScore`, extra sections, or out-of-range scores. Mitigation preserved and re-pointed: strict no-`.default()` zod parse, `.length(4)` + name-set superRefine (rejects missing/extra/renamed sections), per-section bounds clamp, server-injected `rawScore`, and `linkedInSemanticCheck` equality rejection (surfaced as `SCHEMA_VALIDATION_FAILED`, never silently overwritten). The plan must not relax any of these.
- **Stale-cache serving (integrity):** an un-bumped cache variant could return an old-rubric body through the new validator. Mitigation: bump `LINKEDIN_CACHE_VARIANT`.

No secrets touched; no logging of profile content added. Block-on-high: any change that removes a validator rejection is a blocker.
</threat_model>

<objective>
Re-point the LinkedIn grader scoring CORE from the Phase-08.1 weighted-and-normalized 4-section rubric (Experience 18 / Headline 11 / About 11 / Education 4, sum 44, total = round(100 × Σscore/Σmax)) to the 08.3 direct-100-point banded rubric (Headline 15 / About 15 / Experience 45 / Search Alignment, Skills & Credentials 25, sum = exactly 100, total = plain sum of applicable section scores). Update the schema catalogue, the total math, the cache identity, and every offline deno test that hardcodes the old shape so the `verify:baseline` deno gate stays green.

Purpose: This is the deterministic, offline-testable half of the rubric change (D-01/D-02/D-03/D-17/D-18/D-19/D-20/D-26/D-28). The prompt rewrite (Plan 02) and frontend (Plan 03) run in parallel and derive their section names/maxes from the same D-01 contract.

Output: New `LINKEDIN_SECTIONS`, plain-sum total math, bumped cache variant, and green deno suite proving four distinct bands.
</objective>
