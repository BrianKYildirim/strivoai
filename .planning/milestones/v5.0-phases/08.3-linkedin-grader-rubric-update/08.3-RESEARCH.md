## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01** — Exactly four scoring sections, always emitted, fixed order: Headline (15), About (15), Experience (45), Search Alignment, Skills & Credentials (25). Max total = 100.
- **D-02** — Model must NOT emit an overall score; the server calculates the total by summing applicable section scores. No second normalization or percentage conversion.
- **D-03** — No fifth section, no optional/reduced/tier-dependent section sets. Education is evaluated inside Search Alignment, Skills & Credentials.
- **D-04** — Every section uses explicit discrete scoring bands (bands verbatim in PHASE-SPEC.md). Quote/identify evidence, select the single best-matching band, emit an integer within that band, never average toward the middle, never inflate for encouragement, never punish for information absent from the PDF export that no section represents.
- **D-05** — Headline bands 0–2 / 3–5 / 6–9 / 10–12 / 13–15. No rigid formula; no assumption strong headlines must list technologies/value-prop/seniority. Penalize keyword stuffing, unsupported claims, contradictory targets, uncorroborated positioning.
- **D-06** — About bands 0–2 / 3–5 / 6–9 / 10–12 / 13–15. No multi-paragraph, no CTA, no quantified-achievement requirement when other strong evidence exists.
- **D-07** — Experience bands 0–8 / 9–17 / 18–27 / 28–36 / 37–45. Metrics are one form of evidence, not universal. No auto-penalty for students/early-career lacking promotions/tenure; non-technical experience supporting the target is not weak. Title-and-dates-only roles must not receive credit equal to evidence-rich roles.
- **D-08** — Search Alignment bands 0–5 / 6–10 / 11–15 / 16–20 / 21–25. Visible Top Skills count as substantive evidence. Credentials rewarded for relevance/alignment, not existence. No penalty for experienced candidates lacking education detail. Sidebar skills must not be assumed used in a specific job without experience-text support.
- **D-09** — Parsing/grading must preserve section boundaries and reading order in multi-column LinkedIn PDF exports; sidebar content (Top Skills, skill names, languages, certifications, contact info, honors, publications) must never be concatenated into Headline/Summary-About/Experience text.
- **D-10** — The grader must distinguish user-authored text, LinkedIn-generated headings, export metadata, sidebar fields, and main-column content.
- **D-11** — The export heading "Summary" maps internally to the About scoring section without becoming part of quoted About text; never recommend renaming Summary to About.
- **D-12** — Contact info, page numbers, mail links, LinkedIn URLs, PDF footer artifacts must not influence the score. Evidence quotations must reflect source text accurately and never reproduce column-order parsing errors.
- **D-13** — No invented evaluation date; no recalculating LinkedIn-generated durations against an assumed current month; no flagging a role inconsistent merely for an unexpected exported duration. Flag date issues only on explicit contradiction or impossibility. Treat "Present" as ongoing.
- **D-14** — All analysis/suggested copy grounded in the profile. Never invent technologies, frameworks, languages, team structures, collaborators, leadership, employers, projects, metrics, results, certifications, coursework, GPA, honors, goals, targets, dates, role status, user counts, or revenue/cost impact.
- **D-15** — When evidence is insufficient for a truthful paste-ready replacement, exclude that issue from topFixes and put a non-fabricated recommendation in the section's improvements array instead.
- **D-16** — Discoverability evaluated via observable alignment only. No claims about LinkedIn's private ranking algorithm, quantified search-visibility gains, contact-frequency promises, Boolean-search guarantees, or invented character thresholds. - **D-17** — All four sections always emitted. `applicable: false` only when explicit evidence establishes the entire combined section is legitimately irrelevant. Missing content ≠ inapplicable — missing-but-relevant sections stay applicable with an appropriately low score. Lack of formal education must not make Search Alignment inapplicable.
- **D-18** — Preserve existing top-level response structure unless new names/maximums require a schema migration. Raw JSON only. Response contains scoreJustification, nextBestAction, sectionBreakdown, topFixes, keyStrengths.
- **D-19** — sectionBreakdown = exactly four objects in required order; each has name, applicable, maxScore, score, evidence, strengths, weaknesses, improvements. Maximums 15/15/45/25; every score an integer in [0, max].
- **D-20** — Never emit overallScore, totalScore, rawScore, a fifth section, hidden bonus points, negative points, or scores above the maximum. Server total = sum of applicable section scores, no second normalization.
- **D-21** — Return ~4–7 top fixes when enough evidence-supported improvements exist, never more than 7, ranked by likely impact. Each fix has title, currentText, suggestedFix, whyItWorks, pointsGain, priority.

## Summary

Phase 08.3 changes the LinkedIn grader from the Phase-08.1 **4-section, weighted-and-normalized** rubric (Experience 18 / Headline 11 / About 11 / Education 4, `baseMax` sum 44, total = `round(100 × Σscore/Σmax)`) to a **4-section, direct-100-point banded** rubric (Headline 15 / About 15 / Experience 45 / Search Alignment, Skills & Credentials 25, sum = **exactly 100**, total = **plain sum of applicable section scores, no normalization**). The section catalogue lives in exactly one place — `schema.ts` `LINKEDIN_SECTIONS` — and almost every consumer (validator, injector, semantic check, frontend render, comparison modal) is already count- and name-agnostic. So the *structural* delta is small and well-contained; the *content* delta (the prompt rewrite and the PDF-integrity guardrails) is the real work.

The two hardest surfaces are: (1) a substantial hand-written **prompt rewrite** in `prompts.ts` that encodes the five verbatim band tables plus the PDF-evidence-integrity, date-handling, hallucination-prevention, and recruiter-search-claim guardrails; and (2) **multi-column PDF bleed** — the current client-side reconstruction (`pdf-text-layout.ts`) groups items into lines by Y then sorts left-to-right by X, with **no column detection**, so sidebar (Top Skills/languages/certs/contact) text at the same vertical band gets concatenated into main-column lines. That is exactly the D-09..D-12 failure mode.

The single most important architectural decision is the **total-calculation math (D-02/D-20/D-26)**: the literal spec is "sum of applicable section scores, no second normalization." Because the new maxes total 100, `normalizeFromSections` (rescale-to-100) and a plain sum are *identical when all four sections are applicable* and diverge only when a section is `applicable:false` (rare per D-17). Recommend replacing the normalize step with a plain applicable-score sum to honor the spec literally and remove any "legacy normalization" (D-25).

**Primary recommendation:** Edit `LINKEDIN_SECTIONS` (4 new rows: names + maxes 15/15/45/25, keep `.length(4)` + auto-following `superRefine`); replace `normalizeFromSections` with a plain applicable-sum (server owns total, model still forbidden to emit it); rewrite the `prompts.ts` rubric to the five verbatim band tables + guardrails; add PDF sidebar/main-column separation (prompt-level guardrails required, parser column-heuristic optional); rename/extend the frontend section-name constant + loading-step copy and add a new-shape detector alongside the legacy one (backward-compatible renderer, no data migration — D-27); bump `LINKEDIN_CACHE_VARIANT`; and fix the three deno test files that hardcode the 08.1 shape (they are on the `verify:baseline` gate).

## Architecture Patterns (carried forward — DO NOT reopen)

### Single source of truth: `LINKEDIN_SECTIONS`
`schema.ts` L56-61 defines the catalogue; `LINKEDIN_SECTION_NAMES` (L64) derives from it; the `sectionBreakdown` `superRefine` (L161-172) iterates `LINKEDIN_SECTION_NAMES` to require each name exactly once. **Editing the catalogue automatically re-points the required-name set.** Keep `.length(4)` (L160) in lockstep so extra sections are also rejected.

### Server owns the total (math-from-sections)
- The prompt forbids the model from emitting any overall total (`prompts.ts` L104-106, L150).
- `injectLinkedInRawScore` (`validation.ts` L79-89) clamps each section score to `[0, maxScore]` and sets `parsed.rawScore` server-side **before** validation.
- `linkedInSemanticCheck` (`validation.ts` L21-41) recomputes the total and rejects if `rawScore !== <computed>` (surfaced as `SCHEMA_VALIDATION_FAILED`, never silently overwritten).
- `validateLinkedInModelResponse` (`validation.ts` L102-119) is the ONE validation path used by every runtime branch (lifecycle + legacy/merit-dormant fallbacks in `index.ts`).

### Strict no-masking parse
`linkedInGradeSchema` (`schema.ts` L148-175) has no `.default()` on any required field — a missing section or per-section field is a hard parse failure. The only mutation is the bounds-only `.transform` clamp on `score` (L132-137), mirrored by `injectLinkedInRawScore`.

### Determinism (Phase-4 D-02, unchanged)
Discrete evidence-anchored point bands (anti-central-tendency), zero numeric calibration anchors, no follow-up / prior-grade re-injection in `buildUserMessage` (`prompts.ts` L175-188, arity 2), stable cache key from `profileContent` hash + URL only. **Do not reopen determinism design** — only the band values/section names/max total change.

### Frontend dynamic render (name/count-agnostic)
`LinkedInGrader.tsx` renders sections via `orderedSections.map` using per-section `score / maxScore` (L1069-1071), never a hardcoded denominator. The overall ring uses `result.rawScore / 100` (L954). Score-category color/label use `scoreBandLabel(result.rawScore)` on the 0-100 total (L985). **Rendering four differently-named/maxed sections already works** — the required frontend edits are constants, labels, loading-step copy, and the shape detector, not the render loop.

## PDF Parsing & Evidence Integrity (D-09..D-12) — the highest-risk area

### Current path (client-side, then server OCR fallback)
1. `LinkedInGrader.tsx` L469 calls `extractDocumentFromPdf` (`document-extraction.ts`).
2. `document-extraction.ts` L172 calls `extractPDFText` (`extract-pdf-text.ts`) → Web Worker (`pdf-extractor.worker.ts`) → `reconstructPdfPageText` / `reconstructPdfDocumentText` (`pdf-text-layout.ts`). Main-thread fallback uses the same reconstruction (L79-89).
3. If pdfjs text fails a quality bar (`assessBrowserExtractionQuality`, L417-444; linkedin thresholds minWords 80 / minChars 420, L150-153), it renders pages to images and calls the **`ocr-pdf`** edge function (L202-235). OCR returns its own text with **no layout reconstruction** guarantee.
4. The chosen text becomes `profileContent`, sent to `grade-linkedin` (L516-517).

### The bleed mechanism (root cause)
`pdf-text-layout.ts` `reconstructPdfPageText` (L28-47): groups items into **lines by Y coordinate** (`groupIntoLines`, tolerance ~median-height×0.55, L77-94), then within each line **sorts items left-to-right by X** (`renderLine` L96-121) and joins with gap-based spacing. **There is no column detection.** In a multi-column LinkedIn export, a sidebar item (Top Skills / language / cert) and a main-column item sharing the same vertical band collapse into ONE line, sidebar-first (lower X). That is precisely the D-09/D-12 "column-order parsing error" — e.g. `Python About  Led a team of…`.

Note: LinkedIn's own "Save to PDF" is often single-column, but many exports (and the sidebar sections: Contact, Top Skills, Languages, Certifications, Honors) are genuinely two-column, so the risk is real and profile-dependent.

## Total-Calculation Math (D-02 / D-20 / D-26) — the key decision

`normalizeFromSections` (`schema.ts` L83-93) currently returns `round(100 × Σscore_applicable / Σmax_applicable)`. Under the **new** maxes (sum 100):
- **When all four sections applicable** (the D-17 norm): `Σmax = 100`, so `round(100 × Σscore / 100) = Σscore`. Normalize and plain-sum are **identical**.
- **When a section is `applicable:false`** (rare, D-17): normalize *rescales to 100* (drops the section's max from the denominator); plain-sum *does not* (total is just the remaining scores, out of a ceiling <100). These diverge.

D-20/D-26 are explicit: "sum of applicable section scores, no second normalization … no second percentage conversion since maximums already total 100." **Recommendation:** replace the normalize body with a plain applicable-score sum (keep the function name or introduce `sumApplicableScores` and update `validation.ts` call sites). This (a) honors the literal spec, (b) removes the "legacy normalization" D-25 tells us to audit out, and (c) is behavior-preserving for the common all-applicable case. Document the `applicable:false` semantic (a legitimately-inapplicable section lowers the achievable ceiling rather than rescaling) so the frontend's "/ 100" display remains meaningful.

## Legacy Saved Results (D-27)

Old saved grades in `linkedin_grades.grading_data` (and `analysis_results.raw_response`) come in three shapes the frontend already gates: `isV3Grade` (loose), `isV4Grade` (11-section Phase-4), `isV5Grade` (08.1 four: Headline/About/Experience/Education, maxes 11/11/18/4, total via normalize). The 08.3 grade is a **fourth shape** (new names, maxes 15/15/45/25, direct-sum total).

- **Rendering already works** for any shape: `orderedSections.map` + `score/maxScore` + `rawScore/100` are name/max-agnostic. A stored old grade keeps its own maxes and renders correctly.
- **Do NOT recompute** a legacy record's total under the new rubric (its stored `overall_score`/`rawScore` reflects the rubric it was graded under).
- **Recommended (smallest reliable, D-27):** a **backward-compatible renderer** — add a new-shape detector (e.g. `isV6Grade` keyed on the new name set) to `isRenderableGrade`, keep all prior detectors, **no data migration, no backfill**. This mirrors the established 08.1 no-backfill pattern and the `MEMORY.md` note that mixed shapes coexist.
- The legacy "Profile Completeness" render-time reorder (`LinkedInGrader.tsx` ~L219-226) is already an inert no-op for 08.1 grades and stays inert for 08.3 — leave it for legacy v3.

| Problem | Don't build | Use | Why |
|---------|-------------|-----|-----|
| The 0-100 total | New weighting/percentage engine | A plain sum of applicable section scores injected server-side (`injectLinkedInRawScore`) + enforced by `linkedInSemanticCheck` | Maxes already total 100; D-26 forbids a second conversion |
| Required-section validation | New count constant / new checker | Edit `LINKEDIN_SECTIONS`; `.length(4)` + `superRefine` (derived from `LINKEDIN_SECTION_NAMES`) auto-follow | One source of truth |

## Common Pitfalls

### Pitfall 1: `.length(4)` / catalogue / prompt drift → total grader outage
If the schema catalogue, `.length(4)`, and the prompt's emitted section set fall out of sync, **every** real response fails parse (`SCHEMA_VALIDATION_FAILED`) — this exact class (04-GAP-01) once made the grader non-functional. Change `LINKEDIN_SECTIONS`, the prompt's section list, and the OUTPUT SCHEMA example together; keep `.length(4)`.

### Pitfall 2: Deno test fixtures on the `verify:baseline` gate (biggest miss risk)
`validation.test.ts` (`baseMax sum === 44`), `distribution.test.ts` (Education-keyed score maps + `/44` totals), and `prompts.test.ts` (`SECTION_NAMES` includes `Education`) will fail the moment the catalogue changes. These are on the **hard `verify:baseline` deno gate** that blocks `deploy.ps1` before `supabase link`. Run `.\scripts\run-edge-tests.ps1` (or `npm run test:edge`) after the change.

### Pitfall 3: maxTokens truncation under a larger prompt/output
LinkedIn caps are elite/pro **9000**, free **5000** (`getMaxOutput('linkedinGrader')`; `.planning/maxtoken-tuning/TRACKER.md`). On 2026-07-09 a 7000 cap silently truncated a sparse elite profile → `SCHEMA_VALIDATION_FAILED`; the fix bumped to 9000 **and** hard-capped topFixes at 7. The 08.3 rubric asks for evidence quotes across four (now richer) sections + 4-7 topFixes — output size may grow. Keep the topFixes ≤7 cap (D-21), and if post-rewrite responses approach the cap, right-size upward via the central `maxTokensOutput` table (guarded by `pricing-config.snapshot.ts` + `sc12-snapshot.test.ts` — update in lockstep). Input `linkedinInputCharCap` (index.ts L702-705) is unaffected.

### Pitfall 4: Stale cache serving old-rubric bodies
`LINKEDIN_CACHE_VARIANT` (index.ts L79) is part of the cache identity. If not bumped, a repeat profile could return a cached **old-rubric** grade (old names/maxes) through the new validator. Bump it (this also matches the "invalidate on rubric change" precedent at L76-79).

### Pitfall 5: Frontend "legacy normalization" audit (D-25)
D-25 requires confirming no leftover normalization in the UI. Grep confirms the current UI already uses `score/maxScore` and `rawScore/100` directly — no `/44` or reweighting. The audit is mostly *confirming absence* + updating the Education-referencing constant, comments, and loading steps. Do not introduce a new normalization.

### Pitfall 6: Prompt band format tripping `prompts.test.ts` anchor checks
`prompts.test.ts` L66-75 asserts the prompt does NOT contain old numeric anchors (`(0-20 points)` etc.). The new band tables use ranges like `0–2` / `37–45`. Ensure those assertions target the specific old-anchor format and update any that would false-positive on legitimate new band ranges.

### Pitfall 7: "Summary" → About label leakage (D-11)
The prompt must instruct the model to map the export heading "Summary" to the About section internally and NOT quote the literal "Summary" label as About evidence, and to NEVER recommend renaming Summary to About. This is a prompt-only guardrail.
