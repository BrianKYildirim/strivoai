**08.3 change (D-01/D-03):** replace the 4 rows with `Headline` 15 / `About` 15 / `Experience` 45 / `Search Alignment, Skills & Credentials` 25, in that fixed emitted order (D-01). Per Open Question 3, likely all four `core` (SA must stay applicable without education, D-17). `LINKEDIN_SECTION_NAMES` and the `superRefine` auto-follow — do NOT hand-edit the required-name set.

**Total-math pattern to REPLACE** (L83-93) — currently normalize-to-100:
```typescript
export function normalizeFromSections(sections: readonly NormalizableSection[]): number {
  let earned = 0;
  let available = 0;
  for (const s of sections) {
    if (!s.applicable) continue;
    earned += s.score;
    available += s.maxScore;
  }
  if (available <= 0) return 0;
  return Math.round((100 * earned) / available);
}
```
**08.3 change (D-02/D-20/D-26):** replace the body with a **plain sum of applicable section scores** (`earned` only; drop the `available`/`round(100 × …)` rescale). Keep the function name so `validation.ts` call sites are untouched, OR introduce `sumApplicableScores` and update the two call sites. Behavior-identical when all four applicable; diverges only on `applicable:false` (ceiling reduction, not rescale).

**Strict-parse pattern to KEEP verbatim** (L121-175) — `.length(4)` + name-set `superRefine` + no-`.default()` + bounds-only `.transform` clamp:
```typescript
sectionBreakdown: z

  .length(4)
  .superRefine((secs, ctx) => {
    const present = new Set(secs.map((s) => s.name));
    for (const name of LINKEDIN_SECTION_NAMES) {
      if (!present.has(name)) {
        ctx.addIssue({ code: z.ZodIssueCode.custom, message: `missing required section: ${name}`, path: [] });
      }
    }
  }),
```
**Keep `LINKEDIN_SCORE_BANDS` (L97-102) + `scoreBand` (L107-112) unchanged** — still valid on a direct 0-100 total. Update only the header comments (L1-47) that describe "sum to 44 / normalize".

**Pitfall (from RESEARCH #1):** the catalogue, `.length(4)`, and the prompt's emitted section set must change together or every real response fails parse (`SCHEMA_VALIDATION_FAILED`) — total grader outage (class 04-GAP-01).

### `grade-linkedin/validation.ts` (service/validation seam, transform)

**Analog:** itself — `injectLinkedInRawScore` (L79-89) + `linkedInSemanticCheck` (L21-41).

**Server-inject pattern to KEEP (re-point only if math fn renamed)** (L79-89):
```typescript
export function injectLinkedInRawScore(parsed: Record<string, unknown>): void {
  const sections = parsed.sectionBreakdown;
  if (!Array.isArray(sections)) return;
  const normalizable = (sections as Record<string, unknown>[]).map((s) => {
    const maxScore = Number(s.maxScore);
    const score = Math.min(maxScore, Math.max(0, Number(s.score)));
    s.score = score;
    return { applicable: s.applicable === true, maxScore, score };
  });
  parsed.rawScore = normalizeFromSections(normalizable);
}
```

**Semantic-equality enforcement to KEEP** (L27-40) — recompute + reject-on-mismatch, never overwrite:
```typescript
const expected = normalizeFromSections(
  value.sectionBreakdown.map((s) => ({
    applicable: s.applicable === true, maxScore: Number(s.maxScore), score: Number(s.score),
  })),
);
if (value.rawScore !== expected) {
  return { ok: false, detail: `rawScore(${value.rawScore}) != normalizeFromSections(${expected})` };
}
```
**08.3 change:** ONLY the import (L3) and these two call sites if `normalizeFromSections` is renamed to `sumApplicableScores`. Logic (clamp + inject + enforce equality) stays identical. `validateLinkedInModelResponse` (L102-119) — the single validation source of truth — is fully shape-agnostic; leave it. Update stale "11-section" doc comments (L5, L16) cosmetically.

```typescript
const NEW_LINKEDIN_SECTION_NAMES = ['Headline', 'About', 'Experience', 'Education'] as const;
function isV5Grade(grading_data: unknown): boolean {
  if (!grading_data || typeof grading_data !== 'object') return false;
  const g = grading_data as Record<string, unknown>;
  if (!Array.isArray(g.sectionBreakdown) || g.sectionBreakdown.length !== 4) return false;
  const names = new Set((g.sectionBreakdown as Array<Record<string, unknown>>).map((s) => s?.name));
  const namesMatch =
    names.size === NEW_LINKEDIN_SECTION_NAMES.length &&
    NEW_LINKEDIN_SECTION_NAMES.every((n) => names.has(n));
  if (!namesMatch) return false;
  const first = g.sectionBreakdown[0] as Record<string, unknown> | undefined;
  return !!first && typeof first.applicable === 'boolean' && typeof first.evidence === 'string';
}

function isRenderableGrade(grading_data: unknown): boolean {
  return isV3Grade(grading_data) || isV4Grade(grading_data) || isV5Grade(grading_data);
}
```

## Shared Patterns

### Single source of truth (section catalogue)
**Source:** `grade-linkedin/schema.ts` `LINKEDIN_SECTIONS` (L56-64)
**Apply to:** schema validator, prompt OUTPUT SCHEMA, all test fixtures, frontend detector
**Rule:** Edit the catalogue once; `LINKEDIN_SECTION_NAMES` + `.length(4)` + `superRefine` derive automatically. The prompt's emitted section list and the OUTPUT SCHEMA JSON example are the ONLY places that must be hand-kept-in-lockstep — change them in the SAME commit or the grader goes down (Pitfall 1 / 04-GAP-01).

### Server-owns-the-total (math-from-sections)
**Source:** `validation.ts` `injectLinkedInRawScore` (L79-89) + `linkedInSemanticCheck` (L21-41)
**Apply to:** every runtime branch (single path `validateLinkedInModelResponse`)
**Rule:** Model is prompt-forbidden to emit any total; server clamps each score to `[0, max]`, injects `rawScore` BEFORE validation, then semanticCheck recomputes and REJECTS on mismatch (never silently overwrites). 08.3 swaps the inner math (normalize → plain sum) only.

### Strict no-masking parse
**Source:** `schema.ts` `linkedInGradeSchema` (L148-175)
**Apply to:** the model response shape
**Rule:** No `.default()` on any required field — a missing section/field is a hard parse failure. Only mutation is the bounds-only `.transform` clamp on `score`, mirrored by `injectLinkedInRawScore`.

### Backward-compatible legacy renderer (no migration)
**Source:** `LinkedInGrader.tsx` `isV3/isV4/isV5Grade` + `isRenderableGrade` (L92-146)
**Apply to:** the fourth (08.3) grade shape
**Rule:** Add a new detector, keep all prior ones, no backfill. `orderedSections.map` + `score/maxScore` + `rawScore/100` render any stored shape at its own maxes. `linkedin_grades.grading_data jsonb` + `overall_score CHECK 0..100` absorb the new shape with NO DB migration (new total is a direct 0-100 sum).
