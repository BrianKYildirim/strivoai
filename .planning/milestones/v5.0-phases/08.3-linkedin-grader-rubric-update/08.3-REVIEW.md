# Phase 08.3: Code Review Report

**Reviewed:** 2026-07-10
**Depth:** standard
**Files Reviewed:** 11

## Summary

Reviewed the direct-100 rubric replacement end to end: section catalogue + plain-sum
math (`schema.ts`), inject/semantic-check seam (`validation.ts`), the rewritten banded
prompt (`prompts.ts`), cache-variant bump and runtime paths (`index.ts`), the frontend
v6 detector + legacy-shape rendering (`LinkedInGrader.tsx`), and all in-scope tests.

The core design is sound and well-tested: the catalogue sums to 100, `normalizeFromSections`
is a correct plain sum with `applicable:false` ceiling reduction (no rescale), the score
bands are contiguous with boundary tests at 49/50, 69/70, 84/85, the cache variant was
bumped so pre-08.3 cached bodies can never pass the new validator (key-level isolation via
`variant`), the frontend keeps all four legacy detectors and never recomputes a stored
total, and the removed `GraduationCap` import matches the removed Education step.

One material validation gap survives, however: the schema trusts the **model-declared
`maxScore`** rather than pinning it to the catalogue, so the entire "maximum possible
score is 100" contract is enforceable only by prompt compliance, not by the validation
layer whose job is to catch prompt non-compliance.

## Critical Issues

### CR-01: Model-declared `maxScore` is trusted for both the clamp ceiling and the total

**Status:** FIXED — commit `251d755e` (`fix(08.3): CR-01 pin LinkedIn section maxScore to the catalogue`). `LINKEDIN_MAX_BY_NAME` added; superRefine rejects any off-catalogue maxScore; schema `.transform` and `injectLinkedInRawScore` clamp against the catalogue ceiling (before rawScore injection), with tests for inflated/negative maxScore and end-to-end rejection.

**File:** `supabase/functions/grade-linkedin/schema.ts:102` (also `validation.ts:82-83`)

**Issue:** `sectionSchema` validates `maxScore: z.number()` with no constraint tying it
to the catalogue (`LINKEDIN_SECTIONS` baseMax 15/15/45/25). Both the schema `.transform`
clamp (`Math.min(s.maxScore, ...)`) and `injectLinkedInRawScore` clamp each score to the
**model-emitted** `maxScore`, then sum. `linkedInSemanticCheck` passes by construction
because `rawScore` was injected from the same numbers. Consequences if the model deviates
from the OUTPUT SCHEMA example (the exact failure class this validation layer exists to
catch):

- `{ name: "Headline", maxScore: 45, score: 40 }` → validation passes, an **inflated
  total ≤ 100 is silently persisted** to `linkedin_grades.overall_score` and rendered
  as a legitimate grade (incorrect data reaching DB and UI).
- Maxes summing > 100 → `rawScore` > 100 → the `linkedin_score_range CHECK (overall_score
  BETWEEN 0 AND 100)` constraint (`20251129_create_all_tables.sql:56`) rejects the insert
  → user-facing 500 *after* a paid model call, and the frontend ring/band math
  (`rawScore/100`, `scoreBandLabel`) breaks for the returned body.
- A negative `maxScore` makes the clamp produce a **negative score**
  (`Math.min(-5, Math.max(0, n)) === -5`), deflating the total.

The spec is explicit: "Required maximums: Headline 15 / About 15 / Experience 45 /
Search Alignment... 25", "The maximum possible score is 100", "Do not emit... Scores
above the declared maximum". None of this is enforced server-side; only the prompt asks
for it. Every rubric consumer (band mapping, DB CHECK, frontend `/100` denominator,
pointsGain "remaining points" logic) assumes catalogue maxes.

**Fix:** Pin `maxScore` (and thereby the score ceiling) to the catalogue in the existing
`superRefine`, e.g.:

```typescript
.superRefine((secs, ctx) => {
  const maxByName = new Map(LINKEDIN_SECTIONS.map((s) => [s.name, s.baseMax]));
  secs.forEach((s, i) => {
    const expected = maxByName.get(s.name);
    if (expected !== undefined && s.maxScore !== expected) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        message: `section ${s.name}: maxScore ${s.maxScore} != required ${expected}`,
        path: [i, 'maxScore'],
      });
    }
  });
  // ...existing missing-name loop
})
```

Mirror the same pinning in `injectLinkedInRawScore` (clamp to
`Math.min(Number(s.maxScore), catalogueMax)` or simply the catalogue max) so the injected
total matches what a pinned schema accepts. A wrong `maxScore` then fails validation and
takes the existing retry-once path instead of persisting a corrupted grade.

## Warnings

### WR-01: Integer scores are a spec requirement but not schema-enforced

**Status:** FIXED — commit `d3f82108` (`fix(08.3): WR-01 round LinkedIn section scores to integers`). Rounding chosen over hard-fail (avoids failing a whole paid response on a 0.5); `Math.round` applied identically in the schema `.transform` and `injectLinkedInRawScore` so semanticCheck holds by construction; tests cover parse rounding and end-to-end integer scores.

**File:** `supabase/functions/grade-linkedin/schema.ts:103`

**Issue:** Spec: "Every score must be an integer between zero and the section's maximum."
`score: z.number()` accepts `12.5`; the clamp does not round. `normalizeFromSections`
rounds only the **sum**, so a fractional per-section score is persisted in
`grading_data` and rendered fractional in the UI (`score/maxScore` cards), while
`rawScore` stays integer. `validation.test.ts:101-106` even codifies fractional inputs
as accepted. Low likelihood, but it is a one-token schema fix and the phase's own
contract.

**Fix:** `score: z.number().int()` (hard-fail, consistent with the no-masking posture)
or round inside the existing clamp transform:
`score: Math.round(Math.min(s.maxScore, Math.max(0, s.score)))` — mirrored in
`injectLinkedInRawScore` so the injected total matches.

### WR-02: Required section order is not validated

**Status:** FIXED — commit `1414341b` (`fix(08.3): WR-02 enforce LinkedIn catalogue section order positionally`). The superRefine now compares index-by-index against `LINKEDIN_SECTIONS` (subsuming the missing-name loop and hosting the CR-01 maxScore pin); tests cover out-of-order, duplicated, and correctly ordered sections.

**File:** `supabase/functions/grade-linkedin/schema.ts:135-149`

**Issue:** Spec: "The grader must always return exactly these four sections, **in this
order**" / "exactly four objects, in the required order." The `superRefine` checks
name-set membership only. A response emitting `[About, Headline, Experience, SA]`
passes validation, is stored, and renders out of order — the frontend renders
`sectionBreakdown` in stored order (the `orderedSections` reorder only targets the v4
"Profile Completeness" card). Cosmetic impact, but the contract says order and the
check is one line away.

**Fix:** In the same `superRefine`, compare positionally:

```typescript
LINKEDIN_SECTION_NAMES.forEach((name, i) => {
  if (secs[i]?.name !== name) {
    ctx.addIssue({ code: z.ZodIssueCode.custom, message: `section ${i} must be ${name}`, path: [i, 'name'] });
  }
});
```

(This also subsumes the existing missing-name loop.)

## Info

### IN-01: Stale/misleading comment about rawScore provenance

**File:** `supabase/functions/grade-linkedin/schema.ts:126-128`
**Issue:** "The model reports rawScore, but semanticCheck ... enforces" — the prompt
forbids the model from emitting `rawScore`; `injectLinkedInRawScore` sets it before
parse. A future reader could conclude the model is expected to emit it.
**Fix:** Reword to "rawScore is injected server-side by `injectLinkedInRawScore` before
parse; semanticCheck enforces it equals the recomputed sum."

### IN-02: Band fallback maps out-of-range totals to "Exceptional"

**File:** `supabase/functions/grade-linkedin/schema.ts:84-89`; `src/pages/LinkedInGrader.tsx:183-188`
**Issue:** Any total > 100 (reachable only via CR-01) or a fractional total in a band gap
falls through the loop and returns `'exceptional'` / `'Exceptional'` — the flattering
direction. Harmless once CR-01 is fixed and totals stay integer 0-100.
**Fix:** Clamp the input (`Math.max(0, Math.min(100, Math.round(total)))`) before band
lookup, or fall back to `'weak'` for totals above range too.

### IN-03: Off-gate eval weak fixture can fail on a legitimate in-band total

**File:** `supabase/functions/grade-linkedin/__tests__/fixtures/injection/promptfooconfig.linkedin-distribution.yaml:71-73, 84-88`
**Issue:** The weak fixture expects band [0,49] AND `total < 48 || total > 58`. A model
total of 48 or 49 is a correct weak-band grade but fails the anti-cluster clause —
built-in flakiness at the band edge for this costed, operator-run eval.
**Fix:** Either narrow the weak fixture's `expectedBandMax` to 47, or exempt totals that
are in-band from the cluster check (`outsideCluster = inBand && band==='weak' ? true : ...`).

### IN-04: Legacy-shape test omits v3 and v4 shapes

**File:** `src/pages/__tests__/LinkedInGrader.legacy-shape.test.tsx`
**Issue:** The suite proves 08.3 (v6) and 08.1 (v5) grades render, but the v3
(feedback[]/status, no applicable/evidence) and v4 11-section shapes — both still live
in `linkedin_grades.grading_data` per the file's own comment — have no render regression
coverage. `isV3Grade`/`isV4Grade` code paths through the results view are unproven.
**Fix:** Add two fixtures: one v3 grade (sections with `feedback[]`, no `evidence`) and
one 11-section v4 grade, asserting card count and stored total.

### IN-05: Pre-existing index.ts inconsistencies (not introduced by 08.3)

**File:** `supabase/functions/grade-linkedin/index.ts:769, 810, 927`
**Issue:** (a) The MERIT-off legacy path hardcodes `'claude-haiku-4-5-20251001'` while
the merit path uses `getModel(tier, 'linkedin')` — a model bump via tier-config will
silently miss the legacy path. (b) The catch-all handler returns raw `error.message`
to the client in the 500 body (e.g. `AI gateway error: 500`; internal detail leakage,
counter to the repo's "401 with no detail leakage" pattern). Both predate this phase;
noted for a follow-up, no 08.3 action required.
**Fix (follow-up):** Use `getModel(resolvedTier, 'linkedin')` in the legacy path;
return a generic message and keep `error.message` in the structured log only.
