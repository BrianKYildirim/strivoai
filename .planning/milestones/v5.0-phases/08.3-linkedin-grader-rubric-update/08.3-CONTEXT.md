# Phase 08.3: LinkedIn Grader Rubric Update - Context

**Gathered:** 2026-07-09
**Status:** Ready for planning
**Source:** PRD Express Path (.planning/phases/08.3-linkedin-grader-rubric-update/08.3-PHASE-SPEC.md)

<domain>
## Phase Boundary

Redesign the LinkedIn Profile Grader to a 4-section, 100-point banded rubric that scores real profile quality with evidence grounding. Covers: the grading prompt/rubric, PDF-parsing evidence integrity, hallucination prevention in fixes, server-owned total calculation, output schema/validators, frontend section rendering and labels, and safe handling of previously saved grader results. All other LinkedIn grading functionality remains operational unless a change is explicitly required by this phase.

</domain>

<decisions>
## Implementation Decisions

### Section structure (locked)
- D-01: Exactly four scoring sections, always emitted, in fixed order: Headline (15), About (15), Experience (45), Search Alignment, Skills & Credentials (25). Max total = 100.
- D-02: The model must NOT emit an overall score; the server calculates the total by summing applicable section scores. No second normalization or percentage conversion.
- D-03: No fifth section, no optional/reduced/tier-dependent section sets. Education is evaluated inside Search Alignment, Skills & Credentials.

### Banded rubric (locked)
- D-04: Every section uses explicit discrete scoring bands (bands verbatim in PHASE-SPEC.md). The model must quote/identify evidence, select the single best-matching band, emit an integer score within that band, never average toward a middle score, never inflate for encouragement, and never punish for information absent from the PDF export that no section represents.
- D-05: Headline bands 0–2 / 3–5 / 6–9 / 10–12 / 13–15. No rigid headline formula; no assumption that strong headlines must list technologies, a value proposition, or seniority. Penalize keyword stuffing, unsupported claims, contradictory targets, uncorroborated positioning.
- D-06: About bands 0–2 / 3–5 / 6–9 / 10–12 / 13–15. No multi-paragraph requirement, no call-to-action requirement, no quantified-achievement requirement when other strong evidence exists.
- D-07: Experience bands 0–8 / 9–17 / 18–27 / 28–36 / 37–45. Metrics are one form of evidence, not a universal requirement (accepted evidence list in spec). No automatic penalty for students/early-career lacking promotions or tenure; non-technical experience supporting the stated target is not weak. Title-and-dates-only roles must not receive credit equal to evidence-rich roles.
- D-08: Search Alignment bands 0–5 / 6–10 / 11–15 / 16–20 / 21–25. Visible Top Skills count as substantive evidence. Credentials rewarded for relevance/alignment, not existence. No penalty for experienced candidates lacking education detail. Sidebar skills must not be assumed used in a specific job without experience-text support.

### PDF parsing and evidence integrity (locked)
- D-09: Parsing/grading must preserve section boundaries and reading order in multi-column LinkedIn PDF exports; sidebar content (Top Skills, skill names, languages, certifications, contact info, honors, publications) must never be concatenated into Headline/Summary-About/Experience text.
- D-10: The grader must distinguish user-authored text, LinkedIn-generated headings, export metadata, sidebar fields, and main-column content.
- D-11: The export heading "Summary" maps internally to the About scoring section without becoming part of quoted About text; never recommend renaming Summary to About.
- D-12: Contact info, page numbers, mail links, LinkedIn URLs, and PDF footer artifacts must not influence the score. Evidence quotations must reflect source text accurately and never reproduce column-order parsing errors.

### Date and duration handling (locked)
- D-13: No invented evaluation date; no recalculating LinkedIn-generated durations against an assumed current month; no flagging a role inconsistent merely for an unexpected exported duration. Flag date issues only on explicit contradiction or impossibility. Treat "Present" as ongoing.

### Hallucination prevention (locked)
- D-14: All analysis and suggested copy must be grounded in the profile. Never invent technologies, frameworks, languages, team structures, collaborators, leadership, employers, projects, metrics, results, certifications, coursework, GPA, honors, goals, targets, dates, role status, user counts, or revenue/cost impact.
- D-15: When evidence is insufficient for a truthful paste-ready replacement, exclude that issue from topFixes and put a non-fabricated recommendation in the relevant section's improvements array instead.

### Recruiter-search claims (locked)
- D-16: Discoverability evaluated via observable alignment (titles, skills, terminology, experience, credentials, target direction). No claims about LinkedIn's private ranking algorithm, quantified search-visibility gains, contact-frequency promises, Boolean-search guarantees, or invented character thresholds. Impact descriptions remain qualitative and defensible.

### Applicability behavior (locked)
- D-17: All four sections always emitted. `applicable: false` only when explicit evidence establishes the entire combined section is legitimately irrelevant. Missing content ≠ inapplicable — missing-but-relevant sections stay applicable with an appropriately low score. Lack of formal education must not make Search Alignment inapplicable.

### Output contract (locked)
- D-18: Preserve existing top-level response structure unless the new section names/maximums require a schema migration. Raw JSON only. Response contains scoreJustification, nextBestAction, sectionBreakdown, topFixes, keyStrengths.
- D-19: sectionBreakdown = exactly four objects in required order; each has name, applicable, maxScore, score, evidence, strengths, weaknesses, improvements. Maximums 15/15/45/25; every score an integer in [0, max].
- D-20: Never emit overallScore, totalScore, rawScore, a fifth section, hidden bonus points, negative points, or scores above the maximum. Server total = sum of applicable section scores, no second normalization.

### Top fixes (locked)
- D-21: Return ~4–7 top fixes when enough evidence-supported improvements exist, never more than 7, ranked by likely impact. Each fix has title, currentText, suggestedFix, whyItWorks, pointsGain, priority.
- D-22: currentText quotes the profile accurately or states "Missing". suggestedFix is immediately usable, placeholder-free, and uses only profile-supported facts.
- D-23: pointsGain names the affected section, states a realistic gain, never exceeds the section's remaining points, avoids guaranteed total-score claims, and avoids points for rubric-unrelated changes. No overlapping-point claims across fixes.

### Score explanations (locked)
- D-24: Overall justification identifies the most important evidence without unsupported platform-behavior claims. Strengths/weaknesses are profile-specific. Avoid repetitive commentary across scoreJustification, nextBestAction, section weaknesses, section improvements, and topFixes — prioritize actionable insight.

### Frontend and server integration (locked)
- D-25: Update all server-side constants, schema validators, frontend labels, progress calculations, and section-rendering logic depending on old maximums or section names. UI renders exactly four sections. Audit score-category labels against the direct 100-point scale so no legacy normalization remains.
- D-26: Server owns total-score calculation; no second percentage conversion since maximums already total 100.
- D-27: Existing saved grader results handled safely — add a migration, versioned response contract, or backward-compatible renderer if old results use previous names/maximums.
- D-28: Final implementation must produce differentiated scores across sparse, average, strong, and exceptional profiles while remaining deterministic, evidence-based, career-stage-aware, and resistant to PDF parsing errors and fabricated recommendations.

### Claude's Discretion
- Exact prompt wording/structure implementing the banded rubric (spec bands are the contract; phrasing is discretionary).
- Where PDF sidebar/main-column separation is implemented (parser heuristics vs. prompt-level guardrails vs. both), so long as D-09..D-12 hold.
- Choice among migration / versioned contract / backward-compatible renderer for saved legacy results (D-27) — pick the smallest reliable option consistent with repo patterns.
- Test strategy details (fixtures, promptfoo adversarial configs, deno/vitest coverage), following TESTING-STRATEGY.md and existing grade-linkedin test layout.
- Whether schema changes require touching shared validators vs. function-local ones.

</decisions>

<specifics>
## Specific Ideas

- Section maximums and order are exact: Headline 15, About 15, Experience 45, Search Alignment, Skills & Credentials 25 — totals 100 by construction.
- Example anti-hallucination rules from the spec: do not add Node.js because a profile mentions React; do not add "in collaboration with the backend team" without source support; do not fabricate coursework, clubs, leadership, or honors.
- Example date rule: never recommend changing an eight-month duration to three months unless the evaluation date and employment dates make that certain.
- Acceptable qualitative impact phrasings (spec examples): "Makes the candidate's target role easier to identify", "Improves consistency between the headline and experience", "Gives recruiters stronger evidence of a listed skill".
