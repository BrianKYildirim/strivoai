# Phase 15.1: Code Review Report

**Reviewed:** 2026-04-17T12:00:00Z
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

Three files were reviewed covering the Phase 15.1 Free tier token budget optimization. The changes introduce a single-call analysis path for Free tier users (replacing the 3-call parallel fan-out), a consolidated Free prompt builder, and OCR model alignment to `tier-config.ts`.

The core logic is well-structured: boot-time invariant checks enforce token budget constraints (GATE-09, D-18), a quality floor check guards against degenerate model output, and the Free single-call path cleanly bypasses the merge pipeline. The `ocr-pdf` changes are clean and low-risk.

Three warnings were identified: dead-code fallback branches that check for `resolvedTier === 'free'` in locations only reachable after the Free path has already returned, an unused `MERIT_COST` constant, and unchecked Supabase `.update()` results in the Free path that silently swallow database errors. Three informational items cover unused computed variables, a minor pattern around `executiveSummary` type handling, and significant code duplication across the four code paths (merit-streaming, merit-non-streaming, legacy-streaming, legacy-non-streaming).

## Warnings

### WR-01: Dead code -- Free tier fallback branches unreachable

**File:** `supabase/functions/analyze-resume/index.ts:502-503`
**Issue:** In the merit-streaming path, the Free single-call path returns early at line 439-478. The subsequent fallback block at line 501-507 checks `resolvedTier === 'free'` to select `buildFreeConsolidatedPrompt`, but this branch is unreachable because Free users have already returned. The same pattern repeats at lines 660-665 (merit non-streaming fallback), lines 908-913 (legacy streaming fallback), and lines 1196-1201 (legacy non-streaming fallback). While not a bug (the code is functionally correct -- it just never executes for Free), it creates confusion about which code path actually handles Free tier fallbacks, and it will silently become stale if the fallback logic changes.
**Fix:** Remove the `resolvedTier === 'free'` ternary branches from all four fallback blocks. Since Free always takes the early-return single-call path, the fallback code only runs for Pro/Elite tiers. Simplify to:
```typescript
const fallbackPrompt = buildFallbackPrompt(promptParams);
const fallbackMaxTokens = TIER_MAX_TOKENS[resolvedTier];
```

### WR-02: Unused `MERIT_COST` constant

**File:** `supabase/functions/analyze-resume/index.ts:63`
**Issue:** `MERIT_COST` is declared (`{ free: 3, pro: 2, elite: 3 }`) but never referenced anywhere in the file. The `withMerits` call at line 376 passes `'resume_analysis'` as the action key -- the merit cost is presumably looked up from the database or the merit-gateway module, not from this constant. This dead constant will mislead developers into thinking per-tier merit costs are controlled here.
**Fix:** Remove the constant if merit costs are managed elsewhere (e.g., in the merit-gateway or database). If it is intended for future use, add a `// TODO(Phase N): wire into withMerits` comment explaining when it will be consumed.

### WR-03: Unchecked Supabase `.update()` in Free single-call paths

**File:** `supabase/functions/analyze-resume/index.ts:456-460`
**Issue:** In the merit-streaming Free path, the `supabase.from('resumes').update(...)` call's result is not checked for errors. If the DB update fails (e.g., invalid `resumeId`, RLS policy rejection, transient DB error), the user receives a `complete` event with the analysis result, but the result is never persisted -- they will see a blank page on revisit. The same unchecked pattern appears at lines 623-627 (merit non-streaming Free), 856-860 (legacy streaming Free), and 1126-1130 (legacy non-streaming Free). In contrast, the non-Free paths at lines 1268-1279 and 1357-1369 properly check `updateError` and throw.
**Fix:** Check the update result and log errors consistently:
```typescript
const { error: updateError } = await supabase.from('resumes').update({
  overall_score: freeResult.overallScore,
  grading_data: freeResult,
  analyzed_at: new Date().toISOString(),
}).eq('id', resumeId);
if (updateError) {
  log.error('db-update-failed', { resumeId, error: updateError.message });
}
```

## Info

### IN-01: Unused `resumeHash` computed variable

**File:** `supabase/functions/analyze-resume/index.ts:386-389` and `supabase/functions/analyze-resume/index.ts:782-785`
**Issue:** `resumeHash` is computed using a character-level hash but never used anywhere downstream. This wastes CPU cycles on every request (iterates all characters of the resume text, which can be up to 100KB).
**Fix:** Remove both `resumeHash` computations. If content deduplication is planned for a future phase, add a TODO comment instead of computing the value.

### IN-02: `executiveSummary` type inconsistency in Free streaming chunks

**File:** `supabase/functions/analyze-resume/index.ts:449-453`
**Issue:** The Free streaming path types `summaryText` as `string | object` and then checks `typeof summaryText === 'object'`, which always passes when the AI returns the expected `executiveSummary` object shape (`{keyStrengths, keyGaps, highImpactFix}`). Meanwhile, the fallback at line `''` ensures the fallback value is a string. The `JSON.stringify({summary: ...})` call handles both types correctly so this is not a bug, but the type annotation `as string | object` is imprecise -- it should be `as Record<string, unknown> | string` to match the actual prompt schema.
**Fix:** No functional change needed. Consider adding a type alias for the executive summary shape to improve readability.

### IN-03: Significant code duplication across four code paths

**File:** `supabase/functions/analyze-resume/index.ts` (entire file)
**Issue:** The file contains four near-identical code paths for Free tier analysis: merit-streaming (lines 439-478), merit-non-streaming (lines 614-636), legacy-streaming (lines 840-875), and legacy-non-streaming (lines 1117-1152). Each duplicates the same pattern: call `executeFreeAnalysis`, update DB, optionally record usage, return/send result. The Pro/Elite parallel path has a similar 4-way duplication. While this is understandable given the dual merit/legacy and streaming/non-streaming axes, the file is now 1426 lines and future changes (e.g., adding a new field to the Free response) require updating 4+ locations.
**Fix:** No immediate action required -- the duplication is structural (merit vs legacy, streaming vs non-streaming) and factoring it out would require careful design. Consider extracting a `handleFreeResult(freeResult, {resumeId, supabase, usageUserId?, sendEvent?})` helper in a future phase to consolidate the DB update + usage recording + email logic.
