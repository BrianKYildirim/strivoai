# Phase 17.1: Career Compass Results UI Design Specification - Research

**Researched:** 2026-04-18
**Domain:** React component decomposition, tier-conditional UI rendering, SVG data visualization
**Confidence:** HIGH

## Summary

Phase 17.1 decomposes the existing 2036-line `CareerCompass.tsx` monolith into focused subcomponents within `src/components/career-compass/`. The main page becomes an orchestrator (~200 lines) handling state, data fetching, and routing between the input form and a results view composed of dedicated subcomponents. All visual elements already exist in the monolith -- this is a structural refactor with targeted UI-SPEC adjustments, not a visual redesign.

The decomposition is straightforward because the existing code has clear visual sections that map directly to component boundaries: Career DNA card, Best-Fit Role Families, Surprise Fits, six tab panels (Fields, Roles, Readiness, Roadmap, Salary, Strategy), a role comparison dialog, and a cached results banner. Each section reads from a single `analysis` object and a `subscriptionTier` string, making prop interfaces predictable. The primary technical complexity is in the Readiness tab, which handles three distinct rendering states (comparing, multi-role results, single-role results) and contains duplicated score ring + strengths/gaps + skill table rendering that should be extracted into shared sub-components.

**Primary recommendation:** Decompose by visual section. Each component receives `analysis: AnalysisResult` (or a subset) and `subscriptionTier: string` as props. Keep state management in the orchestrator page. Use a barrel `index.ts` to re-export all components.

### Pattern 3: Score Ring with Accent Color

**What:** Career Compass uses `#FF6B6B` (primary accent) for the score ring stroke, not semantic colors.
**When to use:** The ScoreRing component within Career Compass readiness display.
**Example:**
```typescript
// Source: Existing CareerCompass.tsx lines 1345-1372 and UI-SPEC lines 207-212
// src/components/career-compass/ScoreRing.tsx
interface ScoreRingProps {
  score: number;
  size?: number;  // default 160
  radius?: number; // default 70
  strokeWidth?: number; // default 12
}

export function ScoreRing({ score, size = 160, radius = 70, strokeWidth = 12 }: ScoreRingProps) {
  const half = size / 2;
  const circumference = 2 * Math.PI * radius;
  return (
    <div className="relative" style={{ width: size, height: size }}>
      <svg className="w-full h-full transform -rotate-90">
        <circle cx={half} cy={half} r={radius} fill="none"
          stroke="currentColor" strokeWidth={strokeWidth}
          className="text-muted/20" />
        <circle cx={half} cy={half} r={radius} fill="none"
          stroke="#FF6B6B" strokeWidth={strokeWidth}
          strokeDasharray={`${(score / 100) * circumference} ${circumference}`}
          strokeLinecap="round" />
      </svg>
      <div className="absolute inset-0 flex items-center justify-center flex-col">
        <span className="text-4xl font-bold" style={{ color: "#FF6B6B" }}>
          {score}%
        </span>
        <span className="text-xs text-muted-foreground">Ready</span>
      </div>
    </div>
  );
}
```

### Anti-Patterns to Avoid

- **Prop explosion on orchestrator:** Don't pass 20+ individual values to each component. Instead, pass the `analysis` object (or relevant slice) and let the component destructure what it needs. Keeps the orchestrator clean.
- **Duplicating the score ring:** The current monolith has the SVG score ring duplicated twice (lines 1345-1372 for multi-role and lines 1492-1519 for single-role). Extract into a shared `ScoreRing` component and render it once in both paths.
- **Moving state into subcomponents prematurely:** Role comparison state (`roleDialogOpen`, `selectedRoles`, `comparingRoles`, `activeRoleIndex`) should stay in the orchestrator because the dialog and the readiness tab both read/write it. If pushed into ReadinessTab, the orchestrator loses the ability to trigger comparison.
- **Creating a CareerCompassContext:** With only ~2 levels of nesting (page -> section component), React Context is unnecessary overhead. Props suffice and are more explicit.

## Common Pitfalls

### Pitfall 1: Breaking the Input Form During Decomposition
**What goes wrong:** Moving results rendering code inadvertently breaks the input form's state management or event handlers.
**Why it happens:** The orchestrator page contains both input and results rendering with shared state (loading, analysis, etc.).
**How to avoid:** Leave the input form section (lines 754-1001) in the orchestrator page as-is per D-03. Only extract the results section (lines 1002-2031). The input form code can optionally be extracted to a single `CareerCompassInput` component for cleanliness, but it is not redesigned.
**Warning signs:** File upload stops working, analyze button doesn't fire, progress indicators disappear.

### Pitfall 2: Losing Role Comparison State Flow
**What goes wrong:** Role comparison breaks because state is split across components without proper callback wiring.
**Why it happens:** The comparison flow involves: orchestrator state -> dialog component -> API call -> readiness tab render. Breaking this chain causes stale state.
**How to avoid:** Keep `roleDialogOpen`, `selectedRoles`, `comparingRoles`, `activeRoleIndex`, and `handleCompareRoles` in the orchestrator. Pass them as props to `ReadinessTab` and `RoleComparisonDialog`. The dialog calls back to the orchestrator's handler.
**Warning signs:** Dialog opens but compare button does nothing; comparison results don't appear; role tabs don't update.

### Pitfall 3: Duplicate Rendering of Score Ring
**What goes wrong:** The score ring SVG is copied into multiple components instead of extracted as a shared component.
**Why it happens:** The monolith has the identical SVG block at lines 1345-1372 (multi-role) and 1492-1519 (single-role). Copy-paste is tempting.
**How to avoid:** Create a single `ScoreRing` component and render it in both the multi-role and single-role paths of `ReadinessTab`.
**Warning signs:** Inconsistent score ring appearance between comparison and non-comparison views.

### Pitfall 4: Forgetting Tier Checks After Decomposition
**What goes wrong:** A subcomponent renders Pro/Elite content for Free users because the `subscriptionTier` check was lost during extraction.
**Why it happens:** Tier checks are scattered throughout the monolith as inline conditionals. When moving code blocks, it's easy to leave a tier check behind.
**How to avoid:** Each component that has tier-gated content should accept `subscriptionTier` as a required prop. The planner should verify every `subscriptionTier ===` check in the monolith maps to the correct subcomponent.
**Warning signs:** Free users see skill assessments, full roadmap phases, or Elite tabs.

### Pitfall 5: CSS Style Regression with Accent Color
**What goes wrong:** Colors appear wrong because some are hardcoded `#FF6B6B` and others use `text-primary` or `style={{ color: "#FF6B6B" }}`.
**Why it happens:** The existing code mixes CSS variables, inline styles, and Tailwind classes for the same accent color.
**How to avoid:** Follow the preserve + adjust approach (D-06). Keep existing inline styles exactly as they are. Only adjust if the UI-SPEC explicitly calls for a different value. The accent color `#FF6B6B` maps to `var(--primary)` in the design system.
**Warning signs:** Buttons or borders appear in wrong color or disappear entirely.
