## 1. System Classification

**System Type:** Extraction (structured JSON generation — single Anthropic call returning the Runtime §10 nine-section payload, strictly Zod-validated)

**Description:**
Interview Prep is a tier-gated AI coach that turns the authenticated user's most recently analyzed resume + a pasted job description + an expanded 9-field intake into a senior-recruiter-grade rehearsal package. Pro users receive 3 STAR flashcards (read-only); Elite users receive a 5–7 question interactive quiz scored per-answer against STAR (0–100 + per-beat 0–10) plus an end-of-quiz summary; Pro users also get one Elite-taste quiz per calendar month. Every session returns the same nine-section payload (Your Prep Readiness, Coach Verdict, Readiness Breakdown, Focus Areas, Quick Tips, Practice Questions, Prep Roadmap, Strengths & Watch-Outs, Coaching Advice + Biggest Score Mover). "Good" means: radically personalized to THIS resume + THIS JD (never generic), honestly scored (no inflation), every filled optional intake field (`role_title`, `company`, `background_context`) referenced in at least one output section, every STAR beat anchored in a concrete resume signal (company / project / number / tool) or explicitly flagged as missing, and the output copy-paste ready for live interview rehearsal. Backend runs two Supabase Edge Functions (`interview-prep-analyze` for generation, `interview-prep-evaluate` for Elite answer scoring), both calling `claude-haiku-4-5-20251001` synchronously via the existing shared Anthropic HTTP wrapper with Merit deduction / refund-on-5xx via Phase 13 `withMerits`.

**Critical Failure Modes:**
1. **Generic, non-grounded output** — the model ignores the auto-fetched resume and emits role-typical answers that could apply to any candidate, violating Runtime §5 (Resume-as-Source-of-Truth) and §11 (Radical Personalization). Blast radius: Pro/Elite users who paid 8 / 5 Merits feel the feature is "ChatGPT with extra steps" and churn.
2. **Silent drops of optional intake fields** — user fills `role_title`, `company`, or `background_context` and the model's reasoning never references them, violating Runtime §3 and §11 (Every Optional Field Matters). Blast radius: users stop trusting that the intake form "matters" and stop filling it, degrading all downstream quality.
3. **Score inflation** — the model returns a Ready-to-Practice (70–84) or Ready-to-Ship (85–100) band for a resume with weak JD alignment, violating Runtime §9 + §11 (Honest Scoring). Blast radius: users walk into real interviews falsely confident; reputational damage to Strivo as a career platform.
4. **Malformed or truncated JSON that silently degrades the payload** — one or more of the nine required §10 sections is missing/empty after parse + `repairTruncatedJSON`, but the function still returns 200 instead of 502 + refund. Blast radius: broken UI for the paying user + Merit deducted for garbage output.
5. **STAR scoring rubric drift on evaluate** — per-beat scoring (Situation / Task / Action / Result, 0–10 each) contradicts the overall 0–100 score (e.g., all beats ≥7 but overall = 45, or all beats ≤3 but overall = 80), violating Runtime §7 consistency. Blast radius: users cannot trust the feedback; STAR coaching loses its diagnostic value.
6. **Merit refund incorrect on non-5xx errors** — a 400/403/429 path (no resume / Free / cap-reached / Pro-monthly-used / answer-over-500) accidentally deducts Merits, or a 502 Anthropic-upstream path fails to refund. Blast radius: billing complaints + direct Merit economy corruption.
7. **Prompt injection via `job_description` or `background_context`** — an attacker-provided JD or background blob overrides the Global AI Principles / Runtime §11 rules, producing rogue output. Blast radius: compromised tier boundary (Pro sees Elite payload), offensive output, or PII leakage.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Career development / behavioral interview coaching — STAR-method rehearsal for job seekers preparing for structured behavioral, technical, mixed-panel, and executive (staff+) interviews at tech, finance, consulting, and product companies. The nearest professional peers are senior technical recruiters, career coaches certified by associations like the NCDA (National Career Development Association), and internal TA/interviewer-training functions at Amazon-style structured-interview shops.

**User Population:** Authenticated Strivo Pro and Elite subscribers who have already uploaded and analyzed at least one resume on the platform. Heterogeneous career stage: entry-level (new grads), mid-level (2–7 years), senior (7–12), and staff+ (executive/IC-leader) — the Phase 23 `difficulty` enum covers all four. Users invoke Interview Prep in the 24–72 hours before a scheduled interview (behavioral, technical, mixed-panel, or executive), copy-paste a JD they are interviewing against, and optionally supply `role_title`, `company`, and free-form `background_context`. Domain expertise: low to moderate — most users know the term "STAR" but have never been coached against it; Elite users are disproportionately senior ICs and mid-managers who expect feedback that respects their experience level rather than generic "tell a story about teamwork" prompts.

**Stakes Level:** **High.** This is not FDA-regulated healthcare or a legal advice system, but every flashcard and quiz-answer score is consumed as direct pre-interview preparation for a real hiring decision. A single believed-but-wrong piece of coaching (e.g., an inflated 88 readiness score on a weak JD-fit, a STAR rewrite that contradicts the candidate's actual resume, a "just pause and smile" platitude in place of a concrete fix) translates directly into a missed offer, delayed job search, lost income, and lost trust in Strivo as a paid career platform. The blast radius per bad output is one user's livelihood — small per event, but the feature runs at Pro/Elite scale and is priced as senior-recruiter-grade coaching, so the quality bar is the same bar a human interview coach charging $150–$300/session would be held to.

**Output Consequence:** Users walk into a scheduled interview having rehearsed the Pro flashcards verbatim or internalized the Elite per-answer STAR fixes as their mental model for the real interviewer's questions. When the AI recommends a rewrite ("replace 'led the migration' with 'cut p95 from 840 ms to 210 ms across 14 services over 6 weeks'"), users often paste that exact phrasing into their live answer. Downstream: (a) in the real interview they sound specific and quantified — offer likelihood up — or (b) they sound canned, mis-cite a number that is not on their resume, or deliver a Situation-padded answer that the interviewer flags as unstructured — offer likelihood down. There is no human-in-the-loop between Strivo's output and the user's live delivery; the output is trusted as-is.

### What Domain Experts Evaluate Against

**Dimension: Resume-anchored specificity ("could this answer belong to anyone else?")**
- Good: Every STAR Action or Result cites a concrete resume signal — a company name, project codename, metric, tool, team size, or date range that is verifiably present in the candidate's resume. The answer reads as if a senior recruiter who just skimmed the candidate's resume wrote it.
- Bad: Generic role-typical filler — "I collaborated cross-functionally with engineering and product," "I took ownership of the problem," "I communicated with stakeholders" — with no resume-sourced noun, number, or timestamp. Could be swapped into any other candidate's rehearsal package without edit.
- Stakes: Critical. This is the #1 thing a trained interviewer notices in the first 20 seconds of a behavioral answer.
- Source: Amazon STAR / Leadership Principles interviewer training (interviewers are assigned 1–3 LPs and "search for signals" of meet/raise/below bar on concrete behaviors); Ben Kuhn, "How I build and run behavioral interviews" (benkuhn.net) — vague generalities are the dominant failure mode; Indeed and MIT CAPD STAR guides all converge on specificity as the #1 criterion.

**Dimension: STAR structural completeness and proportion**
- Good: Situation + Task together are ≤30% of the answer, Action is ~60%, Result is ~10% and is quantified (percent, currency, time, headcount, or latency). Situation sets enough context for the interviewer in 1–2 sentences; the rest of the time is on what the candidate personally did.
- Bad: Situation-heavy (50%+ of the answer is backstory), Action collapsed into one sentence, Result missing or unquantified ("things got better," "the team was happy"). Or the inverse: Action without Situation/Task so the interviewer cannot evaluate judgment.
- Stakes: Critical for behavioral/mixed-panel/executive interviews; High for technical.
- Source: MIT CAPD STAR worksheet (explicit 20/10/60/10 allocation); Northwestern Career Advancement STAR guide; VA Wizard STAR reference; BigInterview "The STAR Interview Method."

**Dimension: First-person ownership and accountability**
- Good: STAR Action uses "I" — "I designed," "I negotiated," "I shipped." When the candidate genuinely was part of a team, "I" is used for the candidate's specific contribution and "we" is reserved for outcomes the group shared.
- Bad: "We" throughout the Action block, leaving the interviewer unable to attribute anything to this candidate; blame or deflection onto coworkers, managers, or external factors when the story is about failure or conflict.
- Stakes: Critical — Amazon Ownership LP, Meta "Drives Results," Google "Role-Related Knowledge" all grade this explicitly.
- Source: Indeed STAR guide (explicit "use I not we"); LeadershipIQ behavioral-interview research; BigInterview "Tell me about a time you failed."

**Dimension: Quantify-or-flag discipline (Runtime §11 "Quantify-or-Flag")**
- Good: Every Result either contains a number (percent change, dollars, users, latency, team size, duration) sourced from the resume, OR explicitly flags that the resume does not contain a quantified outcome and coaches the user to add one (`signal_missing=true` + a coach note "Your resume shows the Stripe migration but not the p95 delta — try to recover the number before the interview."). No unsourced numbers.
- Bad: Fabricated numbers not present in the resume ("led to a 40% increase in engagement" when the resume says only "improved engagement"), or hollow qualitative claims ("significantly improved," "huge impact") with no number and no missing-signal flag.
- Stakes: Critical. Fabricated numbers are the single most common way AI interview-prep tools erode trust — candidates who repeat an AI-invented "40% lift" in a real interview get asked for detail and collapse.
- Source: Runtime §11 explicit principle; interviewing.io Amazon LP guide ("bar raisers probe on numbers"); Ben Kuhn (benkuhn.net) "interviewers push on the result until it breaks."

**Dimension: Honest scoring calibration (no inflation, no flattery)**
- Good: Readiness band reflects actual JD ↔ resume fit. "Ready to Ship" (85–100) is reserved for candidates whose resume shows ≥3 quantified bullets directly mapping to the JD's top 3 requirements. "Not Yet" (<55) is actually issued when appropriate; Coach Verdict and per-dimension scores agree within ±10 with the overall band. Warmth lives in the coaching voice ("here's the exact sentence that will close the gap"), not in the number.
- Bad: Score inflation to protect feelings — e.g., a 78 "Ready to Practice" band issued on a resume with zero JD-relevant bullets; per-beat STAR scores averaging 3/10 but overall pegged at 72/100; coaching copy that says "great answer, just a small tweak" on an answer the expert would grade as incomplete.
- Stakes: Critical. Inflated scores are the direct cause of the "walked in confidently and bombed" failure mode.
- Source: Runtime §9 + §11 explicitly name this; LeadershipIQ behavioral-interview research on scoring drift; Exponent mock-interview feedback literature on rater leniency bias; SHRM structured-interview guidance on scoring anchors.

**Dimension: Actionability of the fix ("what do I do differently tomorrow?")**
- Good: Every weakness comes with a concrete, copy-paste-ready rewrite or preparation step — a specific sentence to practice, a specific number to recover from old Slack logs, a specific framework to prep for the system-design portion. The fix is scoped (<20 words in the Pro coach note; <60 words in the Elite per-answer fix) and actionable before the interview.
- Bad: Advice that restates the problem ("work on being more specific"), vague directives ("use stronger examples"), or platitudes ("believe in yourself"). Anything that could be photocopied from a generic interview-prep ebook from 2012.
- Stakes: High. The difference between useful and useless coaching is whether the user knows what to practice after reading the feedback.
- Source: Gayle Laakmann McDowell, *Cracking the Coding Interview* (behavioral sections — "every weakness should have a specific rehearsal drill"); Victor Cheng, *Case Interview Secrets* ("diagnostic feedback must be immediately rehearsable"); Exponent and BigInterview coaching methodology.

**Dimension: Role/level calibration (entry vs. mid vs. senior vs. staff+)**
- Good: Coaching voice and example bar scales with the `difficulty` enum. Entry gets "explain the situation and what you learned"; staff+ gets "lead with the system-level tradeoff you owned and the org-wide outcome." Questions generated for a staff+ candidate explore ambiguity, scope, influence-without-authority, and org-design judgment — not "tell me about a time you worked on a team."
- Bad: One-size-fits-all coaching that grades a staff engineer's answer against an entry-level rubric (patronizing) or pushes an entry-level candidate to invent staff-scope stories they have not lived (sets them up to fail when probed).
- Stakes: High — especially at Elite tier, where senior IC/manager sessions are the bulk of volume.
- Source: Cracking the PM Interview (McDowell/Bavaro) on level calibration; Amazon's explicit `SDE-II/SDE-III/Principal` LP-weighting rubric difference; interviewing.io senior-engineer guides.

### Known Failure Modes in This Domain

1. **"ChatGPT with extra steps" genericity.** The model emits role-typical answers that could apply to any backend engineer, any PM, any analyst. Symptom: zero resume anchors, no company names, no numbers, no project codenames. Directly violates Runtime §5 and matches the dominant complaint in published reviews of AI interview tools (Medium's "I tried the 5 best AI interview assistants — honest take") — users cancel within 1–2 sessions.
2. **Confusing Situation with Action.** The STAR rewrite pads Situation with 4–5 sentences of backstory and compresses Action into "I stepped up and led the work." Interviewers trained on Amazon-style structured interviews explicitly dock this — MIT CAPD's proportion rule (S+T ≤30%, A ~60%) is the industry-standard scoring anchor.
3. **Fabricated metrics.** The model invents plausible-sounding numbers not present on the resume ("reduced churn 22%," "saved $1.4M annually") to make answers feel quantified. Candidate repeats the number in the interview, gets probed, and cannot defend it — the most trust-destroying failure for the user and for Strivo's reputation.
4. **Canned-phrasing coaching.** The model recommends rehearsed idioms ("I'm a collaborative problem-solver," "I thrive in ambiguity") that real interviewers immediately recognize as AI/coaching-tool output. Research (LeadershipIQ, finalroundai.com blog) lists canned phrasing as one of the top three recruiter rejection signals.
5. **Score inflation to protect feelings.** The model anchors readiness scores in the 72–82 band regardless of actual fit because low scores feel mean. Runtime §11 names this explicitly. The secondary symptom: per-beat scores (all 3/10) contradicting overall score (72/100). Users walk into the interview falsely confident.
6. **Level/scope mismatch.** Coaching for a staff engineer uses entry-level story templates ("tell me about a time you worked on a team project"), or coaching for a new grad pushes them to claim staff-level scope they have never had. Both are catastrophic — the first patronizes senior users who churn; the second sets junior users up for "that is not on your resume" rejection in the real interview.
7. **Optional-field silent drops.** User fills `company` and `background_context` ("interviewing at Stripe, pivoting from data eng to platform") and the output never references Stripe or the pivot narrative. Users stop filling the intake → downstream quality degrades → the whole feature drifts toward genericity (the failure mode feeds itself).
8. **Deflection/blame framing in failure stories.** For "tell me about a time you failed" questions, the model coaches candidates to blame external factors or teammates ("my manager didn't prioritize it," "the product team changed scope"). Every published behavioral-interview guide flags this as an auto-reject signal.
9. **Rubric drift between analyze and evaluate.** The analyze call returns a readiness score of 82 and Coach Verdict tone "you are close to interview-ready," then the evaluate call returns average per-answer STAR of 4/10 and overall 45/100. Two honest experts would not produce this gap; users experience it as gaslighting.

### Regulatory / Compliance Context

Career coaching is largely unregulated in the US at the federal level, and Interview Prep generates advice for the candidate — it does not screen candidates or make hiring decisions, so the EEOC AI-in-hiring enforcement surface (the 2023 EEOC AI Initiative, NYC Local Law 144 automated-employment-decision-tool audits, the ACLU v. HireVue-style cases) does **not** apply to this system's generation path. That said, three adjacent surfaces are directly relevant to the generation / evaluation contract of Phase 23:

1. **EEO / anti-discrimination sensitivity in how the AI characterizes the candidate.** Even though this is a coaching tool (not a screener), the output must not generate advice that infers or references protected-class characteristics (race, gender, age, national origin, disability, pregnancy, religion) from the resume — e.g., coaching a candidate to "downplay your time at a women-in-tech bootcamp" or "lead with your military background to stand out." Rubric: no coaching language that differentially advises based on inferred protected-class signals in the resume. Source: EEOC AI Initiative (2023 guidance), Brookings "Gender, race, and intersectional bias in AI resume screening."
2. **FTC guidance on AI-generated career claims.** The readiness score and "Ready to Ship" band are consumer-facing claims about a future outcome (interview readiness). FTC 2023/2024 guidance on AI claims requires they not be deceptive or unsubstantiated. Rubric: readiness bands must be grounded in stated criteria (resume coverage of JD requirements, STAR depth, quantification), not marketing fluff. Runtime §9's explicit band anchors and Runtime §11 Honest Scoring already satisfy this if enforced.
3. **PII handling of resume text + JD + background_context.** GDPR/CCPA obligations are mostly handled at the Strivo platform layer (auth, storage, deletion), but the generation path must not echo sensitive PII (SSN-like numbers, full home addresses, DOB) from the resume into the output — the model must mention roles/companies/metrics, not raw PII. Rubric: output PII scan (code-based regex) runs post-generation; any SSN / phone / full address echo triggers a soft flag. Already implicit in `prompt-sanitizer.ts` on the input side; add an output-side check.

State-level salary-negotiation-script regulation (e.g., California, Colorado, NY pay-transparency laws) is **not** directly relevant — this phase does not generate salary negotiation scripts (out of scope per Runtime §15). Revisit if that feature is ever added. No HIPAA, SOC 2, FCA, or PCI surface.

## 2. Framework Decision

**Selected Framework:** Native Anthropic HTTP via the repo's existing shared wrapper `supabase/functions/_shared/anthropic.ts` (`invokeAnthropicText`) + **Zod 3.25.76** for schema validation + the existing `supabase/functions/_shared/json-repair.ts` truncation-recovery helper. No new AI framework is introduced.

**Version:**
- `anthropic-version: 2023-06-01` header (Anthropic `/v1/messages` API, current stable)
- Model: `claude-haiku-4-5-20251001` (locked by Runtime §12 and Phase 14 `tier-config.ts`)
- `zod@3.25.76` (already in `package.json`)
- Existing `_shared/anthropic.ts`, `_shared/json-repair.ts`, `_shared/merit-gateway.ts` (Phase 13), `_shared/tier-prompts.ts` + `_shared/tier-config.ts` (Phase 14)

**Rationale:**
Phase 23 is a textbook single-call structured-generation endpoint: one synchronous Anthropic `/v1/messages` call returning a strict 9-section JSON payload, no tool use, no streaming, no agent loop, locked model. The repo's bare-HTTP `invokeAnthropicText` wrapper is already battle-tested across 20+ edge functions (analyze-resume, analyze-career, grade-linkedin, etc.) and is the exact abstraction this phase needs. Three load-bearing primitives are mandated by upstream phases — Phase 13 `withMerits` (deduct + refund-on-Anthropic-5xx), Phase 14 `loadPromptVariant` (auto-prepend Global AI Principles), Phase 19 `json-repair.ts` (truncation recovery) — and any net-new framework (LangChain, LlamaIndex, Mastra, Vercel AI SDK) would either duplicate or bypass them, for zero capability gain. Zod is already in the dependency graph and gives us one colocated schema in `src/types/interviewPrep.ts` (per D-17) as the single source of truth for the Runtime §10 contract, consumed by both the Deno edge function (runtime validation) and the React frontend (TS types + render-time safety).

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| **Vercel AI SDK (`ai` + `@ai-sdk/anthropic`) with `generateObject`** | Schema-enforced generation is genuinely appealing, but adopting it here demands Deno-compat validation (the SDK targets Node-first, Edge runtimes second), duplicates or replaces the Phase 13 `withMerits` hook boundary, and breaks the Phase 14 `loadPromptVariant` auto-prepend contract. Payoff is small because we already get schema safety from Zod + `json-repair` + a strict server validator. Reconsider in a cross-phase consolidation, not here. |
| **LangChain / LangGraph** | Built for multi-step chains, tools, and agent loops — we have none of those. Adds a large dependency surface, Deno-compat friction, and opaque prompt transformations that fight Runtime §11's "Honest Scoring" and "Radical Personalization" principles. |
| **LlamaIndex** | Optimized for RAG/retrieval over document corpora. Interview Prep has exactly one grounding document (the auto-fetched resume), inlined directly into the user prompt. RAG infrastructure is overkill and introduces a retrieval-failure mode we do not have today. |
| **Anthropic official TypeScript SDK (`@anthropic-ai/sdk`)** | A reasonable drop-in, but the repo has deliberately standardized on the direct-HTTP wrapper (`_shared/anthropic.ts`) so that all 20+ edge functions share one retry / timeout / error-mapping / logging contract. Adopting the SDK in one function only fractures that. Revisit as a platform-wide swap, not per-phase. |
| **Mastra / Inngest Agent Kit / CrewAI / AutoGen** | All multi-agent frameworks. System type here is Extraction, not Agent. Zero fit. |

**Vendor Lock-In Accepted:** **Partial.** We are locked to Anthropic as the model provider (Runtime §12 explicitly names `claude-haiku-4-5-20251001`). Swapping providers would require re-tuning prompts for honest scoring behavior and re-testing JSON-emission quality at the 5K/10K token budgets. The direct-HTTP wrapper actually *minimizes* lock-in at the code level — the only Anthropic-specific surface is the request/response shape in `_shared/anthropic.ts`, which can be swapped behind one abstraction if we ever change providers. Accepted consciously: the model is the moat, not the framework.

### Entry Point Pattern

The canonical shape of `interview-prep-analyze` — copy-paste runnable with the existing shared helpers. Every call is one synchronous Anthropic `/v1/messages` round-trip that returns the Runtime §10 nine-section payload.

```typescript
// supabase/functions/interview-prep-analyze/index.ts (abridged — shows the load-bearing path)
serve(async (req) => {
  if (req.method === "OPTIONS") return handleOptionsRequest({ type: "user" });

  const reqId = crypto.randomUUID().slice(0, 8);
  const log = createLogger("interview-prep-analyze", reqId);

  // 1) Parse body BEFORE auth / Merit (Pitfall 6: validation before deduction).
  const body = await req.json();
  const intake = parseIntakeBody(body); // Zod-validated 9-field intake
  if (!intake.ok) return jsonResponse({ error: "invalid_input", ...intake.detail }, 400);

  // 2) Auth + tier (tier MUST come from profiles.subscription_tier, never the body).
  const user = await requireAuth(req, { type: "user" });
  if (!user) return jsonResponse({ error: "Unauthorized" }, 401);
  if (user.tier === "free") return jsonResponse({ error: "pro_or_elite_required" }, 403);

  const tier = user.tier as Tier;          // 'pro' | 'elite'
  const variant = resolveVariant(tier, intake.value); // 'pro' | 'elite' | 'elite_taste'

  // 3) Auto-fetch most recently analyzed resume (Runtime §5). Frontend never sends it.
  const resumeText = await fetchAnalyzedResumeText(getServiceClient(), user.userId);
  if (!resumeText) return jsonResponse({ error: "no_resume" }, 400);

  // 4) Sanitize attacker-controlled surfaces BEFORE they enter the prompt (T-19-05).
  const safeJD = sanitizeUserContent(intake.value.job_description, "interview-prep-analyze", log);
  const safeBg = intake.value.background_context
    ? sanitizeUserContent(intake.value.background_context, "interview-prep-analyze", log)
    : undefined;

  // 5) Merit-gated, single-call generation. Refund fires automatically on 5xx / 408 / 529.
  const gated = await withMerits(
    { userId: user.userId, tier, corsType: "user" },
    "interview_prep",
    async (_txId) => {
      // 5a) Build prompt via Phase 14 loader — auto-prepends Global AI Principles.
      const systemPrompt = loadPromptVariant("interview", tier, {
        resumeText,
        jobDescription: safeJD,
        backgroundContext: safeBg,
        roleTitle: intake.value.role_title,
        company: intake.value.company,
        interviewType: intake.value.interview_type,
        questionCategories: intake.value.question_categories,
        difficulty: intake.value.difficulty,
        duration: intake.value.duration,
        format: intake.value.format,
        variant, // drives Pro flashcards vs Elite quiz vs Elite-taste branch
      });

      // 5b) Single Anthropic call. No streaming. No tool use.
      const maxTokens = variant === "pro" ? 5_000 : 10_000; // Runtime §12
      const timeoutMs = getTimeout(tier, "quiz");            // 80_000 ms (Phase 14)

      const ai = await invokeAnthropicText({
        model: getModel(tier, "interview"), // claude-haiku-4-5-20251001
        system: systemPrompt,
        messages: [{ role: "user", content: "Generate the 9-section interview prep payload as strict JSON per the system prompt." }],
        maxTokens,
        temperature: 0.4,          // Runtime §11 honest-scoring — lower than creative default
        timeoutMs,
        fixtureKey: "interview_prep",
      });
      if (!ai.ok) throw new MeritRefundable(ai.status, ai.error); // 5xx/408/529 → refund

      // 5c) Parse → repair → Zod-validate. One stricter retry on any of these.
      const payload = await parseAndValidate(ai.text, { retryWith: systemPrompt, tier, variant, timeoutMs });
      if (!payload.ok) throw new MeritRefundable(502, payload.reason); // garbage out = refund + 502

      // 5d) "No silent drops" (Runtime §3, D-11).
      const dropMiss = findDroppedOptionalFields(payload.value, intake.value);
      if (dropMiss.length > 0) {
        log.warn("silent-drop-detected", { fields: dropMiss });
        // planner decides final policy — current: ship + warn after 1 stricter retry
      }

      // 5e) Persist (quiz row / flashcards / streak). Any DB error → MeritRefundable(500).
      const persisted = await persistSession(payload.value, { user, tier, variant, intake: intake.value });

      return jsonResponse(persisted, 200);
    },
  );
  if (!gated.ok) return gated.response;
  return gated.value;
});
```

### Common Pitfalls

1. **Ignoring refund taxonomy (D-02).** `withMerits` only refunds on 5xx / 529 / 408 / AbortError / network/timeout keywords. A 400/401/403/422, a Zod validation error, or a prompt-sanitizer rejection is explicitly **not** refundable. The pitfall is throwing `MeritRefundable` on validation failure to "be safe" — that accidentally refunds legitimately billable work. Throw plain `Error` for non-refundable failures and let `withMerits` log `merit-non-refundable-error` and re-raise.
2. **Forgetting that `loadPromptVariant` auto-prepends principles for Pro/Elite only.** Free variants are returned verbatim to hold the Free cost ceiling (GATE-04). Since Interview Prep is Pro/Elite-only, every call here *will* have the Global AI Principles prepended — budget your 5K/10K token plan accordingly (principles block is ~1.5K tokens). Double-prepending by manually concatenating principles in the user prompt is the other half of this pitfall.
3. **Treating truncation as fatal.** `max_tokens=5000` (Pro) and `max_tokens=10000` (Elite) are large but not unbounded; the model can and does run out on 9 long sections. Always: `JSON.parse` → on throw → `repairTruncatedJSON` → `JSON.parse` again → on throw → stricter retry → on throw → `MeritRefundable(502, ...)`. Skipping the repair step and refunding immediately is cash-burn on recoverable truncation.
4. **Trusting the client's `tier` or `quiz_id`.** Client payloads are attacker-controlled. Always resolve tier from `profiles.subscription_tier` via `requireAuth` (T-19-08) and verify `quiz_id` ownership server-side before scoring answers (`interview-prep-evaluate`). This is also the only correct gate for the Pro-monthly Elite-taste quota (D-02 Phase 23).
5. **Double-sanitizing or sanitizing the system prompt.** `_shared/anthropic.ts` already calls `sanitizeMessages` on `role: 'user'` content only (D-07, D-10). Sanitize `job_description` + `background_context` once at the edge handler (before they enter the prompt body template), not again inside the prompt. Never sanitize the assembled system prompt — that mangles the Global AI Principles.
6. **Using `invokeAnthropicText` without `timeoutMs`.** The wrapper only aborts when you pass `timeoutMs`. Omitting it means a stuck upstream can burn the Supabase function wall-clock budget (150s) and surface as a platform-level `503` instead of a clean 408 refund. Always `timeoutMs: getTimeout(tier, 'quiz')`.
7. **"No silent drops" validator off the final prompt only.** The scan must run on the *parsed JSON* (`coach_verdict`, `focus_areas`, `coaching_advice`) after repair, not on the raw text — raw text includes JSON keys and punctuation that false-positive the substring match. Also: case-insensitive, Unicode-normalized. Miss → one stricter retry (explicit instruction listing the dropped fields); miss again → `log.warn` + ship (planner's final call per D-11).

**Core Pattern:**

One call per request. No streaming, no tool use, no retries besides a single stricter retry on parse/validate/no-silent-drops failure. The pattern for both `interview-prep-analyze` and `interview-prep-evaluate` is identical in shape:

```typescript
// Pattern: guarded, single-call, schema-validated extraction.
// Applies verbatim to both interview-prep-analyze and interview-prep-evaluate.

async function runExtraction<T>(opts: {
  systemPrompt: string;
  userMessage: string;
  schema: z.ZodType<T>;
  model: string;
  maxTokens: number;
  timeoutMs: number;
  log: ReturnType<typeof createLogger>;
  strictRetryInstruction: string; // e.g. "Return ONLY valid JSON..."
}): Promise<{ ok: true; value: T } | { ok: false; reason: string }> {
  // ── Attempt 1 ────────────────────────────────────────────────────────────
  const first = await invokeAnthropicText({
    model: opts.model,
    system: opts.systemPrompt,
    messages: [{ role: "user", content: opts.userMessage }],
    maxTokens: opts.maxTokens,
    temperature: 0.4,
    timeoutMs: opts.timeoutMs,
    fixtureKey: "interview_prep",
  });
  if (!first.ok) {
    // Let withMerits classify → refund on 5xx/408/529, non-refund on 4xx.
    throw new MeritRefundable(first.status, first.error);
  }

  const firstParse = safeParseWithRepair(first.text, opts.schema);
  if (firstParse.ok) return firstParse;

  opts.log.warn("validation-failed-first-attempt", { reason: firstParse.reason });

  // ── Attempt 2 (stricter retry, same tokens, lower temperature) ───────────
  const second = await invokeAnthropicText({
    model: opts.model,
    system: opts.systemPrompt,
    messages: [{ role: "user", content: `${opts.userMessage}\n\n${opts.strictRetryInstruction}` }],
    maxTokens: opts.maxTokens,
    temperature: 0.2,        // tighter on retry
    timeoutMs: opts.timeoutMs,
    fixtureKey: "interview_prep",
  });
  if (!second.ok) throw new MeritRefundable(second.status, second.error);

  const secondParse = safeParseWithRepair(second.text, opts.schema);
  if (secondParse.ok) {
    opts.log.info("validation-passed-on-retry");
    return secondParse;
  }
  return { ok: false, reason: `validation-failed-after-retry: ${secondParse.reason}` };
}

// Parse → repair → parse → Zod.safeParse. Never throws; returns a tagged result.
function safeParseWithRepair<T>(
  raw: string,
  schema: z.ZodType<T>,
): { ok: true; value: T } | { ok: false; reason: string } {
  let candidate: unknown;
  try {
    candidate = JSON.parse(raw.trim());
  } catch {
    try {
      candidate = JSON.parse(repairTruncatedJSON(raw));
    } catch (e) {
      return { ok: false, reason: `json-parse-failed: ${(e as Error).message}` };
    }
  }
  const validated = schema.safeParse(candidate);
  if (!validated.success) {
    return { ok: false, reason: `zod-failed: ${validated.error.issues.slice(0, 3).map((i) => `${i.path.join(".")}:${i.message}`).join("; ")}` };
  }
  return { ok: true, value: validated.data };
}
```

Call site inside `withMerits` (see Section 3 entry point). The "no silent drops" scan runs after `runExtraction` succeeds, and itself may trigger one more stricter retry if any filled optional field is missing from `coach_verdict` ∪ `focus_areas` ∪ `coaching_advice` (D-11).

**Tool Use:**

**None.** Phase 23 has zero tool use. The model is forbidden to invoke tools, fetch URLs, or call functions. `invokeAnthropicText` does not pass a `tools` array, so the model cannot emit `tool_use` blocks. Any `content` block in the response with `type !== 'text'` is ignored by the wrapper (`_shared/anthropic.ts` line 663). Runtime §5 resume grounding is satisfied by inlining the full `resumeText` (truncated to 8,000 chars per existing prompt builder) directly in the system prompt — no retrieval, no function-calling, no browsing.

**State Management:**

The function itself is **stateless** per request. Durable state lives in Postgres and is read/written only through the service-role `getServiceClient()`:

| State | Where | When Read | When Written |
|-------|-------|-----------|--------------|
| Auth identity + tier | `profiles.subscription_tier` via `requireAuth` | At handler entry (after body parse) | Never by this function |
| Resume text (grounding) | `resumes` + Supabase Storage (`resumes` bucket) via `getServiceClient()` | After auth, before Anthropic call (Runtime §5) | Never by this function |
| Merit balance + transaction | `check_and_deduct_merits` / `refund_merits` RPC | Via `withMerits` (deduction at entry) | Via `withMerits` (refund on `MeritRefundable` throw) |
| Quiz session | `interview_quizzes` (+ `interview_quiz_answers`) | `interview-prep-evaluate` reads on ownership check | `interview-prep-analyze` inserts on success |
| Streak + daily cap | `interview_streaks` + `COUNT(*) FROM interview_quizzes` | On Elite-quiz path only, BEFORE Merit deduction (D-11/D-12) | On Elite-quiz path only, AFTER successful generation |
| Pro-monthly Elite-taste quota | `COUNT(*) FROM interview_quizzes WHERE tier='elite_taste' AND created_at >= first_of_calendar_month_utc` | On Pro-monthly branch only, BEFORE Merit deduction | Implicitly on insert (tier='elite_taste') |

Frontend state (per D-18) is a `useReducer` with the union `'loading' | 'free-gate' | 'input-form' | 'generating' | 'flashcard-results' | 'quiz-active' | 'quiz-submitting' | 'quiz-results' | 'error'`. No multi-turn context is retained between calls; a "regenerate" is a brand-new `interview-prep-analyze` invocation with a fresh Merit deduction.

**Context Window Strategy:**

Claude Haiku 4.5 ships with a 200K-token context window — orders of magnitude larger than anything we feed it here. Strategy is **truncate at the source, not the model**:

| Input | Hard cap | Why that cap |
|-------|---------|--------------|
| `resumeText` | 8,000 chars (~2,000 tokens) | Existing `buildContextBlock` cap; covers a generous 2-page resume. |
| `job_description` | 12,000 chars stored / 6,000 chars inlined into the prompt (~1,500 tokens) | Stored raw for future re-analysis; truncated on prompt assembly to protect output budget. |
| `background_context` | 1,500 chars (~375 tokens) | D-03 Phase 23 DB constraint — enforced both at API and DB layer. |
| Global AI Principles (auto-prepended by `loadPromptVariant`) | ~1,500 tokens | Fixed. Principal driver of the prompt-caching win. |
| Interview Prep shared base system prompt | ~2,000 tokens | Defines 9 §10 sections, Runtime §11 principles, honest-scoring rules. Fixed — eligible for caching. |
| Intake enums + optional-field instructions | ~500 tokens | Tier-specific; rebuilt per request. |

**Input prompt total:** ~7,000–8,000 input tokens. **Output budget:** 5,000 (Pro) or 10,000 (Elite). **Total per call:** ~12,000–18,000 tokens — ~6% of Haiku's window.

Prompt-caching win: the wrapper already sets `cache_control: { type: 'ephemeral' }` on the system block (`_shared/anthropic.ts` line 635). The system block contains Global AI Principles + shared base (stable across users) ahead of the per-request grounding (resume + JD + intake). The stable prefix gets a ~5-minute TTL cache hit across back-to-back requests from the same worker, cutting input cost on cache-reads by ~90% (`$0.50/MTok` vs `$5/MTok` for Haiku 4.5-class input pricing tier). Since the shared base is the first thing after principles and the caching breakpoint is auto-placed, no further tuning is needed.

### Structured Outputs with Zod

Anthropic's Messages API does not expose a native structured-output mode; the model emits free-form text. Structured reliability is earned through **prompt + schema + repair + validate + retry** — all load-bearing. Zod is the single source of truth for the Runtime §10 contract, colocated in `src/types/interviewPrep.ts` per D-17 and consumed by both the Deno edge function (runtime validation via `safeParse`) and the React frontend (TS types via `z.infer`).

```typescript
// src/types/interviewPrep.ts
import { z } from "zod";

// ── Shared primitives ───────────────────────────────────────────────────────
const ReadinessBand = z.enum([
  "not_ready",         // 0–39
  "needs_work",        // 40–69
  "ready_to_practice", // 70–84
  "ready_to_ship",     // 85–100

  action: z.string().min(40).max(1200),
```

**Retry logic** (sum of parse, repair, Zod, and "no silent drops"):

| Attempt | Trigger | Action | Temperature | Log |
|---------|---------|--------|-------------|-----|
| 1 (initial) | — | `invokeAnthropicText` with full prompt | `0.4` | `ai-call-start` |
| 2 (retry) | `JSON.parse` fails AFTER `repairTruncatedJSON`, OR `schema.safeParse` fails, OR "no silent drops" scan finds a dropped filled optional field | Re-invoke with the same system prompt + appended stricter instruction (`"Return ONLY valid JSON matching the schema. Reference these fields explicitly: <list>"`). Same `maxTokens` and `timeoutMs`. | `0.2` | `validation-failed-first-attempt` with a `reason` enum |
| Final | Retry still fails Zod or parse | `throw new MeritRefundable(502, "...")` → `withMerits` refunds + gateway re-raises → catch returns `502` to client | — | `merit-refund` auto-logged by gateway |
| Final (soft) | Retry succeeds Zod but "no silent drops" still misses | Per D-11: ship + `log.warn("silent-drop-detected", { fields })`. Do NOT 502/refund on this alone. Planner may promote to hard-fail after production data. | — | `silent-drop-detected` |

**Never retry on:** 4xx from Anthropic (client error), prompt-sanitizer rejection, rate-limit 429, Merit RPC failure. All of these are non-refundable and a retry only compounds the problem.

### Async-First Design

**Deno edge functions run on a V8 isolate with first-class `async`/`await`.** `invokeAnthropicText` is `async` by construction — it uses `fetch` under the hood, honors `AbortController` when `timeoutMs` is provided, and returns a discriminated union (`{ ok: true, ... } | { ok: false, status, error }`). Never call it without `await`; never wrap it in `Promise.race` with your own timeout (the wrapper already does that and will leak the winning race loser).

**The one common mistake on this stack:** forgetting that `withMerits`'s callback runs inside a try/catch inside the gateway — an unhandled promise rejection inside the callback is caught, classified, and either refunded or logged as non-refundable. Returning a `Response` object does **not** stop execution; you must explicitly `return gated.value` at the caller. The second common mistake: dropping a thrown `MeritRefundable` by wrapping the callback body in its own try/catch that swallows everything — this eats the refund path.

**Stream vs. await for this phase: always `await`.** Streaming (`streamAnthropicText`) is reserved for UX-on-text (resume analysis first-byte-time, typing effect) but conflicts with Zod validation — you cannot `safeParse` a partial JSON document. The strict 9-section payload cannot be rendered until the full object validates, so streaming buys nothing and costs both the validation guarantee and the "no silent drops" scan. Keep the single synchronous call with an 80s timeout and a skeleton loader on the frontend.

**Parallelism:** zero within a single request. `interview-prep-analyze` is one call; `interview-prep-evaluate` is one call. Any temptation to fan out (e.g., "parallel call per question in evaluate") is rejected because (a) the answers share the `overall_readiness` roll-up and (b) it would multiply Merit accounting complexity.

### Prompt Engineering Discipline

**System vs. user prompt separation (strictly enforced):**

- **System block** — assembled by `loadPromptVariant`. Contains: Global AI Principles (auto-prepended for Pro/Elite), Runtime §11 behavior principles, the 9-section JSON shape contract, honest-scoring rubric, "no silent drops" instruction listing the filled optional fields, and the grounding documents (resume + JD). This is a ~7K-token static-plus-grounding block — the caching breakpoint lives here.
- **User message** — a single short sentence: `"Generate the 9-section interview prep payload as strict JSON per the system prompt."` The user role exists solely so the model knows to respond; it carries no content. The prompt-sanitizer sees an effectively empty user surface, which is the point.

Placing the resume + JD in the system block (not as a synthetic user turn) has two concrete benefits: (1) the prompt-caching breakpoint can sit on the stable principles+base prefix, (2) the sanitizer does not touch grounding content (sanitization is user-role only per `_shared/anthropic.ts` line 614). Attacker-controlled substrings (`job_description`, `background_context`) are sanitized explicitly at the handler level via `sanitizeUserContent` *before* being pasted into the system block — that is where injection defense actually lives.

**Few-shot: inline, tier-calibrated, minimal.** Each tier variant in `interview-prep-prompts.ts` ships with **one** worked §10 example (a redacted fixture from internal dogfooding) — enough to lock the tone of `coach_verdict` and the `resume_anchor` citation style, not enough to bias scoring. No dynamic few-shot retrieval; no vector store of prior sessions. Add a second example only if eval shows consistent tonal drift (Section 5 will formalize this).

**Token budget (production-only, never unbounded):**

| Call | `max_tokens` | Hard rule |
|------|--------------|-----------|
| `interview-prep-analyze` Pro | `5_000` | Runtime §12. Never exceed — 5K is the Pro economic envelope. |
| `interview-prep-analyze` Elite / Pro Elite-taste | `10_000` | Runtime §12. Never exceed. |
| `interview-prep-evaluate` | `10_000` | Runtime §12. Per-question breakdowns × up to 7 questions fit comfortably. |

`max_tokens` is always an explicit argument to `invokeAnthropicText` — the wrapper falls back to `4096` on undefined, which would silently truncate Elite payloads mid-`prep_roadmap`. Grep for every call site before ship (`rg 'invokeAnthropicText\(' supabase/functions`).

**Honest scoring prompt discipline (Runtime §11):** the shared base system prompt contains a calibration block listing band anchors (e.g. "85–100 is reserved for a candidate with ≥3 quantified resume bullets directly matching the JD's top 3 requirements"). Without this, Haiku 4.5 tends to anchor on 72–78 regardless of fit. Verify during eval (Section 5).

### Context Window Management

System-type-specific: **Extraction with a single grounding document.** Not RAG, not conversational — no retrieval step, no summarization loop, no compaction.

**Strategy:** truncate-at-the-edge, cache-the-static-prefix, budget-the-output.

1. **Truncate inputs at ingestion, not at the model boundary.** Storage-layer caps (resume PDF → text via `extractPDFText` then `.slice(0, 8000)`, JD `.slice(0, 6000)` into the prompt, background `.slice(0, 1500)` at the DB CHECK) mean the model never sees more than ~3K tokens of user-generated grounding. Haiku 4.5's 200K window is never stressed; truncation is about **output quality and cost**, not context overflow. Long grounding dilutes the instruction signal.
2. **Static prefix comes first, grounding comes last.** System block layout: `[Global AI Principles] → [Shared Interview Prep base + 9-section contract + honest-scoring rubric] → [Intake enums + optional-field directive] → [Resume] → [JD]`. The first two are fixed across requests and fill the caching breakpoint set by `_shared/anthropic.ts` line 635.
3. **Do not summarize grounding into the prompt.** Pre-summarizing the resume ("candidate is a backend engineer…") before passing it to the model strips the exact resume anchors Runtime §5 requires STAR beats to cite. Pass the raw text. If a resume exceeds 8,000 chars, the existing `.slice` silently drops the tail — flag in the prompt: `"Some content may have been truncated; cite what is present and mark missing anchors with signal_missing=true."`
4. **No multi-turn conversational memory.** Each `interview-prep-analyze` call is independent; there is no turn-history to compact. Regeneration and retry both start clean, which is the correct behavior for a deterministic extraction contract.
5. **Evaluate call is its own isolated window.** `interview-prep-evaluate` re-reads `interview_quizzes` + `interview_quiz_answers` for the `quiz_id` and rebuilds the prompt from scratch — it never receives the original analyze prompt or output. This is intentional: it prevents "anchoring" where evaluate tries to confirm analyze's readiness score instead of scoring the actual answers.

**Caching strategy:**

- **Exact-match prompt cache (server-side, Anthropic):** already on. The wrapper sets `cache_control: { type: 'ephemeral' }` on the system block. Reuse occurs within a ~5-minute window per worker; hit ratio depends on concurrent user arrival patterns. Expect 10–30% in steady state, higher during marketing pushes. No code change needed.
- **Exact-match response cache (Strivo-side):** **not applicable**. Each request's grounding (resume + JD + intake) is unique per user × session; a response cache would have near-zero hit rate and risks cross-user contamination. Explicitly do not implement.
- **Semantic cache (e.g., vector-similarity on `(resume_hash, jd_hash)`):** **not recommended** for Phase 23. The feature's entire value proposition is radical personalization per (resume, JD, intake). A semantic-similarity hit would return a different user's answers with surface tokens swapped in — that is the exact "generic, non-grounded output" failure mode (Section 1 #1). Revisit only if dogfood shows heavy duplicate (resume, JD) pairs from a single user, in which case de-dupe at the intake step, not post-hoc at the model.
- **Idempotency cache (Strivo-side, short TTL):** **recommended** — a per-user short-TTL (60s) cache keyed on `(userId, sha256(resume_text + jd + intake_json))` prevents double-charges on duplicate submits from flaky client retries. Implement at the handler layer, before `withMerits`. Not a cost optimization, a UX + Merit-economy guardrail.

**Cheaper-model routing:** the platform has already decided Haiku 4.5 is the floor (`TIER_MODELS` locks every tier to it). No sub-task routing exists or is planned for this phase — the 9-section generation is a single indivisible call. The only sub-task candidate would be the "no silent drops" scan, which is pure string operations (no model needed) and runs locally in ~1ms.

## 6. Guardrails

> Online guardrails run on **every** request and must be fast (each adds latency to the user-visible 30s analyze path). Offline flywheel metrics run on samples or on the full reference dataset on a schedule, and feed model/prompt iteration — they never block a single request.

### Online (Real-Time)

| # | Guardrail | Trigger / Detection | Intervention | Layer |
|---|-----------|--------------------|--------------|-------|
| 1 | **Prompt-injection pattern strip** | `_shared/prompt-sanitizer.ts` `sanitizeUserContent()` runs against `job_description` and `background_context` before either is pasted into the system prompt. Multi-word injection regexes (`ignore previous instructions`, `pretend you are`, `you are now`, `act as`, `reveal system prompt`, `disregard …`, `new instructions:`, `override …`, `DAN`/`do anything now`, plus the tier-escalation phrases added per CFM-7). | **Strip silently + `log.warn('sanitization-stripped', { phrase, fn })`** (per `_shared/prompt-sanitizer.ts` D-03/D-16). Do not block the request. Block-and-reject is reserved for the post-response canary check (row 6). | Edge handler — runs in `interview-prep-analyze/index.ts` step 4 (Section 3 entry point), **before** Merit deduction. |
| 2 | **Max input length enforcement** | `job_description.length > 12_000` **OR** `background_context.length > 1_500` **OR** `role_title.length > 120` **OR** `company.length > 120`. Server-side, enforced regardless of frontend validation. | **Block — return 400 `invalid_input` with `{ field, max, actual }`** before auth. **No Merit deduction.** Hard DB CHECK on `background_context` (Phase 23 D-03) is a backstop. | Edge handler — `parseIntakeBody()` Zod schema in step 1. |
| 3 | **Tier-boundary check (Free → 403 before any AI call)** | `requireAuth()` returns user; `user.tier === "free"`. | **Block — return 403 `pro_or_elite_required`.** No Merit deduction (Free has no Merits). No Anthropic call. Frontend renders the upgrade modal. | Edge handler — step 2 (Section 3 entry point). |
| 4 | **Server-side resume existence** | `fetchAnalyzedResumeText(serviceClient, user.userId)` returns null/empty (user has not analyzed any resume yet) OR most recent resume failed PDF extraction. | **Block — return 400 `no_resume` with a frontend-render-able prompt linking to /upload.** No Merit deduction. | Edge handler — step 3 (Section 3 entry point), **before** `withMerits`. |
| 5 | **Server-side answer-length enforcement (evaluate)** | On `interview-prep-evaluate`: any per-question answer body > 500 characters. | **Block — return 400 `answer_too_long` with `{ question_id, max: 500, actual }`.** No Merit deduction. Frontend's textarea also enforces, but server is the source of truth. | Edge handler — `interview-prep-evaluate/index.ts` body-parse step. |
| 6 | **Schema-conformance post-response (Zod after repair)** | After `repairTruncatedJSON()` + stricter retry, `InterviewPrepPayloadSchema.safeParse()` still fails. | **Block downstream + refund.** Throw `MeritRefundable(502, "validation-failed-after-retry: <reason>")`. `withMerits` auto-refunds. Client receives 502 and a "regenerate" CTA; no broken UI. | Edge handler — inside `withMerits` callback, after `runExtraction()`. |
| 7 | **"No silent drops" post-response scan** | `findDroppedOptionalFields(payload, intake)` returns a non-empty array of filled optional intake fields absent from `coach_verdict ∪ focus_areas ∪ coaching_advice`. | **Soft-block on first miss → one stricter retry** with an appended directive listing the dropped fields. **Soft-flag on second miss → ship + `log.warn('silent-drop-detected', { fields })`** per D-11 (planner may upgrade to hard-fail after 30 days of production telemetry). | Edge handler — inside `withMerits` callback, after Zod success. |
| 8 | **Output PII scan (regulatory rubric #3)** | Regex scan on the assembled payload's free-text strings (`coach_verdict`, `coaching_advice.*`, `focus_areas[*].why`, `practice_questions.items[*].coach_note`) for SSN-shaped patterns (`\d{3}-\d{2}-\d{4}`), full US street addresses, raw `tel:`/`mailto:` schemes, and DOB-shaped strings. | **Soft-flag — `log.warn('output-pii-detected', { pattern })`. Ship the response.** Hard-block reserved for SSN match only (returns 502 + refund — never echo SSN to a client). | Edge handler — runs after `findDroppedOptionalFields`, before `persistSession`. |
| 9 | **Idempotency cache (Section 4b)** | Per-user 60-second cache keyed on `(userId, sha256(resume_text + jd + intake_json))`. A second submit with the same key inside the TTL is a duplicate-click. | **Return the cached `200` payload** without a new Merit deduction or Anthropic call. Logs `idempotent-hit`. | Edge handler — runs **before** `withMerits`. |

|---|--------|-------------------|----------------------|---------|
| 1 | **Zod-failure rate (production)** | 100% of production responses (telemetry counter `zod_failure_total / requests_total`). | **Threshold > 2% over any 7-day rolling window** → file a Phase 23 prompt-iteration ticket; if the failure mode clusters on a single Zod path, sharpen the schema or the system prompt instruction for that section. **Threshold > 5% over 24 h** → page on-call (Section 7 Alerts). | Continuous; weekly review; PagerDuty page on the 24 h breach. |

| 3 | **Honest-scoring calibration audit (vs human-labeled dataset)** | Full reference dataset (30 examples) + 10 randomly sampled production sessions per month, all re-labeled by a Senior Technical Recruiter blind to AI band. Calibration metric: `mean(\|recruiter_band_index − ai_band_index\|)`. | **Drift threshold: ±0.1 mean-band-index drift between consecutive monthly audits OR mean drift > 0.5 in any single month → freeze the prompt** (no further changes), root-cause the inflation, and re-audit before unfreezing. **Any single inversion (recruiter `not_ready` ↔ AI `ready_to_ship`) triggers immediate prompt freeze.** | Monthly. |
| 4 | **Prompt-injection regression suite** | Full 12+ adversarial fixture set runs on every PR via Promptfoo CI; full set + 5 newly added fixtures runs monthly against the deployed staging endpoint. | **Threshold: zero bypasses tolerated** (Dimension 12 is **Critical**). One bypass blocks promotion; production-detected bypass triggers immediate prompt-sanitizer pattern addition + nightly canary alert until the new fixture passes. | Per-PR + monthly full sweep. |
| 5 | **STAR per-beat ↔ overall consistency drift (evaluate)** | 100% of production evaluate responses log the `\|overall − 10×mean(beats)\|` delta. Distribution reviewed monthly. | **Threshold: 95th percentile of the absolute delta > 20 over any 30-day window** → re-tune the evaluate scoring rubric block; add an explicit "overall must be within 15 of the per-beat mean" anchor sentence. | Monthly histogram review. |
| 6 | **Cost per session ($)** | Continuous via `_shared/anthropic.ts` token logs (`input_tokens`, `output_tokens`, `cache_read_input_tokens`) → derived USD. | **Threshold: rolling-7-day mean > $0.07/Pro session OR > $0.12/Elite session** → audit prompt for bloat (cacheable prefix grew? `max_tokens` ceiling being hit on every call?). Hard ceiling per ROADMAP cost contract: $0.10/session all-in. | Weekly review. |

## 7. Production Monitoring

**Tracing Tool:** **Staged — Supabase Logs (`_shared/logger.ts` structured JSON) is the source of truth at production launch; Arize Phoenix lands as a fast-follow within 14 days post-launch.** Justification: the existing structured logger already emits every field the alert thresholds below need (`level`, `msg`, `fn`, `ts`, `reqId`, `tier`, `variant`, `durationMs`, `zod_failure`, `silent_drop_detected`, `merit_refund`, `repair_attempted`, `input_tokens`, `output_tokens`, `cache_read_input_tokens`), and Supabase log retention (7 days hot, 30 days cold) is sufficient for the 24 h / 7 d / 30 d alert windows. Phoenix's value is the eval-trace UI and the LLM-judge replay surface — neither is a launch-blocker. The Phoenix fast-follow ships an OTLP exporter wired into `invokeAnthropicText` (one-line span wrapper, gated by `PHOENIX_OTLP_ENDPOINT` env var; absent var = no-op exporter, zero perf impact).

**Key Metrics to Track (5):**

| # | Metric | Definition | Source |
|---|--------|-----------|--------|
| 1 | **Latency p50 / p95 (analyze + evaluate, per tier)** | Wall-clock from handler entry to `Response` emit, bucketed by `(tier, variant, function_name)`. Reported on the `request-end` log line as `durationMs`. | `_shared/logger.ts` timer + Supabase Logs aggregation. |
| 2 | **Zod-failure rate** | `count(level=warn AND msg='zod-failed') / count(level=info AND msg='request-end' AND fn IN ('interview-prep-analyze','interview-prep-evaluate'))` over a 15 m / 24 h / 7 d rolling window. | Structured logs. |
| 3 | **Silent-drop retry rate** | `count(msg='silent-drop-detected') / count(requests_with_filled_optional_fields)` over a 24 h window. Numerator includes both successful-after-retry and ship-with-warn. | Structured logs (D-11 telemetry). |
| 4 | **Anthropic 5xx rate (drives refund path)** | `count(msg='merit-refund' AND reason MATCHES /^(5\d{2}\|408\|529\|network\|timeout)/) / count(merit-transaction)` over 10 m / 1 h / 24 h windows. | `_shared/merit-gateway.ts` structured logs. |
| 5 | **Cost per session ($)** | `sum(input_tokens) × $1.00/MTok + sum(cache_read_input_tokens) × $0.10/MTok + sum(output_tokens) × $5.00/MTok`, bucketed by `(tier, variant)`, daily. | `_shared/anthropic.ts` token-usage log lines. |

**Alert Thresholds (PagerDuty / Slack `#strivo-oncall`):**

| Severity | Condition | Action |
|----------|-----------|--------|
| **Page (P1)** | `p95(analyze, elite) > 25 s` for 5 consecutive minutes | Page on-call. Likely Anthropic upstream slow OR token budget hit causing truncation+retry. Check Anthropic status + recent prompt deploy. |
| **Page (P1)** | `Zod-failure rate > 2% (15-minute window)` | Page on-call. Recent prompt change is producing malformed JSON; consider rolling back the prompt variant. |
| **Page (P1)** | `Anthropic 5xx rate > 1% (10-minute window)` | Page on-call. Anthropic upstream incident likely; verify refund path is firing (no Merit corruption). |
| **Page (P1)** | Any single **prompt-injection bypass** detected in production (post-response canary scan finds the canary string in payload, OR tier-shape mismatch) | Page on-call. **Freeze the variant** (revert to last-known-good prompt) + add fixture to Dimension 12 suite + prompt-sanitizer pattern. |
| **Page (P1)** | Any single **honest-scoring inversion** detected by the monthly audit (recruiter `not_ready` ↔ AI `ready_to_ship`) | Page on-call. Freeze prompt; root-cause; re-audit before unfreeze. |
| **Warn (P2 — Slack only)** | `Silent-drop retry rate > 15% (24 h window)` | File ticket. Stricter retry working too often; sharpen the system-prompt directive for the offending optional field. |
| **Warn (P2)** | `Cost per session > $0.07 (Pro) OR $0.12 (Elite) — 7-day rolling mean` | File ticket. Audit prompt size; verify cache-hit rate; check if `max_tokens` is hitting ceiling on every call. |
| **Warn (P2)** | `Truncation-recovery success rate < 95% (500-request rolling window)` | File ticket. `repairTruncatedJSON()` no longer covering the dominant truncation pattern — add a repair rule. |
| **Info (Slack daily digest)** | Summary of: requests by tier, p50/p95, Zod-failure %, silent-drop %, refund %, cost. | None — operational visibility. |
