<objective>
Replace the client-side race in the Stripe top-up modal. Today `StripePaymentElementModal.tsx:96/100` fires a single `invalidateQueries(['merit-balance'])` the instant Stripe returns `succeeded`/`processing`, but the webhook's `credit_shop_merits` write often has not landed yet, so the re-read returns the stale pre-purchase balance and the user never sees their new merits.

Purpose: An at-cap user (Pro 75/75) buying a 3-pack must see `78 / 75` in the header within 10s of Stripe confirmation (MER-07 above-cap render, MER-08 10s reconciliation), without reintroducing a bonus chip (D-01) and without Supabase Realtime (D-02).

Output: A `reconcileShopCredit(snapshot)` poll helper in `useMerits`, a snapshot-at-submit + detached poll in the modal, and extended vitest coverage driving the poll with fake timers.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → React Query cache | Client reads `shop_balance` from the cached `get_merit_balance` RPC result; the value is server-authored. |
| browser → Supabase RPC | The poll triggers refetches of `get_merit_balance`; no new endpoint, no new write path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-01 | Tampering | client-side balance display | accept | The poll only READS the server-authored `shop_balance` via the existing RPC and compares to a local snapshot. It never writes a balance; crediting remains server-side via `credit_shop_merits`. A tampered client can only fool its own display, not its actual balance. Low risk, no PII. |
| T-32-02 | Elevation of Privilege | reconciliation poll vs server crediting | mitigate | The poll does not bypass or short-circuit server-side crediting/idempotency — it merely re-reads the authoritative balance. No client code grants merits. Verified by Plan 02's idempotency regression (crediting is gated by `credit_shop_merits` + triple-defense). |
| T-32-03 | Denial of Service | poll loop | mitigate | The loop is hard-bounded to a 10000ms ceiling and a 1500ms interval (≈7 refetches max), and runs once per successful purchase. No unbounded retry, no recursion. |
</threat_model>
