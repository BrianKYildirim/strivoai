Test-target RPC (post-Plan 29-04): `public.check_and_deduct_merits(p_user_id uuid, p_feature text, p_tier text, p_idempotency_key text DEFAULT NULL) RETURNS jsonb`.

Expected returns:
- First call with key K against a user with enough balance: `{ success: true, transaction_id: <uuid>, remaining_balance: <int>, deducted_from: {subscription: x, shop: y} }`.
- Second call with same key K (sequential retry): `{ success: true, transaction_id: <same uuid>, already_deducted: true }` — no balance change.
- Parallel race (5 concurrent calls with same key K): exactly ONE returns success without `already_deducted`; the other 4 return `already_deducted: true` with the same `transaction_id`.

Test seeding strategy (per 29-VALIDATION.md "Manual-Only Verifications" exemption — TEST-02 is integration, not manual):
- The test connects to staging Supabase using `SUPABASE_URL_STAGING` + `SUPABASE_SERVICE_ROLE_KEY_STAGING` env vars (operator-supplied at run time; not stored in repo).
- The test creates a fresh `merit_transactions`-eligible test user via `auth.admin.createUser` (using service role) OR reuses a designated `merit-test@strivo.staging` user seeded by an existing script. Planner-decision: use an operator-supplied `MERIT_TEST_USER_ID` env var so the test does not need user-creation privileges; fail-fast if the var is unset.
- The test ensures the test user has enough `user_merits` balance before each test (top up via `admin_credit_adjustment` RPC if needed — exists per `20260331000000_admin_credit_adjustment.sql`).
- After each test case, the test deletes its own `merit_transactions` rows by `idempotency_key` (seeded UUID for traceability — use a `phase-29-test-<random>` prefix or similar marker stored in `metadata`).

Test feature / tier choice: use a feature row that exists in `merit_feature_costs` for the chosen tier. Safe choice: `feature='resume_analysis', tier='free'` — known-shipping config across all environments. If `merit_feature_costs` returns `tier_locked` for the test, fall back to a tier known to have a row.

Env-config block pattern (from `scripts/validate-performance.mjs:45-56` per 29-PATTERNS.md):
- Read `SUPABASE_URL_STAGING`, `SUPABASE_SERVICE_ROLE_KEY_STAGING`, `MERIT_TEST_USER_ID` from `Deno.env`.
- If any is missing, `Deno.test.skip` the test (CI-friendly — Deno reports skipped tests but does not fail CI).
