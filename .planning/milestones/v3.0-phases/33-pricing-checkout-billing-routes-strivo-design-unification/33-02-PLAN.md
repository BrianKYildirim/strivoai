<objective>
Close the one genuine backend gap in this phase: the confirmed Pro→Elite double-billing
bug. Today `create-checkout-session` ALWAYS calls
`stripe.checkout.sessions.create({ mode:'subscription' })`, which (per Stripe docs) creates
a SECOND active subscription for an already-subscribed customer rather than swapping the
existing one — the user is double-billed. Add a server-side swap branch that, for an
existing subscriber, updates their current subscription item's price in place, routing
through the already-working `customer.subscription.updated` webhook branch.

Purpose: This is the only net-new backend capability in Phase 33 and the riskiest piece;
it lands in its own wave-1 plan so the frontend checkout wiring (Plan 03) can build on a
known-correct swap contract.

Output: A swap branch in `create-checkout-session`, a discriminated response so the
frontend knows whether to open the embedded modal (net-new) or just reconcile (in-place
swap), and an edge test asserting an existing subscriber triggers `subscriptions.update`
and NOT a second `checkout.sessions.create`.

UX decision (Open Question 1/2, Assumption A2): For an EXISTING subscriber we do the
server-side in-place swap (no embedded modal) — the card on file from their initial
checkout pays the proration. The function returns a `{ mode: 'swap', tier }` shape (no
clientSecret) so the frontend skips the modal and goes straight to the reconciliation
toast. If the swap fails because there is no usable payment method on file, return a
`{ mode: 'portal_required' }` shape so the frontend can fall back to the customer portal
rather than silently failing. Net-new subscribers keep the existing
`{ clientSecret, id }` embedded path verbatim.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → create-checkout-session | Authenticated user requests an upgrade/checkout for a tier+interval |
| create-checkout-session → Stripe | Edge function mutates a subscription / mints a session |
| Stripe → stripe-webhook-handler | Signed `customer.subscription.updated` grants tier + merits |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-04 | Elevation of privilege | swap branch subscription id source | mitigate | `existingSubId` is read ONLY from the caller's own `profiles` row keyed on `ctx.userId`; the request body's subscription/customer id (if any) is ignored. A user cannot pass another user's subscription id to mutate it. |
| T-33-05 | Tampering | price selection | mitigate | Target price id resolved exclusively from `STRIPE_PRICE_<TIER>_<INTERVAL>` env (STR-12); a client-supplied price/priceId is never forwarded to Stripe. Asserted by edge test. |
| T-33-06 | Repudiation/Replay | duplicate swap requests | accept | `stripe.subscriptions.update` to the same price is idempotent at the tier outcome (item ends on the same price); the authoritative tier/merit grant runs once per `customer.subscription.updated` in the existing webhook (Phase 32 idempotency). No new replay surface added here. |
| T-33-07 | DoS | uncaught Stripe throw | mitigate | All new Stripe calls wrapped in try/catch returning `jsonResponse(..., 500)` with CORS headers, preventing CORS-less error escapes that mask failures (PATTERNS error-envelope). |
</threat_model>
