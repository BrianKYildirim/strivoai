<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → create-checkout-session | Authenticated user requests checkout/swap (mitigations live in Plan 02) |
| browser → create-stripe-portal | Portal fallback for portal_required (server-side ctx.userId customer lookup) |
| Stripe redirect → /dashboard | Untrusted query param `?checkout=complete&session_id=` returns to the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-08 | Spoofing/Tampering | `?checkout=complete` query param | mitigate | The param is a UX trigger only — it triggers a read-only reconciliation poll against the authoritative `['merit-balance']`/`profiles` query keyed on the session user. It grants NO tier/merits itself (the webhook is authoritative). A forged `?checkout=complete` causes at most a harmless ~10s poll that resolves to the user's actual tier. |
| T-33-09 | Tampering | tier passed to create-checkout-session | mitigate | The client passes only `tier`+`interval` to select a CTA; the actual price + swap target are resolved server-side from env (Plan 02, STR-12). A tampered client tier cannot grant a higher tier — the webhook writes tier from the Stripe object, not the client. |
| T-33-10 | Replay | repeated returns to /dashboard?checkout=complete | accept | Reconciliation poll is read-only and idempotent; merit/tier grants are webhook-side and idempotent (Phase 32). Re-poll has no side effect. |
</threat_model>
