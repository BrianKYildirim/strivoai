## Summary

This is a brownfield reliability-hardening phase with an unusually narrow code appetite. The "research" surface is almost entirely **inside this repo**: the substrate (`createLogger`, `corsHeaders`, `requireAuth`, `withMerits`, `invokeAnthropicText`) already exists and is well-characterized by the Phase 3 audit catalog and the Phase 5 test corpus. There is **no external library to evaluate** and **no new infrastructure** — every locked decision (D-04 no new module, D-05 frozen wire contracts, D-06 offline gate) points the same direction: apply tiny inline fixes at proven seams, prove zero-functional-change offline, catalogue everything else.

The single most important finding is that the codebase already contains its own canonical fix pattern. **17 edge functions re-throw a thrown auth `Response` with `if (error instanceof Response) throw error;`** before their generic 500 catch. Exactly the active flows that **lack** that one line are the ones that swallow `requireAuth`'s thrown 401 into a misleading 500 — which is precisely the SB-05-04 class (D-02 code-evident). I re-confirmed SB-05-04 at HEAD and found **two sibling instances** of the identical bug (`recruiting-lens`, `compare-jobs`). That is the spine of RUN-04: a one-line, behavior-preserving, byte-frozen-wire fix replicated at three sites, each behind an operator checkpoint.

The advisory leg is read-only triage via the connected MCP servers. The DB-class advisories (RLS-disabled, function `search_path` mutable, security-definer views, unindexed FKs, multiple permissive policies, auth-rls-initplan) are **all routed to Phase 8** per D-08 — 7.1 only catalogues them and notes a generated-but-unapplied migration where obvious (the known `linkedin_grades` RLS item). The only advisory classes that *could* yield a 7.1 code fix are non-DB runtime/auth-config classes (leaked-password protection, MFA options, the Interview-Prep 503 platform-routing landmine) — and most of those route to `manual-action` / `needs-operator`, not code.

**Primary recommendation:** Make RUN-04 the load-bearing code wave — replicate the existing `if (error instanceof Response) throw error;` guard at the three swallow sites (interview-prep-analyze, recruiting-lens, compare-jobs), each as an isolated `autonomous:false` checkpoint, with the inline `errorCode`-in-logs taxonomy (D-04/D-05) added at the same sites. Treat advisory triage as a read-only cataloguing wave that routes DB-class to Phase 8 and platform-class to operator-action. Gate every change with offline `verify:baseline` (vitest 457 / deno 699-0-11 / Playwright 4pass+1skip+1 documented env-red) and defer the live deploy-smoke as a RESIDUAL-REGISTER residual.

### Pattern 1: The auth-Response re-throw guard (the canonical fix, already in-repo)

**What:** `requireAuth(req,{type:'user'})` THROWS a `Response(401)` on failure (auth.ts:90/99/112). When that call sits *inside* a function's top-level `try`, a generic `catch (err)` that builds a 500 will **catch the thrown 401 Response and convert it into a misleading 500** — unless the catch first re-throws Responses.

**When to use:** Any active flow whose top-level catch returns a generic 500 AND whose `requireAuth` is inside that try.

**Reference (the correct shape — `analyze-skills-gap/index.ts:286-292`):**
```typescript
// Source: supabase/functions/analyze-skills-gap/index.ts (HEAD, verified 2026-06-23)
  } catch (error) {
    if (error instanceof Response) throw error;   // ← the one line the swallow sites lack
    console.error('Error in analyze-skills-gap function:', error);
    return new Response(
      JSON.stringify({ error: error instanceof Error ? error.message : 'Unknown error' }),
      { status: 500, headers: { ...corsHeaders({ type: 'user' }), 'Content-Type': 'application/json' } }
    );
  }
```
17 functions already carry this guard (verified grep: analyze-resume:1045, analyze-career:1806, grade-linkedin:872, analyze-skills-gap:287, chat-agent:79, process-resume-analysis-job:413, process-career-analysis-job:302, interview-prep-evaluate:345, and the 9 email/notify/keep-warm functions). The fix is to **replicate this existing one-liner** — not invent anything.

### Pattern 2: Inline errorCode taxonomy (D-04 / D-05)

**What:** A small per-function `const` mapping the criterion-3 categories to short stable strings, used (a) ALWAYS in the structured `log.warn/error(..., { errorCode })` call, and (b) in the JSON body ONLY for a brand-new fail-closed guard response.

**Example (inline, no shared module):**
```typescript
// Per-function local — NOT a _shared import (D-04)
const ERR = {
  AUTH: 'unauthorized',
  INVALID_INPUT: 'invalid_input',
  MISSING_CONFIG: 'missing_config',
  AI_PROVIDER: 'ai_provider_error',
  DB: 'db_error',
  EXTRACTION: 'extraction_failed',
  RATE_LIMIT: 'rate_limited',
  INTERNAL: 'internal_error',
} as const;

// (a) ALWAYS in logs (observability — D-05):
log.error('unhandled-error', { errorCode: ERR.INTERNAL, error: (err as Error).message });

// (b) in BODY only for a NEW guard (D-05) — never on an existing 401/402/429:
return new Response(
  JSON.stringify({ error: 'internal_error', errorCode: ERR.INTERNAL,
                   message: 'An unexpected error occurred. Please try again.' }),
  { status: 500, headers: { ...corsHeaders({ type: 'user' }), 'Content-Type': 'application/json' } },
);
```
Note the EXISTING generic 500 bodies already use `{ error: 'internal_error', message: ... }` (interview-prep-analyze:716, recruiting-lens:765) — adding `errorCode` to a brand-new fail-closed guard is additive; adding it to the *existing* 401/402/429 contracts is forbidden (D-05).

### Pattern 3: Safe structured-log field plan (RUN-05 allow-list)

**What:** Emit only the criterion-5 allow-listed fields through `createLogger`. The codebase already does this well — `log.warn('auth-failure', { reason, type, userId })` (auth.ts), `log.info('merit-transaction', { user_id, feature, transaction_id, deducted_from, remaining_balance })` (merit-gateway). The 7.1 addition is `errorCode` (+ `retryable`/`stage` where missing).

**Allow-list (emit):** `feature`, `stage`, `userId`/`user_id` (when available), `tier`, `provider`/`model`, merit `amount`/`transaction_id`/`deducted_from`/`remaining_balance`, `retryable`, `errorCode`, `durationMs`, `reason` (a reason-code, never a secret).
**Deny (never emit):** resume/LinkedIn text, prompts/`messages`, `ANTHROPIC_API_KEY`/any secret, payment data (card/intent/customer PII), raw provider payloads (`raw`/`data` from `invokeAnthropicText`).

### Anti-Patterns to Avoid

- **Introducing `_shared/errors.ts`** — forbidden by D-04. Phase 4 deleted exactly this file pair; re-adding it is a blast-radius violation and a deferred Phase-9 item.
- **Touching merit/refund control flow** — D-03. `withMerits`'s refund firing conditions (`isRefundableAnthropicError`, the `MeritRefundable` catch) are the single easiest place to cause an accidental functional change. Log-field adds only, and only behind an operator checkpoint.
- **Mutating an existing parsed error body** — D-05. `AiCreditsContext` parses 402 `{error,resetDate,tier}` and the 429 shape byte-for-byte. Adding `errorCode` there is a wire change.
- **`catch { /* ... */ }` that drops a write error silently on an active flow** — but note the existing intentional swallows (merit-gateway:171 cache-hit usage-row write; the `writer.close()` `/* already closed */` in analyze-resume) are deliberate and documented — do NOT "fix" them.
- **Logging a raw provider payload to debug a parse failure** — RUN-05 deny-list. Log `errorCode` + a length/shape, never the body.

## Common Pitfalls

### Pitfall 1: The `requireAuth`-throws-Response swallow (SB-05-04 class) — the central finding
**What goes wrong:** A thrown 401 becomes a generic 500 with a misleading body. The client sees `internal_error` (or a leaked `err.message`) instead of `Unauthorized`; the 401 wire contract is silently violated and the failure is mis-attributed to the handler.
**Why it happens:** `requireUserAuth` THROWS `Response(401)` (auth.ts:90/99/112) rather than returning null; when the call is inside the top-level `try`, a generic `catch` that doesn't re-throw Responses catches it.
**Confirmed sites at HEAD (2026-06-23):**
| Function | Auth call | Top-level catch | Has `instanceof Response` re-throw? | Verdict |
|----------|-----------|-----------------|-------------------------------------|---------|
| `interview-prep-analyze/index.ts` | `requireAuth` :164 (in try) | :710 → 500 `{error:'internal_error'}` | **NO** | SB-05-04 — re-confirmed. (The `if(!userContext)` null-check at :165-167 is DEAD — `requireUserAuth` never returns null, it throws.) |
| `recruiting-lens/index.ts` | `requireAuth` :490 (try opens :449) | :761 → 500 `{error:'internal_error'}` | **NO** | Sibling instance — Elite-gated active flow. |
| `compare-jobs/index.ts` | `requireAuth` :57 (try opens :56) | :329 → 500 `{error: err.message}` | **NO** | Sibling instance — ALSO leaks `error.message` into the 500 body (RUN-05-adjacent). |
**How to avoid:** Add the one existing-pattern line `if (error instanceof Response) throw error;` as the first statement of each top-level catch. The thrown 401 then propagates unchanged → the frozen `{error:'Unauthorized'}` 401 reaches the client. Behavior on the *success* path is byte-identical; only the *auth-failure* path stops being mis-reported. Each is an `autonomous:false` checkpoint (D-01).
**Warning signs:** A generic 500 catch in a function that calls `requireAuth` inside its try and does NOT grep-match `instanceof Response`.

### Pitfall 2: Mistaking a platform-routing failure for a handler bug (Interview Prep 503)
**What goes wrong:** Treating the Interview-Prep 503 (CONCERNS §1) as a code defect and "fixing" handler code that is not the cause.
**Why it happens:** The 503 has TTFB ~8.91s **after** a *successful* Claude call — it is a Supabase platform router timeout / response-size / cold-start-on-egress issue, NOT handler logic. Interview Prep is also gated off prod.
**How to avoid:** Catalogue it as a **preview-only, low-priority** register entry routed to `manual-action` / `needs-operator` (operator pulls Supabase router logs), NOT a code fix. It is a reminder that some "runtime failures" live at the platform layer.

### Pitfall 3: Accidentally changing merit/refund firing conditions
**What goes wrong:** "Improving error handling" on `withMerits` changes which errors refund (e.g. broadening `isRefundableAnthropicError`, or catching a throw that should propagate) → a real economic behavior change.
**Why it happens:** The refund classification is subtle (5xx/529/408/AbortError refundable; 4xx/parse/sanitizer NOT) and the `MeritRefundable` re-throw is load-bearing.
**How to avoid:** D-03 — triage + catalogue only; the ONLY allowed merit-path edit is a safe structured-log field add (no control-flow, no payment data), behind an operator checkpoint. The Phase-5 `merit-*.test.ts` corpus is the offline proof that a touched merit path didn't change behavior.

### Pitfall 4: Leaking sensitive data into logs while "making logs useful"
**What goes wrong:** Adding a `log.error('parse-failed', { raw: ai.text })` or `{ messages }` to debug — leaking resume text / prompts / provider payload.
**Why it happens:** The natural instinct when hardening a parse/extraction path is to log the offending content.
**How to avoid:** Allow-list discipline (Pattern 3). Log `errorCode`, a length, or a `reason` code — never the content. Run the Phase-2 names-not-values secret-grep over `RUNTIME-RELIABILITY.md` before commit, and confirm no new `log.*` call passes a deny-listed field.

### Pitfall 5: Editing an existing parsed wire contract (D-05 violation)
**What goes wrong:** Adding `errorCode` to the 402/401/429 body to "standardize," breaking `AiCreditsContext` byte-parsing or requiring a deploy-smoke the paused env can't give.
**How to avoid:** errorCode goes in LOGS always; in a BODY only on a brand-new fail-closed guard. Existing 401 `{error:'Unauthorized'}`, 402 `{error,resetDate,tier}`, and the 429 shape stay byte-identical.

### Pitfall 6: Pure-ASCII `.ps1` (if any script is touched)
**What goes wrong:** A non-ASCII char (em-dash, box-drawing) in `deploy*.ps1` breaks Windows PowerShell 5.1 parsing (cp1252) — "missing terminator." Broke + fixed in Phase 5 (cf654246).
**How to avoid:** This phase is unlikely to touch `.ps1`, but if it does, keep it ASCII-only; verify `grep -c $'\xe2'` = 0.

## Generated-but-Unapplied Migration Pattern (RUN-06 / D-08)

For a DB-class advisory with an obvious fix (the known `linkedin_grades` "Anyone can view" RLS), 7.1 **authors but does not apply** a forward migration + rollback, as a Phase-8 handoff:

- **Where:** the migration file is NOT placed in `supabase/migrations/` as an applied, sequence-numbered file (that would risk a Phase-8 auto-apply / sequence collision). Author it as a **Phase-8 handoff artifact** referenced from `RUNTIME-RELIABILITY.md` — either an embedded fenced SQL block in the register's row (forward + rollback) or a clearly-marked `.planning/`-side draft. Phase 8 owns sequencing it into `supabase/migrations/` with a real timestamp.
- **How to mark unapplied:** the register row's `decision = deferred-to-Phase-8`, with `verification command` = the read-only `get_advisors`/`pg_policies` check that confirms the advisory still fires, and `rollback notes` = the inverse SQL. CLAUDE.md MCP rule 6 ("create rollback SQL for every migration") and rule 4 (no prod RLS change without confirmation) apply.
- **Content (forward + rollback skeleton, names-not-values):**
  ```sql
  -- FORWARD (Phase 8): tighten linkedin_grades SELECT to owner-only
  DROP POLICY IF EXISTS "Anyone can view linkedin grades" ON public.linkedin_grades;
  CREATE POLICY "Owners can view their linkedin grades" ON public.linkedin_grades
    FOR SELECT TO authenticated USING (auth.uid() = user_id);
  -- ROLLBACK: restore the prior (over-permissive) policy exactly as captured from pg_policies
  ```
  The exact prior policy text is captured READ-ONLY from `pg_policies` (Source C already has it) so the rollback is faithful. **7.1 does not run either statement** — prod is read-only, preview is paused.

### The offline gate (D-06) — gates every code change
`npm run verify:baseline` = `npm test` (vitest) + `npm run test:edge` (offline deno, `--no-check --allow-all`, `DENO_TEST_SUPABASE_REMOTE=0`) + `npm run test:e2e` (Playwright). It must stay green against the **known documented baseline**:

A change is zero-functional-change-proven when `verify:baseline` is green with these exact counts (vitest unchanged, deno unchanged-or-+N-for-new-guard-tests, Playwright still only the one documented stripe :56 env-red). Also prove `git diff` touches only the intended file(s) and that the **success path is byte-identical** (the swallow fix only alters the auth-failure branch).

### What a deno test for a new guard looks like
The Phase-5 corpus already has the template. `interview-prep-analyze` has a **TRUE handler-invocation** failure-branch suite (Pattern B — `handler(new Request(...))`) that pinned SB-05-04 (05-04: "400 invalid_input x2, 500 auth-swallow"). A guard test:
- Builds a `Request` with NO/invalid `Authorization` header, invokes the handler directly (the `IS_TEST=true` seam skips `serve()` — interview-prep-analyze:724), and asserts the response is **`status === 401`** with body `{error:'Unauthorized'}` (the propagated thrown Response) — replacing the current assertion that it is a swallowed 500.
- Runs offline under `--no-check --allow-all`; no Anthropic, no network (`AI_TEST_MODE`/`AI_FORCE_FAILURE` seam keeps the AI path inert).
- Is registered in the `deno.json` `test:ci` allowlist so it can't silently rot (the 04-04 orphaned-suite lesson; Phase-5 grew the allowlist 35→64 files).
- The merit/refund seams stay covered by the existing `merit-*.test.ts` / `analyze.failure-branches` corpus — the proof that a D-03-adjacent change (log-field only) didn't move refund behavior.

### Deferred-live-smoke residual mechanism (D-06)
Because preview `cimjltzovkahkqecpwgi` is PAUSED, each touched edge function owes a **live staging deploy-smoke** that cannot run offline (the `--no-check` gate does not exercise an HTTP/server path change — same logic as the Phase-6 D-04 edge-consolidation defer). Record it as an **append-only RESIDUAL-REGISTER residual** (Phase 6 **DI-06-05-01** precedent: same paused-project root cause), with: the touched function(s), the smoke to run (invoke with a bad token → assert 401 not 500), and clearance = "preview/test project un-paused, re-run the smoke." It is NOT a blocker — the offline gate + the new deno guard test carry the per-change proof; the live smoke is the deferred confirmation.
