# Phase 7.1: Runtime Error Handling, Supabase Advisory Triage & Production Reliability - Context

**Gathered:** 2026-06-23
**Status:** Ready for planning

<domain>
## Phase Boundary

This INSERTED phase hardens Strivio's **runtime reliability** under v4.0's hard constraint of **zero functional change** (no successful behavior altered). Four legs:

1. **Advisory & log triage** — inspect Supabase advisories + runtime logs **read-only** (prod via MCP; preview as implementation/validation), classify every finding into a register.
2. **Safe error taxonomy** — define a small canonical error taxonomy + safe JSON error-response pattern for active backend/Edge Function flows (the criterion-3 categories: auth, invalid input, missing env/config, merit charge/refund, PDF extraction, AI provider, DB read/write, rate limit, webhook verification, internal).
3. **Loud-not-silent failure paths** — add missing try/catch, null guards, safe fallbacks, and stage-specific internal logs to active critical flows **where they currently fail silently or fail open**, preserving successful behavior exactly.
4. **Useful structured logs** — emit the criterion-5 safe field set, never exposing resume/LinkedIn text, prompts, secrets, payment data, or raw provider payloads.

**Appetite:** surgical + operator-gated (see D-01). The phase **does** land low-risk reversible edge-function code — but only at the bar in D-02, with money paths extra-conservative (D-03).

**Critical flows in scope:** Resume Analysis, LinkedIn Grader, Career Compass, Recruiting Lens, saved-result reuse, merit charge/refund, PDF/text extraction, AI provider calls, Supabase RPC calls, relevant webhook paths, and gated Interview Prep preview/staging surfaces only if still active in repo.

**NOT in this phase (locked):** DB/RLS/schema/table/function/trigger/index/migration-heavy work → **routed to Phase 8** (with a generated-but-unapplied migration + rollback where a fix is obvious); performance/latency refactors → Phase 9; any new feature, pricing/merit/AI-routing/OCR/subscription/schema redesign; any write to production via MCP; any logging of sensitive document/prompt/payment/secret data. The shared `_shared/errors.ts` taxonomy **helper** is explicitly deferred (D-04 / `<deferred>`).

<decisions>
## Implementation Decisions

### Code-change appetite & fix bar (success criteria 4, 6)

* **D-01: Surgical, operator-gated code appetite.** The phase LANDS edge-function code fixes — but only where a critical **active** flow currently fails silently or fails open. It is **not** audit-only, and **not** a broad standardization across every in-scope flow. Each code batch passes an explicit `autonomous:false` operator checkpoint before merge (mirrors Phase 7 ENV-05 D-08). Everything that does not meet the bar is catalogued in the register + routed (Phase 8/9). Chosen over **audit+doc-only (code-free, zero src diff)** and over **broader standardization** (blast radius conflicts with zero-change + per-change deploy-smoke).

* **D-02: Fix bar = "observed OR code-evident."** A code fix is triggered when EITHER (a) a prod/preview log line or Supabase advisory shows a real failure, OR (b) the code plainly swallows/hides an error or lacks a safe fallback on an active flow — e.g. Phase 5's pinned **SB-05-04** (`interview-prep-analyze` swallows `requireAuth`'s thrown 401 into a 500). Logs prioritize order, they do not gate. Chosen over **observed-in-logs-only** (too narrow — leaves quiet-but-broken paths) and **any-code-evident-gap** (too broad — drifts past surgical).

* **D-03: Money paths are extra-conservative.** Merit charge/refund + Stripe webhook **control-flow** (the v3.0-hardened, Phase-5-characterized refund + idempotency invariants) are triaged + catalogued, but ANY control-flow/error-response change to them is held for an explicit operator-reviewed `autonomous:false` checkpoint and **never auto-applied**. Safe structured-logging field additions (no control-flow change, no payment data) ARE allowed. Chosen over **same-surgical-bar** (loses the explicit "don't touch refund control-flow" guardrail) and **logging-only-here** (defers even clearly-safe guards).

### Error taxonomy & safe response pattern (success criterion 3)

* **D-04: Documented spec, applied INLINE — no new `_shared` module.** The canonical taxonomy (errorCode strings for the criterion-3 categories + a safe JSON `{ error, errorCode }` shape) is **defined as a documented spec** in the register; where surgical fixes land it is applied **inline per-function** (a small local const + the existing `cors.ts` / response helpers). **No `_shared/errors.ts` helper is introduced.** Rationale: ENV-05's central-helper defer + Phase 4 actually **removed** the dead `_shared/handler.ts`+`errors.ts` pair, and no error helper exists in `_shared` today; a new shared module imported across many functions exceeds the surgical/zero-change bar. The shared-helper version is a **deferred Phase-9 maintainability candidate** (`<deferred>`). Chosen over **shared `_shared/errors.ts`** and **doc-spec-only-no-code**.

* **D-05: `errorCode` in logs ALWAYS + on NEW guard responses ONLY; existing wire contracts frozen byte-identical.** errorCode is always emitted to structured logs (observability/triage). It is included in a JSON **response body** ONLY for brand-new fail-closed guard responses we add (paths that today fail open/silent with no existing client contract). Existing error responses the frontend parses — **402 `{ error, resetDate, tier }`** (read by `AiCreditsContext`), **401 `{ error: 'Unauthorized' }`**, the 429 rate-limit shape, etc. — are **NOT altered** (status + fields byte-identical). Chosen over **logs-only-wire-frozen** (less useful to clients) and **additive-errorCode-everywhere** (a wire change on parsed contracts → would need per-function frontend-compat verification + a real deploy-smoke).

### Validation strategy (success criterion 7)

* **D-06: Offline `verify:baseline` gates every change; live deploy-smoke DEFERRED as a RESIDUAL-REGISTER residual.** The preview/test project `cimjltzovkahkqecpwgi` (preview ≡ staging ≡ test) is **PAUSED**, so offline `verify:baseline` (vitest + offline deno + Playwright) gates every code change and must stay green against the **known documented env-red baseline** (Playwright stripe :56). The owed **live deploy-smoke** for each touched edge function is recorded as a deferred residual in `.planning/audit/RESIDUAL-REGISTER.md` (Phase 6 **DI-06-05-01** precedent — same paused-project root cause) for the operator to run when preview is next live. Chosen over **operator-un-pause-window (full live smoke)** and the **hybrid single-function window**. (If a touched path is high enough risk, the operator may still elect a one-function un-pause window at the checkpoint — but the default does not block on it.)

### Register home & advisory routing (success criteria 1, 2, 6)

* **D-07: Register at `.planning/audit/RUNTIME-RELIABILITY.md`, INDEX-wired.** The runtime-reliability register lives in the established `.planning/audit/` catalog (alongside `DEAD-CODE.md` / `ENV-INVENTORY.md` / `DATABASE.md` / `PERF-HOTSPOTS.md` / `KEEP-LIST.md` / `RESIDUAL-REGISTER.md`), gets an `INDEX.md` row, and routes to Phase 8 like a Phase-3 consuming-phase handoff. Each reviewed advisory/log warning carries the criterion-2 fields: **source, environment, severity, affected flow, root cause (if known), decision (resolved-now / deferred-to-Phase-8 / accepted-risk / false-positive / manual-action / needs-operator), verification command, rollback notes**. **Names-not-values** discipline (Phase 2 REPO-05) governs every committed line. Chosen over **`docs/runtime-reliability-review.md`** (permanent operator doc, the `docs/ENVIRONMENT.md` precedent) and **both-with-pointer**.

* **D-08: Advisories triaged READ-ONLY in 7.1; DB-class ROUTED to Phase 8.** Supabase advisories are inspected read-only (prod via MCP) and classified into the register; every DB/RLS/schema/index/migration item is routed to Phase 8 with a **generated-but-unapplied migration + rollback** noted where a fix is obvious (criterion 6). 7.1 writes code only for **non-DB** runtime/error-handling/logging findings. Known routed item: Phase 3 flagged `linkedin_grades` "Anyone can view" RLS → **DB-05 / Phase 8**. Chosen over **also-fix-trivial-non-DB-now** and **triage-only-defer-all**.

### Claude's Discretion

* **Log redaction is already an allow-list** fixed by criterion 5 — safe fields (feature, stage, userId-when-available, tier, provider/model, merit amount, retryable, errorCode) vs forbidden classes (resume/LinkedIn text, prompts, secrets, payment data, raw provider payloads). The exact per-function field plumbing is left to planning; no deny-list/regex-redaction helper is needed (and would be deferred on blast-radius grounds if it were).
* **MCP criterion-1 mechanics:** the connected servers are **`supabase-prod-readonly`** (read-only) + **`supabasepreview`** (read-write preview only) — names differ from the ROADMAP's `supabase-prod-ro` / `supabase-preview` labels; the planner verifies connectivity + records the access model verbatim in the phase notes.
* Register schema/column set and ordering; plan/wave slicing; which functions/flows are triaged first; the precise inline taxonomy const shape; exact wording of operator-action + deferred-smoke residual entries — all left to research + planning, consistent with the decisions above.

<specifics>
## Specific Ideas

* The phase is **heavily pre-specified** by the ROADMAP (7 success criteria + MCP model + flow list + non-goals). Discussion was purely about **HOW**, and the operator consistently chose **thorough evidence + conservative action** — the same stance as Phase 7's ENV-04: act surgically, freeze every existing wire contract, treat money paths as untouchable without explicit review, and gate offline while deferring the live smoke rather than un-pausing the shared E2E env.
* The one runtime landmine on record (CONCERNS §1): the Interview Prep **503 is a Supabase platform-routing failure** (router timeout / response-size / cold-start on egress) after a *successful* Claude call — **not** handler code, and IP is gated off prod. Treat it as a low-priority, preview-only triage entry and a reminder that some "runtime failures" are platform-layer (route to manual-action / needs-operator in the register, not a code fix).
* "Improving error handling" on merit/refund/webhook flows is the single easiest way to cause an accidental functional change (a refund's firing conditions, an idempotency catch) — which is exactly why D-03 hard-gates them behind operator review.

</specifics>
