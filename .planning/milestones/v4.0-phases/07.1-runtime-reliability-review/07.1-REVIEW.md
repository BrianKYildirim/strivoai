# Phase 07.1: Code Review Report

**Reviewed:** 2026-06-24T04:00:43Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This phase implements RUN-04 (re-throw thrown auth `Response` objects through a named-handler seam) and RUN-05 (remove the `error.message` body leak in compare-jobs + add structured logging) across three Deno edge functions: `compare-jobs`, `recruiting-lens`, and `interview-prep-analyze`.

The core correctness of the change is sound and I verified it against the actual contracts rather than the comments:

- **The re-throw guard is correct and cannot swallow genuine errors.** I traced every `throw` in `_shared/`. The *only* source of a thrown `Response` is `requireAuth` (`auth.ts` lines 90/99/111/138/144/161/191, all `throw unauthorizedResponse()`). `_shared/anthropic.ts` throws nothing (returns a discriminated union), and `withMerits` *returns* `{ ok:false, response }` for handled failures and re-throws only `Error`/`MeritRefundable` instances — never a `Response`. So `if (error instanceof Response) return error;` catches auth 401s exclusively; non-auth failures still fall through to the generic 500 branch.
- **`return` (not `throw`) is the right idiom here.** All three functions are now named `handler` functions invoked via `serve(handler)`. Returning the `Response` hands it directly to std `serve`; throwing it would let std `serve`'s default `onError` mask it as a 500 — which is the exact bug being fixed. This matches the established `interview-prep-evaluate` pattern.
- **The RUN-05 leak removal is real.** I confirmed against the diff base (34f39984) that compare-jobs previously returned `{ error: error.message }` (raw upstream/internal text) in the client-facing 500 body; it now returns a generic message. The `usage_limit_reached` 429 contract, the frozen `{error:'Unauthorized'}` 401 contract, and the rate-limit/merit/SSE paths are untouched.
- **Tests genuinely exercise the behavior.** I ran the offline handler-invocation tests (`compare-jobs/auth-rethrow.test.ts`, `recruiting-lens/__tests__/auth-rethrow.test.ts`, `interview-prep-analyze/__tests__/analyze.failure-branches.test.ts`) and the static handler-config tests — all 38 pass, and the auth-reject cases actually construct `Request`s, call `handler()`, and assert `status===401` + `body.error==='Unauthorized'` (not just substring scans).

No BLOCKER-class defects were found. The findings below are a stale/misleading test-comment that actively describes the *broken* idiom (Warning, because it invites a regression), a duplicate-field/inconsistency cluster in the 500 bodies and logging (Warning + Info), and several Info-level observations including a real-but-deliberate browser-CORS consequence of the frozen 401 contract.

## Warnings

### WR-01: recruiting-lens auth-rethrow test header documents the WRONG (broken) guard idiom — `throw err` instead of `return err`

**File:** `supabase/functions/recruiting-lens/__tests__/auth-rethrow.test.ts:16`
**Issue:** The file header comment states:

> The 07.1-03 catch guard `if (err instanceof Response) throw err;` now propagates it as the frozen 401 {error:'Unauthorized'} contract...

But the actual code in `recruiting-lens/index.ts:765` is `if (err instanceof Response) return err;`. The distinction is load-bearing: because recruiting-lens is now a *named* `handler` run via `serve(handler)`, `throw err` would let std `serve`'s default `onError` convert the thrown `Response` into a generic 500 — which is precisely the masked-401 bug this phase exists to fix. The comment, taken as guidance, describes a defect. A maintainer "aligning the code to the documented idiom" would reintroduce the bug. The sibling `interview-prep-analyze` test (line 16/128) and the `compare-jobs` test (line 6) both correctly say `return err`/`return error`; recruiting-lens is the lone divergent comment.
**Fix:**
```ts
//  * Response(401). The 07.1-03 catch guard `if (err instanceof Response) return err;` now
//  * propagates it as the frozen 401 {error:'Unauthorized'} contract instead of swallowing
//  * it into a generic 500.
```

### WR-02: 500-error body carries duplicate `error` + `errorCode` fields, both set to the same literal — silent wire-contract drift for clients keying on `error`

**File:** `supabase/functions/compare-jobs/index.ts:339`, `supabase/functions/recruiting-lens/index.ts:768`, `supabase/functions/interview-prep-analyze/index.ts:720`
**Issue:** The new 500 bodies are `{ error: 'internal_error', errorCode: 'internal_error', message: ... }`. `error` and `errorCode` are redundant (identical value). More importantly, this changed the shape of the client-facing body without a documented contract: pre-change, the body was `{ error: 'internal_error', message: ... }` (recruiting-lens / interview-prep) or `{ error: <leaked message> }` (compare-jobs). Adding `errorCode` is harmless additively, but it sets a precedent where two fields must be kept in sync, and no test asserts they match. If a future change sets `error` and `errorCode` to different values (e.g. a more specific `errorCode`), any frontend still keying on `error` silently diverges. Either collapse to a single canonical field or document the two-field contract and add an assertion. The handler-config tests assert `error: 'internal_error'` and `errorCode: 'internal_error'` independently but never assert they are equal, so drift would not be caught.
**Fix:** Prefer one canonical field. If both must stay for back-compat, document why and pin the invariant:
```ts
// keep a single source of truth for the code
const ERR = 'internal_error';
return jsonResponse({ error: ERR, errorCode: ERR, message: 'An unexpected error occurred. Please try again.' }, 500);
```

## Info

### IN-01: Inconsistent error-log shape across the three catch blocks — compare-jobs drops `stack`, the other two keep it

**File:** `supabase/functions/compare-jobs/index.ts:337` vs `supabase/functions/recruiting-lens/index.ts:766` and `supabase/functions/interview-prep-analyze/index.ts:714-718`
**Issue:** The phase context asks for "consistency of the same fix across the three functions." The structured `log.error('unhandled-error', ...)` payloads diverge: compare-jobs logs `{ errorCode, error }` (no `stack`), while recruiting-lens and interview-prep-analyze log `{ errorCode, error, stack }`. `stack` is server-side log only (not in the client body) so there is no leak, but the asymmetry means compare-jobs loses the most useful field for diagnosing the genuine-500 path this phase is meant to harden. Recommend including `stack` in all three (or omitting from all three) for a uniform operator experience.
**Fix:** Add `stack: (error as Error).stack` to the compare-jobs `log.error` call to match the other two.

### IN-02: compare-jobs structured-log message key is `'unhandled-error'` but recruiting-lens uses `'Unhandled error'` — log-filtering inconsistency

**File:** `supabase/functions/compare-jobs/index.ts:337` and `supabase/functions/interview-prep-analyze/index.ts:714` (`'unhandled-error'`) vs `supabase/functions/recruiting-lens/index.ts:766` (`'Unhandled error'`)
**Issue:** Two of the three functions emit the structured event `msg: 'unhandled-error'`; recruiting-lens emits `msg: 'Unhandled error'` (capitalized, spaced). Operators filtering Supabase logs by `msg` for the unhandled-500 path must now match two different strings. The recruiting-lens handler-config test even hard-codes the divergent form (`source.includes('Unhandled error')`, handler-config.test.ts:110), so it is pinned. Low impact, but it undercuts the "same fix across three functions" goal.
**Fix:** Standardize on `'unhandled-error'` in recruiting-lens (and update the handler-config assertion accordingly).

### IN-03: Pre-existing `console.log`/`console.error` calls remain in compare-jobs legacy path despite a `log` instance now being in scope

**File:** `supabase/functions/compare-jobs/index.ts:189, 196, 317, 325`
**Issue:** RUN-05 lifted `console.error` out of the *catch* block in favor of structured `createLogger`, but the legacy non-merit path still uses native `console.log`/`console.error` (e.g. `console.log('Usage limit reached for user:', userId)` at line 189, `console.error('AI gateway error:', ...)` at line 317). The project convention (CLAUDE.md "Logging") is structured `createLogger` for edge functions, and a `log` instance is now created at line 57, making these conversions trivial. These lines are pre-existing and outside the literal RUN-05 catch-block scope, so not a regression — noted as a cleanup opportunity the phase made cheap. Note line 189 also logs a raw `userId` (PII-adjacent) to stdout.
**Fix:** Convert to `log.info(...)` / `log.error(...)` with reason codes; avoid logging raw `userId` in the clear.

### IN-04: Deliberate but real consequence — the frozen 401 body carries NO CORS headers, so browsers see an opaque/blocked response on auth failure

**File:** `supabase/functions/_shared/auth.ts:48-53` (propagated unchanged by `compare-jobs/index.ts:335`, `recruiting-lens/index.ts:765`, `interview-prep-analyze/index.ts:712`)
**Issue:** `unauthorizedResponse()` returns `new Response(..., { status: 401, headers: { 'Content-Type': 'application/json' } })` — no `Access-Control-Allow-Origin`. Pre-RUN-04, compare-jobs/recruiting-lens *swallowed* this 401 and returned a 500 that *did* carry `corsHeaders({ type:'user' })`, so the browser could read the (wrong, leaky) body. Post-RUN-04 the bare, CORS-less 401 reaches the browser directly; cross-origin JS will see a CORS-blocked/opaque response and cannot read `{error:'Unauthorized'}`. This is the documented "frozen 401 contract" and is consistent with the rest of the codebase (interview-prep-analyze/evaluate already behaved this way), so it is NOT a defect introduced by this phase — but it is a real behavioral consequence worth recording: a 401 from these endpoints is observably a network/CORS error in the SPA, not a readable 401 JSON. If the frontend relies on reading the 401 body for these three features, that path regressed from "readable 500" to "opaque 401." Consider adding `corsHeaders` to `unauthorizedResponse()` (a shared, one-line fix that would benefit every consumer) so auth 401s are readable cross-origin.
**Fix:** In `_shared/auth.ts`, build the 401 with user CORS headers (out of this phase's scope, but the cleanest place):
```ts
function unauthorizedResponse(): Response {
  return new Response(JSON.stringify({ error: 'Unauthorized' }), {
    status: 401,
    headers: { ...corsHeaders({ type: 'user' }), 'Content-Type': 'application/json' },
  });
}
```

### IN-05: Dead defensive `if (!userContext)` 401 branch in interview-prep-analyze is unreachable for `type:'user'`

**File:** `supabase/functions/interview-prep-analyze/index.ts:165-167`
**Issue:** After `const userContext = await requireAuth(req, { type: 'user' })`, the code checks `if (!userContext) return jsonResponse({ error: 'Unauthorized' }, 401)`. For `type:'user'`, `requireUserAuth` is typed `Promise<UserContext>` and always throws on failure (never returns null), so this branch is unreachable dead code. It is harmless (and recruiting-lens chose the alternative `userContext!` non-null assertion for the same invariant), but the two functions express the same guarantee two different ways. Not a bug; consistency note. Leave as-is or unify on the `!` assertion to signal the invariant explicitly.
**Fix:** Optional — remove the dead branch or add a comment that it is defensive-only, to prevent a reader assuming `requireAuth` can return null for users.
