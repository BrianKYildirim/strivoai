## Skipped Issues

### IN-04: frozen 401 body carries no CORS headers (shared `unauthorizedResponse()`)

**File:** `supabase/functions/_shared/auth.ts:48-53`
**Reason:** skipped — out-of-scope shared-helper change with unacceptable blast radius and no test coverage. `unauthorizedResponse()` is the single 401 factory thrown by `requireAuth` for ALL THREE auth types (`user`, `internal`, `webhook`) and is consumed by **31 edge functions repo-wide**, not just the three in this phase's scope. Internal-secret and webhook endpoints intentionally carry NO CORS headers (they are not browser-accessible — per CLAUDE.md "Internal Endpoints: No CORS headers" / fail-closed CORS). Unconditionally adding `corsHeaders({ type: 'user' })` to the shared helper would change the auth-failure wire contract for every consumer, including those where CORS absence is deliberate, and there is no test pinning the shared 401 shape — so the change would be unverified. The review itself labels this "out of this phase's scope," and the operator fix-pass guidance explicitly directs erring toward not silently broadening scope.

**Original issue:** Post-RUN-04 the bare, CORS-less 401 from `unauthorizedResponse()` reaches the browser directly; cross-origin JS sees a CORS-blocked/opaque response and cannot read `{error:'Unauthorized'}`. This is the documented "frozen 401 contract" and is consistent with the rest of the codebase (interview-prep-analyze/evaluate already behaved this way), so it is NOT a defect introduced by this phase — but a 401 from these endpoints is observably a network/CORS error in the SPA rather than a readable 401 JSON.

**Recommended follow-up (separate, properly-scoped change):** Open a dedicated task to add `corsHeaders({ type: 'user' })` to `unauthorizedResponse()` (or a CORS-aware variant) ONLY after: (1) auditing all 31 consumers to confirm none rely on the CORS-less 401 (especially the `internal`/`webhook` paths, which should likely keep no-CORS or use a type-aware variant), and (2) adding a `_shared/auth` test that pins the resulting 401 header shape per auth type. This benefits every browser-facing consumer at once and should be verified against preview/staging before any deploy.
