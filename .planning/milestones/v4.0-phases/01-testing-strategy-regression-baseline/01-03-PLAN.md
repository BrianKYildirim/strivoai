<threat_model>
**Surface:** E2E specs that drive real auth/session + real Stripe test mode against a TEST Supabase project; service-role key used in `global-setup.ts`.

**Threats considered (ASVS L1):**
- **Service-role key reaching the browser (T-03-01, HIGH if violated).** `global-setup.ts` uses `SUPABASE_TEST_SERVICE_ROLE_KEY` — it runs in the Node/Playwright process ONLY, never in page context. Mitigation: the key is read from `process.env` in `global-setup.ts` and is NEVER passed to `page.evaluate`, `page.addInitScript`, or any browser-visible surface; the preview build uses only the anon key. Acceptance criteria assert the service-role key never appears in any `.spec.ts` or in page context. Mitigated.
- **Real session tokens committed via storage state (T-03-02, MEDIUM).** `.auth/user.json` holds a live session. Mitigation: `.auth/` is gitignored (Plan 02 Task 1); specs reference it via config, never inline its contents.
- **AI_TEST_MODE shippable to prod (T-03-03, MEDIUM).** The stub is enabled by a Supabase function secret on the TEST project ONLY (user_setup). Mitigation: documented as TEST-project-only; production deploy scripts (`deploy-production.ps1`) are NOT touched and must never set `AI_TEST_MODE`. Note this guard in the SUMMARY for Plan 04's strategy doc.
- **Stripe anti-automation vs. blocking gate (T-03-04, HIGH — needs operator decision).** Stripe officially documents anti-automation on the embedded Payment Element (01-RESEARCH.md Pitfall 4). A full card-submit (`4242…`) in the blocking gate can be CI-flaky. The robust blocking assertions are clientSecret + iframe-mount + reconcile. The card-submit happy path is quarantine-eligible. Because the BLOCKING gate's scope (does "Stripe checkout green" require the automated card submit, or just integration-proven?) is a product/risk decision, this plan includes a `checkpoint:decision`. → `autonomous: false`.

**Residual HIGH:** T-03-04 is gated to an operator decision (checkpoint) rather than silently assumed. `autonomous: false`.
</threat_model>
