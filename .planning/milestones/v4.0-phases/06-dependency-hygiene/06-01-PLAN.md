<threat_model>
Supply-chain / integrity-shaped threats for a removal + declare wave under zero-functional-change.

- T-06-01 (over-removal regression): removing a dependency that has a live but non-obvious consumer (dynamic string-path / `.ps1` / worker import) turns the build or `verify:baseline` RED, or silently breaks a runtime path the offline net can't see. Mitigate: re-run `npm run audit:deps` + knip at HEAD (D-06), then the explicit zero-reference `rg` sweep over `src`+`supabase`+`scripts`+`e2e`+root configs for each of the 4 candidates BEFORE deletion; gate on `npm run build` + `verify:baseline`; never remove `react-pdf`/`pdfjs-dist`/`supabase`/the 14 shadcn `ui/**` false-positives (KEEP-LIST).
- T-06-02 (typosquat / wrong-package on the dotenv declare): declaring `dotenv` could pull a malicious lookalike or a major the tree doesn't already resolve. Mitigate: pin `dotenv` to the ALREADY-transitively-resolved major (`^17.4.2`, confirmed in RESEARCH §DEP-02) so `npm install` dedupes to the existing integrity-hashed copy — not a new download of an unvetted version.
- T-06-03 (lockfile integrity drift): a mid-stream `deno.lock` regen here would produce a lock a later wave invalidates. Mitigate: this wave only reconciles `package-lock.json` via `npm install`; the authoritative `deno.lock` regen + `npm ci` integrity proof is deferred to Plan 06-06 (Wave 4, strictly last) — Pitfall 6.

No HIGH findings: no production-runtime code path changes; the 4 removed packages have zero production consumers (re-confirmed). `dotenv` is dev/test-only (Playwright config).
</threat_model>
