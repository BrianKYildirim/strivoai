<threat_model>
**Over-permissive direction (what these fixes REMEDIATE):**
- `security_definer_view` x4: the 4 analytics views run as the privileged owner, bypassing the caller's RLS.
  Flipping to `security_invoker` makes them obey the caller's RLS (least-privilege).
- `function_search_path_mutable` on `ts_to_utc_date`: an attacker could shadow an unqualified reference; pinning
  `search_path = ''` closes the search-path-injection vector.
- `rls_enabled_no_policy` x3: RLS enabled with no policy is INFO-level — the explicit-deny makes the
  already-effective deny intentional.

**Inverse direction (the availability/functional-change threat this plan GUARDS against):**
- Pitfall 4 — `security_invoker` silently hides analytics rows: flipping a view to invoker changes row visibility
  to the CALLER's RLS. If a non-service-role caller reads the view, it returns fewer rows -> behavior change.
  **Mitigation: read-map each view's callers FIRST. Static evidence (this plan's research): the only caller is
  `supabase/functions/admin-merit-metrics/index.ts`, which uses `getServiceClient()` (service-role bypasses RLS
  -> the flip is invisible). No `src/**` reads any `v_*` view. If 08-01's prod read-map surfaces a non-privileged
  caller, that view's flip is DOCUMENTED accepted-risk + DEFERRED (D-02 permits).**
- Pitfall 3 — `SET search_path = ''` would break a function with unqualified body refs. **Mitigation: this plan
  pins ONLY `ts_to_utc_date` with `= ''` (its body `SELECT ($1 AT TIME ZONE 'UTC')::date` references NO schema
  objects — safe). `increment_rate_limit` (unqualified `rate_limit_counters`) is DEFERRED to Plan 08-04 with
  `= public`, NEVER `= ''`.**
- Anti-Pattern — `CREATE OR REPLACE` on a function/view backing a dependent object. **Mitigation: use
  `ALTER FUNCTION ... SET` (ts_to_utc_date backs `idx_benchmarks_unique_per_day`) and `ALTER VIEW ... SET` (avoids
  the May-2025 dashboard "missing security_invoker flag" bug), NOT re-CREATE.**
</threat_model>
