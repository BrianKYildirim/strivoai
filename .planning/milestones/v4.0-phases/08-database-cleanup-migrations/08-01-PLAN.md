<threat_model>
This DB phase's threat surface is RLS/least-privilege itself, modeled in BOTH directions:

**Over-permissive direction (the security risk this plan SCOPES, does not yet fix):**
- linkedin_grades cross-user SELECT (`USING (true)`, role `public`) — exposes every user's LinkedIn grade.
- anon/authenticated EXECUTE on SECURITY DEFINER RPCs (the x60 grant subset).
- mutable function search_path (search-path injection on `increment_rate_limit` / `ts_to_utc_date`).
- SECURITY DEFINER views bypassing invoker RLS (the 4 analytics views).

**Inverse direction (the availability/functional-change threat this plan GUARDS against):**
- Acting on WRONG-PROJECT evidence: the load-bearing risk is treating the preview-sourced Phase 3 catalog as
  prod truth. A migration authored against the wrong policy name/qual would either no-op silently (name mismatch)
  or — worse — author a rollback that restores a policy prod never had. **Mitigation: this plan re-pulls true
  prod evidence FIRST and re-derives every verdict before any DDL is authored.**
- Dropping `saved_jobs` because it was "absent" — absence is a preview-drift artifact, not a removal target.
  **Mitigation: D-07 — reconcile by what TRUE prod shows, NEVER a destructive drop.**

**This plan applies NO DDL and changes NO grant.** It is the read-only evidence precondition. The threat it
neutralizes is the wrong-evidence trap that would make every later migration's zero-change claim unprovable.
</threat_model>
