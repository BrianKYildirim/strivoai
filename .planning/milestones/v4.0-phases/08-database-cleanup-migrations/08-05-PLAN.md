<threat_model>
**Over-permissive direction (what these revokes REMEDIATE):**
- `anon_security_definer_function_executable` x30 + `authenticated_security_definer_function_executable` x30:
  anon/authenticated can EXECUTE SECURITY DEFINER RPCs. Most are intentional defense-in-depth (the `admin_*` RPCs
  self-guard on `has_role`), but any UNINTENDED grant on a definer RPC is a privilege-escalation surface.

**Inverse direction (the availability/functional-change threat — the dominant risk of this wave):**
- Pitfall 5 / D-03 — revoking EXECUTE on a LIVE RPC breaks live callers. **Mitigation: per-function read-map.
  `can_perform_ai_action`'s authenticated EXECUTE is load-bearing — confirmed live at `src/components/Navbar.tsx:109`
  and `src/pages/SkillsGapAnalysis.tsx:108` (PostgREST RPC). Revoking authenticated EXECUTE on it WOULD break those
  calls -> NEVER revoke it. Revoking `anon` on auth-required pages is likely safe but must still be proven. Each
  RPC's callers are mapped with `rg "\.rpc\('<fn>'" src supabase/functions`; revoke ONLY the provably-unused;
  everything else ships generated-but-UNAPPLIED + gated. Expect MANY deferred.**
- The inverse risk dominates here, so the bar is: a grant is revoked ONLY when a live caller depending on it is
  PROVABLY absent (zero non-service-role `.rpc('<fn>')` call-sites). Doubt -> gate, never revoke.

**No perf-class change in this plan** (auth_rls_initplan / multiple_permissive_policies / unused_index are
Phase 9). Those are documented + routed, not applied — applying them is out of the zero-observable-change /
security-only appetite (D-02).
</threat_model>
