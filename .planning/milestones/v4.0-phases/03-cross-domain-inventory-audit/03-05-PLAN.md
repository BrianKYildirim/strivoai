<threat_model>
**ASVS L1 — the live PROD DB access is the real security surface; least-privilege READ-ONLY + operator-gating is the control.**
- Threat T-3-09: an autonomous or write-capable connection to PROD during an audit could mutate production data (zero-functional-change violation) or expose data. Mitigation (D-10, binding): the live leg is OPERATOR-GATED — this plan does NOT open a prod connection. It delivers a `.sql` pack containing ONLY read-only catalog/stat SELECTs (`information_schema`, `pg_catalog`, `pg_stat_*`, `cron.job`, `pg_extension`) — ZERO INSERT/UPDATE/DELETE/DDL. The operator runs it against the prod SQL editor / psql with read creds and pastes results back. The SQL file header states "ZERO writes" explicitly.
- Threat T-3-10: a prod connection string / credential leaks into a tracked file. Mitigation (snapshot-legacy-tables.ps1 analog): the prod ref/conn is an OPERATOR-supplied input at run time (Open Question 2), never committed; the SQL pack contains no connection string; DATABASE.md records the conn as "(redacted)" / by env name only, never the value.
- Threat T-3-11: reading a low/zero `pg_stat_*` count as definitive "unused" (Pitfall 5). Mitigation (D-11): record `stats_reset` timestamp alongside counts; treat zero-usage as corroborating, never sole, evidence; if `pg_stat_statements` is absent, say so explicitly.
- Threat T-3-12 (DB-02 false positive): classing a gated/live structure (Paddle columns, cron-invoked functions, usage_tracking still-read) as `safe` → Phase 8 drops a live structure. Mitigation: KEEP-LIST cross-ref + D-08 confirmed dependency maps; usage_tracking and Paddle remnants are recorded with their reader/writer maps and classed `needs-investigation`/gated, never `safe`.
- This plan writes ONLY the `.sql` pack + DATABASE.md under `.planning/`. No migration is added/edited; no DB is written. No HIGH-severity threat remains unmitigated.
</threat_model>
