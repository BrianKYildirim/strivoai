<objective>
Build the fire-and-forget diagnostics ingest endpoint (D-11) and register it in all three places this repo requires, so client failure records reach `client_error_diagnostics` without any user flow ever being able to notice.

Purpose: D-11 chose Postgres over console logs because the phase's operative question is a cross-fleet aggregation. XLOG-02's "never logs user documents" only becomes a guarantee when the drop happens server-side; a client-side sanitizer is a promise.
Output: `supabase/functions/log-client-diagnostic/` with a Deno test, plus registration in `supabase/config.toml`, `scripts/deploy.ps1` and `supabase/functions/deno.json`.

This plan ships no frontend code. The client seam is plan 03-06.
</objective>

<threat_model>
- **Spoofing (the endpoint is identity-optional).** Anyone can POST. A client-asserted `user_id` would make the table's identity column meaningless and invite misuse later. Mitigation: `user_id` is derived ONLY from a verified `Authorization` header via `requireAuth`; if the header is absent or invalid the row stores `user_id` NULL. A `user_id` in the request body is dropped because it is deliberately NOT on `ALLOWED_FIELDS`.
- **Flooding / DoS / cost.** A public write endpoint invites a flood that fills the table and burns quota. Mitigation is layered because no single layer suffices: a 4 KB body cap read before parsing; `checkRateLimitByKey` on a truncated, date-salted IP hash (60 per hour); the client-side per-session emit cap and single in-flight slot in plan 03-06; and D-13's failures-only rule so baseline volume scales with breakage, not traffic. **Modelled residual risk:** `checkRateLimitByKey` FAILS OPEN on a DB error (`_shared/rate-limiter.ts`), so during a database incident the limiter is a no-op. That is the correct posture for diagnostics (never fail the user flow) but it is a real hole; the body cap and the schema's lack of free-text columns bound the damage, and the operator-run retention DELETE is the cleanup path.
- **PII leak.** The whole point of XLOG-02. A client bug, a future contributor, or a malicious poster could attach resume text, a filename, a stack, or a raw error message. Mitigation: an explicit `ALLOWED_FIELDS` list — every key not on it is DROPPED, not sanitized — plus a 512-char clamp on every string, plus `error_category` coerced into a closed set with `unexpected` as the fail-closed default, plus a schema (plan 03-01) with no column such content could land in.
- **Information disclosure through the response.** Returning 429/400/500 tells a prober whether their payload stored, what the size cap is, and whether they are limited — and would let a client branch on diagnostics outcomes, which D-11 forbids. Mitigation: return 204 unconditionally, including for a rate-limited beacon. This is a deliberate divergence from `createRateLimitResponse()` (which returns 429); document it in the file.
- **CORS drift.** Hand-written headers would break the `_shared/cors-audit.test.ts` drift guard and could accidentally open the endpoint to any origin. Mitigation: `withCors(req, 'user', handler)` only. Transport nuance worth stating in the file: a `text/plain` sendBeacon is a simple request, so a CORS *response* cannot block the send — the allowlist, not CORS, is the real control here.
- **Silent non-deployment / silent non-testing.** A function missing from `scripts/deploy.ps1 $Functions` is never deployed, silently; `deno.json test:ci` is an explicit file list, so an unlisted test runs in no lane at all. Both failures are invisible on a green gate. Mitigation: all three registrations are acceptance criteria with concrete `rg` assertions.
- **Ships with a SyntaxError.** In this repo an edge function can ship broken while `verify:baseline` stays green unless the module is actually parsed. Mitigation: `deno task check` (which is `deno check */index.ts`) covering the new directory is an explicit acceptance criterion.
</threat_model>

    2. Any method other than POST returns 204 immediately. OPTIONS never reaches the handler — `withCors` owns it.

    6. `checkRateLimitByKey` with key `diag:` plus the ipHash, limit 60, window 3600. When not allowed, return 204 — silently dropped, never 429. Add a comment naming this as a deliberate divergence from `createRateLimitResponse()` and citing D-11.
    7. Build the row by iterating a module-scope `ALLOWED_FIELDS` const array (never by iterating the body), containing exactly: `event_id`, `app_version`, `surface`, `lifecycle_stage`, `error_category`, `error_name`, `script_origin`, `browser`, `browser_version`, `os`, `os_version`, `device_type`, `engine`, `viewport_w`, `viewport_h`, `dpr`, `is_extension`, `capability_tier`, `online`, `connection_type`, `user_agent`, `run_id`.
