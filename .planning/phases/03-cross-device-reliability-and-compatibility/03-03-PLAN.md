<objective>
Stand up the five-project Playwright device matrix and wire it into `verify:baseline`, so the rest of the phase has a real observation apparatus rather than assumptions (D-22, matrix-first discovery).

Purpose: `playwright.config.ts` is chromium-only at HEAD — that single fact is the core XTEST-01 gap and the reason every cross-engine defect in this codebase has been invisible. Everything in waves 2 onward is measured by this lane.
Output: 5 projects (+2 opt-in real-browser channels), an `@xdev` tag convention, a seed spec proving the lane executes and can fail, `verify:baseline` wiring, and a measured wall-clock number.

Scope guard: this plan does NOT author the discovery specs (plan 03-05) and does NOT touch `playwright.prod.config.ts`.
</objective>

<threat_model>
- **A vacuous green lane (the dominant risk).** A matrix that runs zero tests on four of five projects reports green forever and provides false assurance — exactly the 09-09 rot recorded in TESTING-STRATEGY.md. Mitigation: a seed `@xdev` spec plus a mandatory mutation proof — deliberately break the assertion, confirm all five projects report a failure, restore, confirm green.
- **Gate bypass through slowness.** D-02's entire rationale is that a gate that gets slow gets skipped with `-SkipVerify`, which disables the seven-layer precondition before every deploy. A 5x e2e blow-up would do exactly that. Mitigation: per-project `grep` restricting the four added projects to `@xdev`, plus a measured hard budget of ≤ +3 min, with the documented remedy being to cut tests from the subset rather than drop a project.
- **Credential/session leakage across engines.** All five projects reuse one `storageState` produced by a single chromium `setup` run. If that file ever contained a production session it would now be replayed into four more browser profiles. Mitigation: the config already loads `.env.test.local` with `override: !CI` specifically so an ambient production `VITE_*` cannot leak into the test build — this plan must not weaken that, and must not hardcode any URL, key or password.
- **Real-channel projects breaking CI.** `channel: 'msedge'` throws at launch when Edge is absent (CI Linux, the operator's Mac). An unguarded channel project turns the whole gate red for an environment reason. Mitigation: the channel projects are appended only when an explicit opt-in env var is set, so absence is the default and the failure mode is "not run", never "red".
- **Money-path amplification.** Adding the matrix to `playwright.prod.config.ts` would run real analyses on real accounts five times, multiplying real Merit spend and destroying the one-job/one-charge evidence that config exists to produce. Mitigation: an explicit acceptance criterion that `playwright.prod.config.ts` is byte-unchanged.
- **Flake as a trust solvent.** Cross-engine timing differences produce flakes; a flaky blocking gate gets bypassed, which is the same failure as slowness. Mitigation: the seed spec asserts a structural, non-timing property (the app boots and the document has no horizontal overflow at a fixed viewport), and any flake found during the mutation proof must be fixed or the test cut — never retried away.
</threat_model>
