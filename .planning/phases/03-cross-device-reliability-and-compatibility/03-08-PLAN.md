<objective>
Fix the highest-value single defect in this phase: the Supabase auth storage override that both white-screens the app on a `SecurityError` and disables the library's own restricted-storage fallback (XDEV-04).

Purpose: `src/lib/supabaseClient.ts` passes `storage: typeof window !== 'undefined' ? localStorage : undefined`. That guard protects against SSR, not against restricted storage — and it does two kinds of damage. The bare `localStorage` reference is evaluated at module scope, so a `SecurityError` on property access (Chrome with site data blocked, some managed profiles) throws during module evaluation and nothing renders. And because `settings.storage` is truthy, `GoTrueClient` never calls `supportsLocalStorage()` and never installs `memoryLocalStorageAdapter`, so Safari private browsing degrades into a logout loop instead of an in-memory session.
Output: the override deleted, a separate diagnostic probe, and a five-project regression test that reproduces both failure modes.

Scope guard: the user-facing `CLIENT_STORAGE_BLOCKED` copy and card are Surface C/B work (plans 03-11 and 03-12). This plan supplies the signal and fixes the crash.
</objective>

<threat_model>
- **Session integrity regression (the real risk of this change).** Removing a storage option from an auth client is a change to where the session token lives. If the library's default resolves differently than expected, users could be silently logged out on next load, or — worse — a session could persist somewhere unintended. Mitigation: the change is a DELETION that hands control to the library's documented default, `persistSession` and `autoRefreshToken` are left untouched, and the existing `e2e/auth-session.spec.ts` plus the control case in the regression spec assert a session still survives a reload under normal storage.
- **Silent degradation to an in-memory session.** When storage is genuinely unavailable, `memoryLocalStorageAdapter` keeps the user working for the tab's lifetime but the session vanishes on reload. Left unsignalled, this reads to the user as random logouts. Mitigation: the independent probe reports `storage_blocked` to diagnostics once per session, and plans 03-11/03-12 surface the mapped `CLIENT_STORAGE_BLOCKED` message with a concrete action. Never a silent logout loop.
- **Re-implementing the probe as an attack on correctness.** A hand-rolled `StorageAdapter` would have to handle the getter throw, the write throw, quota, and partitioned storage — the library already does, memoized. A worse copy is a permanent liability. Mitigation: explicitly forbidden; the acceptance criteria assert no custom adapter object is passed.
- **Probe as a side channel.** A storage probe that writes a predictable key can be read by any script on the origin (including an extension) and used to fingerprint. Mitigation: the probe writes a single short, non-identifying key, immediately removes it, and never writes anything derived from user data or the session.
- **Token exposure in test artifacts.** The regression spec manipulates storage on an authenticated context. Logging storage contents would print a session token into CI output. Mitigation: assert only on booleans and element presence; never log storage values, cookies or headers.
- **False confidence from a green test.** If the getter-throw injection is written incorrectly the spec passes at HEAD and would keep passing after a regression. Mitigation: the spec must be shown to FAIL against pre-fix code (plan 03-05 already reproduced it) and to PASS after — both results recorded.
</threat_model>
