<objective>
Ship UI-SPEC Surface B: the in-app, token-styled capability gate that decides `supported | degraded | unbootable` from real feature detection and blocks only the money paths (XDEV-01, D-06, D-07, D-08b).

Purpose: the ES5 guard from plan 03-07 can only cover what an ES5 classic script can honestly cover. The fine-grained probes — module workers, `structuredClone`, `ReadableStream`, secure-context `crypto.randomUUID`, storage, Stripe embedding — require the bundle. This is the layer that turns "the app half-works on your browser" into an explicit, honest, non-destructive block.
Output: `capabilities.ts` with a tested probe set, `CapabilityGate.tsx` implementing B1-B4, wiring at the five AI start CTAs and both checkout entry points, and a five-project proof that degraded tier issues zero money-path network calls.

Scope guard: this plan does not create the client error taxonomy (plan 03-12) and does not touch the waiting surface (plan 03-15).

Shared-file ordering (stated explicitly because two plans now write these files): this plan (wave 5) is the FIRST writer of `src/pages/{Upload,LinkedInGrader,CareerCompass,RecruitingLens}.tsx`; plan 03-16 (wave 8, `depends_on: ["03-11", "03-14"]`) is the second writer, adding the D-29 submit guard on top. Because 03-16 declares 03-11 as a dependency, the two never execute concurrently and there is no write conflict — 03-16's Task 2 read_first already anticipates finding `BlockedAiEntryPoint` in place. `src/pages/InterviewPrep.tsx` is touched by THIS plan only; 03-16 does not include it. `src/pages/Onboarding.tsx` is 03-16's alone — it is a post-signup resume submit, not one of the five AI start CTAs, and is deliberately not gated here.
</objective>

<threat_model>
- **Blocking a browser that actually works (false positive).** An over-eager probe locks a paying Elite user out of the product they bought. This is the most expensive failure mode here. Mitigation: probe only capabilities HEAD actually uses — no `TextDecoderStream`, no `EventSource`, no `Object.fromEntries` in the fine-grained set; polyfill first per D-09 and probe AFTER polyfill install so `crypto.randomUUID` and `Map.prototype.getOrInsertComputed` are tripwires rather than gates; and `WebSocket` presence is recorded as informational only, never as a block, because realtime failure is network-shaped.
- **Allowing a browser that will fail mid-flow (false negative).** Worse for trust than a block: the user pays Merits, the run starts, extraction dies in the worker, and the ledger has a charge with no result. D-07 chose to block AI and checkout precisely to protect the Merit ledger. Mitigation: the module-worker probe (the binding constraint for document extraction) is a real behavioral probe using the option-getter technique, unit-tested against a stubbed `Worker` constructor rather than assumed.
- **Money movement behind a "blocked" UI (the XRUN-01 hazard).** A CTA that renders as blocked but still fires its handler would create a run or a Stripe session with no visible surface — the worst possible combination. Mitigation: the block returns early BEFORE any network call, and the Playwright proof counts requests to `analyze-*`, `create-checkout-session` and `create-payment-intent` and asserts zero on all five projects. Loading `js.stripe.com` is not a Strivo session-creating call and is explicitly excluded from that count.
- **A gate that was never actually wired at one of the five entry points.** If one AI page is missed, OT-4 fails there — or worse, passes vacuously because the test never located that page's CTA. Mitigation: all five pages are named in `files_modified`, in Task 3's `<files>`, and in an `rg` acceptance criterion that requires a `BlockedAiEntryPoint` reference in each of the five files; OT-4 additionally asserts a blocked-state testid is VISIBLE on each page, so an unwired page fails loudly rather than silently.
- **Accessibility trap.** Using `disabled` on the blocked CTA removes it from the tab order and announces nothing, so a keyboard or screen-reader user gets a dead control with no explanation. Mitigation: `aria-disabled="true"` with `aria-describedby` pointing at the explanation card, focus moved to the explanation heading on activation, and `role="note"` on the card.
- **Fingerprinting and information disclosure.** A capability report that enumerates exact API availability and version strings is a fingerprinting vector and leaks implementation detail into user-facing copy. Mitigation: B4 lists plain-language areas only — no API names, no probe names, no version strings; the machine-readable tier goes only to diagnostics, where the closed field set already bounds it.
- **Probe side effects.** The module-worker probe constructs a `Worker` with a `data:` URL. In a strict CSP or a hostile extension environment this can throw or, worse, leave a worker running. Mitigation: the probe is wrapped in try/catch (the option getter firing is the signal, so a throw is still informative), terminates immediately, and runs at most once per session with a memoized result.
- **Banner as an interruption.** A toast would auto-dismiss before it is read; a fixed banner would eat mobile viewport. Mitigation: B1 is in normal document flow under the navbar, `role="status"`, session-dismissible, never `destructive`, never a toast.
</threat_model>
