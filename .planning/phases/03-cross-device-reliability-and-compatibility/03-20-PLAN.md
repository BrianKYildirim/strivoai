<objective>
Publish the honest supported-browser matrix and write the eight-item completion report with its final verdict (XTEST-04, XDEV-02 closure).

Purpose: the brief makes honest reporting a first-class deliverable — the matrix must distinguish "supported" from "partially verified" and must list remaining unsupported environments explicitly rather than implying blanket coverage. D-05 sets the bar: a browser is supported only with an engine pass AND a real-device spot-check. This plan is where the phase either tells the truth about its coverage or quietly overclaims.
Output: the published matrix, a user-facing version guidance doc, the updated residual register, and the completion report with a READY / READY WITH WARNINGS / NOT READY verdict.

Scope guard: this plan writes documentation. It fixes nothing. Any defect discovered while writing goes to the register and the verdict, not into a code change.
</objective>

<threat_model>
- **Overclaiming coverage (the failure this deliverable exists to prevent).** Listing WebKit-the-engine as "Safari supported", or listing an emulated Pixel as "Android Chrome supported", produces a document that will be trusted and is wrong — and the next user-reported failure will land in an environment the matrix claimed was covered. Mitigation: D-05's two-evidence rule is applied mechanically, cell by cell, with the evidence named in each cell; any cell with one kind of evidence is "partially verified"; the matrix states in prose that WebKit is not Safari.
- **A verdict driven by effort rather than evidence.** After a long phase there is strong pressure to write READY. Mitigation: the verdict rule is stated before the verdict is chosen — any unrecorded operator-pass item, any open high-severity defect, or any gate lane never proven able to fail forces at minimum READY WITH WARNINGS; an open defect on a money path forces NOT READY.
- **Publishing a version list that reads as a promise.** D-06 chose feature detection precisely because the `getOrInsertComputed` bug shipped in current browsers, so a version number is not a guarantee. Publishing it unqualified would recreate the failure mode the phase removed. Mitigation: the list is labelled GUIDANCE ONLY in both the internal matrix and the user-facing doc, with one sentence explaining that Strivo checks capabilities rather than version numbers.
- **Documentation drift between two published surfaces.** `public/supported-browsers.html` (plan 03-07) and `docs/SUPPORTED-BROWSERS.md` can diverge, leaving the bundle-independent page saying something different from the docs. Mitigation: an explicit consistency check asserting the same floors appear in both.
- **Requirement-ID collision.** v4.0 already shipped `RUN-01..07` and `STATE.md` references `RUN-03` in that sense. Writing `RUN-*` in this report would corrupt live traceability. Mitigation: D-26 is asserted — a grep confirms no bare `RUN-0` appears in this phase's report.
- **Leaking secrets into a shipped document.** A completion report naturally wants to include environment detail and commit context. A project ref, a key fragment or a signed URL in a committed doc is a real exposure. Mitigation: names-not-values discipline — environment variables are referenced by name only; no key, token, project ref or signed URL appears anywhere.
- **Register rot at the finish line.** A residual register that was never reconciled against the final state leaves accepted risks undocumented. Mitigation: the register is walked one final time and every row gets a disposition: fixed, deferred to a named follow-up, or permanently accepted with a reason.
</threat_model>
