<objective>
Lock the instant-open checkout behavior, make it assertable on every device, and close the one remaining gap — a pending state that can spin forever (UI-SPEC Surface G).

Purpose: "Stripe checkout UI appears immediately" is an explicit operator requirement in the brief. A recent quick task shipped instant open; without a device-level assertion it will regress the first time someone adds an `await` before `setOpen(true)`. And today a checkout session that never returns a client secret leaves the user watching `Preparing secure checkout…` indefinitely with no exit.
Output: a 15000ms pending timeout, mobile viewport and safe-area correctness, a static guard on the open path, and a five-project proof with the session route stalled forever.

Scope guard: the capability-tier block on the CTA is plan 03-11's and is only asserted here. The submit-guard primitive is plan 03-16's; checkout keeps its own existing in-flight refs.
</objective>

<threat_model>
- **Double session / double charge.** Two rapid taps creating two Stripe sessions or PaymentIntents is a direct financial defect and is more likely on a touch device than a desktop, where a 300ms tap delay and a slower render widen the window. Mitigation: the existing `checkoutInFlightRef` and `inFlightPackRef` remain the mechanism and are not replaced; the spec asserts a session-creating request count of exactly 1 under rapid tap on both mobile projects.
- **Stuck pending as a payment trap.** A dialog that spins forever on `Preparing secure checkout…` blocks the user from paying and gives no signal that anything is wrong — the worst possible state on a revenue path. Mitigation: a 15000ms timeout closes the dialog and surfaces a mapped message from the frozen table. The timeout must not itself create a second session on the next attempt.
- **Provider error text reaching the user.** Stripe error objects carry codes, request ids and internal detail. Rendering them violates XRUN-06 and leaks infrastructure detail. Mitigation: every failure message comes from the frozen client taxonomy; the raw provider error goes to diagnostics under `checkout_failed` only; the leak-guard regex is asserted against the rendered dialog in both themes.
- **Instant-open regression.** The natural refactor — awaiting session creation before opening — silently reintroduces the original defect and no functional test would catch it, because with a fast network the dialog still appears quickly. Mitigation: the Playwright assertion stalls the session route INDEFINITELY, so a dialog that waits on the response can never appear; plus a static-source guard that no `await` precedes the open call.
- **Mobile clipping and scroll lock.** An embedded payment element clipped by the iOS URL bar or the home indicator makes payment impossible, and a dismissal that leaves `body` scroll locked bricks the page behind it. Both are classic device-specific defects. Mitigation: the dvh utility with a vh fallback, internal `overflow-y-auto`, safe-area bottom padding, and an explicit assertion that `document.body.style.overflow` returns to its prior value after dismissal.
- **Focus regression.** Radix moves focus into the dialog on open and returns it to the triggering CTA on close. A hand-rolled open path can break both. Mitigation: preserve Radix defaults; assert focus enters the dialog on open and returns to the CTA on close.
- **Testing against real money.** Any assertion that completes a real checkout would move real money. Mitigation: all cases stall or fail the session route; no case completes a payment; `playwright.prod.config.ts` is unchanged.
</threat_model>
