<objective>
Create the Postgres landing table for privacy-safe client device diagnostics (XLOG-01/XLOG-02), separate from Phase 02's `ai_call_telemetry` (D-12), and get it onto Preview under Claude's own hands while leaving the Production apply to the operator.

Purpose: D-11 requires Postgres persistence because the operative question — "which browser/OS combinations fail at which lifecycle stage" — cannot be answered against console logs. Nothing else in this phase can be validated until the observation apparatus exists (D-25 stage 1).
Output: One forward migration, one paired rollback, a verified Preview apply, and an operator-owned Production hand-off.

This plan writes SQL and applies it to Preview only. It ships no application code.
</objective>

<threat_model>
- **Cross-phase collision (highest practical risk).** Phase 02 owns `ai_call_telemetry` and is in flight under separate ownership. Editing that migration, its rollback, or `_shared/ai-telemetry.ts` would corrupt a concurrent workstream. Mitigation: those files are read-only templates; the acceptance criteria assert `git diff` touches neither.
- **Privilege escalation via default grants.** In this project a bare `REVOKE ALL ... FROM public` does NOT lock down a new object — `anon` and `authenticated` retain grants and a browser could read every diagnostics row through PostgREST, exposing the fleet's failure map. Mitigation: explicit `REVOKE ALL ... FROM anon, authenticated` on the table AND the bigserial sequence, plus RLS with a deny-all policy, plus a `DO $$` block that fails the migration if RLS is off or no policy exists.
- **PII leak by schema affordance.** If the schema offers a free-text column (e.g. `message`, `stack`, `filename`), a future contributor will fill it and XLOG-02's guarantee dies quietly. Mitigation: the schema is the structural backstop — there is deliberately no such column. `error_name` is the constructor name only; `user_agent` is bounded and is the single high-cardinality string.
- **Re-identification via IP.** A raw IP is PII and is also the natural rate-limit key. Mitigation: the column is `ip_hash` only, populated server-side with a date-salted, truncated hash. The schema has no `ip` column at all, so a mistake in the edge function cannot land a raw address.
- **Unbounded growth / cost.** D-13 records failures only, so volume scales with breakage rather than traffic; but a client render loop could still flood. Mitigation is layered: per-session emit cap and rate limiting live in plans 03-04/03-06; here the retention policy is documented as an operator-run DELETE, deliberately not automated (mirrors `ai_call_telemetry`).
- **Production blast radius.** An autonomous production `db push` violates this repo's access policy. Mitigation: Task 3 is a blocking human-action checkpoint; Claude is read-only on production.
</threat_model>
