<objective>
Extract the shared submit-guard primitive D-29 calls for, and route every money-path submit through it so one click starts exactly one job and exactly one Merit charge (XRUN-01, XRUN-02).

Purpose: four money-path pages call `crypto.randomUUID()` inline to build the `attemptNonce` the server uses for Merit idempotency, while `useIdempotencyKey` sits unused. That is four independent definitions of the most financially consequential behavior in the product, plus four copies of a secure-context dependency that the E2E gate structurally cannot catch because `localhost` is a secure context. D-14's own threshold for extraction is already met.
Output: `useSubmitGuard`, migration of all money-path call sites including the Elite re-run path, and a static guard that the pattern cannot regress.

Scope guard: the concurrency and re-run E2E proof is plan 03-17. Checkout's in-flight refs are plan 03-18. This plan owns the AI submit paths and the shared primitive.
</objective>

<threat_model>
- **Double charge (the highest-consequence failure in this phase).** Two rapid clicks producing two runs means two Merit debits for one user intent, on a real ledger, with a support burden and a refund path. Mitigation is deliberately two-layer per D-15: a client in-flight lock stops the second request being built at all, and the server idempotency key — unchanged and reused per D-16 — remains the only guarantee that survives a second tab, a refresh, or a restored session. The client lock alone is NOT trusted; it exists to keep the UI honest on slow devices.
- **Collapsing a deliberate Elite re-run (the opposite failure).** Over-aggressive deduplication silently swallows a re-run the user paid for, which reads as "the button does nothing" and is a revenue and trust failure. Mitigation: the primitive distinguishes a duplicate click on the start CTA (collapse) from an explicit re-run affordance after a terminal state (new attempt, new nonce). `e2e/elite-rerun-merit.spec.ts` already guards this boundary and plan 03-17 extends it.
- **A predictable or reused nonce.** If the nonce is derived from a timestamp, a counter, or a value another user could guess, two users' attempts could collide in the server's idempotency space. Mitigation: the nonce comes from `crypto.randomUUID` (with plan 03-09's guarded RFC-4122 v4 fallback from `getRandomValues`), never from `Math.random`, never from a timestamp, and never from user-supplied input.
- **Lock leak (a stuck button).** A lock that is not released on error, on unmount, or on a terminal server state leaves the CTA permanently disabled and the user unable to retry — a self-inflicted outage. Mitigation: release on terminal state, on error, and on unmount; a unit test asserts release in each case; and the lock is time-bounded so a lost callback cannot strand it forever.
- **Cross-feature lock bleed.** One shared hook used by five features could, if keyed globally, let a LinkedIn Grader run block a Resume Analysis submit. Mitigation: the lock is keyed per feature and per input identity, not globally.
- **Regression by reintroduction.** The pattern that produced this defect — an inline `crypto.randomUUID()` in a submit handler — is the natural thing to write. Mitigation: a static-source guard asserting no page under `src/pages/` calls `crypto.randomUUID()` in a submit path and that every money-path submit imports the primitive.
- **Accessibility regression on the locked CTA.** Using `disabled` while in flight removes the control from the tab order mid-interaction and announces nothing. Mitigation: `aria-disabled="true"` plus `aria-busy="true"` on the form, matching UI-SPEC D6.
</threat_model>
