<objective>
Close the platform-API gaps at source (XDEV-03) using the guarded polyfill pattern this repo already proved in production, and settle the one question that dominates the published support matrix.

Purpose: the `getOrInsertComputed` incident on 2026-07-26 is this phase's explicit template — prove the failing call site, fix at source, install in every realm, add a guard test. The same discipline now applies to `crypto.randomUUID()`, which four money-path submit handlers call unguarded to derive the `attemptNonce` that protects against double Merit charges. A throw there is not degraded UX; it aborts the submit before the request is built. It hides because `localhost` IS a secure context.
Output: a guarded `crypto.randomUUID` polyfill, a polyfill barrel installed in all three realms, a realm source guard, and a recorded finding on the Firefox floor.

Scope guard: routing the four pages through a shared submit-guard primitive is plan 03-16 (D-29). This plan makes the API exist; that plan makes the call sites share one definition.

Shared-file ordering (`src/main.tsx`): plan **03-07** is in the SAME wave (4) and also declares `src/main.tsx`. The two edits target **disjoint regions** and are safe in either order — this plan rewrites the polyfill import block at the TOP of the file (replacing the direct `./lib/pdf-worker` / polyfill imports with the barrel); 03-07 appends a boot handshake immediately AFTER the `createRoot(...).render(...)` call at the bottom. Neither may reformat, reorder, or reflow the other's region. `execute-phase`'s intra-wave `files_modified` overlap check will force these two plans to run sequentially rather than in parallel, so the wave-4 parallelism implied by the wave number does not apply to this pair. If you are executing this plan and find 03-07's boot handshake already present at the bottom of `src/main.tsx`, that is expected — leave it untouched. The polyfill barrel MUST remain the first import so it is installed before any pdf.js or Stripe code evaluates.
</objective>

<threat_model>
- **A weak polyfill on a security-adjacent path.** `crypto.randomUUID` here produces the `attemptNonce` that the server uses for Merit idempotency. A predictable or colliding fallback could let two distinct submits collapse into one attempt (a lost run) or let a crafted nonce collide with another user's (a cross-user idempotency hazard). Mitigation: the fallback derives from `crypto.getRandomValues` with correct RFC-4122 v4 version and variant bits. If `getRandomValues` is ALSO absent the polyfill installs NOTHING — it does not fall back to `Math.random` for this path — and the capability tier blocks the AI/checkout flows instead (D-09's "block only where honest emulation is impossible").
- **Prototype pollution / native override.** A polyfill that unconditionally overwrites a native method can break a browser that is actually fine, and is a classic supply-chain-shaped hazard. Mitigation: mirror `map-get-or-insert.ts` exactly — `define()` no-ops when the native method exists, installs non-enumerably with `writable: true, configurable: true`, and never touches anything else on the object.
- **Realm gaps.** A polyfill installed only in the window realm leaves both pdf.js worker realms broken — precisely the shape of the `getOrInsertComputed` bug. Mitigation: a single barrel plus a static-source guard asserting each of the three realm entries imports it, and imports it BEFORE any other app import (import order is load-bearing for side-effect installs).
- **Breaking document extraction.** Touching the worker entry files risks the PDF pipeline, which is a business-critical path. Mitigation: worker files receive an added import line and nothing else; the existing worker tests and the upload-parity spec from plan 03-05 must stay green; the classic-worker experiment is investigation-only and must not be merged unless it passes those same gates.
- **A vacuous polyfill test.** A test that runs in a jsdom environment where `crypto.randomUUID` already exists proves nothing. Mitigation: the test explicitly deletes `crypto.randomUUID` before asserting, asserts the v4 shape and version/variant nibbles, asserts uniqueness across many draws, and asserts the native implementation is preserved when present.
- **Scope creep into a rewrite.** The Firefox-floor question is genuinely valuable but genuinely risky. Mitigation: it is timeboxed, its deliverable is a written finding rather than a merged change, and a negative result (keep 114) is an acceptable and expected outcome.
</threat_model>
