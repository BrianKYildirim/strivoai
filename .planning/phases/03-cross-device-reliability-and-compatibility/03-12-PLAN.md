<objective>
Ship UI-SPEC Surface C: a frozen, exhaustive, closed set of nine client-side error codes, and prove by machine that no raw JavaScript, database, provider or stack text can reach a user (XRUN-06), while isolating extension-injected errors (XDEV-08).

Purpose: the brief's requirement is absolute — raw errors never appear. The repo already proved this pattern server-side with a frozen 13-code taxonomy and a `getSafeStreamErrorMessage()` chokepoint. What has never existed is the client half: transport and platform failures that never reach the server taxonomy at all, and which today surface as whatever the engine happened to throw.
Output: `client-error-taxonomy.ts` with an exhaustive test, the two error boundaries sourcing their copy from it, and a five-project leak-guard assertion.

Scope guard: the server taxonomy is frozen and untouched. This plan adds no server code and rewrites no server copy.
</objective>

<threat_model>
- **Information disclosure through error text (the requirement itself).** A raw `TypeError`, a PostgREST code, a `chunk-xyz.js` filename or a stack frame in the UI leaks implementation detail, aids an attacker mapping the app, and destroys user trust. Mitigation: a frozen table is the only source of client copy; a machine-checkable regex is asserted against `document.body.innerText` on every client state in both themes on all five projects; and a vitest assertion runs the same regex over every string in the table itself, so a bad copy string cannot even be committed.
- **Fall-through to raw text.** The realistic failure is not a deliberately leaked message but an unmapped condition rendering `String(err)`. Mitigation: fail closed — the mapper's default branch is `CLIENT_UNEXPECTED`, and the exhaustive table test asserts every code has copy, a retryable flag and an affordance, so a new code cannot be added without them.
- **Retry that deterministically fails.** Offering `Try again` on a terminal condition (an unsupported browser, blocked storage) trains users to hammer a dead control and can drive repeated money-path attempts. Mitigation: `retryable` is a property of the code; the component renders a primary retry only when it is true; the table test asserts the terminal codes are not retryable.
- **False Merit claims in copy.** Telling a user "no credits were used" after a reservation, or staying silent when nothing was charged, are both trust failures with financial meaning. Mitigation: the rule is encoded in the table — pre-reservation client failures carry the `no credits were used` phrasing; post-reservation codes say nothing about credits and defer to the server refund path. The table test asserts no post-reservation code contains a credit claim.
- **Extension noise misattributed to the app.** Grammarly-class injectors throw constantly. Rendering their errors as Strivo failures both misleads the user and buries real defects. Mitigation: the boundaries classify `script_origin` (already implemented) and treat `browser-extension` origin as isolated — recorded to diagnostics, never surfaced as an app failure message.
- **Two error surfaces at once.** A client code and a server code rendering simultaneously produces contradictory instructions ("try again" next to "your credits were returned"). Mitigation: one error surface at a time, server terminal state wins — asserted in the component logic and exercised by the leak-guard spec.
- **Breaking the one error surface that works.** `AnalysisErrorBoundary`'s copy is locked and its auto-recover-once behavior is proven. Mitigation: its user-visible strings and recovery behavior are preserved exactly; only their SOURCE moves into the frozen table.
</threat_model>
