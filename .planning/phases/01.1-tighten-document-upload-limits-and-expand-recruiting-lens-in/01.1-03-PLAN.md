<objective>
Build the fixture generators every downstream validation test depends on, and convert D-06's LOW-confidence premise about DOCX `<Pages>` into recorded fact.

Purpose: The phase's entire fail-open DOCX design rests on an unverified assumption about which word processors populate `<Pages>` in `docProps/app.xml`. RESEARCH flags Google Docs behaviour as unknown with no authoritative source. This is a ~10-minute empirical check that must happen BEFORE the validation logic is written, not after.
Output: three fixture modules and a findings document.

This plan is `autonomous: false` — Task 1 requires the operator to export documents from Google Docs and Apple Pages, which Claude cannot do.
</objective>

<threat_model>
- **A fixture that does not reflect reality.** If the generated DOCX differs structurally from what Word/Google Docs actually emit, every downstream unit test passes while the deployed validator fails on real files. Mitigation: Task 1's empirical matrix constrains Task 2's generator; the generator must reproduce at least one real-world observed shape.
- **Committed binaries.** Adding `.docx` binaries to the repo would enroll them in `src/test/security/phase9-pii-guard.test.ts`'s fixture-provenance regime and put opaque bytes in the diff. Mitigation: generate in-memory; no binary is committed.
- **Spoofing fixtures are attack payloads by construction.** They must contain only synthetic, non-PII content and must never be uploaded to production. Mitigation: fixtures are code-generated with inert placeholder text; no real resume content, no PII.
- **Backstop calibration.** A wrongly-calibrated word-count backstop is a silent policy hole (too high) or a false-rejection generator (too low). Mitigation: Task 1 records real word counts alongside `<Pages>` so the 1,600 default is validated against observed 2-page documents rather than reasoning alone.
</threat_model>
