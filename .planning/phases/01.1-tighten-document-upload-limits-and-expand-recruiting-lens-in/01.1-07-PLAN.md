<objective>
Apply the `resumes` bucket MIME revocation to preview, empirically settle the D-28 spoofing question against a real bucket, and route production application through the operator.

Purpose: A migration file on disk changes nothing. Build and type checks pass without it, so verification would read green while the bucket still accepts `text/markdown`. This is the phase's `[BLOCKING]` schema-push gate.
Output: a recorded apply log with actual migration-history and `SELECT` output at each stage.

Per CLAUDE.md: preview is Claude's to apply and verify; production is read-only for Claude and applied by the operator.
</objective>

<threat_model>
- **Applying a destructive change to production without approval.** Mitigation: Task 3 is a `checkpoint:human-action`; Claude does not run the production write under any circumstance. Claude's production access in this plan is read-only `SELECT` verification.
- **A wrong rollback.** The rollback restores the `20260607050000` six-element array. If production has DRIFTED from that array, the rollback would silently install the wrong state. Mitigation: Task 1 reads production's current array read-only BEFORE anything is applied and compares it element-by-element to `20260607050000`. A mismatch halts the plan.
- **An unrelated pending migration rides the push.** `supabase db push` applies every pending local migration, not just the file named by this phase. Mitigation: Task 1 records local/remote migration history, Task 2 reruns `supabase migration list --linked` plus `supabase db push --dry-run`, and the checkpoint fails closed unless the only pending version is exactly `20260723120000`.
- **False sense of security (D-28).** It would be easy to declare "spoofed files are blocked" once the allowlist is narrowed. It is not true: `allowed_mime_types` validates the client-declared `Content-Type`. Mitigation: Task 2 empirically uploads a text file with a forced `contentType: 'application/pdf'` to the preview bucket and records the result. The expected outcome is that it SUCCEEDS, which is the evidence that the validation seam — not the bucket — is the enforcement. This plan must not claim otherwise.
- **Historical data.** No existing storage object, `resumes` row, or analysis record is touched (D-14). `allowed_mime_types` gates new uploads only. No `DELETE`, `DROP`, `ALTER`, or policy change is executed.
- **Secret handling.** `SUPABASE_ACCESS_TOKEN` may be needed for non-TTY `supabase db push`. Never print it, never write it to the log file, never commit it.
</threat_model>
