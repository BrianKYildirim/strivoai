<objective>
Implement the authenticated authoritative document-validation seam and its real PDF parser, then register it everywhere required for type-checking, testing, and deployment.

Purpose: Client validation is only fast feedback. UPL-05 requires a direct-HTTP-bypass-resistant server decision over raw bytes, while D-26 forbids inventing a public endpoint for the anonymous demo path.
Output: `validate-document`, the isolated `pdf-lib` parser, handler tests, and all three registration edits.
</objective>

<threat_model>
- **CPU denial of service.** Authenticate before reading/parsing the body, reject a declared or measured body above `MAX_UPLOAD_BYTES` before `pdf-lib`/ZIP work, and rate-limit by authenticated user. Never log file bytes or extracted text.
- **Content spoofing.** File extension and `Content-Type` are attacker-controlled. Require extension/content agreement after magic-byte/container inspection; a `.pdf` without `%PDF-` and a `.docx` without `word/document.xml` fail closed.
- **Parser bypass.** PDF parse errors must reject as unsupported; fail-open is permitted only for a structurally valid DOCX whose `<Pages>` metadata is absent/implausible and whose word count is at or below the conservative backstop.
- **Auth confusion.** `verify_jwt = false` at the gateway does not make the handler anonymous. The handler must call `requireAuth(req, { type: 'user' })` and rely on `withCors` to serialize the thrown 401.
- **LinkedIn regression.** The endpoint accepts only `x-document-type: resume`; LinkedIn profile controls never invoke it, so their 12-page allowance cannot be overwritten by an extension-keyed check.
- **Silent non-deployment.** Registration is three-place and machine-asserted. A green local module that is absent from `deploy.ps1` is not complete.
</threat_model>
