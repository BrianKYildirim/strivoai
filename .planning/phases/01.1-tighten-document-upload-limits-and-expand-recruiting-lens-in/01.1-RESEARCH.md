### Locked Decisions

**Two-Page Limit — Scope**

- **D-01:** The two-page cap applies to **resume-class documents only** — every surface where `documentType === 'resume'`. Concretely: `src/pages/Upload.tsx:376`, `src/pages/Onboarding.tsx:605`, `src/pages/Profile.tsx:478`, `src/pages/CareerCompass.tsx:928`, `src/pages/Jobs.tsx:207`, `src/components/ActionFirstHero.tsx:241`, `src/components/MinimalHero.tsx:374`.
- **D-02:** **LinkedIn profile PDF uploads are exempt** and keep their existing allowance (`PAGE_LIMITS.linkedin_profile = 12` in `src/lib/document-extraction.ts:143`). Rationale: LinkedIn's own "Save to PDF" export is routinely 3-8 pages and is a required input to LinkedIn Grader and Recruiting Lens (both Elite-paid). A 2-page cap there would break paying users on a change intended to enforce resume-length discipline. Affected LinkedIn surfaces that MUST NOT be capped at 2: `src/pages/LinkedInGrader.tsx:859`, `src/pages/RecruitingLens.tsx:907`, `src/pages/Onboarding.tsx:691`, `src/pages/Profile.tsx:550` (all use `LINKEDIN_PDF_ACCEPT`).
- **D-03:** Do **not** introduce a second, tightened LinkedIn page cap in this phase. The LinkedIn allowance is unchanged.
- **D-04:** User-facing rejection message is exactly: `Your document is longer than the 2-page limit. Please upload a PDF or DOCX file containing no more than 2 pages.`

**Two-Page Limit — DOCX Page Counting**

- **D-05:** DOCX page count is read from `<Pages>` in `docProps/app.xml`. The existing ZIP-entry reader (`readZipTextEntry`, `src/lib/document-extraction.ts:326`) already performs exactly this class of read and should be reused rather than adding a ZIP dependency.
- **D-06:** **Fail-open with a word-count backstop.** If `<Pages>` is present and > 2 → reject. If `<Pages>` is absent, zero, or implausible (common for Google Docs / Pages / LibreOffice exports, which are a large share of real users) → accept, unless a conservative word-count backstop indicates the document cannot be two pages. Suggested backstop threshold: **~1,600 words** (planner may refine, but it must be conservative — a false rejection of a valid 2-page resume is worse than accepting an occasional 3-pager).
- **D-07:** Do **not** add a server-side DOCX-to-page converter. No such converter exists in the Deno edge runtime today and adding one is out of scope.
- **D-08:** PDF page count comes from the authoritative `pdf.numPages` (pdfjs), not from `PAGE_LIMITS`, which today is only an OCR *render* cap (`src/lib/document-extraction.ts:277`) and is not a rejection gate.

**Backend Enforcement Point**

- **D-09:** Introduce **one shared server-side validation seam** that receives the raw file bytes (or the just-uploaded storage object) and returns accept/reject based on: extension allowlist, magic-bytes/content sniffing (so renamed and MIME-spoofed files are caught), and page count.
- **D-10:** That seam must be invoked **before Merit deduction and before any `analyze-*` invocation**. Constraint driving this: today no edge function ever receives the raw file — `ocr-pdf` receives pre-rendered page images (`supabase/functions/ocr-pdf/index.ts:251`) and the `analyze-*` functions receive already-extracted text. Client-side page counting alone is therefore trivially bypassed by a direct API call, which would not satisfy the brief's "enforce during actual file processing, not only through frontend copy or picker constraints."
- **D-11:** Client-side checks remain, but only as fast-feedback UX. The server check is authoritative.
- **D-12:** Validation failure must leave **no partial state** — no orphaned storage object, no resume row, no analysis record, no Merit deduction. This continues the Phase 1 rule that failure paths preserve state rather than half-commit.

## Summary

Three of the four workstreams in this phase are mechanically simple and low-risk: the Recruiting Lens character-limit change touches exactly four literals (three client, one edge), the `.md`/`.txt` removal is a single-const edit that propagates transitively to all seven `accept=` sites (verified — no page hardcodes a file-type string), and the bucket MIME revocation is a five-line `UPDATE`. The fourth workstream — the shared server-side validation seam (D-09..D-12) — is where essentially all the design risk, all the new dependency risk, and all the regression risk live. Plan accordingly: it should be its own plan file, sequenced last, behind the three low-risk ones.

Two findings materially change the shape of the work versus what CONTEXT anticipated. **First**, the resume upload sequence today is `storage.upload → createSignedUrl → resumes.insert → extractDocumentFromFile`. Extraction — the only place a page count could be observed — happens *after* the storage object and the `resumes` row already exist. Every rejection this phase adds at the extraction point would therefore leave exactly the orphaned state D-12 forbids, and `document-extraction-primary.test.ts:74-77` actively asserts the insert-before-extract ordering. The validation seam must therefore sit **before `storage.upload`**, not at extraction, in all three storage-writing flows (`Upload.tsx:133`, `MinimalHero.tsx:103`, `CareerCompass.tsx:531`) plus `Onboarding.tsx:274` and `Profile.tsx`. **Second**, `maxCharactersInput` carries a machine-enforced "exactly 4× `maxTokensInput`" invariant (`src/config/__tests__/sc12-snapshot.test.ts:35-51`) plus a byte-for-byte snapshot guard (`src/config/pricing-config.snapshot.ts`). D-21's 48,000 → 51,000 is therefore a **three-file lockstep change** (`pricing-config.ts` chars + tokens, `pricing-config.snapshot.ts`), not the one-cell edit CONTEXT implies. Doing it as a one-cell edit turns `npm test` red and blocks the whole `verify:baseline` gate.

For server-side page counting: the repo deliberately removed backend raw-byte PDF parsing in Phase 51 (`supabase/functions/_shared/pdf-parser.ts:9-11`), so nothing exists to reuse. Hand-rolling a byte-scanning page counter is a trap — it works on the E2E fixture generator's uncompressed PDFs and fails silently on the compressed-xref/object-stream PDFs that Word, Google Docs, and Canva actually produce. Use `npm:pdf-lib` (pure JS, no native deps, already the idiomatic import style in this repo — `npm:stripe`, `npm:@supabase/supabase-js`). DOCX needs no new dependency: `readZipTextEntry` is dependency-free and `DecompressionStream('deflate-raw')` is confirmed available in Deno and already proven in this repo's edge runtime (`_shared/archive-reader.ts` uses `DecompressionStream('gzip')` on the blocking gate).

**Primary recommendation:** Extract the shared limits into a new browser-free `src/config/document-limits.ts` (dual-imported by edge via the established `_shared/tier-config.ts` re-export pattern), add one new edge function `validate-document` that receives raw bytes as a `Blob` body (never base64), invoke it from every resume-class flow strictly before `storage.upload`, and sequence the phase as four plans: (1) Recruiting Lens limits, (2) `.md`/`.txt` removal + migration, (3) shared constants module, (4) the validation seam + fixtures + tests.

Fails on the majority of real-world resumes: PDF 1.5+ writers (Word 2007+, LibreOffice, Google Docs, Chrome print-to-PDF, Canva) put page objects inside Flate-compressed **object streams** and the xref in a compressed **xref stream**, so neither `/Type /Page` nor `/Count` is present as plaintext. Silent under-count → the cap silently stops enforcing. |
| `pdf-lib` | `unpdf` / `pdfjs-serverless` | Both are edge-oriented PDF.js redistributions and would also work, but `unpdf` has a **documented history of failing specifically on deployed Supabase Edge Functions** ("PDF.js is not available. Please add the package as a dependency", unjs/unpdf#3) and both are substantially larger bundles than pdf-lib. pdf-lib does not need a worker or canvas — page counting needs neither. |
| `pdf-lib` | Client-only page count, trusted by the server | **Rejected by D-10/D-11.** Trivially bypassed by a direct API call. |
| A new edge function | Extend `ocr-pdf` | `ocr-pdf` is on the extraction path and receives pre-rendered images; the validator must run *before* extraction and *before* upload. Coupling them inverts the required ordering. |
| Deno-side DOCX ZIP lib (`jszip`, `@zip-js/zip-js`) | — | Unnecessary. `readZipTextEntry` is ~40 lines and already proven; adding a ZIP dependency for one entry read violates "avoid unnecessary abstractions" (CLAUDE.md). |

## Architecture Patterns

### Recommended module layout

```

└── document-limits.ts          # NEW — browser-free shared constants (D-24)

                                #   ACCEPTED_RESUME_DOCUMENT_EXTENSIONS

src/lib/document-extraction.ts  # re-exports the extension consts for back-compat;
                                # adds client-side countPdfPages()/countDocxPages()

supabase/functions/_shared/
├── tier-config.ts              # + re-export document-limits (established pattern)
└── document-validation.ts      # NEW — pure, testable: sniffMagicBytes(), countDocxPages(),
                                #        wordCountBackstop(), decideVerdict()
supabase/functions/validate-document/
├── index.ts                    # NEW — HTTP shell: auth, CORS, rate limit, body read
└── pdf-pages.ts                # NEW — the ONLY file importing npm:pdf-lib
```

**Why `src/config/document-limits.ts` and not `src/lib/document-extraction.ts`:** the latter imports `@/lib/pdf-worker`, `@/lib/extract-pdf-text`, and `@/lib/fetchWithTimeout` — all browser-only, all `@/` path-aliased. Deno cannot resolve `@/`, and pdfjs will not load in the edge runtime. `src/config/pricing-config.ts` is dependency-free, which is precisely why the dual-import works. **The new constants module must have zero imports.**

**Why the pure logic lives in `_shared/document-validation.ts` and not in `index.ts`:** the offline deno lane (`deno task test:ci`) is an explicit allowlist of files that must be importable without network/Supabase. A pure module with no `npm:pdf-lib` import is trivially unit-testable there; `pdf-pages.ts` gets characterized separately or via the remote lane.

### Pattern 1: Validate-before-upload (the D-12 seam)

**What:** The single ordering rule for every resume-class flow.
**When:** Every surface in inventory §D.

```ts
// src/pages/Upload.tsx — INSERT BEFORE line 133 (`storage.from('resumes').upload`)
// Fast-feedback client pre-check (D-11: UX only, NOT authoritative)
const local = await precheckResumeDocument(file);   // extension + pdf.numPages / docProps <Pages>
if (!local.ok) { toast.error(local.message); setIsUploading(false); return; }

// Authoritative server check (D-10). Raw bytes — no base64, no multipart.
const { data: verdict, error: verdictError } = await invokeWithTimeout<ValidateDocumentResponse>(
  'validate-document',
  { body: file, headers: { 'x-document-type': 'resume', 'x-file-name': encodeURIComponent(file.name) } },
  30000,
);
if (verdictError || !verdict?.ok) {
  toast.error(verdict?.message ?? 'We could not validate this file.');
  setIsUploading(false);
  return;                       // ← nothing uploaded, nothing inserted, nothing charged
}

// …existing storage.upload / createSignedUrl / resumes.insert / extractDocumentFromFile
```

`supabase-js` sets `Content-Type: application/octet-stream` automatically for `Blob` / `File` / `ArrayBuffer` bodies (`FunctionsClient` — "we automatically attach the Content-Type header for `Blob`, `ArrayBuffer`, `File`, `FormData` and `String`"). Sending the `File` directly avoids the ~33% base64 inflation and keeps the payload at the file's true size.

The `documentType` and filename ride in **headers**, because the body is the file. Alternative if you prefer a single JSON-ish envelope: `FormData` with a `file` part plus fields — also auto-typed by `supabase-js`, marginally more code on both sides, and `req.formData()` is available in Deno. Either is fine; headers are simpler.

### Pattern 4: Magic-byte sniffing

```ts
// supabase/functions/_shared/document-validation.ts
export type SniffedKind = 'pdf' | 'docx' | 'zip-not-docx' | 'unknown';

export function sniffKind(bytes: Uint8Array, zipEntryNames: string[] | null): SniffedKind {
  // PDF: '%PDF-' at offset 0. The spec tolerates leading junk, so scan the first 1 KiB.
  const head = new TextDecoder('latin1').decode(bytes.subarray(0, 1024));
  if (head.includes('%PDF-')) return 'pdf';
  // ZIP local file header: 50 4B 03 04
  if (bytes[0] === 0x50 && bytes[1] === 0x4b && bytes[2] === 0x03 && bytes[3] === 0x04) {
    return zipEntryNames?.includes('word/document.xml') ? 'docx' : 'zip-not-docx';
  }
  return 'unknown';
}
```
**Both checks matter.** `PK\x03\x04` alone accepts `.xlsx`, `.pptx`, `.odt`, `.jar`, and a plain `.zip`. Requiring `word/document.xml` in the central directory is the discriminator — and `readZipTextEntry` already walks the central directory, so exposing an entry-name lister from the same walk is a ~5-line addition.

An empty/short-circuit ZIP (`PK\x05\x06`, the EOCD signature of a zero-entry archive) will not match `PK\x03\x04` — it correctly falls to `unknown`.

### Pattern 5: DOCX page count with fail-open backstop (D-05, D-06)

```ts
export function parseDocxPages(appXml: string | null): number | null {
  if (!appXml) return null;
  const m = /<Pages>\s*(-?\d+)\s*<\/Pages>/.exec(appXml);
  if (!m) return null;
  const n = Number(m[1]);
  return Number.isFinite(n) && n > 0 ? n : null;   // 0 / negative / NaN → "unknown"
}

export function docxVerdict(pages: number | null, wordCount: number, maxPages: number, backstop: number) {
  if (pages !== null) return pages <= maxPages ? { ok: true } : { ok: false, reason: 'page_limit' };
  // <Pages> absent or implausible → FAIL OPEN unless the word count makes 2 pages impossible.
  return wordCount <= backstop ? { ok: true } : { ok: false, reason: 'page_limit' };
}
```

### Anti-patterns to avoid

- **Enforcing at the extraction point.** `extractDocumentFromFile` runs *after* the storage object and `resumes` row exist in five of the flows. Rejecting there is precisely the orphaned state D-12 forbids.
- **Repurposing `PAGE_LIMITS`.** It is an OCR *render* budget (`:277`), consulted only on the OCR fallback path. A text-layer PDF never reaches it. Using it as the gate would mean a clean 3-page PDF is silently accepted. D-08 already says this; it bears repeating because the name is misleading.
- **Base64-encoding the file into a JSON body.** Inflates by ~33%, burns CPU on both sides against the 2 s edge CPU budget, and adds a decode failure mode. Send the `Blob`.
- **Changing `maxCharactersInput` without `maxTokensInput` and the snapshot.** Turns `npm test` red → `verify:baseline` red → deploys blocked.
- **Extension-keying the page cap.** Breaks LinkedIn (D-02).
- **Deleting `'plain_text'` from the `ExtractionProvider` union.** Historical `resumes.extraction_metadata` rows carry it; removing it breaks type-safe reads of preserved history (D-14).

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| PDF page count from raw bytes | Regex over `/Type /Page` or `/Count` | `npm:pdf-lib` `getPageCount()` | Object streams (`/Type /ObjStm`) and cross-reference streams (`/Type /XRef`) — standard since PDF 1.5 and emitted by Word, LibreOffice, Google Docs, Chrome, Canva — are Flate-compressed. Page objects are simply not present as plaintext. A regex scanner returns 0 or 1 and **silently stops enforcing the cap**. Also handles: linearized PDFs, incremental updates (multiple xref sections where the *last* wins), inherited `/Count` in nested page-tree nodes, and `>>`-nested dictionaries. |
| Encrypted-PDF handling | Custom decrypt | `PDFDocument.load(bytes, { ignoreEncryption: true })` | pdf-lib throws `EncryptedPDFError` by default. Owner-password-protected (but readable) PDFs are common in resume exports; `ignoreEncryption: true` still yields a correct page count. Do **not** silently accept a PDF that fails to parse at all — see Pitfall 6. |
| ZIP entry extraction in Deno | New ZIP dependency | Port `readZipTextEntry` (`document-extraction.ts:326-394`) | Already written, already dependency-free, already handles stored (method 0) and deflate (method 8) entries via `DecompressionStream('deflate-raw')`, which Deno supports and this repo already runs in production edge (`_shared/archive-reader.ts`). |
| Content-type trust | Trusting `file.type` or the bucket's `allowed_mime_types` | Magic-byte sniff + ZIP entry check | The browser derives `File.type` from the **extension**, and `supabase-js` forwards it as the upload `Content-Type` — so the bucket allowlist validates a *client-declared* string. Renaming `evil.md` → `evil.pdf` produces `type: 'application/pdf'` and passes the bucket check. The brief explicitly requires catching this. |
| Word-count backstop tokenizer | New regex | Reuse `/[\p{L}\p{N}][\p{L}\p{N}.'-]*/gu` filtered to `length > 1`, from `assessBrowserExtractionQuality` (`:419-420`) | Keeps client and server counting identically — otherwise the fast-feedback check and the authoritative check disagree at the margin and users see "accepted, then rejected". |
| Rate limiting / auth / CORS on the new function | Bespoke | `_shared/{auth,cors,rate-limiter}.ts` | Project convention (D-25: preserve existing security behavior). |

**Key insight:** every one of these has a failure mode that is *silent* — the validator returns "fine" and the cap quietly stops existing. That is strictly worse than not shipping the cap, because the acceptance criteria will read green.

## Common Pitfalls

### Pitfall 1: The 4:1 char:token invariant (WILL turn the gate red)

**What goes wrong:** You change `maxCharactersInput.recruitingLens` 48000 → 51000 per D-21, and `npm test` fails with two errors: the snapshot equality check and `recruitingLens/pro: chars=51000 tokens=12000`.
**Why:** `src/config/__tests__/sc12-snapshot.test.ts:35-51` machine-enforces `chars === tokens * 4` on every non-null row, and `:16-22` asserts byte-equality against `src/config/pricing-config.snapshot.ts`.
**How to avoid:** Three-file lockstep —
- `pricing-config.ts:145` → `recruitingLens: { free: null, pro: 12750, elite: 12750 }`
- `pricing-config.ts:156` → `recruitingLens: { free: null, pro: 51000, elite: 51000 }`
- `pricing-config.snapshot.ts:45,53` → same two cells, with a dated `UPDATED — Phase 01.1` comment block matching the file's existing convention (the file header explicitly instructs: "if product requirements have actually changed, update BOTH the caps AND this snapshot in lockstep").

**Resolved by D-21:** use 51,000 / 12,750 exactly. The earlier 52,000 / 13,000 alternative is superseded; plans must not reopen it or add a confirm gate.

**Also note:** `maxTokensOutput` has a `tierSums` assertion (`:24-33`) — but that is *output*, untouched by this phase. No action.

### Pitfall 2: `--use-api` bundling caps the function at 5 MB

**What goes wrong:** `validate-document` deploys fine locally and fails at `supabase functions deploy` in CI/prod.
**Why:** `scripts/deploy.ps1:159` runs `supabase functions deploy $fn --no-verify-jwt --use-api`. Supabase documents **20 MB** for CLI-local bundling but **5 MB** for server-side (`--use-api` / Management API / Dashboard) bundling.
**How to avoid:** pdf-lib is ~1.1 MB minified with no transitive deps, so it should fit comfortably — **but prove it, do not assume.** Add an explicit verification step to the plan: deploy `validate-document` to preview and record the bundle size. If it breaches, the fallbacks in order are (a) drop `--use-api` for this one function, (b) use a slimmer import path, (c) fall back to the dependency-free counter for the *common* PDF shapes plus a conservative reject-on-unparseable policy.
**Warning signs:** `The function size exceeds the allowable limit` at deploy.

### Pitfall 3: `invokeWithTimeout` types reject a `Blob` body

**What goes wrong:** `npm run type-check` fails — `Type 'File' is not assignable to type 'Record<string, any>'`.
**Why:** `src/lib/fetchWithTimeout.ts:11` declares `body?: Record<string, any>`. `supabase-js` itself accepts `Blob | ArrayBuffer | File | FormData | String | object`; only the wrapper's type is narrow.
**How to avoid:** Widen additively:
```ts
body?: Record<string, any> | Blob | ArrayBuffer | File | FormData | string;
```
No runtime change (it is passed straight through at `:94`). Zero behavior risk to the ~30 existing callers.

### Pitfall 4: The anonymous hero paths have no auth and no merit

**What goes wrong:** You add `requireAuth` to `validate-document` and the landing-page "first scan is free" flow breaks with a 401.
**Why:** `ActionFirstHero.tsx:39` and `MinimalHero.tsx:170` call `extractDocumentFromFile` and then `analyze-resume` with **no signed-in user** (`MinimalHero.tsx:105` gates on `if (currentUser)`; the `else` branch is fully anonymous). These are pre-signup demo paths — no storage write, no `resumes` row, no Merit deduction.
**Resolved by D-26 after pattern mapping:** the seam is authenticated-only. The anonymous hero demo runs the shared browser precheck before extraction/sessionStorage and never calls `validate-document`; there is no public validation route and no anonymous server-auth posture to design.

### Pitfall 5: `allowed_mime_types` validates a client-declared header, not content

**What goes wrong:** The migration lands, and a renamed `resume.md` → `resume.pdf` still uploads successfully.
**Why:** Supabase Storage rejects uploads that violate the bucket restrictions — but the MIME it checks is the request's `Content-Type`, which `storage-js` populates from `File.type`, which the browser derives from the **filename extension**. There is no server-side content sniffing.
**How to avoid:** This is exactly why D-09 requires magic-byte sniffing in the validation seam. The migration is defense-in-depth (and closes the honest-client case + the direct-storage-API case); the seam is the actual enforcement. **Do not write an acceptance test that claims the migration blocks spoofed files — it does not.**
**Confidence:** MEDIUM. Verify empirically against preview during execution: upload a renamed text file with a forced `contentType: 'application/pdf'` and observe.

### Pitfall 6: Fail-open on unparseable PDFs re-opens the hole

**What goes wrong:** `PDFDocument.load` throws (corrupt, exotic, or genuinely encrypted-with-user-password file) and the catch block returns `{ ok: true }`, so any attacker can bypass the cap by emitting a deliberately malformed PDF.
**Why:** Fail-open is correct for **DOCX `<Pages>`** (D-06 — the metadata is legitimately absent in a large share of real files) but wrong for **PDF page count**, where the count is always structurally present and a parse failure means "this is not a usable PDF."
**How to avoid:** Asymmetric policy, stated explicitly in the plan:
- PDF parse throws → **reject**, with the *unsupported type* message (D-13), not the page-limit message. Rationale: the file is not a readable PDF, so extraction would fail downstream anyway. This also preserves today's UX, where an unreadable PDF already errors at extraction.
- DOCX `<Pages>` missing/implausible → **accept**, subject to the word-count backstop (D-06).
- DOCX ZIP unreadable / no `word/document.xml` → **reject** as unsupported type.

### Pitfall 7: Client and server disagreeing at the boundary

**What goes wrong:** The client accepts a file (its `pdf.numPages` says 2) and the server rejects it, or vice versa — users see a spinner then a confusing error.
**Why:** Two independent implementations of the same rule (pdfjs client-side per D-08, pdf-lib server-side).
**How to avoid:** Both read the *same* constant from `src/config/document-limits.ts`, and both use `<= MAX_PAGES` (not `<`). pdfjs `numPages` and pdf-lib `getPageCount()` both report the page-tree leaf count and agree in practice — but add a fixture-driven parity test (§ Test Strategy) that runs the same 1/2/3-page PDFs through both and asserts identical counts. This is cheap and it is the only way you find a divergence before a user does.
**Warning signs:** Any bug report of the form "it let me pick the file but then said it was too long."

### Pitfall 8: The `document-extraction-primary.test.ts` migration assertion goes stale, not red

**What goes wrong:** You ship the new migration, and `:57-60` still passes — because it reads `20260607050000_allow_resume_document_mime_types.sql` by absolute path, and that historical file is (correctly) never edited.
**Why:** The test asserts on a *file*, not on the *effective bucket state*.
**How to avoid:** Rewrite the assertion to read the **new** migration and assert the four text/markdown types are **absent** and pdf/docx **present**. A test that silently keeps passing while asserting the opposite of the requirement is worse than no test.

### Pitfall 9: The 2 s edge CPU budget

**What goes wrong:** Intermittent 546/CPU-limit errors on large files.
**Why:** Supabase Edge Functions cap **CPU time at 2 s** per request (memory 256 MB, wall clock 150 s free / 400 s paid).
**How to avoid:** Bound the input before parsing. The `resumes` bucket already carries `file_size_limit = 5242880` (5 MB, from `20251113102013_*.sql`), so a matching byte cap in the validator is *mirroring an existing constraint*, not inventing a new product limit — and the v5.0 milestone report already logs "no upload byte-size guard exists in the product" as a residual risk. Reject over-limit bytes before touching pdf-lib. Measure a 5 MB PDF's parse time on preview and record it.

```ts
export async function precheckResumeDocument(
  file: File,
  documentType: DocumentType = 'resume',
```

### Forward

```sql
-- supabase/migrations/<ts>_revoke_text_mime_types_from_resumes_bucket.sql

UPDATE storage.buckets
SET allowed_mime_types = ARRAY[
  'application/pdf',
  'application/vnd.openxmlformats-officedocument.wordprocessingml.document'
]::text[]
WHERE id = 'resumes';
```

```sql
-- ROLLBACK for <ts>_revoke_text_mime_types_from_resumes_bucket.sql
-- Restores the 20260607050000 state exactly.
UPDATE storage.buckets
SET allowed_mime_types = ARRAY[
  'application/pdf',
  'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
  'text/plain',
  'text/markdown',
  'application/markdown',
  'application/x-markdown'
]::text[]
WHERE id = 'resumes';
```

## Regression Surface

Ranked by expected blast radius.

1. **LinkedIn PDF flows (HIGHEST).** Four surfaces, all Elite-paid, all routinely 3-8 pages. Any extension-keyed cap breaks all four. Mitigation: key on `documentType`, and add the UPL-07 non-regression test against a real multi-page LinkedIn export.
2. **The `verify:baseline` gate itself.** Three known-red-by-design assertions (`document-extraction-primary.test.ts:53`, `sc12-snapshot.test.ts` ×2). Plus any new deno file omitted from the `deno.json` allowlist runs in no lane. Plus a new function omitted from `scripts/deploy.ps1`'s explicit list never deploys.
3. **`Upload.tsx` insert-before-extract ordering.** `document-extraction-primary.test.ts:74-77` asserts it. Adding validation **before** `storage.upload` preserves it; refactoring extraction earlier would break it.
4. **The OCR fallback path.** `renderPdfPagesToImages` reads `PAGE_LIMITS[documentType]` (`:277`). Do not repurpose or lower `PAGE_LIMITS.linkedin_profile`. If you lower `PAGE_LIMITS.resume` 8 → 2, OCR renders fewer pages — harmless once a 2-page gate exists upstream, but it is a change with no requirement behind it. Recommend leaving it.
5. **Re-analysis of historical documents.** `Upload.tsx:115-130` short-circuits to a prior analysis on `file_hash` match **before** any upload. Placing validation before `storage.upload` means it runs *after* the dedup check if you insert at line 133, or *before* it if you insert at line 111. **Recommendation: insert after the dedup check (i.e. immediately before line 132/133)** so a user re-submitting a historical 3-page resume still reaches their existing report instead of being newly rejected. This preserves D-14's "history stays readable" spirit. Flag the choice explicitly in the plan — it is a real product decision, not an implementation detail.
6. **Recruiting Lens combined trimmer.** With the ceiling at 51,000 and per-field caps of 5,000 (resume) + 6,000 (JD) + 4,000 (LinkedIn) = 15,000 max, the trimmer is now unreachable in practice. That is D-21's intent. The `input-trimmed` log line (`:541`) will simply stop firing — **expected, not a regression**, but note it so nobody reads the silence as breakage.
7. **Phase 02 telemetry (D-23).** `getMaxInputChars('recruitingLens')` is a Phase 02 calibration input. Land a dated note in `.planning/phases/02-ai-token-cost-optimization/` recording the 48,000 → 51,000 discontinuity and the date, so pre-01.1 measurements are never compared directly to post-01.1 ones. `02-MEASUREMENT-LOG.md` already has uncommitted edits — coordinate.
