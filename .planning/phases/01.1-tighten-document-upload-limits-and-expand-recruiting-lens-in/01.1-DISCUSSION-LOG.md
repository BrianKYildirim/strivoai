## LinkedIn PDF scope

| Option | Description | Selected |
|--------|-------------|----------|
| Resume-class only (Recommended) | Cap applies where `documentType === 'resume'`; LinkedIn profile PDFs keep their existing allowance. Protects two Elite features from mass breakage. | ✓ |
| Everything, no exceptions | Literal brief reading — every PDF/DOCX capped at 2 pages including LinkedIn exports. | |
| Resume 2 pages, LinkedIn tightened separately | Resume 2 pages; LinkedIn gets its own lower-than-12 cap decided this phase. | |

**User's choice:** Resume-class only
**Notes:** Scout finding that drove this: LinkedIn's "Save to PDF" export is routinely 3-8 pages and is a required input to LinkedIn Grader and Recruiting Lens, both Elite-paid. The codebase already models `linkedin_profile` as a distinct `DocumentType` with `PAGE_LIMITS.linkedin_profile = 12`, so the split fits the existing shape.

## DOCX page counting

| Option | Description | Selected |
|--------|-------------|----------|
| app.xml, fail-open w/ backstop (Recommended) | Read `<Pages>` from `docProps/app.xml`; reject if > 2; if absent/implausible, accept unless a conservative word-count backstop says otherwise. | ✓ |
| app.xml, fail-closed | Reject any DOCX whose `<Pages>` is missing/unreadable. Strictest, but rejects most Google Docs / LibreOffice exports. | |
| Convert-then-count | Server-side DOCX render for a true page count. Most accurate; no converter exists in the Deno edge runtime. | |
| Heuristic only | Ignore app.xml; reject on page-break count plus word/char thresholds. | |

**User's choice:** app.xml, fail-open with word-count backstop
**Notes:** DOCX has no reliable stored page count — `<Pages>` is written by Word but frequently omitted or stale in Google Docs / Pages / LibreOffice exports. Accepted trade-off: a false rejection of a valid 2-page resume is worse than occasionally accepting a 3-pager. Suggested backstop ~1,600 words, refinable by the planner in the conservative direction only.

## Server enforcement point

| Option | Description | Selected |
|--------|-------------|----------|
| Shared server validation seam (Recommended) | One validator receiving raw bytes / the stored object; checks extension + magic bytes + page count; runs before Merit deduction and any `analyze-*` call. | ✓ |
| Harden ocr-pdf + text-side guards | Extend `ocr-pdf` (already sees `images.length`) plus text-boundary guards. No new function, but the primary path (pdfjs succeeds, ocr-pdf skipped) stays client-enforced. | |
| Client enforcement + backend type-only | Page count client-side only; backend enforces extension/MIME and text length. Smallest change; only partially meets the brief. | |

**User's choice:** Shared server validation seam
**Notes:** Driving constraint from the scout — no edge function currently receives the raw file. `ocr-pdf` gets pre-rendered images; `analyze-*` gets extracted text. Without a new seam, page count is spoofable by direct API call and the brief's "enforce during actual file processing, not only through frontend" cannot be met.

## Recruiting Lens — combined input ceiling interaction

The operator confirmed interpretation **1**: the **job-description limit itself** is revised from 8,000 to **6,000**, superseding `01.1-BRIEF.md`.

`01.1-BRIEF.md` was updated in the same commit — objective, requirement heading, bullets, locked message, Required Tests, and Acceptance Criteria — with a dated revision note, so the brief and CONTEXT no longer disagree.
