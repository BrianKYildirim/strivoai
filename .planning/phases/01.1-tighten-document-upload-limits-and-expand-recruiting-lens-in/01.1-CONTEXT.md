# Phase 01.1: Tighten Document Upload Limits and Expand Recruiting Lens Input - Context

**Gathered:** 2026-07-23
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase tightens Strivo's document-upload contract and raises Recruiting Lens job-description capacity:

1. Enforce a **two-page limit** on PDF and DOCX uploads in resume-class upload surfaces.
2. **Remove `.md` and `.txt`** upload support end to end (frontend allowlists, backend validation, storage bucket MIME allowlist, extraction path, and user-facing copy).
3. Raise the Recruiting Lens job-description limit from 3,000 to **6,000** characters (revised down from the brief's original 8,000 — see D-15), with no silent truncation.

Rejections must occur **before** Merit deduction, before any Anthropic call, and before completed-analysis persistence.

Phase 02 (AI Token & Cost Optimization) is paused and resumes only after this phase completes.

</domain>

<decisions>
## Implementation Decisions

### Two-Page Limit — Scope

- **D-01:** The two-page cap applies to **resume-class documents only** — every surface where `documentType === 'resume'`. Concretely: `src/pages/Upload.tsx:376`, `src/pages/Onboarding.tsx:605`, `src/pages/Profile.tsx:478`, `src/pages/CareerCompass.tsx:928`, `src/pages/Jobs.tsx:207`, `src/components/ActionFirstHero.tsx:241`, `src/components/MinimalHero.tsx:374`.
- **D-02:** **LinkedIn profile PDF uploads are exempt** and keep their existing allowance (`PAGE_LIMITS.linkedin_profile = 12` in `src/lib/document-extraction.ts:143`). Rationale: LinkedIn's own "Save to PDF" export is routinely 3-8 pages and is a required input to LinkedIn Grader and Recruiting Lens (both Elite-paid). A 2-page cap there would break paying users on a change intended to enforce resume-length discipline. Affected LinkedIn surfaces that MUST NOT be capped at 2: `src/pages/LinkedInGrader.tsx:859`, `src/pages/RecruitingLens.tsx:907`, `src/pages/Onboarding.tsx:691`, `src/pages/Profile.tsx:550` (all use `LINKEDIN_PDF_ACCEPT`).
- **D-03:** Do **not** introduce a second, tightened LinkedIn page cap in this phase. The LinkedIn allowance is unchanged.
- **D-04:** User-facing rejection message is exactly: `Your document is longer than the 2-page limit. Please upload a PDF or DOCX file containing no more than 2 pages.`

### Two-Page Limit — DOCX Page Counting

- **D-05:** DOCX page count is read from `<Pages>` in `docProps/app.xml`. The existing ZIP-entry reader (`readZipTextEntry`, `src/lib/document-extraction.ts:326`) already performs exactly this class of read and should be reused rather than adding a ZIP dependency.
- **D-06:** **Fail-open with a word-count backstop.** If `<Pages>` is present and > 2 → reject. If `<Pages>` is absent, zero, or implausible (common for Google Docs / Pages / LibreOffice exports, which are a large share of real users) → accept, unless a conservative word-count backstop indicates the document cannot be two pages. Suggested backstop threshold: **~1,600 words** (planner may refine, but it must be conservative — a false rejection of a valid 2-page resume is worse than accepting an occasional 3-pager).
- **D-07:** Do **not** add a server-side DOCX-to-page converter. No such converter exists in the Deno edge runtime today and adding one is out of scope.
- **D-08:** PDF page count comes from the authoritative `pdf.numPages` (pdfjs), not from `PAGE_LIMITS`, which today is only an OCR *render* cap (`src/lib/document-extraction.ts:277`) and is not a rejection gate.

### Backend Enforcement Point

- **D-09:** Introduce **one shared server-side validation seam** that receives the raw file bytes (or the just-uploaded storage object) and returns accept/reject based on: extension allowlist, magic-bytes/content sniffing (so renamed and MIME-spoofed files are caught), and page count.
- **D-10:** That seam must be invoked **before Merit deduction and before any `analyze-*` invocation**. Constraint driving this: today no edge function ever receives the raw file — `ocr-pdf` receives pre-rendered page images (`supabase/functions/ocr-pdf/index.ts:251`) and the `analyze-*` functions receive already-extracted text. Client-side page counting alone is therefore trivially bypassed by a direct API call, which would not satisfy the brief's "enforce during actual file processing, not only through frontend copy or picker constraints."
- **D-11:** Client-side checks remain, but only as fast-feedback UX. The server check is authoritative.
- **D-12:** Validation failure must leave **no partial state** — no orphaned storage object, no resume row, no analysis record, no Merit deduction. This continues the Phase 1 rule that failure paths preserve state rather than half-commit.

### Removing `.md` / `.txt`

- **D-13:** Scope is **code + bucket MIME revocation, history preserved**:
  - Update the shared const `ACCEPTED_RESUME_DOCUMENT_EXTENSIONS` (`src/lib/document-extraction.ts:17`) to `['.pdf', '.docx']`, and `RESUME_DOCUMENT_TYPE_LABEL` (`:19`) accordingly. All seven `accept=` sites consume `ACCEPTED_RESUME_DOCUMENT_ACCEPT`, so they update transitively — verify, don't re-hardcode.
  - Remove the `plain_text` extraction branch (`src/lib/document-extraction.ts:84-87`) and the `extractPlainText` helper (`:304`). Preserve `extractDocxText` and all shared ZIP/canonicalization utilities — they remain in use.
  - New migration revoking `text/plain`, `text/markdown`, `application/markdown`, `application/x-markdown` from the `resumes` storage bucket, superseding `supabase/migrations/20260607050000_allow_resume_document_mime_types.sql`. **Ship rollback SQL alongside it** (project convention).
  - Update the literal-assertion test at `src/pages/__tests__/document-extraction-primary.test.ts:53` (asserts the four-extension array verbatim) and `:57-58` (assert the migration contains `text/plain` / `text/markdown`).
  - Rejection message is exactly: `Unsupported file type. Please upload a PDF or DOCX file.`
- **D-14 (data):** Historical resumes originally uploaded as `.md`/`.txt` are **left intact and readable**. `allowed_mime_types` gates only *new* uploads, so revoking it does not orphan existing rows or break analysis history. Do **not** migrate, flag, or purge legacy user data — that is destructive on production and outside the brief.

### Recruiting Lens Character Limit

- **D-15:** **The limit is 6,000 characters, not 8,000.** This supersedes the original `01.1-BRIEF.md` figure (operator decision, 2026-07-23). The brief has been updated in the same commit so the two artifacts agree. All Required Tests in the brief that referenced 8,000/8,001 now reference 6,000/6,001.
- **D-16:** User-facing message is exactly: `Job descriptions may contain up to 6,000 characters.`
- **D-17:** **Reject, never truncate.** Delete `jobDescription.slice(0, 3000)` (`supabase/functions/recruiting-lens/index.ts:490`) and replace it with validation: > 6,000 → `400` carrying the D-16 message. Rejection happens before Merit deduction and before any Anthropic call. The existing `< 50` minimum-length guard (`:499`) is unchanged.
- **D-18:** Client: `maxLength={6000}` (`src/pages/RecruitingLens.tsx:857`) and counter reads `{n}/6000` (`:864`).
- **D-19:** The counter's warning threshold stays **proportional at 90%** — currently hardcoded `2700` (`src/pages/RecruitingLens.tsx:863`), becomes **5,400**. Derive it from the limit constant rather than hardcoding a second number, so the two cannot drift.
- **D-20:** There is **no DB constraint and no Zod schema** on `job_description` — confirmed by scout. The 3,000 lives in exactly three places (`RecruitingLens.tsx:857`, `:863-864`, `recruiting-lens/index.ts:490`). Do not invent new persistence-layer constraints; do confirm the value is not duplicated anywhere the scout missed.

### Recruiting Lens Combined Input Ceiling

- **D-21:** Resolve the second, larger trimmer by **raising the combined input ceiling** so the JD increase is fully additive. **CONFIRMED 2026-07-23 (post-research): 51,000 / 12,750.** This is a **three-file lockstep change**, not a single cell:
  - `maxCharactersInput.recruitingLens` (`src/config/pricing-config.ts:156`): **48,000 → 51,000** for both `pro` and `elite`
  - `maxTokensInput.recruitingLens` (`src/config/pricing-config.ts:150`): **12,000 → 12,750** for both `pro` and `elite`
  - `src/config/pricing-config.snapshot.ts`: updated in the same commit

  **Why all three:** `src/config/__tests__/sc12-snapshot.test.ts:35-51` machine-enforces `maxCharactersInput === maxTokensInput * 4` on every non-null row, plus a byte-equality snapshot guard. Changing only `maxCharactersInput` turns `npm test` red and blocks every deploy. 12,750 × 4 = 51,000 exactly.
- **D-22:** **Trim priority order is unchanged** (`linkedinText → jobDescription → resumeSummary`, `supabase/functions/recruiting-lens/index.ts:540-558`). With a fully-additive ceiling the trimmer cannot realistically reach the JD, so reordering would add churn to working code for no practical gain. The existing `input-trimmed` log line (`:541`) stays as the audit trail.
- **D-23:** **Phase 02 interaction — call this out in the plan.** `getMaxInputChars('recruitingLens')` is one of the inputs Phase 02's token measurement calibrates against. Because 01.1 lands before Phase 02 resumes, the measurement will observe the new 51,000 reality — but any Phase 02 baseline captured before this change must not be compared directly against post-01.1 numbers. Note this in `.planning/phases/02-ai-token-cost-optimization/` when the change lands.

### Post-Research Additions (2026-07-23)

- **D-26 (REVISED 2026-07-23 after pattern mapping — supersedes the original wording):** **The server validation seam is authenticated-only. The anonymous hero path is gated client-side instead.**

  *Corrected premise:* an earlier draft of this decision said the seam must "mirror `analyze-resume`'s anonymous posture." **That posture does not exist.** `analyze-resume` hard-rejects unauthenticated callers with 401 at `supabase/functions/analyze-resume/index.ts:1352-1357`. The anon hero branch (`src/components/MinimalHero.tsx:171-195`) performs no `storage.upload`, no `resumes` insert, and no merit deduction — it extracts text client-side, writes it to `sessionStorage`, absorbs the 401, and returns `isDemo: true` after a fixed 8-second wait. There is no live anonymous bypass.

  *The real exposure:* `src/pages/Auth.tsx:42-88` replays `pendingResumeText` after signup — inserting a `resumes` row and invoking `analyze-resume` for a **real** analysis. By then the `File` object is gone and only extracted text remains, so a server seam can never inspect it.

  *Decision:* validate file type and page count **client-side in the anon branch** of `MinimalHero` and `ActionFirstHero`, **before anything is written to `sessionStorage`**. The `File` object is in scope there, so pdfjs `numPages` (D-08) and the DOCX `app.xml` read (D-05) both work. Nothing invalid reaches `sessionStorage`, so the `Auth.tsx` replay is clean by construction. Do **not** create a publicly-callable validation endpoint — it would add real attack surface against a threat that does not exist while missing the one that does. The server seam (D-09..D-12, D-27) stays authenticated-only and covers the five flows that actually write to storage.
- **D-27:** **The validation seam sits before `storage.upload`, not after extraction.** Research established that every resume flow currently runs `storage.upload → createSignedUrl → resumes.insert → extractDocumentFromFile` — extraction (the only place page count is observable today) happens *after* the storage object and DB row exist, and `src/pages/__tests__/document-extraction-primary.test.ts:74-77` actively asserts that ordering. To satisfy D-12 (no partial state), validation must run **before** `storage.upload` in all five flows: `Upload.tsx:133`, `MinimalHero.tsx:103`, `Onboarding.tsx:274`, `Profile.tsx`, `CareerCompass.tsx:531`. Insert it **after** the `file_hash` dedup check so historical 3-page resumes still reach their existing report.
- **D-28:** **`allowed_mime_types` is defense-in-depth only, not spoofing enforcement.** It validates the client-declared `Content-Type`, which `storage-js` derives from `File.type`, which the browser derives from the extension. Magic-byte sniffing in the seam is the actual anti-spoofing enforcement. Do not write an acceptance test claiming the bucket allowlist catches spoofed content.
- **D-29:** **`Jobs.tsx` receives the transitive const change only.** It invokes a `match-jobs` function that does not exist under `supabase/functions/`, so the page appears dead. It picks up the new `accept` value for free via the shared constant — do not invest in tests, fixtures, or investigation for it beyond that.
- **D-31:** **Shared frontend/edge constants are re-exported, never duplicated.** Pattern mapping established that `src/config/pricing-config.ts` is the only proven dual-import module, and that zero dependencies is the load-bearing property that makes it importable from Deno. Edge callers reach it via the re-export bridge in `supabase/functions/_shared/tier-config.ts:168-191` using a literal `'../../../src/config/pricing-config.ts'` path. Any new shared limits module (D-24) MUST copy both halves of that pattern — zero imports, plus a `_shared` re-export bridge. Do not duplicate the constants across the boundary.
- **D-32:** **Every new edge function and test file needs three-place registration**, each silently no-op when missed: `supabase/config.toml`, the `$Functions` list in `scripts/deploy.ps1` (unlisted → never deploys), and the `test:ci` file-list allowlist in `supabase/functions/deno.json` (unlisted → never runs, reads as green).
- **D-33:** **Rollback SQL is a separate file**, at `supabase/migrations/rollback/<same-timestamp>_<same-name>.rollback.sql`, with line 1 = `-- Rollback for <forward filename>`.
- **D-30:** Two research risks become **explicit execution-blocking checkpoints**, not assumptions: **(a)** Plan 03 cannot complete until direct Google Docs and Apple Pages DOCX `<Pages>` observations are recorded; **(b)** Plan 12 cannot proceed to production until the `validate-document` preview deploy proves `--use-api` bundle acceptance and boot under the 5 MB server-side cap. Plan 11 remains deterministic/local and cannot satisfy D-30(b).

### Cross-Cutting

- **D-24:** Prefer **shared constants** over duplicated literals wherever frontend and backend both need a limit, to prevent the drift the brief calls out. The existing `ACCEPTED_RESUME_DOCUMENT_EXTENSIONS` pattern is the model.
- **D-25:** Preserve authentication, authorization, billing, Merit, analytics, and existing upload-security behavior unchanged. Do not alter Recruiting Lens pricing or Merit costs. Do not change unrelated text-input limits (e.g. `interview-prep-prompts.ts` 6000/4000 slices are prompt-construction budgets, not user-facing limits — leave them alone).

### Claude's Discretion

- Exact file/module boundary for the shared server validation seam (new edge function vs. extending an existing one), its request/response shape, and its test seams — provided D-09 through D-12 hold.
- Exact word-count backstop threshold for DOCX (D-06), provided it is conservative in the accept direction.
- Component boundaries, query keys, semantic-token styling, spacing, and responsive layout within established Strivo patterns.
- Exact supporting/helper copy may be polished, but the four locked user-facing messages (D-04, D-13, D-16) must appear verbatim.

</decisions>

## Existing Code Insights

### Reusable Assets
- **`ACCEPTED_RESUME_DOCUMENT_EXTENSIONS` / `ACCEPTED_RESUME_DOCUMENT_ACCEPT`** (`src/lib/document-extraction.ts:17-18`): a genuine single source of truth already consumed by all seven resume `accept=` sites. Changing the array propagates automatically — this is the intended lever, not per-page edits.
- **`readZipTextEntry`** (`src/lib/document-extraction.ts:326`): existing dependency-free ZIP central-directory reader with `deflate-raw` inflation. Reads `word/document.xml` today; reading `docProps/app.xml` for `<Pages>` is the same call with a different entry name.
- **`invokeWithTimeout`** (`src/lib/fetchWithTimeout.ts`): established client→edge invocation wrapper with JWT-refresh retry; the natural transport for a new validation seam.
- **`getMaxInputChars` / `getMaxOutput`** (`src/config/pricing-config.ts`): the central per-feature/per-tier limit table. The ceiling change belongs here, not inline in the edge function.

### Established Patterns
- **Separate document types.** `DocumentType = 'resume' | 'linkedin_profile'` with per-type `PAGE_LIMITS` and `QUALITY_THRESHOLDS` records already exists — D-01/D-02's resume-vs-LinkedIn split fits the existing shape rather than introducing a new axis.
- **Layered caps.** Recruiting Lens already has two independent limits (per-field slice, then a combined ceiling with priority trimming). Changing only the per-field one leaves the second in place — this is exactly the trap D-21 addresses.
- **Literal-assertion tests.** Several tests assert source literals verbatim (`document-extraction-primary.test.ts:53`), so constant changes intentionally break tests. Expect and update them; do not weaken the assertions.
- **Migration + rollback.** Every migration ships rollback SQL; production application is operator-gated (`CLAUDE.md`).
- **Fail-before-charge.** Merit deduction happens at submit time behind `MERIT_SYSTEM_ENABLED`; all new rejections must land upstream of it.

### Integration Points
- New server validation seam ↔ the client upload flows in `Upload.tsx`, `Onboarding.tsx`, `Profile.tsx`, `CareerCompass.tsx`, `Jobs.tsx`, and the two hero components.
- New seam ↔ Merit deduction and `analyze-*` submit boundary (must run strictly before both).
- Bucket MIME migration ↔ the `resumes` storage bucket and any code path that re-uploads or re-processes stored documents.
- `getMaxInputChars('recruitingLens')` ↔ Phase 02 telemetry baselines (D-23).

</code_context>

<specifics>
## Specific Ideas

- The four user-facing messages are locked verbatim and must appear exactly as written: the 2-page message (D-04), the unsupported-type message (D-13), and the 6,000-character message (D-16).
- The operator explicitly revised the Recruiting Lens limit down from the brief's 8,000 to **6,000** mid-discussion (D-15). Anyone reading the original brief text without this CONTEXT would implement the wrong number — the brief has been updated in the same commit to remove that trap.
- Protecting LinkedIn PDF uploads from the 2-page cap (D-02) was the highest-risk finding of the scout: the literal brief reading would have broken LinkedIn Grader and Recruiting Lens for most real users.

</specifics>

## Deferred Ideas

- **Tightening the LinkedIn profile page allowance** (currently 12). Considered and explicitly declined for this phase (D-03). If LinkedIn-export size becomes a cost or quality concern, it belongs in its own phase — likely alongside Phase 02's token work, since the driver would be input tokens rather than the resume-length discipline motivating this phase.
- **Server-side DOCX-to-page conversion** for exact page counts (D-07). Requires a converter that does not exist in the Deno edge runtime; revisit only if the fail-open backstop proves too permissive in practice.
- **Purging or flagging legacy `.md`/`.txt`-sourced resumes** (D-14). Destructive to historical user data; out of scope here.
