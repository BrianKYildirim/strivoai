# Phase 04.2: Add Costing Telemetry for Product Usage, AI Calls, and OCR

**Status:** Not planned
**Inserted after:** Phase 4
**Scope boundary:** Production costing telemetry that requires code changes. Do not modify the costing spreadsheet, pricing, merit costs, feature behavior, prompts, outputs, or user interface.

## Objective

Add the production telemetry required to replace estimated costing-sheet inputs with real Strivo usage data.

The implementation must accurately measure:

1. Product MAU by subscription tier.
2. Feature usage by tier.
3. Merits charged and refunded.
4. Anthropic token usage and cost by feature.
5. AI retries, failures, and wasted AI cost.
6. PDF and DOCX extraction behavior.
7. OCR usage, pages, retries, failures, provider, and cost.

## 1. Audit the current implementation

Before changing code, inspect and document:

- Every production feature entry point.
- Resume Analysis.
- LinkedIn Grader.
- Career Compass.
- Recruiting Lens.
- Interview Prep Coach, if currently active.
- Merit charging and refund logic.
- Free versus Elite access checks.
- Monthly versus annual Elite subscription storage.
- Every Anthropic API call.
- Existing shared AI wrappers.
- Automatic retry logic.
- Model fallback logic.
- PDF parsing.
- DOCX parsing.
- OCR or document-vision fallback logic.
- Existing request IDs, diagnostics, analytics, or logging tables.

Reuse reliable existing infrastructure where possible. Do not create duplicate telemetry for data that is already recorded accurately.

## 2. Use one identifier for each feature run

Create one server-generated `feature_run_id` for every user-triggered analysis.

The same `feature_run_id` must connect:

- The feature request.
- Merit charging.
- Merit refunds.
- Document processing.
- OCR processing.
- Anthropic calls.
- AI retries.
- The final feature result.

Do not trust a client-generated identifier.

Do not create a new feature-run record for each retry or internal AI step.

- `subscription_period_at_time` records `monthly` or `annual` for Elite users.

- Record the actual merits refunded after failures.

## 4. Record the full feature-run lifecycle

When a feature begins:

- Insert one feature-run record.
- Record the user, feature, tier, subscription period, input type, and start time.

When merits are charged:

- Update the same record with the exact number charged.

When the feature succeeds:

- Set the status to `completed`.
- Record the completion time.

When the feature fails:

- Set the status to `failed`.
- Record the completion time.
- Record a safe error code and category.
- Record any merits refunded.

When the request is canceled:

- Set the status to `canceled`.

Avoid leaving normal finished requests permanently marked as `started`.

## 6. Use a shared Anthropic telemetry wrapper

Create or extend a shared Anthropic wrapper so all AI calls are logged consistently.

The wrapper must:

1. Receive the current `feature_run_id`.
2. Receive the feature name.
3. Receive an `operation_name`.
4. Receive the user ID and tier.
5. Record the model.
6. Record the attempt number.
7. Record whether the attempt is a retry.
8. Create the AI-call telemetry record.
9. Execute the Anthropic request.
10. Read token usage from the response.
11. Record success or failure.
12. Calculate the estimated cost.
13. Preserve existing application error behavior.

Search the entire repository for direct Anthropic SDK or HTTP calls.

Every production Anthropic call path must either:

- Use the shared wrapper, or
- Record equivalent telemetry.

Do not leave untracked direct Anthropic calls.

## 7. Centralize model pricing

Create one central model-pricing configuration used to calculate AI-call costs.

Support:

- Input-token price.
- Output-token price.
- Cache-write price.
- Cache-read price.
- Exact model identifier.
- Effective date or pricing-version identifier.

Calculate each call's cost from its actual model and token usage.

Do not duplicate token prices across separate feature files.

Preserve token counts so historical costs can be recalculated when pricing changes.

## 8. Distinguish required AI steps from retries

Some features may intentionally make multiple AI calls.

Use `operation_name` to distinguish required steps, such as:

```text
resume_parse
resume_score
resume_recommendations
linkedin_score
career_recommendations
```

A separate required operation is not a retry.

A retry is an additional attempt of the same logical operation caused by:

- Timeout.
- Rate limit.
- Provider error.
- Invalid structured output.
- Parsing failure.
- Explicit retry handling.
- Model fallback repeating the same logical operation.

Use:

- `attempt_number = 1` for the original attempt.
- `attempt_number > 1` for later attempts.
- `is_retry = true` only for retry attempts.

## 9. Measure AI failures and wasted cost

The data must distinguish:

- A failed call that later succeeds on retry.
- A failed call that causes the full feature run to fail.
- A successful AI call followed by a later application failure.
- A failed feature run where merits are refunded.
- A user-visible failure that still consumed AI tokens.

The implementation must support calculations for:

```text
Total AI cost
Retry AI cost
Failed AI-call cost
AI cost linked to failed feature runs
AI cost by feature
AI cost by tier
AI cost by model
AI cost per completed feature run
```

Refunding merits must not remove or hide the actual AI cost.

## 12. Measure OCR routing

Inspect and instrument the actual OCR or document-vision fallback route.

Record `ocr_triggered = true` only when a document is actually sent through OCR or a vision-based extraction route.

Record:

- Why OCR was triggered.
- OCR provider.
- OCR model, when applicable.
- Number of pages processed.
- Number of attempts.
- Final OCR status.
- Provider request identifier, when available.
- Provider-reported cost, when available.
- Safe failure category.

Possible OCR trigger reasons may include:

```text
empty_extraction
insufficient_text
scanned_document
parser_error
unsupported_encoding
manual_fallback
other
```

Use only reasons that reflect real application behavior.

If Strivo currently uses an AI vision model instead of a dedicated OCR provider:

- Record the actual provider and model.
- Record its tokens and calculated cost.
- Do not label it as a different provider.
- Avoid double-counting the same call in OCR and Anthropic totals.

If Strivo does not currently have an OCR route:

- Do not add a new OCR provider.
- Do not invent an OCR cost.
- Instrument the existing document-processing behavior.
- Keep the schema ready to record OCR later.

## 16. Prevent duplicate records

Make writes idempotent where requests may be retried by the browser, server, Edge Function, or network.

Add appropriate unique constraints based on the actual architecture.

Possible uniqueness rules include:

```text
feature_run_id
feature_run_id + operation_name + attempt_number
provider_request_id
request_id + document identifier
```

Do not create duplicate feature runs for the same server-side action.

Do not create duplicate AI-attempt records for the same provider request.

Telemetry failures should be logged, but a noncritical telemetry failure should not cause an otherwise successful user analysis to fail.

## 17. Security and privacy

Use the project's existing Supabase security model.

Requirements:

- Sensitive telemetry writes must happen in trusted server code, Edge Functions, or service-role contexts.
- Client code must not be able to submit arbitrary token counts or AI costs.
- Users must not be able to read other users' telemetry.
- Do not expose service-role credentials.
- Do not store raw prompts.
- Do not store document text.
- Do not store generated reports.
- Do not store payment details.
- Do not store secrets in error records.
- Avoid unnecessary personal data.

Add appropriate Row Level Security policies.

## 19. Separate production from non-production

- QA.
- Staging.

Ensure production and non-production Anthropic usage can be separated accurately.
