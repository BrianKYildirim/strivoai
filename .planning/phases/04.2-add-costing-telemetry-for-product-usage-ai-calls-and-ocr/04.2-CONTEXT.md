# Phase 04.2: Add Costing Telemetry for Product Usage, AI Calls, and OCR - Context

**Gathered:** 2026-08-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Add server-owned, privacy-safe production telemetry that measures product feature runs, Merit charges and refunds, Anthropic attempts and costs, document extraction, and the existing OCR fallback chain. The resulting monthly production-only views and canonical SQL must replace estimated costing inputs with auditable real usage while preserving all current feature behavior.

The authoritative scope is `04.2-BRIEF.md`. This phase does not change pricing, subscriptions, Merit allowances or costs, feature access, prompts, outputs, onboarding, document limits, OCR providers, the costing workbook, or any user-facing interface. Telemetry failure must never turn an otherwise successful analysis into a user-visible failure.

</domain>

<decisions>
## Implementation Decisions

### Run-counting boundaries

- **D-01:** A `feature_run` begins only after authentication and request-envelope validation succeed, but before content validation, document extraction, Merit activity, or AI work. Unauthorized and structurally malformed traffic belongs in existing diagnostics/logging, not product-costing telemetry.
- **D-02:** An exact-input cache hit is a completed feature run because the user successfully used the product. Mark it as cache/reuse-served, record zero new AI cost, and record the actual Merits charged (normally zero). It counts toward product MAU and feature usage.
- **D-03:** Every deliberate rerun and incremental Elite unlock creates a new feature run. Retain the canonical feature value (for example, `resume_analysis`) and distinguish the action with a run variant such as `rerun` or `elite_unlock`; do not mutate the original run or invent a separate feature family.
- **D-04:** Use `canceled` only when the server receives a confirmed cancellation. A stale or unrecoverable run must be terminalized as `failed` with a controlled abandonment or timeout code. Never leave normally finished or irrecoverable work permanently marked `started`.

### Historical continuity and ledger ownership

- **D-05:** Preserve the existing Phase 02 `ai_call_telemetry` rows as partial historical evidence. The Phase 04.2 production activation timestamp begins the first complete costing epoch; never infer missing historical correlations, tier snapshots, environments, or prices.
- **D-06:** Extend `ai_call_telemetry` additively in place. Keep its current name and existing report compatibility, use nullable new fields for legacy rows, and do not introduce a second AI-call source of truth or a dual-write cutover.
- **D-07:** Create a dedicated `feature_runs` costing ledger. Link an `analysis_jobs` row when one exists, but do not repurpose the operational queue/lifecycle table as the universal costing ledger because it does not uniformly cover every live feature path.
- **D-08:** Standard reports may include pre-04.2 rows only in clearly labeled AI-only historical outputs carrying a completeness or telemetry-version marker. Exclude them from complete joined costing metrics that require a valid feature-run relationship.

### Cost valuation and pricing history

- **D-09:** Standard monthly reports use the price effective when each provider call occurred and label that amount as incurred cost. Current-rate revaluation is allowed only as a separate, clearly labeled comparison; it must never silently rewrite historical incurred totals.
- **D-10:** Maintain one append-only pricing catalog keyed by exact provider/model identifier and effective timestamp. Price changes are reviewed and applied through database migrations; historical pricing rows are never overwritten in place.
- **D-11:** When an OCR provider supplies a final, attributable per-request cost, preserve both provider-reported and independently calculated values. Use the provider-reported value for incurred reporting, fall back to the calculated value when necessary, and expose any variance.
- **D-12:** Claude vision/OCR cost is owned by the corresponding `ai_call_telemetry` record and referenced from document telemetry. It must not be counted again as a second OCR cost.
- **D-13:** A failed attempt with no reported tokens, pages, or billed cost has `unknown` cost, not zero cost. Reports must show known-cost totals together with explicit unknown-cost attempt counts; modeled averages must not be presented as measured production spend.

### Reporting, exclusions, retention, and deletion

- **D-14:** Deliver service-role-only monthly views for stable costing inputs plus checked-in canonical SQL for drill-down, per-run evidence, and reconciliation. Do not add a user-facing analytics dashboard.
- **D-15:** Production test and internal accounts are excluded through an explicit server-owned account classification or `exclude_from_costing` flag. Snapshot the classification on each feature run, default ordinary accounts to included, and never derive historical exclusion from email addresses or current admin membership.
- **D-16:** Automatically retain identifiable raw event telemetry for 24 months and privacy-safe monthly aggregates for 5 years. Retention must be enforced automatically rather than through the existing manual cleanup note.
- **D-17:** When an account is deleted, immediately sever its Supabase Auth UUID while retaining an irreversible costing subject identifier so distinct-user MAU and historical cost totals remain accurate. The surviving identifier must not provide a route back to the deleted account; normal retention later removes the raw rows.

### the agent's Discretion

- Exact table and column types beyond the locked names and semantics above, including the concrete run-variant, telemetry-version, cost-confidence, exclusion-snapshot, and costing-subject field names.
- Exact controlled error taxonomy and stale-run deadline, provided cancellation is never inferred and every irrecoverable run reaches a truthful terminal state.
- Exact migration sequence, idempotency constraints, indexes, aggregation mechanism, and automated pruning mechanism, provided existing Phase 02 rows remain valid and telemetry never breaks a product flow.
- Exact implementation of the versioned pricing lookup and current-rate revaluation query, provided there is one append-only pricing source and incurred reporting uses the effective price at call time.
- Exact secure operator workflow for changing the internal/test-account classification, provided clients cannot control it and its value is snapshotted on each run.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `public.ai_call_telemetry` plus `_shared/ai-telemetry.ts`: already records one row per Anthropic attempt with feature, tier, call name, attempt, request/user IDs, exact model, token categories, stop reason, success, HTTP status, and timing. Phase 04.2 should extend this asset rather than duplicate it.
- `_shared/anthropic.ts`: the shared Anthropic seam used by the production feature functions. It already extracts cache token categories and emits telemetry for success and failure paths.
- `_shared/telemetry-coverage.test.ts`: scans the repository for uninstrumented Anthropic call sites and can be extended to enforce the new feature-run and operation context.
- `analysis_jobs` and `_shared/analysis-lifecycle.ts`: provide useful server-side idempotency, state, Merit settlement, retry, and terminalization patterns even though they are not a universal live feature ledger.
- `_shared/document-extraction.ts` and its typed metadata: already expose the real parser/Mistral/Textract/Claude routing order, attempted providers, quality outcomes, and fallback reasons.

### Established Patterns

- Costing and diagnostic tables are backend-only: RLS is enabled, authenticated access is denied, and direct grants are revoked. New telemetry and reporting surfaces must preserve that posture.
- Telemetry writers are awaited for durability but have a never-throws contract, so database instrumentation cannot fail an analysis.
- Existing AI rows intentionally omit foreign keys to user accounts so auth deletion cannot block or cascade away measurement history. D-17 replaces the raw Auth UUID link with an irreversible costing subject on deletion.
- Exact-input cache reuse, async queue work, deliberate reruns, and incremental Elite unlocks are distinct runtime paths. They must converge on the same server-generated feature-run identity contract without changing their behavior.
- Current environment separation is not a single shared backend primitive. Planning must establish a trusted explicit environment snapshot for every telemetry record and keep monthly costing views production-only.

### Integration Points

- `feature_runs` begins after shared auth/request-envelope validation and is threaded through Merit activity, document processing, every AI operation/attempt, persistence, and terminalization.
- `ai_call_telemetry` gains feature-run correlation, environment, retry semantics, cost/pricing-version fields, and safe failure classification while preserving legacy rows and existing Phase 02 reports.
- Document processing records extend the existing extraction metadata with page/file counts, trigger reasons, provider/model/request IDs, attempt totals, outcome, and cost references.
- Merit charge and refund results update the same feature run; refunds never erase incurred AI or OCR cost.
- Service-role monthly views filter `environment = 'production'`, exclude the snapshotted internal/test cohort, use completed runs for product MAU, and expose unknown-cost counts beside known totals.

</code_context>

<specifics>
## Specific Ideas

- Treat the Phase 04.2 production activation timestamp as a named telemetry epoch so operators can distinguish partial Phase 02 history from fully correlated costing data without guessing.
- Keep feature vocabulary stable while adding a separate run-variant dimension for cache service, reruns, and `elite_unlock` actions.
- Label monetary outputs explicitly as `incurred` or `current-rate revaluation`; never present them as interchangeable.
- A reported zero means a verified zero. Missing provider usage or billing evidence is `unknown` and remains visible in monthly reconciliation.
- Monthly views are the stable workbook-input surface; checked-in SQL is the audit trail back to attempts and runs.

</specifics>
