# Phase 04.2 Research: Costing Telemetry for Product Usage, AI, and OCR

**Researched:** 2026-08-01
**Method:** Live-code manual fallback. The configured `gsd-phase-researcher` could not start because its fixed model is unavailable for this ChatGPT account; no agent research result is claimed.
**Confidence:** High for repository architecture; provider prices must still be seeded through reviewed migrations and verified against official pricing at implementation time.

## Summary

Phase 04.2 should extend the existing telemetry seam rather than introduce parallel event systems. The repository already has a never-throws, service-role-only `ai_call_telemetry` writer behind the shared Anthropic client. The missing layer is a durable server-generated feature-run identity that is created before costly work and threaded through Merit settlement, document extraction, OCR, every Anthropic attempt, and terminal completion.

The safest architecture is three raw ledgers plus one append-only pricing catalog:

1. `feature_runs` is the product/costing parent record and snapshots tier, subscription period, environment, run variant, costing exclusion, Merit charge/refund, and terminal outcome.
2. Existing `ai_call_telemetry` is extended additively with `feature_run_id`, true per-operation attempt semantics, environment, safe error classification, pricing version, and incurred cost. Legacy Phase 02 rows remain nullable and explicitly incomplete.
3. `document_processing_runs` records one row per processed PDF/DOCX and the actual parser/OCR route. Claude vision work references its AI row instead of duplicating its cost.
4. `provider_pricing` is append-only and effective-dated. Each charged event snapshots the applied pricing row and calculated amount so historical incurred cost never changes.

Monthly service-role views should read only complete Phase 04.2 production rows, exclude snapshotted internal/test runs, and publish known cost plus unknown-cost counts. A scheduled database retention function should detach raw Auth UUIDs immediately on account deletion, retain irreversible costing subjects, aggregate before the 24-month raw-event cutoff, and retain privacy-safe aggregates for five years.

## Existing Architecture

### AI telemetry already exists and is the correct seam

- `supabase/migrations/20260721000000_ai_call_telemetry.sql` defines the current raw AI event ledger. It is service-role-only, keeps exact token categories, and intentionally has no Auth foreign key.
- `supabase/functions/_shared/ai-telemetry.ts` has the correct reliability contract: the write is awaited for durability but never throws into the product path.
- `supabase/functions/_shared/anthropic.ts` is the production Anthropic chokepoint. It already records successful token usage, cache creation/read tokens, stop reason, HTTP result, and duration, including failed HTTP attempts with unknown usage.
- `supabase/functions/_shared/telemetry-coverage.test.ts` statically checks enrolled feature functions for telemetry context.
- `supabase/queries/ai_call_telemetry_report.sql` is a Phase 02 AI-only report with embedded model prices and a manual 180-day retention note. It must remain usable for legacy evidence but cannot be the complete costing report.

Do not create a second `ai_calls` table. D-06 makes additive evolution of `ai_call_telemetry` the only source of truth.

### Retry numbering is currently ambiguous

`supabase/functions/_shared/ai-retry.ts` can invoke the same Anthropic operation multiple times while forwarding an unchanged `telemetry.attempt`. Caller-level validation retries sometimes set attempt 2, but retries inside either logical attempt can reuse that number. This breaks uniqueness, retry-rate reporting, and debugging chronology.

Implement an operation-scoped attempt allocator owned by the retry wrapper or caller context. Every physical provider request for the same `(feature_run_id, operation_name)` must receive a monotonically increasing attempt number. Required parallel operations remain distinct through `operation_name`; they are not retries.

### OCR coverage is incomplete

`supabase/functions/ocr-pdf/index.ts` calls `invokeAnthropicText` from `runClaudePageOcr` without telemetry context, and `ocr-pdf` is not enrolled in `telemetry-coverage.test.ts`. This is a real missing-cost path.

The shared extraction chain is parser -> Mistral -> Textract -> permitted Claude vision. Its current metadata is useful operational evidence, but the provider clients return only `{ text }` or a safe failure reason:

- `mistral-ocr-client.ts` discards model, page count, response/request identifiers, duration, and cost metadata.
- `textract-client.ts` calls an internal compatible endpoint and discards provider request identifiers, AWS operation/region, billable pages, retries, duration, and cost metadata.
- Claude OCR is an Anthropic call and must be linked, not charged twice.

The browser extraction layer also uses `pageCount: 0` as an unavailable sentinel in some PDF and DOCX paths. Telemetry must normalize unavailable counts to SQL `NULL`; zero is only valid when the provider explicitly processed zero pages.

### Operational rows are not event ledgers

`resumes.extraction_metadata`, `profiles.linkedin_pdf_extraction_metadata`, document hashes, and accepted extraction versions describe the latest persisted document state. They cannot answer how many attempts, fallbacks, failures, or costs occurred. Keep them unchanged and write separate append-only document-processing events.

### Cache, queue, and rerun paths require convergence

Exact-input `analysis_cache` hits perform no new Anthropic work. Per D-02 they still need a completed `feature_runs` row with a reuse marker, zero new AI cost, and the actual Merit amount.

`analysis_jobs` contains strong lifecycle/idempotency patterns for resume and career queue paths, but it does not cover every feature or synchronous route. Add a nullable `analysis_job_id` link to `feature_runs`; do not replace either ledger with the other.

Deliberate reruns and Elite unlocks create new feature runs using the same canonical feature and a separate variant. They must not mutate or attach new costs to the original run.

## Recommended Data Model

### `costing_subjects`

Use a durable random UUID (or equivalent high-entropy identifier) as `costing_subject_id`. While the account exists, keep a unique nullable `auth_user_id` mapping in a service-role-only table. Raw ledgers reference `costing_subject_id` and may additionally carry nullable `user_id` only for bounded operational tracing.

An Auth `BEFORE DELETE` trigger must null the mapping and raw ledger `user_id` fields transactionally. The costing subject is random and contains no email-derived, UUID-derived, or reversibly hashed material. This satisfies D-17 while preserving distinct-user history. The existing deletion model aggressively cascades user-owned data; these costing ledgers must therefore avoid `ON DELETE CASCADE` to `auth.users`.

### `feature_runs`

Recommended fields beyond the brief:

- `id uuid` server-generated primary key (`feature_run_id`).
- `request_id text` and optional `idempotency_key_hash text`; never trust a client feature-run ID.
- `costing_subject_id uuid`, nullable `user_id uuid` without a cascading FK.
- `analysis_job_id uuid null` where a queue job exists.
- constrained `feature`, `run_variant`, `status`, `input_type`, and `environment` text values.
- `tier_at_time`, nullable `subscription_period_at_time`, `exclude_from_costing_at_time`.
- `telemetry_version` and `costing_epoch`.
- `served_from_cache boolean` and optional safe cache-source code.
- exact `merits_charged` and `merits_refunded`, defaulting to verified zero only after settlement evidence.
- `started_at`, `completed_at`, `created_at`, `updated_at`, safe `error_code` and `error_category`.

Create the row after auth and request-envelope validation and before content validation. Insert idempotently on the server action key. Terminal updates must be idempotent and may never downgrade a completed terminal state.

The subscription period snapshot should be resolved from the exact `profiles.stripe_price_id` through `buildPriceMap()`/a new interval-returning resolver. Unknown or non-Elite periods remain `NULL`; do not guess from tier or current profile state later.

### Additive `ai_call_telemetry` fields

Add nullable fields for legacy compatibility:

- `feature_run_id`, `costing_subject_id`, nullable `user_id` detachment support.
- canonical `operation_name` (with `call_name` preserved as a compatibility alias/source).
- `is_retry`, true monotonic `attempt_number` semantics (preserve existing `attempt`).
- `provider` (`anthropic`), `environment`, `exclude_from_costing_at_time`, `telemetry_version`, `costing_epoch`.
- `started_at`, `completed_at`, safe `status`, `error_code`, `error_category`.
- `pricing_id`, calculated `incurred_cost_usd`, and `cost_known`/`cost_confidence`.
- optional unique provider request ID if the Anthropic response headers expose one.

Keep token fields raw. A failed attempt with no usage has null incurred cost and increments `unknown_cost_attempts`; missing token categories on a successful response may normalize to verified zero only when the provider response establishes their absence.

### `document_processing_runs`

Create one row per document, not one row per provider attempt. Include a stable server-generated document event ID and an idempotency key derived from the feature run plus the server-recognized document position/hash. Do not store the hash if it would create an unnecessary cross-run tracking surface; a run-local ordinal is sufficient where available.

Record:

- parent correlation, user/costing subject snapshots, feature/tier/environment/exclusion snapshots.
- `file_type`, nullable `page_count`, `file_size_bytes`, `document_count`/ordinal.
- initial extractor and final extractor, extraction status, character count, and duration.
- actual OCR trigger boolean/reason, provider/model, nullable pages, attempt count, final status.
- provider request ID when returned, provider-reported and calculated cost, cost source, variance, and pricing ID.
- nullable `ai_call_telemetry_id` for Claude OCR cost ownership.
- safe errors and timestamps.

For a parser success, `ocr_triggered=false`, OCR attempts/cost are verified zero. For a configured-provider failure with no page/billing evidence, cost remains unknown. For accepted extraction reuse, record reuse as the extraction route and do not invent OCR work.

### `provider_pricing`

Use an append-only table keyed by `(provider, exact_sku_or_model, effective_from)` with optional `effective_to` enforced as non-overlapping periods. Include pricing unit (`per_million_tokens`, `per_1000_pages`, etc.), input/output/cache-write/cache-read/page amounts, currency, region/API variant where relevant, source URL, and migration/version label.

Never update a historical price row. Insert a new effective version. Each event stores the selected pricing ID and calculated amount.

Current official sources show why this must be versioned:

- Anthropic pricing distinguishes input, 5-minute and 1-hour cache writes, cache reads, output, model, and long-context conditions: https://docs.anthropic.com/en/docs/about-claude/pricing
- Mistral's current catalog distinguishes OCR model/version and standard versus annotated pages: https://mistral.ai/pricing/api/
- AWS Textract varies by API, feature combination, usage tier, and region: https://aws.amazon.com/textract/pricing/

Seed only SKUs actually used by deployed configuration. The Textract-compatible endpoint must disclose the real operation, region, request ID, and billable-page semantics before its calculated cost can be marked known.

A signed short-lived correlation token or server lookup keyed to an authenticated pending run avoids client authority while preserving the existing browser-assisted flow.

## Reporting and Retention

Create service-role-only views for monthly product MAU, feature usage, AI usage, and document/OCR usage. Default filters are:

- `environment = 'production'`
- `exclude_from_costing_at_time = false`
- complete Phase 04.2 `costing_epoch`/`telemetry_version`

Product MAU is distinct `costing_subject_id` among completed feature runs, grouped by the run-time tier and subscription period. It must be labeled product MAU, not Supabase billable Auth MAU.

Views should expose both `known_incurred_cost_usd` and `unknown_cost_attempts`/`unknown_cost_documents`. Current-rate revaluation belongs in separately named views or SQL. Use `NULLIF` for safe division and `COALESCE` only where a semantic zero is verified.

Before raw rows exceed 24 months, a security-definer scheduled function should roll them into privacy-safe monthly aggregates, then delete raw AI/document/run rows. Aggregate rows must use cohort dimensions and enforce a small-cohort protection rule or suppress the distinct-user dimension where re-identification is possible. Delete aggregates after five years. Reuse the established idempotent `pg_cron` migration pattern from `phase42_layer5_lifecycle_archive.sql`; replace the old manual 180-day AI cleanup note.

## Security and Reliability Requirements

- All raw tables, pricing tables, aggregate tables, functions, and views are service-role/operator-only. Enable RLS and revoke `anon`/`authenticated` access; clients never write token or cost values.
- Add one explicit fail-closed backend environment variable (for example `STRIVO_RUNTIME_ENV`) to `docs/ENVIRONMENT.md` and environment skeletons. Accept only the locked vocabulary. Do not infer environment from `APP_URL`, project URL, Vite mode, or email.
- Snapshot the internal/test exclusion from a server-owned account-classification table. Default new ordinary users to included; no historical joins to current admin roles or email patterns.
- Telemetry helpers remain awaited and never throw. Log safe failure reasons through the existing structured logger.
- Controlled errors must contain no prompt, text, file, provider body, email, payment data, or secret.
- Idempotency constraints must protect feature runs and physical provider attempts without collapsing legitimate reruns.

## Known Pitfalls

1. Treating `0` as unknown corrupts page and cost averages. Use null plus explicit unknown counters.
2. Embedding current provider prices in reporting SQL silently rewrites history. Snapshot the applied pricing row and amount.
3. Reusing `req_id` as a feature-run ID is unsafe; request IDs are nullable and their lifecycle differs.
4. A model fallback is another attempt of the same operation, with the actual fallback model and its effective price.
5. Cache hits count as product use but not AI calls.
6. A successful AI attempt inside a later failed feature still incurs cost; never filter AI totals only to completed feature runs.
7. Merit refunds do not reverse provider cost.
8. Provider success without attributable billing data is not proof of zero cost.
9. Current Auth deletion cascades aggressively. A direct Auth UUID foreign key would either erase history or block deletion.
10. Adding telemetry only to top-level feature functions misses Claude OCR and worker paths. Coverage tests must enumerate all production Anthropic call sites.
11. Telemetry writes can fail. Product correctness and Merit settlement must remain unchanged and must not depend on the telemetry database write succeeding.

## Validation Architecture

### Test layers

1. **Pure Deno unit tests** for pricing selection/calculation, environment parsing, safe error classification, attempt numbering, subscription-period resolution, and no-throw telemetry behavior.
2. **Static coverage tests** proving every production `invokeAnthropic*` call supplies feature-run/operation context, including `ocr-pdf`, and proving no direct Anthropic fetch bypass exists.
3. **Feature contract tests** with mocked Supabase/provider calls for run creation timing, cache-hit completion, multi-operation versus retry semantics, Merit charge/refund updates, queue correlation, reruns, and terminalization.
4. **Document/OCR tests** for parser success, empty/insufficient extraction, Mistral/Textract/Claude routing, page counts, retry/failure, request IDs, unknown cost, and Claude no-double-counting.
5. **Database migration tests or preview-schema assertions** for RLS/grants, append-only pricing, idempotency constraints, deletion detachment, retention, and monthly view arithmetic.
6. **Remote preview tests** for durable row correlation across feature -> Merit -> document/OCR -> AI -> terminal result. No paid provider calls; use test mode/mocked providers.
7. **Full baseline** through `npm run verify:baseline` before phase verification.

### Minimum focused cases

Preserve the brief's 16 cases and add coverage for:

- exact cache reuse creates a completed feature run and no AI row;
- internal retry attempts are monotonic and model fallback records the actual model;
- failed attempt with absent usage yields unknown cost;
- legacy Phase 02 rows remain queryable but are absent from complete costing views;
- account deletion removes the Auth UUID link but preserves the irreversible subject and MAU grouping;
- 24-month raw and five-year aggregate retention boundaries are idempotent;
- production test/internal exclusion is snapshotted and not retroactively changed;
- DOCX/PDF unavailable page count is null, never a fabricated zero;
- Claude OCR cost appears once across joined AI and OCR reporting.

### Execution gates

- Run focused Deno files after each implementation task.
- Run `npm run test:edge` after each plan wave where practical.
- Apply migrations to the preview/test Supabase project and verify the live schema before remote correlation tests. This is a **blocking preview gate**.
- Production schema/function deployment remains a separate operator gate and requires the explicit signal `apply production`.
- Run `npm run verify:baseline` before verification; report any environment-gated leg honestly.

## Planning Recommendation

Split implementation into four dependency-aware plans:

1. Database foundation: subjects, feature/document ledgers, additive AI columns, pricing, RLS, deletion/retention, views, and migration tests.
2. Shared telemetry primitives: environment, subject/run lifecycle, pricing, retry numbering, AI/document writers, and coverage tests.
3. Feature integration: synchronous and queued feature entry points, Merit settlement, cache/rerun/unlock behavior, and OCR correlation.
4. Reporting and verification: canonical SQL, preview migration/live-schema gate, remote correlation, retention/deletion proof, and full baseline.

Do not begin production deployment during execution without explicit operator authorization.
