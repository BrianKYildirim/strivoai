## Blocker

```
[webkit] e2e/cross-device/realtime-fallback.spec.ts:344 OT-11: reload restores the waiting surface inside the 2000ms budget

    Expected: <= 2000
```

Run 1: 1 failed / 320 passed / 52 skipped. Run 2: 2 failed / 319 passed / 52 skipped.
Every other leg is green: lint, type-check, vitest 1196/1196 across 153 files, `test:edge`
1585/0/12, `test:edge:remote` 40/0, build.

What I established:

- **Load-dependent, not deterministic.** The spec passes 31/31 across all five Playwright
  projects when run alone, and 5/5 on webkit alone. It only fails inside the full ~370-test
  matrix.
- **Not on this phase's change path.** The test drives `/results/:id`, and `Results.tsx` is
  not among Phase 04.2's frontend changes. The one 04.2-touched module it imports,
  `useResumeStream`, has its changes confined to the submit and terminal branches — the
  correlation envelope is a plain object and `getFeatureRunToken` (the only network call)
  runs before extraction on a deliberate submit, not on mount.
- **The same gate was green for the operator today** on identical frontend code, during
  `deploy.ps1 -Env test`.

What I did **not** do, deliberately: widen `RESTORE_BUDGET_MS`, quarantine the test, or
declare the baseline green. `TESTING-STRATEGY.md` is explicit that flaky tests are
quarantined and never used to weaken the gate, and a quarantine entry requires an issue,
owner, and expiry — an operator decision, not an executor's. Per this plan's own acceptance
criterion the exact failing leg is recorded and the plan stays incomplete.

## Deviations from Plan

### Four defects in this plan's own deliverables, all caught by the operator gate

This is the headline finding and it deserves plain statement: **the offline suites could not
have caught three of these four.** `npm run type-check` never reads SQL, `npm run test:edge`
never executes SQL against a live Postgres, and nothing offline reaches a live PostgREST. The
failure modes were structurally invisible until a real `supabase db push` and a real HTTP
round trip ran. Four cycles of the Task 2 gate found them.

**1. [Rule 1] Invalid `format()` specifier aborted the preview push** — `28f4f2e9`
- **Origin:** 04.2-01 (already closed out), surfaced at the Task 2 gate
- **Issue:** `format('CREATE POLICY "Service role only - %" ON public.%I ...')`. `%` followed
  by `"` is not a valid specifier; Postgres raised SQLSTATE 22023 at statement 36 and rolled
  the whole migration back. No partial schema, no history repair needed.
- **Fix:** `%s` for the policy name (it sits inside the template's own quotes; `%I` would emit
  a second pair), `%I` retained for the relation. Audited both migrations and both rollback
  files, then scanned every file under `supabase/migrations/**`: zero remaining malformed
  templates.
- **Guard added:** two assertions in `costing-schema-contract.test.ts` — one extracts every
  `format()` template in the four Phase 04.2 files and validates each specifier, one pins the
  policy template positively. Both were proven to fail against the original defect before
  being committed. This is the one defect of the four that offline testing *could* have
  caught, and now does.

**2. [Rule 1] Product-MAU off-by-one, and the hand-counted-literal hazard behind it** — `edd0ad34`
- **Origin:** my Task 1 deliverable
- **Issue:** the assertion expected `6` while its own message enumerated seven subjects.
  Verified independently: ten subjects seeded, exactly three unable to reach MAU, and no
  subject spanning two tier/period buckets. The view and fixture were both correct.
- **Fix:** not a renumber. Expectations now derive from `mauCountable`/`mauUncountable`
  registries whose enumeration *is* the number, from run registries replacing the literal `9`
  (three occurrences), and from reductions over the seeded AI/document fixtures. `buildWorld`
  asserts every seeded subject and run is classified exactly once, so an unclassified addition
  fails loudly instead of silently shifting a total.
- **Kept literal on purpose:** the excluded-account `< $1` tripwire, which must stay
  independent of the derivation to remain a real check.

**3. [Rule 1] Probe error conflated with an absent relation** — `e37f03b4`
- **Origin:** my Task 1 deliverable, worsened by my own fix `9ead6188`
- **Issue:** the probe hardcoded `?select=id`, but `costing_account_classifications` is keyed
  on `costing_subject_id` and has no `id`. PostgREST answered 400; the code read "not 200" as
  "absent", printed *"the object is absent from this project"* about a present table with RLS
  on, and **skipped that table's anon-deny check**. The guard introduced to prevent vacuous
  passes became the vehicle for one.
- **Fix:** no probe names a column (`select=*&limit=0` with `Prefer: count=exact`), and
  probing is four-state — `present` / `absent` (404 or PGRST205) / `denied` (401/403, a
  definite answer) / `probe-error` (anything else, reported as a script defect, never as
  absence, never able to skip a security check).

**4. [Rule 1] The Claude-OCR invariant passed when its own probe failed** — `e37f03b4`
- **Origin:** my Task 1 deliverable; found while auditing defect 3
- **Issue:** `(count ?? 0) === 0` is true for `null`, so a failed probe reported the
  no-double-counting invariant as *proven*. A second live vacuous pass, unrelated to the 400.
- **Fix:** requires `state === present` **and** an exact zero. Evidence probes that fail now
  record a failing check instead of a blank line that reads as a benign zero.

### Scope-honoring adjustments

**5. [Rule 3] `begin-feature-run` was missing from the deploy function set** — `5ef22664`
- 04.2-03 created the endpoint and `config.toml` declares it, but `deploy.ps1`'s list never
  got it, so a normal deploy would silently leave it undeployed and every browser-assisted
  extraction would fall back to a backend-created run. Confirmed fixed: the operator's deploy
  shipped it with `feature-run-token.ts`, `feature-run-telemetry.ts`, `runtime-environment.ts`,
  and `price-resolver.ts`.

**6. Reporting inconsistency documented rather than migrated**
- The `costing_monthly_document_usage` view counts referenced-AI (Claude vision) documents
  inside `unknown_cost_documents`, because their `cost_known` is false. No dollar is lost —
  that spend is fully in Block A3 — but the counter overstates "cost we could not establish",
  and my Block E4 already used the refined definition. Two surfaces, two meanings, one column
  name. The view ships in 04.2-01 and is applied to preview, so rather than migrate for a
  labelling nuance I documented the caveat in Block A4, added `referenced_ai_documents` and a
  `unknown_cost_documents_genuinely_unpriced` column so reconciliation is one subtraction, and
  asserted both definitions in the remote suite. **Flagged for a future phase** if the view
  itself should be corrected.

**7. Unrelated working-tree work preserved**
- The in-progress Recruiting Lens account-state debug files were never staged, modified, or
  reverted. Every commit staged explicit paths.
