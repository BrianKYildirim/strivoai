# Phase 04.1 Research: Costing Workbook Completion

**Researched:** 2026-08-01  
**Scope:** `docs/Strivo AI Final Costing Plan.xlsx`  
**Confidence:** High for workbook structure, code-discovered service inventory, Stripe mechanics, and published base prices; medium for OCR blends and operating-loss rates until production billing/telemetry replaces estimates.

## Research Summary

Phase 04.1 should be implemented as a surgical extension of the existing workbook, not as a new financial model. The three scenario sheets already have identical serialized dimensions and formula patterns. Preserve those sheets as the operating views, add one global `Sources & Inputs` sheet, and make demand the only scenario-specific input family.

The most important modeling correction is to separate gross billings from recognized/net revenue through a sequential payment-loss waterfall. Subscription and Merit-shop transactions need separate calculations because transaction counts, average ticket sizes, annual amortization, and Stripe Billing applicability differ. Global loss rates may be shared, but the formulas must not apply failed payments, refunds, and disputes independently to the same gross base.

The workbook should use measured actuals when available and official prices otherwise. Every uncertain production driver must remain non-zero, visibly labeled `Estimate`, and listed in the production-data To-Do. A `$0` row is valid only when its status explains `Inactive`, `Not configured`, or `Included`.

## Recommended Input Model

Create `Sources & Inputs` with four compact sections:

1. **Global operating assumptions** — failed-payment rate, refund rate, dispute rate, retry/failure overhead, OCR incidence/pages, founder split, tax assumption, and production-data status.
2. **Vendor pricing and activation** — Item, Status, Include?, Actual Paid, Official Price, Active Price, Unit, Usage, Included Allowance, Overage Rate, Monthly Cost, Source ID.
3. **Source audit** — Source ID, item, source type, plan, value, units, included limit, overage, URL/reference, pricing/billing date, last verified, status, notes.
4. **Production-data To-Do** — every measurement required by CWB-11 with owner/status/evidence cell if space permits.

Use formulas equivalent to:

- `Active Price = IF(ISNUMBER(Actual Paid), Actual Paid, Official Price)`
- `Active Source Type = IF(ISNUMBER(Actual Paid), "Actual", "Official")`
- `Optional Base Cost = IF(Include?="Yes", Active Price, 0)`
- `Overage Units = MAX(0, Usage - Included Allowance)`
- `Monthly Vendor Cost = Optional Base Cost + Overage Units * Overage Rate`

Use input validation for status/include fields. Formulas should interpret only the approved activation value as active so typos fail closed. Do not use volatile functions, external workbook links, macros, or hidden assumptions.

## Payment-Loss Waterfall

Build the same waterfall separately for subscriptions and Merit-shop:

1. `Gross Billings`
2. `Failed Payment Loss = Gross Billings * Failed Payment Rate`
3. `Collected Revenue Before Refunds = Gross Billings - Failed Payment Loss`
4. `Refunded Revenue = Collected Revenue Before Refunds * Refund Rate`
5. `Revenue After Refunds = Collected Revenue Before Refunds - Refunded Revenue`
6. `Chargeback Revenue Loss = Revenue After Refunds * Chargeback Rate`
7. `Net Collected Revenue = Revenue After Refunds - Chargeback Revenue Loss`
8. `Stripe Processing Fee = successful transaction volume * percentage fee + successful transaction count * fixed fee`
9. `Chargeback Fees = disputed transaction count * dispute fee`

For annual Elite, calculate the annual charge and transaction economics first, then amortize revenue, processing fee, failed-payment loss, refund loss, and dispute economics over 12 months. Keep annual users in monthly AI/OCR usage counts.

Stripe Billing fees, if proven active, belong only to recurring subscription volume and should be distinct from card processing fees. Do not apply card percentage/fixed fees to failed transactions.

## OCR Cost Model

Keep provider details in the source audit but expose only two global active blended rates: `Free OCR Cost/Page` and `Elite OCR Cost/Page`.

For each tier, document provider weights that sum to 100% across the actually allowed fallback path. The active blended rate is `SUMPRODUCT(provider page rate, provider share)`. If a provider is unconfigured, its share must be zero and its status visible. Claude OCR should use a documented token-to-page estimate or measured telemetry and may contribute only to the tier where code permits it.

Track four driver groups per scenario: Free resume, Elite resume, Free LinkedIn, and Elite LinkedIn. Each group uses:

`Uploads * OCR Incidence * Average OCR Pages * Tier Blended OCR Cost/Page`

Use separate resume and LinkedIn incidence/page assumptions. Preserve the two-page resume boundary and LinkedIn's larger page allowance from Phase 01.1. Missing incidence data must use conservative non-zero estimates and be listed in CWB-11.

## Summary and Reconciliation Design

Each scenario needs the same formula positions for:

- subscription gross billings and net collected revenue;
- Merit-shop gross billings and net collected revenue;
- total net revenue;
- Stripe processing and Billing fees;
- failed-payment, refund, chargeback revenue loss, and dispute fees;
- base Claude AI cost and retry-adjusted Claude AI cost;
- OCR cost;
- Supabase, Vercel, domain, Development Tools, and other service costs;
- total fixed costs, total usage-based costs, total monthly costs;
- monthly profit before owner tax;
- amount per founder using the existing split/tax assumptions;
- cost per Free user, cost per Elite user, revenue/user, profit/user, and paid-user percentage.

Visible checks should return `OK` or a specific error label, never merely an unlabeled boolean:

- user mix equals total MAU;
- fixed + usage-based equals total monthly costs;
- subscription + Merit net collected revenue equals total subscription revenue used by summary;
- Merit detail equals Merit summary;
- total revenue - total costs equals monthly profit;
- founder allocation reconciles to the intended distributable-profit basis;
- provider weights equal 100% for every active OCR blend.

Guard ratio formulas with `IFERROR` or explicit zero-denominator handling. Error suppression must never turn a broken financial total into zero.

## Security and Integrity Threat Model

| Threat | Mitigation | Verification |
|---|---|---|
| Malicious or malformed source text becomes a spreadsheet formula | Treat URLs, notes, IDs, and status text as strings; prefix/escape values beginning with `=`, `+`, `-`, or `@` when they are data | Scan source/audit cells and formulas; allow formulas only in designated calculated columns |
| Hidden external links or data connections leak data or make results non-reproducible | Use plain source URLs as text; do not create external workbook links, queries, macros, or remote data connections | OOXML scan for `externalLinks`, connections, VBA, and formulas containing external references |
| Secrets, invoice identifiers, or PII enter the workbook | Store source names, public URLs, dates, and aggregate actual costs only; never copy API keys, customer data, full invoice payloads, or account identifiers | Search workbook strings for secret-like patterns and known env names before completion |
| Formula drift across scenarios | Generate/copy formulas from one canonical coordinate map and normalize sheet-local references | Structural/formula-hash parity test across all three scenario sheets |
| Corrupt or partially written workbook replaces the original | Save to temporary path, reopen with two readers, recalculate/render, then perform an atomic in-scope replacement | ZIP integrity, workbook reopen, calculation, render, and file-size/sheet-count sanity checks |
| Silent stale cached values | Force full calculation and save in Excel/LibreOffice; set automatic calculation | Reopen with data-only reader and compare key cached outputs to independently computed expectations |

## Validation Architecture

### Test Layers

1. **Static OOXML checks:** ZIP opens; expected four visible sheets; no external links/macros; formula cells parse; no broken-reference strings; style and formula parity across scenarios.
2. **Independent formula oracle:** A small script calculates expected waterfall, vendor overage, OCR, total-cost, profit, and founder results from selected input cells and compares them with recalculated cached workbook values within currency tolerance.
3. **Sensitivity matrix:** Mutate one input at a time in a temporary copy—MAU, paid mix, feature usage, vendor price, failed-payment rate, refund rate, chargeback rate, OCR incidence/pages, retry overhead—and prove the expected dependent cells change while unrelated global assumptions remain identical.
4. **Visual regression:** Render every sheet; compare scenario layout/format patterns and manually inspect clipped text, broken borders, unreadable source URLs, number formats, and error cells.
5. **Repository boundary checks:** only the target workbook is a deliverable; `.gitignore` unchanged; `.planning` remains uncommitted.
